# Architecture

Internal reference for how `@mui/x-studio` is put together. For install/quick-start, see [`README.md`](./README.md).

## Overview

`x-studio` is an embedded analytics dashboard builder: a single `<Studio>` React component that lets end users compose pages of widgets (charts, grids, KPIs, maps, pivots, filters, text) backed by pluggable data sources, with an optional AI chat assistant that can drive the same authoring actions a human would through the UI.

The package is organized around four layers:

1. **State** — `StudioController` (a `Store<StudioState>` with undo/redo) is the single source of truth; there is no local component state for dashboard content, layout, filters, or selection. `StudioState` is partitioned by lifetime into `doc` (the user-authored dashboard — the only persisted, undoable, reducer-mutable partition), `session` (ephemeral UI: mode + shell), and `runtime` (host-injected data sources); see State management below.
2. **Data pipeline** — a layered, aggressively-cached row-transformation pipeline (`internals/`) that turns raw `dataSources[id].rows` into the exact rows a widget renders.
3. **UI** — a React component tree (`components/`) that reads/writes the controller exclusively through `useStudioSelector`/`useStudioController` and never holds layout or dashboard state itself.
4. **Server adapters** — optional (`server/`) helpers for wiring a widget's data to a remote backend (e.g. `@mui/x-studio-data-middleware`) instead of in-memory rows, including automatic request batching and cross-source join resolution.

The state-model layer sits one level below `x-studio` itself: `@mui/x-studio-schema` (`packages/x-studio-schema`) owns every `StudioState`/widget/data/expression/AI-protocol type, `createDefaultStudioState`/`createDefaultWidget`, the pure `applyMutation` reducer, state persistence (`serializeState`/`deserializeState`/`migrateState`), and anomaly-detection math. `x-studio` (client) and `@mui/x-studio-ai-middleware` (server) both depend on it, so a `StudioState` shape change is made in exactly one place. See `packages/x-studio-schema/ARCHITECTURE.md` for that package's own internal structure.

## The shared schema package (`@mui/x-studio-schema`)

`packages/x-studio-schema/src/index.ts` is the single source of truth for the data model:

- `baseTypes.ts`, `dataTypes.ts`, `widgetTypes.ts`, `expressionTypes.ts`, `stateTypes.ts`, `aiTypes.ts` — every `StudioState`, widget, data-source, filter, expression, and AI-protocol type. `stateTypes.ts` defines the lifetime-partitioned `StudioState` (`doc` / `session` / `runtime` — see State management) and its `StudioDoc`/`StudioSession`/`StudioRuntime` members. `widgetTypes.ts` composes the widget model from per-kind interfaces (`StudioGridConfig`, `StudioChartConfig`, `StudioKpiConfig`, `StudioTextConfig`, `StudioFilterWidgetConfig`, `StudioPivotConfig`, `StudioMapConfig`, `StudioSharedWidgetConfig`) rather than one flat interface, and exposes the per-kind discriminated union `StudioWidget`/`StudioWidgetOf<K>`/`StudioWidgetConfigForKind<K>` alongside the flat patch type `StudioWidgetConfig`. The chart slice is split one level finer: `StudioChartWidgetConfig` is a discriminated union of ten per-family interfaces (bar, line/area, mixed, heatmap, funnel, gantt, sankey, pie, scatter, gauge) keyed by `StudioChartType` (a closed union of sixteen literals — no custom chart types, per `AGENTS.md`'s "x-studio custom charts" rule), with `StudioChartConfigOfType<T>` narrowing to a single family and the flat `StudioChartConfig` recomposed from those families as the generic/patch type. See the `StudioChartWidget` section for how `x-studio` consumes the per-family types, and `@mui/x-studio-schema`'s own `ARCHITECTURE.md` for the full design (including why key retention across `chartType` switches is a deliberate feature).
- `statePersistence.ts` — `serializeState`/`serializeDoc`/`deserializeState`/`migrateState`, `CURRENT_SCHEMA_VERSION`, the `SerializedStudioState`/`SerializedStudioSession` shapes, and the migrations registry. Persists only the `doc` partition (see Persistence below). `x-studio` re-exports these from `store/index.ts`, so app-facing imports are unchanged.
- `createDefaultStudioState` / `createDefaultWidget` / `normalizeGridColumn` (`factories.ts`) — `createDefaultStudioState` builds the default partitioned `StudioState` (one page, no widgets, `doc.schemaVersion: 1`, default `session`, empty `runtime.dataSources`); `createDefaultWidget` is the single factory both the UI ("Add widget" drawer) and the AI (`addWidget` tool) use, dispatching off a `BUILTIN_WIDGET_DEFAULTS: Record<BuiltinStudioWidgetKind, () => {...}>` table so UI-created and AI-created widgets start from the same defaults and a widget kind added without a table entry fails to compile.
- `applyMutation` / `mutationLabel` (`applyMutation.ts`) — the pure reducer that maps a `StateMutation` (see AI integration below) onto a `StudioState`, dispatched through a `MUTATION_HANDLERS` table keyed by mutation type (each entry co-locates its `apply` and `label` logic, so a variant missing a handler is a compile error). It is the _one_ implementation of every mutation's effect: the AI middleware server computes its threaded `nextState` with it, and the client's controller applies the identical function, so the two sides can never disagree about what a tool call did (page-targeting, config merge order, column-span cleanup).
- `detectAnomaliesIQR` (`anomalyDetection.ts`) — Tukey IQR outlier detection, shared so the AI's anomaly-detection tool and the chart widget's client-side detection agree.

The schema package has **zero runtime dependencies** (no React, no Node built-ins) so it is importable from both a browser bundle and a server bundle. UI-only concerns — `KpiFeatureFlags`/`ChartFeatureFlags`/`GridFeatureFlags`/`StudioFeatureFlags` (the `<Studio>`/`<StudioProvider>` feature-flag props) — live in `packages/x-studio/src/models/featureFlags.ts`, not the schema package, since the AI middleware never consumes them. `packages/x-studio/src/models/index.ts` is a thin re-export (`export * from '@mui/x-studio-schema'` plus `export * from './featureFlags'`) alongside the package's own React-dependent `customWidgetTypes.ts` (custom-widget registration types, which reference `React.ReactNode`/`React.ComponentType` and so cannot live in the dependency-free schema package). Application code imports types from `@mui/x-studio`'s public surface (or `../models` internally) — the schema package is an implementation detail two packages share, not a place app code imports from directly.

Anything that is _only_ a pure state-shape transform (mutation reducers, default-state/default-widget factories, anomaly math) belongs in the schema package. Anything that touches React, MUI components, the DOM, in-memory row data (the pipeline, caches, chart rendering), or is a component prop rather than persisted state (feature flags) stays in `x-studio`.

## State management

### `StudioController` (`src/store/StudioController.ts`)

Wraps a `Store<StudioState>` from `@mui/x-internals/store` (`packages/x-internals/src/store/Store.ts`) — a minimal observable with `state`, `subscribe(listener)`, `setState(next)`, and `getSnapshot()`, built to back `useSyncExternalStore`.

**`StudioState` is partitioned by lifetime** (defined in `@mui/x-studio-schema`'s `stateTypes.ts`):

- `doc` (`StudioDoc`) — the user-authored dashboard: `dashboard`, `pages`, `widgets`, `relationships`, `filters`, `expressionFields`, optional `filterPresets`/`ai`, and a `schemaVersion: 1` stamp. This is the **only** partition that is persisted, undoable, and mutable by the shared `applyMutation` reducer. Cross-filter-scoped filter entries live in `doc.filters` too — the reducer manipulates them (cleanup on `removeWidget`/`removePage`/`applyBulkUpdate`, and `applyCrossFilter` is deliberately undoable) — and are stripped only at the persistence boundary.
- `session` (`StudioSession`) — ephemeral UI state: `mode` (`view`/`edit`) and `shell` (`openDrawers`, `selectedWidgetId`/`selectedFieldId`/`selectedSourceId`). Never persisted, never undoable, never touched by the reducer. `mode` lives here deliberately so a view↔edit switch is not a Ctrl+Z-able dashboard edit.
- `runtime` (`StudioRuntime`) — host-injected `dataSources`. Never persisted, never undoable, never touched by the reducer — an undo must never revert live data to stale rows.

`StudioController` never mutates `StudioState` in place; every method computes a brand-new object and passes it to a private `commitState`, which:

- Pushes the previous **`doc`** onto the undo stack (typed `StudioDoc[]`, capped at `MAX_UNDO_HISTORY = 100`) — and only when `nextState.doc !== current.doc` by reference. A commit that touches only `session`/`runtime` (drawer toggle, selection, data refresh) takes effect immediately but creates **no** undo entry, regardless of the `undoable` flag, because there is no authored-document change to revert. Passing `{ undoable: false }` additionally suppresses the entry even when the doc _did_ change — used for transient doc writes like interactive-filter selection, `setGlobalCrossFilterMode`/`setCrossFilterAllPages`, and `setActivePage` navigation. (Cross-filter selection — `applyCrossFilter` — is NOT in this list: it commits with the default `undoable: true`, deliberately, so a chart-click cross-filter is Ctrl+Z-able like any other doc edit; see `:68`/`:108`.) The same convention covers system-initiated normalization: `setDashboardDateRangeAll` takes an `{ undoable?: boolean }` option, and the date-range bar's coverage-reconciliation effect (`StudioDateRangeBar.tsx`, which expands a persisted single-source date-range preset to cover sources injected by the host after load) passes `{ undoable: false }` so a normalization the user did not author neither pushes an undo entry on mount nor clears the redo stack when it re-fires. A user picking a preset in the bar stays undoable (the default). The reconciliation itself is **additive and field-preserving**, not rebuild-all: `docTransforms.setDashboardDateRangeAll` indexes each page's existing `dashboard-date-range` filters by source, reuses an existing filter's `id`/`field`/`fieldType` for any source it already covers, and only mints a fresh filter for a source with none yet — carrying forward each already-covered source's filter untouched rather than discarding and rebuilding the whole set. This matters most for the `'custom'` preset: `StudioDateRangeBar`'s effect reads the _existing_ filter's `from`/`to` bounds and threads them through as `customFrom`/`customTo` on every reconciliation call, and `buildDateRangeFilter` keeps an existing filter as-is when it would otherwise build an empty one (a `'custom'` preset called with no bounds). Previously the effect always passed `undefined` for custom bounds, so a `'custom'`-preset dashboard with 2+ sources (or a second source injected after a persisted single-source custom range loaded) would rebuild an empty filter set whose length mismatch against the stored custom filters triggered a full, non-undoable removal of every custom date-range filter on the page — the Select silently flipping to "All time" with no Ctrl+Z recovery.
- Clears the redo stack on every new undoable doc commit.
- Optionally appends a `{ label, at }` entry to a capped recent-mutation log (`MAX_MUTATION_LOG = 20`), surfaced to the AI assistant via `getRecentMutations()` so the model has a sense of what the user changed recently. The push is gated only on `nextState.doc !== current.doc` (the doc actually changed) — NOT on `undoable` — so a non-undoable doc mutation still gets logged; only a session/runtime-only commit (never reaches this branch) and a full `resetHistory` (which clears the log outright) skip it. This matters for `applyExternalMutation`'s `setActivePage`/`renameAIThread` calls, which commit non-undoably (see below) but are still real, AI-authored document changes the model's change log must surface — gating the log push on `undoable` would have silently dropped them, contradicting `applyExternalMutation`'s own "logging/label behaviour is unchanged" comment.
- Calls `store.setState(nextState)`, which synchronously notifies subscribers.

Several composition helpers sit on top of `commitState`, each the one-liner base for a family of writer methods so no method hand-spreads the nested partition structure:

- `commitDocPatch(patch, options?)` shallow-merges a `Partial<StudioDoc>` onto the current `doc` (leaving `session`/`runtime` untouched), with a reference-equality no-op guard: a patch whose every key is reference-equal to the current `doc` field commits nothing (no undo entry, no log line, no rebuilt `doc` object). This is the base for the doc-writer methods (relationships, filters, presets, page fields, date ranges).
- `commitShellPatch(patch)` merges onto `session.shell` and always commits non-undoably (shell selection / drawer state is ephemeral UI).
- `commitDataSourcePatch(sourceId, patch)` merges onto a single `runtime.dataSources` entry, always non-undoably, no-op on a missing source.
- `updateState({ doc?, session?, runtime? })` is a partition-aware partial update that shallow-merges each named partition onto its current value — callers name the partition explicitly.

Every mutation — dragging a widget, editing a filter, an AI tool call — funnels through one of `StudioController`'s methods (`addWidget`, `updateWidget`, `setWidgetLayout`, `addFilter`, `applyCrossFilter`, `setDashboardDateRange`, `addPage`, `duplicateWidget`, …). There is no other path to change dashboard state.

**The `commitMutation` choke-point.** Both the AI path and the user-driven methods that have a shared `StateMutation` equivalent funnel their state transition through one private helper, `commitMutation(mutation, { label?, undoable?, transform? })`. It runs the mutation through the shared `applyMutation(state, mutation)` reducer from `@mui/x-studio-schema` (rather than re-deriving the effect in hand-written code), skips the commit entirely when the reducer returns the same state reference (an unknown-id / already-applied mutation → no undo entry, no log line), defaults the log label to the reducer's own `mutationLabel`, and applies any client-only `transform` (React shell selection, live-data title inference) _after_ the reducer. Because the reducer is the single implementation of every mutation's effect, the user-driven and AI-driven paths — and the server-threaded state the model was told about — cannot disagree.

`commitMutations(mutations, { label?, undoable?, transform? })` (plural) is the multi-mutation sibling: it folds an ordered SEQUENCE of `StateMutation`s through `applyMutation` with `Array.prototype.reduce` and commits the final state as ONE undoable step, one subscriber notification, and one log line (labelled by joining the mutations' own `mutationLabel`s with `' + '`, unless overridden). `commitMutation` is a thin wrapper — `commitMutations([mutation], options)` — so a single-mutation caller is byte-identical (a one-element join has no separator). This lets a composite gesture that needs several mutations (a cross-page widget move = "rewrite source page's rows" + "rewrite target page's rows"; a compose-drawer insert-at-position = `addWidget` + `setWidgetLayout`) converge onto the reducer without a bespoke `StateMutation` variant, while still collapsing to a single undo entry: because `applyMutation` is pure, the whole fold happens before the store is touched. The whole-fold no-op check runs on `transform`'s OUTPUT, not on the raw reducer-fold result — `transform` always runs, even when the mutation fold itself was already a no-op, because some callers (`updateWidget` re-triggering title inference off an idempotent `changes` payload) rely on `transform` alone to produce the real change; checking `next === state` before `transform` ran would silently skip title re-inference on every no-op payload. To keep this from reintroducing spurious commits for genuine no-ops, the `transform` callbacks that layer shell selection (`addWidget`/`insertWidgetAt`/`moveWidget`/`moveWidgetToPage`'s selection side effect) guard on the target widget's actual post-fold presence before manufacturing a new session object, and `applyInferredTitles` is reference-stable (returns the input `widget` unchanged) whenever the inferred title/subtitle _text_ didn't actually change (comparing `undefined`/`''` as equivalent — `titleMode`/`subtitleMode` bookkeeping normalization alone doesn't count).

- **AI mutations**: `applyExternalMutation(mutation, label?)` is a thin wrapper over `commitMutation` (public, wire-adjacent — the SSE `state-mutation` handler validates via `parseStateMutation`/`applyStateMutation` before calling it).
- **User-driven methods that delegate** through `commitMutation`/`commitMutations`: `addWidget`, `removeWidget`, `updateWidget`, `updateWidgetConfig`, `setWidgetLayout`, `addFilter`, `removeFilter`, `addPage`, `removePage`, `renamePage`, `setDashboardTitle`, `setActivePage`, and — via multi-mutation commits — `insertWidgetAt`, `moveWidget`, `moveWidgetToPage`, `duplicateWidget`. Each still owns the argument-shaping and validation that isn't the reducer's job: `addFilter` stamps a page filter with the active page, `setWidgetLayout` throws on unknown/orphaned widget ids before delegating, `addPage` generates the page id via `createPageId()` — the same collision-resistant scheme (timestamp + per-process counter + random suffix, from `@mui/x-studio-schema`'s `factories.ts`) that `createWidgetId()`/`createFilterId()`/`createPresetId()` use, so two ids minted within the same millisecond (a rapid AI bulk turn, a double-click) never collide (the same collision-resistant-id policy has since been extended to the remaining `Date.now()`-only ids outside the controller: `WidgetFiltersPanel`'s widget-filter-add button now calls the shared `createFilterId()` instead of `wf-${widgetId}-${Date.now()}` — a double-click no longer silently no-ops the second filter via the reducer's duplicate-id idempotency — and `InlineFormulaBar`/`StudioExpressionFieldDialog` each pair a timestamp with a module-level monotonic counter for their expression-field ids, with the dialog's id additionally generated once via a lazy ref instead of recomputed every render, so it no longer churns the field's validation/draft memos on every keystroke before save), `setActivePage` keeps its same-value early return and stays non-undoable/unlogged, and `addWidget`/`removeWidget`/`updateWidget`/`updateWidgetConfig`/`insertWidgetAt`/`moveWidget`/`duplicateWidget` pass a `transform` for their shell/title side effects. `insertWidgetAt` (compose-drawer drop) composes `addWidget` + `setWidgetLayout`; `moveWidget` (drag-and-drop) and `moveWidgetToPage` (context menu) share a private `commitWidgetMove` core that composes the source/target `setWidgetLayout` pair; `duplicateWidget` composes `addWidget` + `setWidgetLayout` + one `addFilter` per cloned widget-scoped filter — except a cloned **rank** (Top-N) filter, which is dropped guard-and-continue via the shared `hasConflictingRankFilter` check (the same one `addFilter`/`updateFilter` use) before the mutations are built. The clone always lands on the active page, so a cloned rank filter would otherwise resolve to the same page context as the source widget's own rank filter — two rank filters on one page, the exact state the filters drawer assumes cannot exist — and the reducer's `addFilter` handler applies a mutation verbatim with no rank check, so without this guard the invariant violation would persist into the saved doc. In every case the caller owns the canvas-side geometry/splice math that computes each page's final rows, while column-span cleanup is the reducer's `enforceLayoutColSpans`.
- **Unknown-widget-id transforms never throw**: `updateWidget`'s and `updateWidgetConfig`'s `transform` callbacks both guard with `Object.hasOwn(next.doc.widgets, widgetId)` before dereferencing the (possibly absent) widget, returning `next` unchanged when it's missing. Because `commitMutations` runs `transform` even when the reducer fold itself was a no-op (see above), an unguarded transform reading `next.doc.widgets[widgetId].sourceId` for title re-inference would throw a `TypeError` on a stale/unknown id — reachable from a custom setup panel holding a stale widget id, or a race with an AI `removeWidget` mutation. Every sibling method stays guard-and-continue on unknown ids; these two transforms are no exception.
- **`updateWidget`'s `undefined`-voiding is wire-safe**: callers void a top-level field by passing an explicit `undefined` (e.g. `GridSetupPanel` resetting `sourceId`, `FormatPanel` clearing `subtitle`), but the reducer's `updateWidget` handler skips `undefined`-valued `changes` keys (an `undefined` can never survive JSON). So `updateWidget` splits the caller's `changes` into real-valued keys (→ `args.changes`) and keys explicitly set to `undefined` (→ `args.unsetFields`, which the reducer deletes), preserving every call site's resulting widget state while routing through the shared reducer. It layers auto-title re-inference via `transform` (skipped when the caller sets an explicit title/subtitle) and passes `label: null` so it writes no recent-mutation-log line. Required fields (`kind`/`title`/`config`) are never voidable — an explicit `undefined` for one is dropped rather than sent as an unset.
- **Methods with no shared `StateMutation` equivalent are permanently controller-owned by design**: shell/selection (`setSelectedWidget`, `selectField`, `clearSelection`, drawer toggles), data-source injection (`upsertDataSource`, `setDataSourceRows`, `setDataSourceAdapter`, `updateDataSourceField`), transient interactive filters (`applyInteractiveFilter`, `clearInteractiveFilter`), cross-filters (`applyCrossFilter`, `clearCrossFilter`, `clearAllCrossFilters`), filter presets (`saveFilterPreset`, `applyFilterPreset`, `deleteFilterPreset`, `renameFilterPreset`), relationships, expression fields, date-range filter building, and `reorderPages`. These either touch React/runtime-only state the dependency-free reducer must never own, or are multi-step compositions with no wire-facing variant. Adding a new `StateMutation` variant is deliberately avoided (each variant is nominally AI-tool-facing wire surface); a composite like `moveWidgetToPage` converges by composing EXISTING `setWidgetLayout` mutations into one commit via `commitMutations`, not by adding a variant.
- **Drag-and-drop layout**: the pointer drag-and-drop widget move and compose-drawer drop in `StudioCanvas.tsx` do not hand-roll layout. The compose-drawer drop calls `controller.insertWidgetAt(widget, pageId, rows)` and the canvas-widget move calls `controller.moveWidget(widgetId, sourcePageId, pageId, targetRows)` — both routed through `commitMutations`/the reducer, so drag-and-drop, keyboard reorder (`setWidgetLayout`), and the AI path share one column-span-cleanup implementation (`enforceLayoutColSpans`). The canvas retains only the geometry/splice math that computes the desired final rows from the drop position, plus its data-source-required guard. Unlike the public `setWidgetLayout` (which throws on unknown/omitted widget ids), `insertWidgetAt`/`commitWidgetMove`/`duplicateWidget` accept caller-computed geometry with no such validation, so a canvas geometry bug could silently orphan a widget (leave it in `doc.widgets` but out of every page's rows); `warnOnOrphanedWidgets` is a dev-mode diagnostic run after both `insertWidgetAt` and `duplicateWidget` that scans every page's rows against `doc.widgets` and warns if one doesn't appear anywhere, surfacing that class of bug instead of letting a widget silently disappear.
- **Expression-field cycle guard**: `addExpressionField`/`updateExpressionField` call `hasExpressionCycle`/`detectCycles` (`utils/expressionEvaluator.ts`) before committing and reject (dev-warn, no-op) a field whose formula would introduce a cyclic reference — the same validation the expression dialog's save button already ran, now enforced at the controller boundary too so a persisted doc or a host call can't slip a cycle past it. As a second line of defense, `evaluateExpression`'s field-reference resolution carries a `resolvingFieldIds` visited-set (`EvaluationContext`) that short-circuits (returns `null`) rather than recursing forever if a cycle reaches evaluation anyway (e.g. from state that predates the write-time guard).
- **`updateWidgetConfig`'s write-side config-key guard**: `StudioWidgetConfigForKind<K>`/`StudioChartConfigOfType<T>` only constrain code that reads `widget.config` after narrowing on `kind`/`chartType` — this method is generic because it patches a widget's config before any such narrowing happens, so nothing stops a wrong-kind or wrong-chart-type key from being written. It runs the incoming patch through `@mui/x-studio-schema`'s write-side key validators before committing, two layers deep: `validateConfigKeysForKind(existingWidget.kind, config)` first (catches, e.g., a Chart-only key patched onto a Grid widget), then, for a `chart`-kind widget, `validateChartConfigKeysForType` against the widget's effective chart type (catches a `sankey`-only key patched onto a widget whose current — or patch-supplied — `chartType` is `gauge`; `resolveChartType` resolves the effective type). Unlike the AI middleware's tool-call boundary (`executeToolOnState.ts`'s `update_widget`/`apply_bulk_update`, which reject the call outright), this is a WARN-AND-STRIP guard matching the controller's never-throw-on-bad-input style: an offending key is dropped from the patch (logged via `console.warn` in non-production only) rather than failing the whole call, since a stray key reaching this path is a UI bug, not untrusted input. Both layers validate only the incoming PATCH, never the widget's already-stored config — a stored config legitimately carries keys from the widget's previous chart type (key retention across `chartType` switches is a deliberate feature), so re-validating it would incorrectly flag normal state.

**Extracted pure `doc` transforms.** Two families of `StudioDoc → StudioDoc` logic live outside the controller class so the methods stay thin `this.commitDocPatch(module.xxx(this.getState().doc, ...args))` wrappers:

- `store/docTransforms.ts` — the date-range setters (`setDashboardDateRange`, `setDashboardDateRangeAll`, `setWidgetDateRange`, sharing one `buildDateRangeFilter` helper) and filter-preset operations (`saveFilterPreset`, `applyFilterPreset`, `deleteFilterPreset`, `renameFilterPreset`). Each returns a new doc with only the changed top-level field replaced, or the SAME `doc` reference for a logical no-op, so `commitDocPatch`'s reference-equality no-op guard behaves exactly as it would with the bodies inline. `buildDateRangeFilter` encodes the custom-vs-preset value logic once (`'custom'` stores explicit `{from,to}`; every other preset stores `value: null`, resolved fresh at query time by `resolveDateRangePreset`). A page filter's `dependsOn` (cascading-filter references to OTHER page filters' ids, e.g. a City filter narrowed by a Country filter) survives a preset save/apply round-trip through the same id-remapping both directions already do: `saveFilterPreset` re-keys each captured filter's own id to `${presetId}-${f.id}` and rewrites `dependsOn` through the identical scheme (dropping any reference outside the captured set), and `applyFilterPreset` builds an oldId→freshId map (`createFilterId()` per filter) up front and rewrites `dependsOn` through that map (dropping unresolved references) as it re-materializes the preset's filters onto the active page. Without this, a saved cascade's `dependsOn` still pointed at the pre-save ids, which never re-materialize on apply, and `FilterBody` silently dropped the dangling references — the Country→City narrowing quietly stopped working.
- `internals/rankFilterScope.ts` — `resolveRankFilterPageId`/`hasConflictingRankFilter`, the per-page rank-filter-uniqueness resolution shared between the controller's `addFilter` and `updateFilter` rank guards and the filters-drawer rows, so all three scope rank uniqueness to a page context rather than the drawer independently scanning dashboard-wide. Both mutation entry points reject a second rank filter on the same page (with a dev-mode warning), so an AI `add_page_filter` call can no longer create the conflicting second rank filter that only `updateFilter` used to catch.

Other responsibilities live directly on the controller:

- **Undo/redo**: `undo()`/`redo()`/`canUndo()`/`canRedo()` pop/push the two `StudioDoc[]` stacks and swap **only** the `doc` partition into the current state (`session`/`runtime` carry forward unchanged), so time-travel never touches mode, selection, or live data. Several deliberate cross-partition fix-ups live here: `carryTransientDocState` overlays the current doc's non-undoable transient `doc` state onto the swapped-in doc — interactive-filter selections, the `globalCrossFilterMode`/`crossFilterAllPages` cross-filter toggles, and `doc.ai` (the AI chat-thread state, written non-undoably by `useChatThreads` on every streamed token) — so a Ctrl+Z on an unrelated edit does not silently revert any of them. Cross-filter entries themselves are NOT carried, because they are undoable by design. `activePageId` gets the same treatment, but re-derived rather than blindly carried: it overlays the current doc's `activePageId` only when `Object.hasOwn(incomingDoc.pages, currentDoc.dashboard.activePageId)` is true, and otherwise falls back to the incoming doc's own first page id — so an undo of `addPage` (which removes the very page the user was viewing) or a redo of `removePage` lands on a page the swapped-in doc actually contains, instead of a dangling id. `normalizeSessionAfterDocSwap` nulls `shell.selectedWidgetId` when the swapped-in doc no longer contains that widget (e.g. an undo reverted the `addWidget` that created it); the same helper is also invoked directly (not only on an undo/redo swap) by `removeWidget`, `removePage`, and `applyExternalMutation`, since a user-driven removal or an AI-driven mutation can dangle the selection just as easily as time-travel can — a dangling selected-widget id otherwise renders the compose drawer blank instead of the add-widget view. `selectedSourceId`/`selectedFieldId` reference `runtime.dataSources`, which an undo never touches, so they cannot dangle.
- **Persistence**: `serializeState()`, `loadSerializedState()` (applies migrations, resets history, preserves the host's data sources), `serializeSession()`/`restoreSession()` (see Persistence below).
- **Title inference**: `applyInferredTitles` re-derives a widget's auto title/subtitle from its data source (via `inferWidgetTitles`, `internals/widgetUtils.tsx`) whenever `updateWidget`/`updateWidgetConfig` changes something that could affect it, unless the caller explicitly set a title/subtitle.
- **Layout math**: the live canvas renders a 24-column grid (`canvasGridConstants.ts`'s `GRID_COLS = 24`, `MIN_SPAN = 6`), and the between-widget resize handle commits spans in 24-column units via `setAdjacentWidgetColSpans`. The AI `set_widget_width` tool flows through `@mui/x-studio-schema`'s `setWidgetColSpan` handler, which imports the same `GRID_COLS`/`MIN_SPAN` constants (the controller imports `MIN_SPAN` from the schema package too), so a manual drag-resize and an AI-driven resize clamp/rebalance in the same unit system.
- **Value-equality bail before committing**: several writers build a fresh object unconditionally (`{ ...x, ...changes }`), which defeats `commitDocPatch`'s reference-equality no-op guard even when every patched key already holds its incoming value — the commit still pushes a (no-op) undo entry and wipes any pending redo stack. `setAdjacentWidgetColSpans`/`reorderPages` established the pattern of bailing out on a value-identical write before it ever reaches `commitDocPatch`; `setPageStackBreakpoint`, `updateActivePage` (the page-fields writer backing rename/theme/date-range edits), and `updateRelationship` now do the same — each compares every key the incoming patch would touch against the stored value first and returns without committing when they all already match. Without this, re-confirming a page's stack breakpoint or theme (or re-saving an unmodified relationship) it already has would silently clear a user's pending redo stack and insert a dead undo entry.
- **Async adapter bookkeeping**: `setDataSourceAdapter` first no-ops (no cache invalidation, no commit) when the incoming `adapter` reference is identical to the source's current one — the guard that keeps `StudioDashboard` safe to call with an inline `dataAdapters={{ orders: ordersAdapter }}` map on every render: without it, a host that also has an `onStateChange` storing the new state would create commit → parent re-render → new inline map identity → effect refires → commit again, an unbounded refetch loop. `upsertDataSource` has the same-shaped guard for the same hazard: after resolving whether to carry over an existing adapter (see below), it early-returns (no invalidation, no commit) when the resulting entry is reference-identical to the one already stored in `runtime.dataSources` — a host re-injecting the same `dataSource` object from an effect/poller is otherwise a clean no-op instead of bumping the source generation and evicting every cached adapter result on each call. The adapter-carry branch always allocates a fresh object, so it is never reference-equal and still commits/invalidates as before. `upsertDataSource`/`setDataSourceAdapter` otherwise invalidate the module-singleton `studioRequestCache` (`StudioRequestCache.ts`) for the affected source. Invalidation also generation-tags in-flight requests: it bumps the source's generation so an in-flight result started before the invalidation is not written back to the cache, and a caller arriving _after_ the invalidation sees that in-flight entry as absent (via `getInflight`) and starts a fresh fetch rather than joining a promise that will resolve to pre-invalidation rows. A caller already awaiting the in-flight promise still receives its result. `upsertDataSource` calling a bare `dataSource` (no `adapter` field — e.g. from a `StudioDashboard` `config` swap, which round-trips through `serializeState()`/JSON) preserves an adapter previously registered on that source id via `setDataSourceAdapter`/the `dataAdapters` prop instead of overwriting it with `undefined`; an incoming source that DOES carry its own adapter still wins. Cache invalidation on `upsertDataSource` always runs regardless of whether the OLD or NEW entry carries an adapter, so a config-swap replacing an adapter-backed source can never serve pre-swap cached rows for the new entry. `StudioRequestCache` also caps its entry count (`MAX_ENTRIES`, LRU-evicted, with expired entries swept first) on every `set()`, rather than only removing an entry when that exact `cacheKey` happens to be re-requested after its TTL — bounding the module-singleton's growth across a long interactive session (each filter/date-range tweak produces a new `cacheKey`) instead of letting it grow monotonically. Registration itself has a narrower gap than this same-reference guard can close on its own: `setDataSourceAdapter` no-ops entirely when the target source doesn't exist yet in `runtime.dataSources`, so a host that mounts with a stable `dataAdapters` map covering a source the initial `config` doesn't yet include gets that adapter dropped on the floor at mount, with nothing left to re-apply it later purely from inside the controller — the fix has to live in the caller that owns both the config and the adapter map (see `StudioDashboard` below).

### React integration (`src/context/StudioContext.tsx`)

`StudioProvider` puts the `StudioController` instance into `StudioContext` (plain `React.createContext<StudioController | null>`) and wraps UI configuration (`tableSourceMode`, `featureFlags`, merged `localeText`, `aiConfig`, `customWidgets`, `geographies`, `onOpenFilterPanel`) into a second `StudioUIConfigContext.Provider`. A module-level `EMPTY_FLAGS = Object.freeze({})` constant is the fallback when no `featureFlags` prop is passed, rather than a fresh `{}` literal per render, so the `uiConfig` object's `useMemo` stays stable across re-renders instead of being busted by a new empty-object reference.

- `useStudioController()` — throws if called outside a `StudioProvider`.
- `useStudioState()` — subscribes to the _entire_ state (rarely used directly; prefer a selector).
- `useStudioSelector(selector)` — `controller.store.use(selector)`, a `useSyncExternalStore`-based hook that only re-renders when the selected slice changes (by `Object.is`).
- A library of reusable selectors lives in `src/context/selectors.ts`: simple property selectors (`selectFilters`, `selectDataSources`, `selectRelationships`, `selectWidgets`, `selectMode`, `selectActivePage`, `selectGlobalCrossFilterMode`, `selectCrossFilterAllPages`, …) and selector _factories_ for per-ID/per-page lookups (`makeSelectExpressionFieldsForSource(s)` / `makeSelectExpressionFieldsForSources(sourceIds)` — the latter scopes to a whole `Set` of source ids in one subscription, used by `useWidgetRows`, `useChartWidgetData`/`StudioChartWidget`, `StudioKpiWidget`, and `StudioGridWidget` (own source + directly-related sources, plus any many-to-many relationship's junction source — see Chart support below), and `useBlendedSeriesRows` (a blended chart's foreign source ids), `makeSelectPartitionedFiltersForPage(pageId)`, `makeSelectActiveCrossFilter`, `makeSelectIncomingCrossFilters`). `makeSelectActiveCrossFilter` and `makeSelectWidgetActiveCrossFilter` (the widget-card removable cross-filter chip) share one `isActiveCrossFilter` predicate — both excluding `disabled` entries — so the two never answer the "is this cross-filter active for this widget/page" question differently. `makeSelectIncomingCrossFilters` honors the dashboard-level `crossFilterAllPages` toggle (reading `state.doc.dashboard.crossFilterAllPages`) — a cross-filter emitted on another page counts as "incoming" here when the toggle is on, matching the predicate `useWidgetRows`'s `hasChartCrossFilters` and `filterScoping.ts`'s row-scoping already use (`crossFilterAllPages || f.scope.pageId === pageId`); without this the selector disagreed with the rows a chart actually rendered, so hover/highlight gating reading `hasIncomingCrossFilters` behaved as if no cross-filter were incoming even while `useWidgetRows` was filtering/ghosting the same widget's rows for it. Factories are memoized per call site with `React.useMemo` so each widget subscribes to only the state slice it needs — e.g. `useWidgetRows` computes `relevantSourceIds` (a widget's own source plus its directly-related sources) and builds a scoped expression-field selector from it, so adding an expression field to an unrelated source never re-renders this widget.
- The filter-partitioning selector variants share one core: `partitionFilters` (splits a page's filters into page/widget/cross-filter/interactive buckets) plus `isPartitionUnchanged` (a cheap reference-based equality check) are composed via a `makePartitionedFiltersSelector` factory, so `makeSelectPartitionedFiltersForPage`, `makeSelectPartitionedFiltersForWidget`, and the base-filter variants are thin wrappers around the same logic instead of independently-drifting copies. `selectPartitionedFilters` is the deliberate exception: it stays on the older `createSelectorMemoized` factory because its per-store-instance `__cacheKey__` memoization is load-bearing for correctness across multiple `StudioController` instances and isn't safe to fold into the shared closure-based factory.

Multi-instance mounting (two `<StudioDashboard>`s on one page) is an explicitly supported scenario, and it extends to keyboard shortcuts: `useStudioKeyboardShortcuts(rootRef)` (`internals/useStudioKeyboardShortcuts.ts`, wired up per instance by `components/Studio/StudioContent.tsx`) still attaches its undo/redo `keydown` listener at `window` level (removing it would break shortcuts fired while focus sits on a portaled MUI popover outside the Studio DOM subtree), but gates every keypress on `isActiveInstance()` — true when `document.activeElement` is contained within that instance's root, or, when focus is currently outside every Studio root (e.g. on a portal), when this instance was the last one to hold focus (a module-level `lastFocusedRoot` arbiter). Two mounted instances therefore never both react to the same Ctrl+Z keypress.

Concretely, for a drag-and-drop widget move: `useStudioDraggable`/`useStudioDropTarget` (built on `@atlaskit/pragmatic-drag-and-drop`) report the drop to `StudioCanvas`'s drop handler, which recomputes the target page's `widgetRows` (the canvas-side geometry/splice math) and commits via a single `controller.moveWidget(widgetId, sourcePageId, targetPageId, targetRows)` call — the source page's rows and every page's column-span cleanup are then derived by the shared reducer. A compose-drawer drop of a brand-new widget commits via `controller.insertWidgetAt(widget, pageId, rows)` the same way.

## Data pipeline

The pipeline turns `dataSources[id].rows` into the rows a specific widget renders, in four numbered layers plus widget-facing hooks that stitch them together.

### L1 — Normalize (`src/internals/normalizedRowsCache.ts`)

`getCachedNormalizedDataSource(dataSource, usedFieldIds?)` calls `normalizeDataSourceRows` (`temporalUtils.ts`) to canonicalize date/datetime values and pre-build per-field distinct-value indexes, then caches the result in a `WeakMap<Row[], Map<fieldSetKey, entry>>` keyed on the source's `rows` array. When `usedFieldIds` is passed, normalization is scoped to only the fields a given widget actually uses ("lazy-by-widget"), so adding an unused field to a different widget's config is zero cost — each field set gets its own cache slot.

### L2 — Enrich (`src/internals/enrichedRowsCache.ts`)

`getCachedEnrichedRows(rows, sourceId, expressionFields, dataSources, relationships, usedFieldIds?)` evaluates non-measure `StudioExpressionField`s (calculated columns, including cross-source `JoinFieldExpression`s) via `enrichRowsWithExpressions` (`utils/expressionEvaluator.ts`) and merges the computed values onto each row. Caching is two-level (`rows` WeakMap → `fieldSetKey` Map); a cache entry is invalidated only if its own rows changed, a _relevant_ expression-field object changed (by reference — editing a formula replaces the object), a joined foreign source's rows changed, or a relevant relationship changed. `expandWithDependencies` walks each requested field's transitive expression dependencies (field A referencing field B pulls B in too) so a widget only pays for the expressions it needs. Measure expressions (`isMeasure: true`) are excluded from row-level enrichment entirely.

### L3 — Filter (`src/internals/filterScoping.ts`, `dataSourceGraph.ts`, `resolvedRowsCache.ts`)

1. `selectFiltersForWidget(filters, { widgetId, widgetSourceId, activePageId, include, crossFilterAllPages })` is the single source of truth for filter _scoping_ — it decides which of `state.doc.filters` apply to a given widget by switching on `scope.kind` (`page` / `widget` / `cross-filter` / `interactive` / `dashboard-date-range`), then runs `resolveDateRangePresets` to turn a stored preset into concrete from/to bounds computed at query time (so a stored filter never holds a stale absolute date). The `include` parameter (`'all' | 'no-cross' | 'no-chart-cross'`) lets one scoping function serve all three baselines `useWidgetRows` needs.
2. `resolveRows` (`dataSourceGraph.ts`) takes the scoped filters and does the actual row filtering: it separates _native_ filters (same source as the widget) from _cross-filters_ (`filterSourceId` differs, or the field is an expression owned by another source), resolves a `JoinPath` for each cross-filter via `findJoinPath` (one-hop direct relationship, or two-hop via a many-to-many junction), semi-joins the widget rows against the matching foreign rows, and finally runs `applyFilters`/`compileRowTest` (`filterUtils.ts`) for the native rows.
3. `resolveRowsCached` (`resolvedRowsCache.ts`) wraps `resolveRows` with a `WeakMap<Row[], Map<cacheKey, entry>>` cache. The cache key folds in a content-based `filterFingerprint` of every scoped filter (operator, value, mode, rank settings, field type, target source — not just id/value, so an operator edit alone invalidates the entry) plus the sorted `usedFieldIds` set. A hit is served only if every foreign source actually joined against (tracked via a `collectJoinedSourceIds` out-param) still has the same `rows` reference, `relationships` is the same array, and every relevant (non-measure) expression field on the widget source or a joined source is still the same object. `collectJoinedSourceIds` is threaded all the way down into `resolveRows`'s own L2 enrichment call (`getCachedEnrichedRows`), not just its cross-filter semi-join loop — a widget-source expression column that JOINs a foreign source (e.g. `customer_name = join(customers.name)`) makes that foreign source's rows a tracked dependency of the L3 result even with **no cross-filter present at all**. Before this was wired through, refreshing the foreign source's rows left the cache serving stale joined values indefinitely, including for filters evaluated _on_ that expression column.

### L4 — Re-anchor (chart widgets only) (`src/internals/grainResolution.ts`, `chartAggregation.ts`/`chartSupport.ts`)

When a chart's x/y/series fields span more than one related source, aggregating the L3 result directly can double-count or under-count due to fan-out joins. `chartSupport.analyzeChartSupport` determines each requested field's owning source (`findDirectFieldOwner`, walking one-hop and many-to-many relationships) and whether the configuration can be safely aggregated (`isSafeWidgetBridgeOwner`). `findDirectFieldOwner` resolves a related-source field from either `source.fields` or the `expressionFields` list filtered to that source, so the caller must pass an expression-field list covering the widget's own source, every directly-related (one-hop) source, **and** — for a many-to-many relationship — its junction (bridge) source, or a related-/junction-owned calculated field used as a dimension can never be found and the guard falsely reports `field_not_found_or_not_direct`. `useChartWidgetData.ts`, `StudioChartWidget.tsx`, `useWidgetRows.ts`, and `StudioKpiWidget.tsx` all build this scoped `relevantSourceIds` set the same way — own source plus every one-hop related source plus, for each `many-to-many` relationship touching the widget's source, that relationship's `junctionSourceId` too (mirroring `dataSourceGraph.getReachableSourceIds`'s semantics) — and subscribe via `makeSelectExpressionFieldsForSources(relevantSourceIds)`, matching the full-universe check `ChartSetupPanel.tsx` already ran, so the setup panel and the rendered widget can no longer disagree about whether such a configuration is supported. Before the junction source was added to this set, a junction-owned expression field (a supported topology — see the many-to-many branch below) was invisible to the guard even though the physical junction fields resolved fine, so a chart/KPI reported a junction-owned calculated dimension as unsupported while the setup panel (which read the full expression-field list) allowed it, and a filter targeting that column could be neither classified as junction-scoped nor evaluated at L3/L4.

A many-to-many relationship is only actually usable as a join bridge — for `findDirectFieldOwner`'s two-hop field-owner resolution, `isSafeWidgetBridgeOwner`/`isManyToManyReachableOwner`'s bridge checks, and every junction-anchor selection site below — when **both** `junctionSourceField` and `junctionTargetField` are present, matching `findJoinPath`'s own completeness check (`dataSourceGraph.ts`). A relationship missing either field cannot actually resolve rows between its two endpoints through the junction table; treating it as a usable bridge anyway used to fall through to `enrichRowsWithRelatedFields`'s two-hop lookup, which has the identical field-completeness requirement and so silently resolved the dimension to `undefined` (a blank bucket) or the measure to a count fallback, instead of the clean fail-closed `mixed_cross_source_fields` state every other incomplete/unsupported shape gets. An incomplete junction is only reachable from a host-injected or AI-authored relationship config — `RelationshipDialog` validates both junction fields before saving — so this was a robustness gap, not a UI-reachable one. When it can, `resolveChartRowsForAggregation` calls the shared L4 core, `grainResolution.resolveRowsAtGrain(widgetRows, widgetSourceId, anchorSourceId, requestedFields, fieldOwners, …)`, which re-derives the row grain relative to the chosen `anchorSourceId`:

- **No re-anchor** (`anchorSourceId === widgetSourceId`) — just enrich with related fields (`enrichRowsWithRelatedFields`, one-hop or two-hop joins) and, if needed, expression fields. This is the ONLY branch in which `enrichRowsWithRelatedFields`'s two-hop first-match-only M:N lookup feeds an aggregation, and it is safe here precisely because each widget row is its own group (a single representative related value per row is correct); every fan-out-unsafe topology is either re-anchored below or rejected by the support guard before reaching this branch (finding 1.1). The lookup is otherwise a genuine display-column path (grid/map columns). An earlier "display columns only" framing was too strong — the no-re-anchor branch also uses it for aggregation, correctly.
- **Many-to-one anchor** (widget is the "one" side, anchor is the "many" side) — expand each widget row into one row per matching anchor-source row, merging in the requested anchor fields plus any remaining widget fields via FK lookup.
- **Many-to-many anchor** (anchor is a junction source) — walk the junction rows, keeping only those linking to an allowed widget row, merging widget row + remote row + junction row per output row. A third source reachable many-to-one from the widget source (distinct from the junction and the M:N remote endpoint — e.g. y lives on the junction while x/series is owned by `customers`, one-hop from `orders`) is enriched onto the widget rows here too, mirroring the many-to-one branch's own third-source enrichment, and the junction rows themselves are routed through L2 (`enrichSourceRowsWithExpressions`) when a requested field is a junction-owned expression column. Before this, `analyzeChartSupport` could report such a configuration as "supported" while every dimension value on the third source resolved to `undefined`. `analyzeChartSupport` also junction-anchors a configuration whose measure is entirely **widget-owned** (or fieldless — a plain count) when a grouping dimension (x/series/an `extraField`) is owned by the **remote endpoint** of a many-to-many relationship with the widget source: leaving `anchorSourceId = widgetSourceId` in that topology would instead route L4 through `enrichRowsWithRelatedFields`'s first-match-only M:N lookup, attributing each widget row to a single arbitrary junction link and silently under/over-counting the aggregate (e.g. "sum of order total by tag" on an order linked to two tags). Anchoring on the junction instead lets this same M:N branch fan each widget row out to one row per matching junction entry, so the widget-owned measure is read off the merged `{...widgetRow, ...remoteRow, ...jRow}` result once per link; the measure-ownership check (normally requiring `owner === anchorSourceId`) is relaxed specifically to permit `owner === widgetSourceId` under this junction anchor. Two distinct M:N remote dimensions in the same chart have no single junction grain and fail closed as `mixed_cross_source_fields` rather than silently picking one. Symmetrically, when the measure is **not** widget-owned but anchors on a **different directly-related many side** (a plain many-to-one anchor) while a grouping dimension is owned by the **remote endpoint or junction** of an M:N relationship with the widget source, there is no single grain combining that many-side measure with the M:N fan-out — so the guard fails closed as `mixed_cross_source_fields` too, rather than letting the many-to-one branch resolve the dimension through `enrichRowsWithRelatedFields`'s first-match-only lookup and silently mis-attribute each widget row's measure to one arbitrary junction link (or, for a junction-owned dimension, read `undefined` for every row). The junction-anchor relaxation above is deliberately scoped to the widget-owned-measure topology; this is its non-widget-owned counterpart, which has no safe grain (finding 1.1).

Both the many-to-one and many-to-many branches also accept the widget's fully resolved filter set (`widgetFilters` — page + widget + cross-filter + interactive, presets already resolved to concrete bounds, i.e. exactly what produced the L3 `widgetRows`) and apply the subset scoped to the **anchor source itself** directly to the anchor/junction rows, before the expansion join. A filter's target source is derived via `effectiveFilterSourceId` (mirroring L3's own derivation), not read off `filterSourceId` alone: a drawer filter on an anchor-owned **expression** field carries no explicit `filterSourceId`, so classifying on the raw field would leave it invisible to the re-application and re-introduce the resurrection bug for exactly that shape (finding 1.3a). The enrichment set passed to the anchor/junction rows is also widened to include any field referenced by an anchor-scoped filter — otherwise an anchor/junction-owned expression column referenced by a filter but not among the requested chart fields would be `undefined` when `applyFilters` evaluates it, dropping every anchor/junction row and rendering the chart empty (finding 1.3b). L3 enforces an anchor-source-field filter only as a semi-join (keep a widget row if it has ≥1 matching anchor row); without re-applying the anchor-scoped filter at this layer, the expansion join used to read every one of a surviving widget row's anchor rows straight from the unfiltered data-source store — resurrecting exactly the rows the filter had excluded (e.g. summing paid **and** unpaid orders for a customer with at least one paid order, instead of just the paid ones). The many-to-many branch additionally re-applies the subset scoped to the **M:N remote endpoint** (`filterSourceId === remoteSourceId`, e.g. `tags.category = 'priority'`) to the remote rows (enriching them first, in case the filter targets a remote-owned expression column) before building the `remoteRowLookup`, and drops any junction row whose target key is absent from that filtered remote key set — L3 enforces a remote-endpoint filter only as a semi-join on the widget rows too ("keep orders having ≥1 matching tag"), so without this the expansion join would otherwise walk every junction link of a surviving widget row, resurrecting weights for the categories the filter excluded, one relationship hop further out than the anchor-source case above. This filter set is threaded through the whole call chain: `resolveChartRowsForAggregation` → `useChartRows` → `useChartWidgetData`.

`resolveChartRowsForAggregation`'s own result cache (`chartSupport.ts`) is keyed on `widgetRows`/`anchorRows`/a config fingerprint, `relationships`, the relevant expression fields, and (now that anchor-source filters are applied inside grain resolution) the anchor-scoped subset of the filter fingerprint (classified by the same `effectiveFilterSourceId` derivation, so a foreign-owned expression-field filter with no explicit `filterSourceId` is folded in too — finding 1.3a) — plus, when the anchor is an M:N junction, the subset scoped to that junction's remote endpoint too, so editing/adding/removing a remote-endpoint filter also busts the cached result instead of serving a stale one — but grain resolution also reads rows from related sources that are neither the widget's own source nor the anchor (enrichment joins, many-to-many remote-endpoint rows, many-to-one third-source rows pulled in for a `seriesField`/extra-dimension field). `resolveRowsAtGrain` takes an optional `collectReadSourceIds` out-param that every branch (direct enrichment, many-to-one, many-to-many) populates with every foreign source id it actually read; the cache records each such source's `rows` reference alongside its result and a hit additionally requires every one of those references to be unchanged — so updating a non-anchor related source's rows (e.g. `customers` when a chart on `orders` splits by `customers.segment`) correctly busts the cached result instead of serving stale segment values indefinitely.

This function is deliberately scoped to the "fan-out" direction only (grouping dimension on the coarser side); the opposite "fan-in" direction (aggregate a one-side measure grouped by a many-side field, e.g. a grid summing `orders.total` grouped by `order_items.category`) has no single global grain and instead uses a per-group dedup helper, `utils/gridGrouping.symmetricAggregate` — `analyzeChartSupport` never selects an anchor that would need it, so charts never hit that path.

L3 semi-joins, L4 re-anchoring, display-column enrichment, and grid fan-out dedup share one join-key coercion policy: `normalizeJoinKey` (`src/internals/joinKeys.ts`). It maps `null`/`undefined` → `null` (so a missing FK never spuriously matches an empty key), `Date` → its ISO string, and everything else → `String(value)` (so a numeric FK and a string PK compare equal). `indexRowsByKey` and `collectKeySet` build `Map`/`Set` lookups on top of this policy and are reused by `dataSourceGraph.ts`, `grainResolution.ts`, `crossSourceEnrichment.ts`, and `utils/gridGrouping.ts`. **L2 follows the same policy**: `utils/expressionEvaluator.ts`'s join-field-expression evaluation (both its precomputed-index fast path and its single-row fallback) keys its join index by `normalizeJoinKey(...)` rather than the raw target-field value, so a numeric-FK-vs-string-PK relationship resolves consistently whether it's read through a grid's cross-source aggregate or a join-field expression column — there is no longer a pipeline stage that silently disagrees on join-key coercion.

### Aggregate & render

Per-chart-type aggregation lives in `internals/aggregators.ts` (`aggregateByField`, `aggregateByTwoFields`, `aggregateMultipleSeries`, `aggregateBlendedSeries`, plus shared `orderLabels` sorting and rank-on-aggregated-value helpers). These honour per-series aggregation on every render path, not just the blended one: `aggregateByTwoFields` takes the widget's `config.yAggregation`, and `aggregateMultipleSeries` accepts either a single function or a per-field `Record<fieldId, fn>` map so each series applies its own `StudioChartSeries.yAggregation`. A plain multi-series or split-by chart therefore produces the same numbers as the server aggregation push-down (and the blended-series client path), rather than defaulting every series to `sum`. The same precedence is threaded through the single-series and seriesField (split-by) client paths too: `useChartWidgetData.ts`'s `singleSeriesYAggregation` resolves as `config.ySeries?.[0]?.yAggregation ?? config.yAggregation`, mirroring the multi-Y path and the server/adapter push-down order in `chartTypeRegistry`. `internals/chartShapes/` (one file per chart-type-specific shaping step: `scatter.ts`, `heatmap.ts`, `sankey.ts`, `funnel.ts`, `gantt.ts`). `internals/chartAggregation.ts` is a composition barrel: `export * from './chartSupport'`, `'./aggregators'`, `'./chartShapes'`, so `chartAggregation` imports resolve through one entry point while the implementation stays split across focused modules. After aggregation: temporal label-gap-filling (`temporalUtils.ts`, whose `truncateToGranularity` delegates to `@mui/x-studio-schema`'s `truncateToPeriod` for the date-bucketing math, keeping the client and the AI middleware's `summarise_page` tool in agreement on period boundaries), forecast overlay (`forecastUtils.ts` — linear-regression projection), anomaly annotation (`anomalyDetection.ts` — Tukey IQR over the aggregated series), and number formatting (`numberFormat.ts`), before handing off to `@mui/x-charts`. A temporal line/area x-axis always renders chronologically ascending (`getTemporalAxisData` sorts labels internally), but the aggregated series values are produced in whatever order the chart's sort settings or a rank filter left them in — `chartWidgetHelpers.ts`'s `getTemporalSortOrder` computes the permutation from unsorted to chronological order once, and `sortAggregatedTemporally`/`sortMultiSeriesTemporally`/`sortMultiYTemporally` apply that same permutation to `chartData`/`seriesFieldData`/`multiYData` before `StudioLineAreaChart` renders them, so a value is never plotted against the wrong date. `forecastUtils.ts`'s overlay series places its connection point at the last historical index (`values[n - 1]` repeated at index `n - 1`, not `n`) and carries every forecast value from there — so the dashed forecast line meets the end of the historical series and the projection isn't shifted a period late — and its label-extension logic recognizes `YYYY-Qn`/`YYYY-Www` period keys (including year rollover) in addition to plain dates, so a weekly/quarterly forecast gets real period labels rather than degrading to a `+1`/`+2` point scale. Non-ISO or zone-ambiguous date inputs (a `'1/15/2024'`-shaped string, a zone-less datetime, a `Date` object, a numeric timestamp) are read via their local Y/M/D components (`temporalUtils.ts`'s `isZonedDateInput`/`toLocalYmd`) rather than through `toISOString()`, so ingestion doesn't day-shift for viewers ahead of UTC; canonical ISO date/datetime strings are unaffected. Grid widgets substitute DataGridPremium's own native `rowGroupingModel`/`aggregationModel` (group-by aggregation) plus `utils/gridSummary.ts` (footer totals) for the chart-specific aggregation step; `utils/gridGrouping.ts`'s `buildGroupedGridRows`/`symmetricAggregate` are NOT on this path (they have no non-test callers) — instead, `StudioGridWidget.tsx` registers custom DataGridPremium aggregation functions (`makeFanoutSafeAggregationFunction`) that dedupe a many-to-one joined column by its FK before reducing, reusing `gridGrouping.ts`'s shared `aggregateValues` reducer, so grouping+summing a fanned-out cross-source column (e.g. `orders.total` on an `order_items` grid) isn't double-counted the way a naive per-row native sum would be.

An adapter-backed source's `avg` aggregation is routed the same way `count` already is: `createBatchingAdapter.ts` (both its simple and relationship-aware request builders) checks `xGroupBy && hasAvgAggregation(...)` and, when true, strips the aggregation spec and warns (`warnAvgXGroupByRoutedClientSide`), fetching raw rows instead of pushing `avg` to the server. This is necessary because the wire protocol has no way to express the client's re-bucketing granularity: a server-side `avg` computed at the raw x-grain (one average per day) and then client-re-bucketed by month would average those per-day averages together — mathematically wrong unless every day has an equal row count. `sum`/`min`/`max` re-aggregate correctly across grains and are still pushed down; `avg` and `count` are the two aggregations that must be finalized client-side over raw rows whenever `xGroupBy` re-buckets the server's grain.

`analyzeChartSupport` (`internals/chartSupport.ts`) takes a trailing `extraFields` array for dimension-like fields a non-xy chart family reads but that aren't expressed via x/y/series (heatmap's `heatYField`, sankey's `sankeyTargetField`, funnel's `funnelReachedField`, the `gantt*` fields) — they're resolved/grain-validated exactly like `seriesField`, never mistaken for a y-measure anchor, so an unresolvable extra dimension field correctly makes the guard report the chart unsupported instead of silently ignoring it. Critically, a _resolvable_ cross-source extra dimension field is also fully wired end to end, not just validated: `useChartWidgetData.ts` builds a per-chart-type `extraFields` list and threads it into both `analyzeChartSupport` and `useChartRows`, which forwards it into `resolveChartRowsForAggregation` so the extra field's owning source takes part in L4 grain resolution/enrichment the same as x/y/series fields do. The five non-xy renderers (`renderHeatmap`, `renderFunnel`, `renderSankey`, `renderGantt`, `renderGauge` in `chartTypeDefs.tsx`) aggregate `ctx.enrichedRows` (the L4-resolved, cross-filter-mode-aware baseline), not the raw L3 `ctx.filteredRows` — so a many-to-one `heatY`/`funnelReached`/`sankeyTarget`/Gantt field that the support guard reports as supported actually renders real values instead of one blank bucket, and (since `enrichedRows` derives from `effectiveRows`, which is itself `crossFilterMode`-aware) a `'none'`-mode heatmap/funnel/sankey/gantt/gauge no longer reacts to sibling cross-filters the way every xy chart family already didn't.

All numeric aggregation in the package shares one null/boolean/numeric-string-coercion policy in `internals/aggregate.ts` so the widget kinds cannot drift apart on how they treat empty or non-numeric cells: `coerceAggregateValue(value)` maps booleans → `0`/`1` (so `avg` yields a ratio), finite numbers → themselves, and non-empty numeric strings (`"12"`, `"-2.5"`) → their parsed number — CSV/JSON sources have no native number type, so measures routinely arrive as numeric strings, and parsing them here keeps every accumulator in agreement with the `Number.isNaN(Number(v))` pre-detect the chart aggregators use to decide whether a field is numeric — and skips everything else (`null`/`undefined`/`NaN`/empty or non-numeric strings/objects) so it never inflates an `avg` denominator or a `min`/`max` comparison; `aggregateNumbers(values, fn)` reduces an already-coerced value list (`sum`/`avg`/`min`/`max`/`count`/`count_distinct`) — `min`/`max` reduce with a loop rather than `Math.min(...values)`/`Math.max(...values)`, since the spread form throws `RangeError: Maximum call stack size exceeded` past roughly 125k elements; and a streaming accumulator (`createAggregateAccumulator`/`accumulateValue`/`finalizeAccumulator`) folds values one at a time over large row sets without buffering them. The KPI widget's `computeAggregate`, the map widget's `aggregateValues`, the pivot's `addToAgg`/`resolveAgg`, the chart cell accumulator (`aggregators.ts`'s `finalizeCell`), the grid's `utils/gridGrouping.ts`/`utils/gridSummary.ts` (group-by aggregation and footer totals — previously the one holdout, filtering with a raw `typeof v === 'number'` check that silently excluded numeric-string and boolean cells instead of coercing them), and the expression evaluator's measure aggregation (`utils/expressionEvaluator.ts`) all route through this module, so a KPI over a raw field and a KPI over a measure expression wrapping that same field return the same number on data containing nulls, and a Grid's footer total agrees with a KPI/Chart/Pivot aggregating the identical field. `gridGrouping`'s `min`/`max` also reduce with a loop rather than spreading into `Math.min`/`Math.max`, for the same large-array `RangeError` reason as `aggregate.ts` and `gridSummary.ts`. Critically, the generic chart aggregators (`aggregateByField`/`aggregateByTwoFields`/`aggregateMultipleSeries`) route each row's _raw_ cell value through `coerceAggregateValue` before it ever reaches the accumulator (not just at `finalizeCell` time) — they used to accumulate `Number(row[y] ?? 0)` directly, which coerced a null/non-numeric cell to `0` and inflated `avg` denominators or dragged `min` toward zero. All three of `aggregateByField`, `aggregateByTwoFields` (the split-by path), and `aggregateMultipleSeries` share the same first-non-null-value pre-detect and fall back to `count` when the y-field is non-numeric (e.g. a string ID) — `aggregateByTwoFields` used to lack this fallback, so a split-by chart on a string measure rendered every cell `null` (a blank chart) instead of degrading to row counts the way removing the split-by field already did (finding 2.4).

`'count'` means row-count (`COUNT(*)`) semantics everywhere in the package, independent of whether a per-row measure value is usable: the map widget's region aggregation and the pivot's cell/row/column/grand totals tally every row that falls into a bucket via a dedicated row-counter, kept separate from the null-skipping accumulator `sum`/`avg`/`min`/`max` read — so a region or pivot cell whose measure values are all null/non-numeric still reports its true row count instead of disappearing from the map or reading `0`. This matches the KPI's `computeAggregate` (`rows.length`) and the chart aggregators' `'count'` path (tallies every row per bucket regardless of measure value), so "count of X grouped by Y" returns the same number for every widget kind over the same data. `applyRankToSeriesFieldData` (a seriesField rank filter) coerces both the ranked series' names and the aggregated data's series keys through `String(...)` before the membership test, since a numeric split-by value (e.g. a year) survives as a genuine `number` in `seriesNames` while `Object.keys`/`Object.entries` on `seriesData` are always strings — comparing them without coercion silently dropped the kept series' data column and crashed the renderer.

### Query-descriptor field/aggregation dispatch (`src/internals/queryDescriptor.ts`, `chartTypeRegistry.ts`)

The async-adapter path (and cross-source field collection generally) needs to know, per widget kind / chart type, which field IDs belong in the SELECT clause and which aggregation specs to push down to the DB tier. `queryDescriptor.ts` builds the `StudioQueryDescriptor` but delegates the per-type branching to `internals/chartTypeRegistry.ts`'s `getDescriptor(kind, config)`, which returns a `ChartTypeDescriptor` (`collectFields` + `buildAggregationSpecs`). Chart widgets look up `config.chartType` in a `chartTypeRegistry` map (`satisfies Record<StudioChartType, ChartTypeDescriptor>`, so a new chart type without an entry is a compile error); non-chart kinds look up `kind` in a `widgetKindRegistry` (grid/kpi/map/pivot). The registry encodes each type's push-down policy in one place — e.g. KPIs never push aggregations to the server (they aggregate client-side via `computeAggregate`; a server-side `COUNT` over one pre-aggregated row would return 1, not the real count), scatter/gantt return raw rows, and foreign-source sparkline/blended-series fields are excluded from the primary SELECT and joined in-memory instead. Gauge is the same hazard as KPI and has its own dedicated `gaugeDescriptor` for it: it is not routed through the shared `xyDescriptor` (which every other xy-style chart type uses), and its `buildAggregationSpecs` always returns `[]` — `renderGauge` aggregates client-side via `computeAggregate(rows, yField, yAggregation)`, so pushing a server-side spec would return one pre-aggregated row and re-aggregating over it would collapse a `count` to `1` (or otherwise return the wrong value) instead of the real aggregate. Every descriptor that reads a chart's value field — including heatmap, funnel, and sankey — resolves it as `config.yField ?? config.ySeries?.[0]?.fieldId`, mirroring the same fallback the corresponding `render*` function in `chartTypeDefs.tsx` uses, so a config authored with the value field only in `ySeries` (no `yField`) is neither dropped from the adapter SELECT nor missing from lazy expression-field enrichment. Sankey is the one family with no `yAggregation` concept — a link's weight is always the sum of its underlying rows — so its descriptor hardcodes `fn: 'sum'` rather than reading `config.yAggregation` the way the xy/heatmap/funnel descriptors do. A `filterMode: 'rank'` filter (top-N/bottom-N) has no wire representation at all — its reduction is a post-aggregation operation the in-memory path applies via `compileRowTest`/`applyFilters`, not a predicate a server can evaluate — so `queryDescriptor.ts` strips every `filterMode === 'rank'` leaf before building the server filter tree (both for a widget-scoped and a page-scoped rank filter; `filterScoping.ts`'s widget-scope case explicitly excludes `filterMode === 'rank'` filters from the match) and the rank reduction is applied client-side against the fetched rows afterward, the same way the sync path does it. `buildXYAggSpecs` (the shared yField/ySeries spec builder for the xy-style descriptors) de-duplicates by SQL alias (the field id): `config.yField` and a `config.ySeries` entry routinely name the same field (the setup panel writes both when a measure is picked), so emitting two specs for one alias would produce an ambiguous duplicate-alias query — the more specific per-series fn wins over the `yField`-derived one.

### `useWidgetRows` (`src/internals/useWidgetRows.ts`) and its helpers

The central widget-facing hook. It branches on whether the widget's data source has an `adapter`:

- **Sync (in-memory) path**: computes `usedFieldIds` from the widget's config plus active filter fields, where "active filter fields" means only filters that `selectFiltersForWidget` actually scopes to this widget (`reachableFilters`) — not every filter in `state.doc.filters` — so a filter added anywhere else on the dashboard doesn't widen this widget's field set or invalidate its L1/L2 cache entries; runs L1 (`getCachedNormalizedDataSource`) once per render, then a memoized `computeFilteredRows(include)` callback calls `selectFiltersForWidget` + `resolveRowsCached` (L2+L3) for whichever of the three filter baselines is requested.
- **Async adapter path**: the fetch is encapsulated in `internals/useAdapterRows.ts`, which builds a `StudioQueryDescriptor` (`queryDescriptor.ts`), checks the module-singleton `studioRequestCache` (30s TTL, in-flight dedup — see `StudioRequestCache.ts`), and calls `dataSource.adapter.getRows(descriptor)` in a `useEffect`. `useWidgetRows` then re-applies L2 client-side on the returned rows (adapters return physical columns only; the server cannot compute a calculated field) plus cross-filters/interactive filters, reusing the exact same `selectFiltersForWidget` + `resolveRowsCached` calls as the sync path (just scoped to `include: 'no-cross' | 'no-chart-cross'`), so the two paths can't disagree about scoping.

The hook returns three row baselines plus derived flags, all built to make cross-filter/cross-highlight rendering correct and cheap:

- `filteredRows` — every active filter applied (page + widget + cross-filter + interactive).
- `filteredRowsNoCross` — page + widget filters only; identical reference to `filteredRows` when there are no incoming cross/interactive filters (downstream memos short-circuit automatically).
- `filteredRowsNoChartCross` — page + widget + interactive, but _not_ chart-click cross-filters; the correct "all rows" baseline for a grid's cross-highlight overlay, because interactive (filter-widget) selections are always hard filters (BI convention) while chart-click cross-filters drive a dim/highlight overlay instead of removing rows.
- `hasCrossFilters` / `hasChartCrossFilters` / `shouldShowGhost` — whether a ghost/ghost-bar overlay should render (only for `crossFilterMode === 'cross-highlight'` and an actual chart-click cross-filter — interactive selections never trigger the ghost).
- `effectiveRows` — the widget's primary dataset, selecting `filteredRowsNoCross` in `crossFilterMode === 'none'` and `filteredRows` otherwise.
- `isLoading` / `isRecomputing` / `isError` / `errorMessage` — adapter fetch state (`isLoading`/`isError`) and a `useDeferredValue`-driven `isRecomputing` flag for page/widget filter changes on the sync path (used to show a subtle loading overlay without blocking the UI).

Cross-source display columns (grid columns or map fields referencing a many-to-one related source) go through a separate, source-scoped enrichment step — `enrichWithCrossSourceFields`/`enrichWithCrossSourceColumns` (`crossSourceEnrichment.ts`) — applied after filtering via the `enrichIfNeeded` callback, itself a no-op (reference-preserving) when the widget has no cross-source columns.

Two chart-specific pipeline hooks sit on top of `useWidgetRows`: `internals/useChartRows.ts` encapsulates L4 (chart-grain re-anchoring) by wrapping `resolveChartRowsForAggregation` with store subscriptions for `dataSources`/`relationships`/`expressionFields`, and `components/widgets/StudioChartWidget/useBlendedSeriesRows.ts` independently fetches each foreign-source series of a mixed chart against its own source (a blended series has no single grain to re-anchor to). Rather than hand-rolling its own filter matching, each foreign source's applicable filters are resolved through `selectFiltersForWidget` — the same single scoping authority every other widget path uses — called with a synthetic widgetId (so no real `scope: 'widget'` filter can ever match) and `include: 'no-cross'`, then further narrowed to filters whose field actually exists on that foreign source OR names one of that source's own non-measure expression fields (`sourceExpressionFields.some((ef) => ef.id === f.field && !ef.isMeasure)`, mirroring the derived-ownership check `dataSourceGraph.ts` already uses for the primary series' L3 cross-filter routing) — a foreign series aggregates independently in its own source, with no cross-source join, so a filter naming a field that lives only on the primary source or elsewhere must stay unconstrained here rather than being evaluated against `undefined` and spuriously dropping every row; a filter on the foreign source's OWN calculated column, however, IS evaluable (those fields are enriched into the very rows the series aggregates via `spec.expressionFields`) and previously fell through the native-fields-only gate, silently exempting the foreign series from a filter the primary series honored (finding 2.3). Routing through the shared authority (rather than a hand-rolled `scope.kind === 'page' || 'dashboard-date-range'` match with no `pageId`/`sourceId` check) fixes a page filter authored on a different page leaking into a foreign series, and resolves a `dashboard-date-range` preset via `resolveDateRangePresets` instead of leaving it `value: null`/incomplete and silently skipped. The hook also subscribes to each foreign source's own expression fields (`makeSelectExpressionFieldsForSources` over the distinct foreign source ids) and threads them through L2 enrichment on both paths — the sync path passes them into `resolveRowsCached`, and the adapter path both widens the query descriptor's SELECT (`buildQueryDescriptor(..., expressionFields, relationships)`) and re-enriches the adapter's returned rows (mirroring `useWidgetRows`'s `enrichedAdapterRows`) — so a foreign series backed by a calculated field renders its real values instead of all zeros. A failed refetch clears (rather than retains) that source's previously-cached async rows, so a series whose descriptor changed (filters/xField/xGroupBy) and then failed to refetch renders empty instead of silently serving indefinitely-stale pre-change rows while the primary series reflects the new filters.

### The recurring design theme

Every cache in `internals/` (`normalizedRowsCache`, `enrichedRowsCache`, `resolvedRowsCache`, the L4 anchor path, `computedCache.ts`) uses **per-entry dependency tracking instead of blanket invalidation** — an entry stays valid unless the _specific_ upstream references it actually depends on (its own rows, the specific expression-field objects it evaluated, the specific foreign sources it joined against, the filter fingerprint) changed. An unrelated edit elsewhere on the dashboard never forces recomputation for a given widget. New caching code in this package follows the same pattern.

### The non-React pipeline façade (`src/internals/StudioPipeline.ts`)

`createStudioPipeline(state)` builds a small pure-TypeScript object (`resolveWidgetRows`, `resolveChartRows`, `getEnrichedRows`) closing over a snapshot of `{ dataSources, relationships, expressionFields, filters }`, delegating to the exact same cached pipeline functions the React hook layer uses. It accepts either a bare `StudioPipelineState` snapshot or a full partitioned `StudioState` (detected via `'doc' in state`, then read from `state.runtime.dataSources` + `state.doc.{relationships,expressionFields,filters}`). It exists for callers outside a render cycle: CSV export, the `benchmarks/` suite (`pipeline.bench.ts`, `run.ts`), and pipeline unit tests (`StudioPipeline.test.ts`). `resolveChartRows` takes optional trailing `extraFields`/`widgetFilters` parameters, threaded straight through to `resolveChartRowsForAggregation`, so a non-React caller can opt into the same non-xy-dimension resolution and anchor-scoped filter re-application the render path gets — both default to the underlying function's own `[]`/`undefined` defaults, so an existing caller that omits them keeps its prior (pre-fix) behavior unchanged until it opts in (finding 2.2).

## Widget system

Seven built-in widget kinds live under `src/components/widgets/`: `StudioChartWidget`, `StudioGridWidget`, `StudioKpiWidget`, `StudioMapWidget`, `StudioPivotWidget`, `StudioTextWidget`, `StudioFilterWidget`.

### The widget-kind registry (`src/internals/widgetRegistry.ts` + `builtinWidgetDefs.ts`)

The registry TYPES — `StudioWidgetRenderProps` (the normalized prop bag every kind's render wrapper receives), `StudioWidgetCapabilities` (`export: 'csv' | 'png'`, `expand`, `widgetFilters`, `minHeight`, `contentSx`, `skeletonHeight(widget)`), and `StudioWidgetDef` (extends the consumer-facing `StudioCustomWidgetDef` shape) — live in `internals/widgetRegistry.ts`. The VALUES live in `internals/builtinWidgetDefs.ts`: `BUILTIN_WIDGET_DEFS` is a `Record<BuiltinStudioWidgetKind, StudioWidgetDef>` — one entry per built-in kind, each with a `label`, a render wrapper component (`GridWidgetRender`, `ChartWidgetRender`, …), a `setupPanel` wrapper for the compose drawer, an `aiInsight` flag, and a `capabilities` object. It is declared `satisfies Record<BuiltinStudioWidgetKind, StudioWidgetDef>`, so omitting a kind when adding one to `StudioWidgetKind` is a compile error. `useWidgetDefMap()` merges this registry with any consumer-registered `customWidgets` (custom entries win on a kind collision) into one `ReadonlyMap<string, StudioWidgetDef>` — the single lookup every kind-dispatch site (widget card, compose drawer, edit dialog, builtin preview) uses; built-in and custom kinds are otherwise indistinguishable to callers.

The types and values are split across two files deliberately: `builtinWidgetDefs.ts` needs direct component references to every built-in widget/setup-panel, and those modules import hooks (`useStudioFeatures`, `useStudioGeographies`, `useStudioUIConfig`) back from the UI-config context — importing the concrete defs into the context/registry-types file would create a real module cycle (in a couple of cases a literal self-cycle, e.g. `ChartSetupPanel.tsx` → context → `ChartSetupPanel.tsx`). So the concrete component wiring lives in a file that depends on the context but is never depended on by it.

### `StudioChartWidget` (`src/components/widgets/StudioChartWidget/`)

`StudioChartWidget.tsx` is the orchestrator: it owns the data hook, the cross-filter selection/hover state machine (`handleItemClick`, `getSelectedDataIndices`, stale-hover reset on chart-shape change), the unconfigured/error/no-data guard chain, anomaly-detection reference lines, and a registry dispatch that delegates every chart type's actual rendering to its own component. It does not render any chart type's series/axes inline — each type has its own presentational component:

- `StudioGaugeChart.tsx` — gauge charts (thin wrapper over `@mui/x-charts`' `Gauge`).
- `StudioScatterChart.tsx` — scatter plots. A color-by ("split-by category") scatter pins each category's color via `buildScatterCategoryColorMap` (`internals/chartShapes/scatter.ts`), keyed by category identity rather than array/series index — the ghost (baseline, unfiltered) and highlighted (filtered) series lists can differ in length/order (a category present in the baseline can have no points, and therefore no series, in the current filtered set), so a positional `colors[seriesIndex]` lookup would shift every subsequent category's color and give a category's ghost a different hue than its highlighted series. The color map's category order comes from the baseline series list (a superset of the filtered categories) so a category's color never shifts as the filter changes; ghost series also carry no `label`, so the legend shows each category once (from its highlighted series) rather than twice.
- `StudioMixedChart.tsx` — mixed bar+line combination charts. A rendered series' config is always matched to its `multiYData.series` entry by `fieldId`, for both blended and non-blended charts — a blended chart's aggregated series order does not reliably line up with `ySeries` by array index, since `useChartWidgetData`'s blended-series builder drops any `ySeries` entry with no `fieldId` yet (an incomplete row mid-configuration in the setup panel), which would otherwise shift every subsequent series one index out of alignment with a positional lookup. Its band x-axis and per-series `valueFormatter`s apply the same `formatLabel`/field-format resolution every other categorical chart family uses, so a period-grouped x-axis (`xGroupBy`) and a formatted/currency value field render consistently instead of showing raw period keys and unformatted numbers.
- `StudioFunnelChart.tsx` — funnel charts (uses `chartShapes/funnel.ts` for shaping).
- `StudioGanttChart.tsx` — Gantt/timeline charts (uses `chartShapes/gantt.ts`); axis ticks and item bars are both positioned through one shared `msToPct(ms, minMs, rangeMs)` helper against the same date range and the same reference width, so bars land on the identical x-scale as their gridlines instead of drifting proportionally to date.
- `StudioSankeyChart.tsx` — Sankey diagrams (uses `chartShapes/sankey.ts`).
- `StudioHeatmapChart.tsx` — heatmap charts (wraps `@mui/x-charts-premium`'s `HeatmapPremium`).
- `StudioPieChart.tsx` — pie/donut charts: single-series with `pieMaxSlices` "Other"-grouping, grouped concentric rings (one ring per x-category, sliced by a series field — each ring aggregates via the widget's configured `yAggregation`, not a hardcoded sum, and its ring categories are grouped by `xGroupBy` when the field is temporal, matching every other chart family), arc labels, an optional custom below-chart legend, and cross-filter ghost/overlay highlighting via `PieCrossHighlightContext`. The grouped-ring path's row baseline defaults to the widget's normally-filtered rows (so an interactive filter-widget selection or a `crossFilterMode: 'filter'` cross-filter hard-filters the rings like every other widget) and falls back to the unfiltered baseline — rendering every slice and dimming the filtered-out ones — only when a chart-click cross-highlight ghost is genuinely active, mirroring the single-ring path's `pieBaseData = isPieHighlightActive ? allChartData : chartData`. Ring slice colors and legend entries are keyed by a stable union of split-by categories across ALL rings (computed once, after `pieMaxSlices` "Other"-grouping is applied identically to every ring so the kept category set — and therefore the color mapping — doesn't vary ring to ring), so the same split-by category is always the same color and appears in the legend exactly once, regardless of which ring first introduces it; this reconciles with the single-ring path's `pieColors` (explicit `chartColors` > theme `MuiPieChart` default > `resolvedChartColors`) so dimmed and un-dimmed arcs, and the single- vs grouped-ring paths, always draw from the same palette. Ring tooltips also apply the measure `valueFormatter` (previously raw numbers) to match the single-ring path.
- `StudioLineAreaChart.tsx` — line and area charts (plain/stacked/100%): seriesField (split-by), multi-Y, and single-series (line and area share one series-construction path, parameterized on `isArea`) rendering, ghost series with the alpha baked directly into `series.color` (line 25% / area ~19% — `@mui/x-charts` resolves `series.color ?? colors[i]`, so the color itself must already carry the ghost alpha), and single-series forecast trend/confidence-band overlays (`computeWidgetForecast`; bands are line-only, never area). The single-series ghost baseline is aligned to the filtered axis via `alignFilteredToAllLabels` (the same helper the bar chart uses), so a cross-filter that removes an entire x-bucket doesn't misplot the ghost values or desync the "filtered / total" tooltip pairing. The multi-Y series builder, `lineSeries.ts`'s `buildMultiYLineSeries`, resolves each series' field def via the shared `resolveFieldDef()` (checking the data source's native fields AND `expressionFields`) and the same `makeValueFormatter` defaults the y-axes use — the same resolution the ghost-active branch already used and the bar multi-Y path already used — so a computed (expression) y-field's legend label/tooltip format and a native field's tooltip number style are identical whether or not a cross-filter ghost happens to be active, rather than only being correct while a ghost is on.
- `StudioBarChart.tsx` — bar charts (grouped/stacked/100%/horizontal): seriesField, multi-Y, and single-series (vertical and horizontal share one render, differing only in axis orientation, `axisTickFontSize` — horizontal-only — and `margin.right`) rendering, cross-filter ghost overlays via `CrossFilterBarContext`/`CrossFilterGhostBar` (a slot-based overlay, unlike line/area's baked-in color — bars encode value as geometry, so ghosting needs a dedicated overlay rather than a faded fill), and multi-select source-dimming via `SourceSelectionContext`/`SourceSelectionBar`. Its 100%-stacked cross-filter tooltip normalizes the raw filtered/total values into the same percent frame as the rendered series before formatting, so the ghost tooltip never mixes a raw value with `formatPercentValue`. Its single-series Top-N "Other" bucket label is resolved through `useStudioLocaleText().chartOtherBucketLabel` (the merge-with-an-existing-"Other"-category check and the axis-click cross-filter guard key on the same localized label), matching the pie chart's already-localized bucket so a non-English locale doesn't show the English literal "Other" next to translated UI or fail to merge with a real category of the same translated name. `CrossFilterGhostBar` anchors its foreground fill at each bar segment's axis-adjacent edge — the bottom for a non-negative (upward-growing) bar, the top for a negative (downward-growing) one, and the mirrored left/right edges in horizontal layout — and treats any _defined_ filtered value (including `0` or a negative number, e.g. the sum of a signed measure) as present, so a cross-filter on a signed measure neither hides the foreground bar nor draws its partial fill from the wrong end.

Each renderer is a plain presentational function component (not `React.memo`) with a local `Studio*ChartProps` interface and no Studio context/store access — the orchestrator computes every cross-cutting concern (cross-filter selection, hover state, ghost basis data, series colors) once and passes it down as props; a renderer computes only what's specific to its own chart type (including, for pie/line-area/bar, its own locally-scoped hover/highlight gating from the raw `hoveredItem`/`hoveredAxis` props plus `hasActiveXFilter`/`hasIncomingCrossFilters`). The three chart-type-specific ghost-rendering mechanisms (pie's `PieCrossHighlightContext`, line/area's baked-in series color, bar's slot-based `CrossFilterGhostBar`) are deliberately NOT unified — each is shaped by what its underlying `@mui/x-charts` component actually needs.

The dispatch is a registry, not an if-chain: `chartTypeDefs.tsx`'s `CHART_TYPE_DEFS` (`satisfies Record<StudioChartType, ChartTypeDef>` — exhaustive the same way `BUILTIN_WIDGET_DEFS` is over widget kinds and `chartTypeRegistry` is over query-descriptor dispatch) maps each of the sixteen `StudioChartType` literals to a `ChartTypeDef<T>` describing its guard-order behavior (`needsXField`/`runsSupportGuard`/`runsNoDataGuard` — `gauge` is the only type that skips all three, handling its own unconfigured state in `renderGauge`; `gantt` skips only the shared xField guard, since it has its own label/start/end field guard) and a `render(ctx: ChartRenderContext<T>)` method (declared as a method, not an arrow property, so its `ctx` parameter is checked bivariantly, letting a family-narrow renderer satisfy the `Record<StudioChartType, ChartTypeDef>` union). Both types are generic over `StudioChartType`: `ChartRenderContext<T>`'s `config` field is narrowed to `StudioSharedWidgetConfig & StudioChartConfigOfType<T>` (the schema package's per-family chart config), so each `render*` function (`renderBar`, `renderLineArea`, `renderMixed`, `renderHeatmap`, `renderFunnel`, `renderGantt`, `renderSankey`, `renderPieDonut`, `renderScatter`, `renderGauge`) reads only the config keys its own chart family owns, with no per-renderer `as` cast. `StudioChartWidget` builds one `ChartRenderContext<StudioChartType>` (the union-typed default, resolving to the full `StudioChartWidgetConfig` union) and the single documented dispatch cast at the `(chartTypeDef as ChartTypeDef<StudioChartType>).render(renderContext)` call site narrows the dynamically-indexed lookup — a contained TS "correlated union" inference gap, not a soundness hole, since the resolved `chartType` and `renderContext.config.chartType` are the same value. The lookup falls back to the `bar` entry for an unrecognized/legacy `chartType`.

**Chart config's retention-across-type-switch invariant.** Switching a chart's type (bar → gauge → bar) keeps the config keys the prior type used (`xField`/`ySeries` survive the round-trip) — a deliberate UX feature, not a bug. It is respected by the write-side validators (`updateWidgetConfig` validates only the incoming patch, never the stored config — see State management) and by the setup panels (a type-specific section reads only its own family's keys, leaving the others untouched in the stored config).

Supporting modules: `useChartWidgetData.ts` (data-fetch/aggregation orchestration hook — notably, it returns a `null` single-series `chartData` whenever more than one y-field is active, which is why each renderer's multi-Y branch must be reachable independently of the shared "empty chartData" guard the seriesField/single-series branches sit behind — `renderBar` and `renderLineArea` (`chartTypeDefs.tsx`) both compute their own `hasMultiY` flag and check it ahead of the shared `!chartData` guard, so a multi-measure bar or line/area chart renders instead of falling through to the empty-state placeholder), `lineSeries.ts` (`buildMultiYLineSeries`), `chartWidgetHelpers.ts` (value formatters, `crossFilterValueEquals`/`normalizeCrossFilterValue` — the equality check deciding whether a clicked data point matches an incoming cross-filter value, `densifyBarLabels`, `alignFilteredToAllLabels`, `createLineXAxisConfig`/`makeCrossHighlightLineFormatter` (line/area-only), `resolveFieldDef()` — the single shared field-lookup helper resolving a chart field's `StudioDataField` across the widget's own source and any blended/foreign sources, `isBarStacked`/`isAreaStacked` — the single shared "does this chart type/layout combination stack its series" predicate for bar and line/area respectively, and `computeStackTotals`/`formatPercentValue`/`formatPercentAxis` — the shared 100%-stacked-normalization totals-per-label-index reducer and its series/tooltip/axis percent formatters, previously hand-rolled at each of the four multi-Y/split-by bar and line/area render sites), and the cross-filter/source-selection React contexts (`CrossFilterBarContext.ts`, `SourceSelectionContext.ts`, `PieCrossHighlightContext.ts`). Anomaly-annotation reference lines are identified via `internals/anomalyDetection.ts`'s `isAnomalyAnnotation()`/`ANOMALY_ANNOTATION_ID_PREFIX`/`ANOMALY_ANNOTATION_LABEL` — the single source of truth for the sentinel id/label format an anomaly annotation uses.

Independent per-series Y-axes (multi-Y charts with `useIndependentAxes`) bind each series via the real `@mui/x-charts` `series.yAxisId` prop (`` `y-${i}` `` per series index when independent axes are enabled, `undefined` otherwise) — `StudioBarChart`, `StudioLineAreaChart` (both its multi-Y series builder and `lineSeries.ts`'s `buildMultiYLineSeries`), and `StudioMixedChart` all bind through this same prop name.

A few narrow display-only asymmetries are deliberately preserved (each a "preserve, don't harmonize" call): the multi-Y bar ghost has no `preserveXFieldBaseline` gate (every other ghost path does); the multi-Y line/area cross-filter `highlightedItem` targets a bare `fieldId` that can never match the rendered `${fieldId}-${index}` series id, so that particular highlight is a no-op; and the single-series area chart's active series never gets the "filtered / total" cross-highlight tooltip formatter that line gets (area shows the plain value). None affect correctness of the underlying data.

Annotation/anomaly reference lines are rendered relative to the chart's DEFAULT (vertical) orientation in the `StudioChartAnnotation` model — `axis: 'y'` means a numeric value threshold, `axis: 'x'` means a category/anomaly marker — but a bar chart with `barLayout: 'horizontal'` swaps which physical axis carries the measure vs. the category band. `StudioChartWidget`'s annotation-line builder detects `barLayout: 'horizontal'` and swaps the physical `x`/`y` `ChartsReferenceLine` props accordingly, so a numeric threshold always lands on the measure axis and a category marker always lands on the band axis, regardless of bar orientation.

### Other built-in widgets

- `StudioGridWidget` — data table; group-by via DataGridPremium's own native `rowGroupingModel`/`aggregationModel` (see the fan-out-safe aggregation-function note in Aggregate & render above — `utils/gridGrouping.ts`'s `buildGroupedGridRows` itself has no production caller), footer totals via `utils/gridSummary.ts`; resolves its effective cross-filter mode as `globalCrossFilterMode ?? config.crossFilterMode ?? 'cross-highlight'` — the same precedence `useWidgetRows` resolves internally — and uses `filteredRowsNoCross` (not `filteredRows`) as its row baseline in `'none'` mode, so the dashboard-wide `globalCrossFilterMode` override and a widget-level `'none'` setting are both honored the same way every other widget kind (chart/KPI/map/pivot, and CSV export) already did; column render order follows the user-configured `config.columns` order rather than data-source field order — the exported pure `computeOrderedFieldIds(configColumns, allFieldIds)` puts configured fields first in their stored order, then any remaining source fields not yet added to `config.columns`, so a drag-and-drop / keyboard reorder in `GridSetupPanel` is reflected in the rendered grid (which also feeds `initialState`'s ordering) rather than affecting only visibility; a configured cross-source column (the setup panel lets you add a column from a related source) is resolved via `resolveCrossSourceFieldDefs(configColumns, ownSourceId, dataSources, expressionFields)`, which looks the field up in `dataSources[c.sourceId]` for every configured column whose `sourceId` differs from the widget's own, falling back to that related source's own non-measure `expressionFields` (normalized to a `StudioDataField`-shaped def) when no physical field matches — a related source's **calculated** column has no entry in `dataSources[c.sourceId].fields`, so without this fallback it was selectable in `GridSetupPanel` but produced no column def and never rendered. Resolving the def is not enough on its own: the related source's raw rows carry no value for its own calculated column either, so the widget also subscribes to its own source's plus every one-hop related source's expression fields (`getReachableSourceIds` + `makeSelectExpressionFieldsForSources`) and, for just the configured columns that are a related source's calculated field, supplementally routes those related rows through the shared L2 cache (`enrichWithCrossSourceFields`'s `expressionFields` parameter, itself backed by `getCachedEnrichedRows` scoped to the requested field ids) before the cross-source join — a reference-stable no-op when the widget has no such columns. `resolveCrossSourceFieldDefs`'s result is folded into `allFieldIds` before `computeOrderedFieldIds`/`columnVisibilityModel` run, and `buildGridColumnDefs` resolves each column's field def through a `field ?? expressionField ?? crossSourceField` fallback chain (marking a cross-source column non-editable), so a cross-source column (physical or calculated) renders on screen with the same field def CSV export already used, instead of silently disappearing from the grid while still exporting. The footer summary (`utils/gridSummary.ts`'s `computeGridSummary`) resolves a configured `sum`/`avg`/`min`/`max`/`count` field against the SAME merged field-def list (own physical fields + own expression fields + `resolveCrossSourceFieldDefs`'s cross-source defs) rather than the widget source's physical fields alone — a missing def previously made a cross-source or calculated summary field resolve as non-numeric and silently degrade to a `count`. A fanned-out cross-source summary field (one whose value was joined onto several widget rows sharing the same FK) is also FK-deduped before reducing — `extractSummaryValues` collects at most one value per distinct FK key (skipping a row with no FK, same as a row that never joined) and hands the deduped list to `gridGrouping.ts`'s shared `aggregateValues` reducer — so the footer's cross-source total agrees with the grouped view of the same column instead of double-counting the fan-out the grid's native grouping aggregation (`makeFanoutSafeAggregationFunction`) already avoided. `runWidgetExport`'s CSV export mirrors this on-screen resolution end to end: it passes the widget's own expression fields into its `enrichWithCrossSourceFields` call (so a related-source calculated column's value resolves before export, not just its def) and folds the same `resolveCrossSourceFieldDefs` result into `buildCsvContent`'s field map, so a cross-source column's exported header label and number/currency formatting match the rendered grid instead of falling back to the raw field id with no formatting. Cross-highlighted rows are matched against the incoming cross-filter by object reference (a `Set` of the actual row objects) rather than by `row.id`, so highlighting works for data sources whose rows have no stable `id` field. `getRowId`'s synthetic-id fallback spreads `row` first and sets the id key last, so a row whose own `id` field is nullish doesn't have the fallback overwritten back to that nullish value (which would collide every such row onto the same DataGrid row id). `evalConditionalFormat` (exported for direct testing) excludes `null`/`undefined`/`''` cells from the numeric comparison operators (`greater_than`/`less_than`/etc.) — `Number(null)`/`Number('')` coerce to `0`, so without the exclusion a rule like "less than 5" would spuriously match genuinely empty cells; only `is_empty` matches blanks.
- `StudioKpiWidget` — single-metric card; `kpiUtils.ts` computes the aggregate + period-over-period trend, `KpiSparkline.tsx`/`KpiTrend.tsx`/`KpiValue.tsx` render the pieces. Its value field can be owned by a directly-related "many" (child) source (e.g. a KPI on `customers` using `orders.total`) — `analyzeChartSupport`'s single-y-field branch anchors only this direction (widget on the "one" side, value field on the related "many" side); the reverse fan-in direction (widget on the "many" side aggregating a "one"-side value field) reports `mixed_cross_source_fields` and is never anchored. All four of the widget's `resolveChartRowsForAggregation` call sites (`computePeriodValue`'s trend anchoring, `useKpiGrainAnchoredRows`' headline anchoring, the sparkline's cross-source time-field join, and the fixed-period trend's cross-source-date join) thread a `widgetFilters` argument — the widget's resolved filter set, computed the same way `useChartWidgetData.ts` computes it (`selectFiltersForWidget`, matching the `'no-cross'`/`'all'` scope each row baseline uses) — so an anchor-source-scoped filter (e.g. a page filter `orders.status = 'paid'` while the value field is `orders.total`) is re-applied to the anchor rows during re-anchoring instead of only being enforced by L3's semi-join; without it, the expansion join resurrected every anchor row (paid + unpaid) for each surviving widget row, so a KPI could disagree with an identically-configured chart widget on the same page. All four sites also thread `crossFilterAllPages` (subscribed via `selectCrossFilterAllPages`) into their `selectFiltersForWidget` calls, matching the chart widget's pattern — without it a cross-page cross-filter (the dashboard-level "cross-filter across all pages" toggle) that `useWidgetRows` already applied to the rendered `currentRows` was excluded from the KPI's own L4/trend scope, so the re-anchored headline/trend could disagree with the rows the KPI actually rendered. The widget's expression-field subscription mirrors `useWidgetRows`'/`useChartWidgetData`'s `relevantSourceIds` pattern (own source + one-hop related sources +, for a many-to-many relationship, its junction source), not just its own source: an own-source-only list left an anchor-, related-, or junction-owned **expression field** (as opposed to a physical field) invisible to this widget specifically, which broke the `widgetFilters` re-application above for that one field shape — a filter on such a column carries no explicit `filterSourceId`, so `effectiveFilterSourceId` can only classify it as anchor/junction-scoped by finding it in the expression-field list; with it missing, the filter was neither re-applied at L4 (resurrecting excluded anchor/junction rows, reintroducing the exact bug the `widgetFilters` threading above was meant to close for this one shape) nor, once classified, could it be evaluated (dropping every anchor row and reading the KPI as `0`, since the anchor rows were never enriched with a column the widget's own-source-only enrichment couldn't reach). The trend's previous-period `resolveRows` call had the same blind spot in its cross-filter-routing `exprFieldIndex`, which mis-routed a related-source expression-field page filter as native and dropped every previous-period row (a bogus infinite/NaN delta against a zero previous period). `extractDateRange` treats a single-sided date filter symmetrically regardless of direction — `less_than`/`less_than_or_equal` ("until X") derives the current window as ending AT X (mirrored backward by the equivalent span), matching how `greater_than(_or_equal)` ("since X") derives a window starting at X, so the trend and sparkline are never computed over the excluded side of the filter. The "previous calendar period" comparison basis uses its own `comparisonGranularity` (week/month/quarter/year by day-count), deliberately separate from `autoGranularity` (which buckets the sparkline) — reusing the sparkline's granularity for the comparison window was what made a ~15–90 day current range overlap its own "previous period". `computeFilterBasedTrend`, the sparkline's date-filter/time-field derivation, and the KPI's hover filter-subtitle summary all scope their filter set through `selectFiltersForWidget` (the same scoping authority the widget's headline rows use) rather than a raw `scope.kind === 'page'`/`'widget'` match with no pageId/disabled check, so a disabled date filter or another page's filter can no longer drive (or be listed against) a KPI it doesn't apply to. A KPI whose value field is a measure expression field (`isMeasure: true`) aggregates via `evaluateMeasure` for its headline, trend, AND sparkline — `evaluateMeasure` returns `number | null` (`null` only when the expression's own top-level node is a `divide`/`modulo` by zero, matching the row-context calculated-column null policy; nested inside other arithmetic a `null` still coerces to `0`, same as a row-context calculated column) — since a measure's value doesn't exist per row (it is never enriched onto rows the way a calculated column is), so `computeAggregate`/`computeSparklineData` reading a nonexistent `row[measureId]` would otherwise silently produce a correct headline/trend (which already special-cased measures) alongside a flat-zero sparkline. The sparkline's field-def lookup (for tooltip format/currency) also checks `expressionFields`, not just `dataSource.fields`, matching `useKpiValue`'s headline lookup. Every cache key that depends on a measure expression's aggregate value — the headline/previous-value key (shared `measureKey`, `` `measure:${measureExprField.id}:${stableStringify(measureExprField.expression)}` `` for a measure field, `` `agg:${aggregation}` `` otherwise) and the sparkline's own key — folds in a `stableStringify` of the measure's `expression` AST, not just its id; since measures are deliberately excluded from row-identity cache invalidation (their value doesn't exist per row), editing a measure's formula changes nothing about row identity, so the fingerprint is what busts `cachedCompute` and makes the headline/trend/sparkline all reflect the new formula instead of serving the pre-edit number. `computeFilterBasedTrend`'s previous-period window boundaries are formatted via `toLocalYmd` (local Y/M/D components), not `date.toISOString().slice(0, 10)` — `computePreviousPeriodRange` computes those boundaries in local time, so serializing through UTC would day-shift the window for a viewer not on UTC.
- `StudioMapWidget` — choropleth map; `geographyLoaders.ts` lazily loads topojson for built-in (`world`/`usa`/`europe`) and consumer-registered geographies, `countryUtils.ts` normalizes country-name/code matching (its alpha-3/name lookup tables cover every code its own built-in Europe map renders, including small states like Malta, Andorra, and Kosovo), `StudioMapShapePlot.tsx` renders shapes, `StudioMapTooltipContent.tsx` the hover tooltip. Each geography load is tagged with a monotonically increasing request id so a fast geography-toggle can't apply a stale topology under the wrong projection, and a rejected loader sets a retryable error state (surfaced via `StudioWidgetErrorOverlay`) instead of leaving the widget permanently blank. Clicking a region that merges multiple raw country-code/name variants (e.g. `'US'`/`'USA'`/`'United States'`) into one displayed shape emits an `in` cross-filter over every raw variant that feeds it, not just the first — so downstream widgets filter to exactly what the clicked region visually aggregates. `MapSetupPanel` offers `mapValueField` from every visible source, including ones related to the widget's own by a many-to-one relationship — `useWidgetRows`' cross-source enrichment joins that one-side value onto every many-side widget row sharing the FK, the same fan-in topology charts/KPI fail closed on (`mixed_cross_source_fields`) and the grid FK-dedupes. The `regionData` memo resolves this real FK-dedup rather than restricting the panel: when the value field's source differs from the widget's own, it resolves the relationship's FK field on the widget's own rows (`buildManyToOneRelationshipIndex`) and, per region, tracks a `Set` of already-counted normalized FK keys (`normalizeJoinKey`) so a related record fanned out across several widget rows is aggregated into the region exactly once — the map analogue of the grid's `utils/gridGrouping.ts` `symmetricAggregate`. A row whose FK doesn't resolve (or a same-source value field, where `valueFkField` is `null`) falls back to the plain per-row reduce, which is already correct in that case.
- `StudioPivotWidget` — pivot table; `pivotUtils.ts`'s `buildPivotMatrix` computes the cross-tab (row/column category sets, plus a `cells`/`rowTotals`/`colTotals`/`grandTotal` map of shared aggregation state), `PivotTable.tsx` renders it. A row/column category is membership, independent of whether its measure is usable: `buildPivotMatrix` records the row's `cells` map entry (even if empty) before checking whether the cell's value is unusable, so `matrix.cells.get(rowValue)` always returns a `Map` (possibly empty) for any row that occurred in the input, never `undefined`. Each cell/row-total/column-total/grand-total tracks a `rowCount` (every row landing there, unconditionally) separately from its `AggregateAccumulator` (which only advances for coerced-numeric measure values), so `'count'` reads the unconditional `rowCount` — COUNT(\*) semantics — while `sum`/`avg`/`min`/`max` read the accumulator; a cell whose measure values are all null/non-numeric therefore still reports its true row count under `'count'` instead of the accumulator's empty result. Row/column category values are ordered with a `naturalCompare` comparator (numeric-looking strings compare numerically, e.g. `"2"` before `"10"`, otherwise falls back to lexicographic) rather than a plain lexicographic `.toSorted()`. CSV export and the on-screen table round a cell to the same precision via the shared `roundPivotValue` (2 decimals), so an exported `avg` cell can no longer differ from its displayed value in the third decimal. `pivotToCsv` takes a `totalLabel` parameter (defaulting to the English literal for back-compat) so the CSV export's totals caption matches `PivotTable.tsx`'s on-screen locale-aware label instead of always reading "Total"; its download plumbing (`downloadCsv`, re-exported from `internals/widgetUtils.tsx` — see below) is shared with the grid's CSV export rather than duplicated.
- `StudioTextWidget` — markdown text block (`renderMarkdown.tsx`); `useTextWidgetAI.ts` supports AI-assisted content generation/refresh. Its `/chat` request also has its own `privateMode` gate, separate from `studioBackendAdapter.ts`'s: `dashboardState` (every widget config, filter, field name, layout) and `pageSnapshot` (CSV-style sampled real row values from sibling widgets) are each only built (and included in the POST body) when `aiConfig?.privateMode !== true` — under private mode neither is computed at all, matching the guarantee the main chat path already gave. Its snapshot/cache-key memo subscribes to `selectWidgets`/`selectDataSources`/`selectFilters`/`selectExpressionFields`/`selectRelationships` in addition to `activePage`/`dashboard` — the memo body reads sibling widget configs, row data, active filters, calculated fields, and relationships via `controller.getState()`, none of which changes `activePage`/`dashboard` identity on their own, so a runtime data refresh, a sibling widget's config edit, **or an added/edited page filter** now correctly recomputes the memo (and busts the cached markdown) instead of serving a stale, pre-filter narrative until a manual `refresh()` (the `filters` partition was the one trigger missing before — an added page filter re-rendered every sibling widget filtered but left the text widget's AI narrative describing the unfiltered numbers, and clicking "refresh" re-sent the same stale, memoized snapshot). This hook's chat request also declares `allowedTools: ['query_data_source', 'summarise_page']` (no chat UI exists here for a human to review a tool-approval prompt) and its SSE handler auto-approves a `tool-approval-request` only when the request's own `toolName` is actually in that read-only list — a defense-in-depth client-side guard against a server that (by bug or drift) asks approval for a tool outside what this request itself restricted, rather than an unconditional rubber-stamp `approved: true`.
- `StudioFilterWidget` — an on-canvas filter control; per-control-type implementations under `controls/` (`DateRangeControl`, `MultiSelectControl`, `SliderControl`, `ToggleControl`). `DateRangeControl` tracks per-field focus (`fromFocusedRef`/`toFocusedRef`) so the external-value sync effect skips resetting a field the user is still actively editing — without it, a debounced intermediate commit (e.g. an incomplete "From" date round-tripping through the store as `{ from: undefined, to }`) would clear the field out from under the user's in-progress typing roughly 300ms later. ### Custom widgets

Consumers register `StudioCustomWidgetDef[]` (kind, label, `component: React.ComponentType<StudioCustomWidgetProps>`, optional `setupPanel`, `requiresDataSource`, `aiInsight`, `defaultConfig`, `fullBleed`, `shouldHide`) via `Studio`'s (or `StudioProvider`'s) `customWidgets` prop. `useWidgetDefMap()` folds them into the same registry `BUILTIN_WIDGET_DEFS` populates, so custom and built-in widgets are dispatched identically everywhere. `StudioCustomWidgetProps.dataSource.rows` includes L2 enrichment (expression fields pre-resolved) but not filters/cross-filters — a custom widget that needs those calls `useStudioSelector` itself. Per `AGENTS.md`/`CLAUDE.md`'s "x-studio custom charts" guidance, a bespoke chart type belongs in an app-level custom widget composing the public `@mui/x-charts*` APIs — never patched into the shipping `x-charts*` packages.

### Widget chrome (`src/components/StudioWidgetCard/`)

`StudioWidgetCard` wraps every widget kind (built-in or custom) with shared chrome — title/subtitle, loading/error/empty states, and the hover action overlay. `StudioWidgetCardActionsOverlay.tsx` renders that overlay's per-action buttons (export, expand, AI insight menu, anomaly toggle/explain, AI refresh) as shared components (`ExportAction`, `ExpandAction`, `InsightMenuAction`, `AnomalyToggleAction`, `AnomalyExplainAction`, `AiRefreshAction`), reused identically between the edit-mode and view-mode toolbars. Both toolbars gate the expand button on a `canExpand` prop (`def?.capabilities?.expand === true`) rather than `isChart` — the same condition `StudioWidgetCard` uses to decide whether to mount `StudioWidgetExpandDialog` at all — so a custom widget kind that declares `capabilities.expand: true` gets a working expand button, not just an expand dialog implementation with no way to open it. `StudioWidgetExpandDialog.tsx` is the full-screen expand view (chart only).

The card composes its cross-cutting concerns from focused modules in the same directory rather than inlining them: `widgetExport.ts`'s `runWidgetExport` owns the CSV/PNG export dispatch across widget kinds — for a grid widget with cross-source columns, it first runs the same `enrichWithCrossSourceFields` enrichment `useWidgetRows` applies for display, so a cross-source column that renders correctly on screen no longer exports as an empty one — `useStudioWidgetInsights.ts` owns the AI-insight and anomaly state/routing, and `useStudioWidgetCardDrag.ts` owns the canvas drag wiring — its `document.body` drag flag and inline card opacity are cleared not only on drop but also on unmount or a mid-drag `canDrag` flip, so a global drag flag (and any CSS keyed on it) can't leak if the card unmounts or leaves edit mode while a drag is in flight. An untitled widget falls back to a localized kind label. CSV export (both here and the pivot widget's `pivotToCsv`) routes every text cell through the shared `internals/csvUtils.ts` `escapeCsvCell`, which applies standard CSV quoting (double-quote wrapping + quote doubling) and neutralizes spreadsheet formula injection by prefixing any cell that begins with `=`/`+`/`-`/`@`/tab/CR with a `'`. Whether a cell is treated as "numeric" for escaping purposes is decided by the cell's _runtime_ value, not its column's declared field type — a `number`-typed column can still hold a non-numeric runtime value from dirty data or a misbehaving adapter, and that value must still go through the full formula-injection guard rather than being waved through because its column says `number`. A genuine runtime number is still wrapped in quotes (`quoteNumericCsvCell`, in `internals/widgetUtils.tsx`) — `Intl.NumberFormat`'s default thousands separator (e.g. `1,234.50`) would otherwise split the row into an extra unquoted CSV column — but is exempt from `escapeCsvCell`'s leading-apostrophe rewrite, since a genuine number can never itself be interpreted as a spreadsheet formula and the apostrophe would corrupt a legitimate leading `-` (e.g. `-5`). The browser-download mechanics (`Blob`/`createObjectURL`/anchor-click, plus filename sanitization that strips non-alphanumeric characters while preserving the file extension) are one shared `downloadCsv` function in `internals/widgetUtils.tsx`, used by both the grid's `exportGridToCsv` and the pivot widget's CSV export (re-exported from `pivotUtils.ts` for its existing importers) — previously duplicated near-line-for-line between the two with inconsistent filename sanitization.

## Canvas / layout (`src/components/StudioCanvas/StudioCanvas.tsx`)

`StudioCanvas` renders the active page's `widgetRows` (`string[][]`, each inner array a row of side-by-side widget IDs) as a flex grid. Key exported helpers:

- `getWidgetMinSpan(widget)` — minimum resizable column span (`MIN_SPAN` from `canvasGridConstants.ts`, i.e. `GRID_COLS / 4`; a KPI widget without a sparkline gets a smaller `KPI_NO_SPARKLINE_MIN_SPAN = 4` since it doesn't need room for a chart).
- `LiveDragState` — `{ leftId, rightId, leftSpanLive, totalSpan }`, the transient (non-committed) state of an in-progress between-widget resize drag.
- `computeGridLineLefts(row, widgetColSpans, liveDrag)` — computes CSS `left` values for the column-divider overlay lines shown during a resize drag, one per grid-column boundary.

The drop handler computes the target page's desired final `widgetRows` from the drop position and hands them to `controller.moveWidget(...)` (an existing widget) or `controller.insertWidgetAt(...)` (a compose-drawer widget), which route through the shared reducer's `enforceLayoutColSpans` — so no column-span cleanup logic lives in the canvas. For a same-row move, the handler locates the dragged widget's column index in the row before removing it, then shifts the target insertion index back by one only when the drop target sits after that original position — otherwise removing the widget first (to re-splice it at the drop point) would land a rightward drag one slot past the gap the user actually targeted. An empty page (no widget rows) registers its own `useStudioDropTarget` directly on the empty-state `Paper` — `StudioPageRows` (and the `InsertionPoint`/`WidgetGap` affordances it would otherwise provide) is never rendered when there are no widget rows, so without this the edit-mode empty state's "drag them here" copy had no drop target to back it and a drag was a dead drop; the empty-page handler mirrors `StudioPageRows`' two drop branches (a new compose-drawer widget, or an existing widget dragged in from another page) but always produces a single fresh row.

The empty-state `Paper` and the populated-state root `Box` are different DOM nodes rendered in mutually exclusive branches of the same persistent, memoized `StudioCanvas` component, so a plain `[ref]`-only effect reading `ref.current` once would never re-run the very first time a page's emptiness flips after mount (delete the last widget, or add one back) — the hook would keep referencing a detached/never-attached node. `useStudioDropTarget` takes an explicit `watch` value (`StudioCanvas.tsx` passes `isEmptyPage`) included in its effect's dependency array specifically to force re-registration on that transition even though `ref` itself never changes identity. The canvas' `ResizeObserver` (which measures `canvasWidth` for the responsive stack-tier breakpoints) is attached via a genuine callback ref instead (`setCanvasNode` backing a `canvasNode` state value, wrapped into a `{ current: canvasNode }` ref for the observer hook) rather than a stored `RefObject`, so swapping which branch's `Box` mounts calls the callback again and the observer re-attaches to the new node automatically.

Drag-and-drop uses `@atlaskit/pragmatic-drag-and-drop` via `useStudioDraggable.ts`/`useStudioDropTarget.ts` (canvas-widget and compose-drawer-widget drag types defined in `studioWidgetDndTypes.ts`), with `@atlaskit/pragmatic-drag-and-drop-auto-scroll` wired in for autoscroll near the viewport edge. `StudioDragLayer.tsx` renders the floating drag preview; `createClonePreview.ts` builds it. `InsertionPoint.tsx` and `WidgetGap.tsx` render the drop-target affordances between/around widgets. `RowResizeHandle.tsx` is the draggable divider between two widgets in the same row, committing through `StudioController.setAdjacentWidgetColSpans`. `StudioDateRangeBar.tsx` is the dashboard-level date-range control; its preset `Select` includes a `'custom'` item whenever `activePreset === 'custom'` (a value a host or the AI can set via an explicit `customFrom`/`customTo` range, but which has no dedicated authoring UI in this bar), so a persisted custom preset renders as a valid selected value instead of out-of-range/blank — selecting it is a deliberate no-op, since there's nothing here to edit the custom bounds themselves. `StudioCrossFilterBar.tsx` shows the active cross-filter mode/scope toggle; `StudioQuickFilterBar.tsx` surfaces active page filters as removable chips.

Test files co-located with the canvas target specific concerns: `StudioCanvas.gridLines.test.ts` (grid-line math), `StudioCanvas.responsive.test.ts` (stack-breakpoint behavior), `StudioCanvas.regressions.test.ts` (layout regressions), `StudioCanvas.remount.test.tsx` (state continuity across remounts).

## Filters

`StudioFilterState.scope` (defined in `@mui/x-studio-schema`'s `stateTypes.ts`) is a discriminated union — `{ kind: 'page' }`, `{ kind: 'widget'; widgetId }`, `{ kind: 'cross-filter'; sourceWidgetId; pageId }`, `{ kind: 'interactive'; sourceWidgetId; pageId }`, `{ kind: 'dashboard-date-range'; sourceId; pageId }` — the sole scope descriptor; there is no separate `widgetId`/`pageId`/`isDashboardDateRange` field to keep in sync. `internals/filterScoping.ts`'s `selectFiltersForWidget` is the single scoping authority consumed by both the sync and async-adapter code paths in `useWidgetRows` and by the non-React `StudioPipeline`.

- `src/components/StudioFiltersDrawer/` — the page/widget filter authoring UI: `PageFilterRow.tsx`/`WidgetFilterRow.tsx` (row UI), `FilterValueInput.tsx`/`DateValueInput.tsx`/`RelativeDateInput.tsx`/`SelectionFilterInput.tsx`/`RankFilterInput.tsx` (per-mode value editors), `CrossFilterSection.tsx`/`InteractiveFilterSection.tsx` (read-only summaries of live cross-filter/interactive state — `InteractiveFilterSection`'s clear button routes through `controller.clearInteractiveFilter(sourceWidgetId)`, the same non-undoable path the originating widget's own clear-pill uses, rather than the undoable `removeFilter`, so a Ctrl+Z elsewhere can no longer resurrect an interactive filter the user just cleared from the drawer), `filterDrawerUtils.ts` (`getOperators` and other drawer-specific helpers), `useFieldValues.ts` (distinct-value fetching for selection filters), and `FilterCard.tsx`/`FilterSection.tsx`/`FilterBody.tsx`/`SecondCondition.tsx`/`FilterModeToggle.tsx` (the row UI's decomposed sub-pieces).
- `filterOperatorMetadata.ts` is the single source of truth for which `StudioFilterOperator`s are valid per field type (`string`/`number`/`date`/`datetime`/`boolean`) and their display labels, shared by both `StudioWidgetEditDialog/FilterRow.tsx` and `StudioFiltersDrawer/filterDrawerUtils.ts`. Both `getOperators` (drawer) and `summarizeFilter` (the plain-language filter-chip summary shown in the quick-filter bar and drawer) are routed through the caller's `localeText` (`useStudioLocaleText()`'s `StudioLocaleText`) rather than hardcoding English, so operator labels and filter summaries localize consistently everywhere a filter is displayed.
- `src/components/StudioCanvas/StudioQuickFilterBar.tsx` — canvas-level chip row for active page filters (enable/disable/remove without opening the drawer). Its "Clear all" action computes the resulting `filters` array up front (every page filter removed, every cross-filter for a cleared source widget removed) and commits it in one `controller.updateState({ doc: { filters } })` call, rather than looping `removeFilter`/`clearCrossFilter` per filter — so one click is one undo entry, and a single Ctrl+Z restores every cleared filter at once instead of only the last one removed.
- Cross-filter value comparison (deciding whether a clicked chart data point matches an existing cross-filter's stored value) is centralized in `chartWidgetHelpers.ts`'s `crossFilterValueEquals`/`normalizeCrossFilterValue` (used by `StudioChartWidget` when rendering cross-highlight state) rather than being re-implemented per chart type.
- Filter _evaluation_ (turning a `StudioFilterState` into a per-row predicate) lives in `internals/filterUtils.ts` (`applyFilters`, `compileRowTest`, `resolveDateRangePresets`, relative-date resolution). `resolveDateRangePresets` resolves every scoped filter's preset via the singular `resolveDateRangePreset`, which turns a non-custom preset (`'last7Days'`, `'thisMonth'`, …) into concrete `{ from, to }` bounds computed fresh at query time regardless of the filter's `scope.kind` — both dashboard-wide (`dashboard-date-range`) and widget-scoped presets (e.g. a per-KPI date range) resolve the same way, so a stored filter is never a stale absolute date. In `compileRowTest`'s selection-mode branch, an `operator: 'not_in'` selection (the multi-select filter widget's "Exclude" toggle) compiles to a row test that excludes the selected set, mirroring the "Include" (`in`) branch's inverse — the operator is explicitly consulted rather than always compiling the inclusive test. Date-typed `equals`/`not_equals` conditions route both sides through the same `toComparable` normalization (resolving a `RelativeDateValue` and normalizing Date/ISO/timestamp forms) that `greater_than`/`less_than`/`between` already used, rather than a raw `==`/`!=`, so a relative-date "On" filter or a `datetime` field compared against a date-only picker value still matches.
- The per-page rank-filter-uniqueness guard is `internals/rankFilterScope.ts` (see State management) — one rank filter per page context, shared by `updateFilter` and the drawer rows.
- A `between` filter's value is a `{ from, to }` object, not a scalar, so both `FilterValueInput.tsx` (filters drawer) and `StudioWidgetEditDialog/FilterRow.tsx` (the widget edit dialog's lower-fidelity filter row) give it a dedicated two-input editor — a `from`/`to` pair of number inputs for numeric fields, and the same `DateValueInput` picker rendered twice for date/datetime fields — instead of routing it through the generic single-value `TextField` path, which would stringify the object to `[object Object]` and clobber it into a scalar on the first keystroke. Switching a filter's operator either direction across the `between`/scalar value-shape boundary resets the value rather than stranding it: `FilterBody.tsx` (drawer) and `FilterRow.tsx` (edit dialog) both clear a shape-incompatible value when the new operator isn't `between`, and the `between` branch of `FilterValueInput`/`FilterRow` defensively coerces a non-object value when switching into `between` — so neither direction can leave a `{from,to}` object behind for a scalar operator (which `toComparable` would coerce to `NaN`, silently matching nothing, while the input renders `"[object Object]"`) or a bare scalar behind a `between` editor. The reset predicate in both files explicitly excludes `isRelativeDateValue(filter.value)` (`filterDrawerUtils.ts`) from the "value looks like a `between` shape" check: a `RelativeDateValue` (`{relative: true, amount, unit, direction}`) is also a plain object, but it's a fully-supported scalar filter value, not a `between`-shaped one, so switching between two scalar operators (e.g. "On" → "Before") no longer silently discards a configured relative-date value. `SecondCondition.tsx` mirrors both of the primary condition's safeguards for the second condition: it resets `value2` under the same shape-vs-relative-date predicate whenever `operator2` leaves `between`, and `PageFilterRow.tsx`/`WidgetFilterRow.tsx`'s non-undoable self-repair effect (see below) now repairs a stored `operator2` invalid for the field's current type alongside `operator`, not just the primary one. A `FilterRow` field switch also resets `operator`/`value` together (mirroring the drawer's phase-1 field pickers), so switching, say, a string `contains` filter to a number field can't leave an operator outside that field type's allowed set.
- `WidgetFilterRow.handleFilterChange` (like `PageFilterRow`) commits only the changed fields to `controller.updateFilter`, which already merges the patch onto the CURRENT store filter — passing a full render-time filter snapshot instead (as the row previously did) let a debounced value commit (`FilterValueInput`'s 150ms debounce captures the `filter` snapshot from the keystroke's render) silently revert a concurrent operator/conjunction edit that landed in between; a rank-filter's auto-wired `field` is the one case that still needs to be added to the delta.

## Persistence & schema migrations (`@mui/x-studio-schema`'s `statePersistence.ts`)

Persistence is a pure state-shape transform, so it lives in the schema package (`packages/x-studio-schema/src/statePersistence.ts`) alongside the reducer and factories; `x-studio` re-exports `serializeState`/`serializeDoc`/`deserializeState`/`migrateState`/`CURRENT_SCHEMA_VERSION` and the `Serialized*` types from `store/index.ts`, so consumers still import them from `@mui/x-studio`. The persisted JSON is exactly the `doc` partition minus its cross-filter entries — `session` and `runtime` are reconstructed fresh on load (session defaults, runtime from the host).

`CURRENT_SCHEMA_VERSION` is an integer (currently `1`), carried on `doc.schemaVersion` and stamped onto every serialized payload.

- `serializeDoc(doc)` → `SerializedStudioState` is the shared inner logic: it spreads every `StudioDoc` field (so a newly-added doc field is carried automatically — no hand-picked field list to forget) then strips `scope.kind === 'cross-filter'` filter entries (runtime-only interaction state) and omits the empties (`expressionFields`/`filterPresets`/`ai` when empty). `serializeState(state)` is a thin wrapper that reads exclusively from `state.doc`, so transient `session` (mode/shell) and host-injected `runtime.dataSources` are excluded by construction.
- `deserializeState(serialized, dataSources, shellOverrides?)` → full partitioned `StudioState`: rebuilds `doc` from the serialized fields (defaulting the empties-omitted fields to `[]`), reconstructs `session` (`mode: 'edit'`, `shell` from `createDefaultStudioState()` merged with any `shellOverrides`), and injects the host's live `dataSources` as `runtime`. Also runs `normalizeGridColumn` over any grid widget's `config.columns` for forward-compatible column-shape normalization.
- `migrateState(raw)` reads `raw.schemaVersion` (defaulting to `0` for pre-versioned payloads), refuses to "migrate" from a _newer_ version than the running code supports, and otherwise applies the `migrations` registry (keyed by the **old** version number) sequentially, one version at a time, collecting per-step errors into a `MigrationResult`.
- **Migration policy** (documented at length in the source, restated because it is easy to violate by accident): never add a `fooV2`-shaped parallel field when a type's shape needs to change. Keep exactly one clean field name in the TypeScript interfaces, bump `CURRENT_SCHEMA_VERSION`, and add a migration function keyed by the previous version that rewrites old persisted shapes into the new one — the running code only ever reads the new shape. Add a fixture-based test in `statePersistence.test.ts` for each migration.
- `StudioController.serializeSession()`/`restoreSession()` go one level further, capturing the present doc _and_ the undo/redo stacks (`SerializedStudioSession` — a `present` snapshot plus `past`/`future` arrays) so a page reload can resume with full undo history, not just the current dashboard. Each `SerializedStudioSnapshot` pairs a `SerializedStudioState` with a `mode`; because `mode` lives in the non-undoable `session` partition, every snapshot in a saved session carries the SAME mode (the session mode at save time), and `restoreSession` reads mode from the `present` entry only — the per-snapshot `mode` field is retained purely for on-disk backward compatibility. The stacks rehydrate as `StudioDoc[]` (migrate → deserialize → `.doc` per snapshot), and restoring drops any individual history entry that fails to migrate rather than aborting the whole restore.

## AI integration

`x-studio` is UI-only — no LLM calls happen inside this package. `StudioAIConfig.endpoint` points at an `@mui/x-studio-ai-middleware` HTTP handler (see `examples/x-studio-dev-server`), which owns the API key, system prompt construction, and server-side tool execution.

- `src/components/StudioChatPanel/StudioChatPanel.tsx` (orchestrator) — the chat UI, built on `@mui/x-chat`'s `ChatBox`/`ChatMessage`/`useChat`/`useChatComposer` headless primitives, composing roughly 18 decomposed files: `useChatThreads.ts` (thread list state, switching, and a `StreamThreadPin` that pins an in-flight stream's writes to the thread it started on, so switching threads mid-response can't write the response into the newly-active thread — every one of its `doc.ai` thread write-backs, including the one that fires on each streamed token delta, calls `controller.setState(next, { undoable: false })`; a `{ undoable: true }` write here would push a fresh undo snapshot per delta — hundreds per response — flooding and evicting the user's real document-edit undo history, even though chat-thread state lives in the persisted `doc` partition). Switching threads mid-stream aborts the previous thread's in-flight fetch first — a `stopStreamRef` mirrors `useChat`'s `stopStreaming` out of the pinned-write component, and `handleNewThread`/`handleSelectThread` call it before resyncing `ChatBox`'s controlled `messages` prop to the newly-selected thread — so the partial response already written to the previous thread is cleanly terminated and preserved rather than silently truncated as further tokens arrive for a message id that no longer exists in the active thread. `chatIds.ts` (collision-resistant message/thread id generation), `chatToolRenderers.tsx` (per-tool inline tool-call card rendering), `chatSuggestions.ts`/`chatPanelUtils.ts` (suggested-prompt and misc chat helpers), `StudioSendButton.tsx`, `StudioMessageActions.tsx` (whose retry action regenerates the assistant reply in place via `useChat`'s `regenerate(messageId)`, replacing the failed answer rather than appending a duplicate user turn), `StudioMessageRoot.tsx`, `StudioReasoningPart.tsx`, `StudioComposerToolbar.tsx`, and `useChatVoiceInput.ts` (voice-input wiring). `STUDIO_TOOL_ICONS` maps each AI tool name (`add_widget`, `update_widget`, `set_widget_layout`, `add_page_filter`, `summarise_page`, …) to an icon for the inline tool-call cards; `STUDIO_TOOL_LABEL_KEYS` maps the same tool names to a `StudioLocaleText` key (not a hardcoded English string) so the card title renders through `useStudioLocaleText()` and localizes like every other UI string. Streaming a tool call emits a `tool-input-delta` chunk (input as text, for the composer's live-typing effect) followed by a `tool-input-available` chunk carrying the already-parsed input object — the delta alone never populates `toolInvocation.input` in `@mui/x-chat`'s stream processor, so without the second chunk the tool card would render a name/status but never its arguments.
- `studioBackendAdapter.ts`'s `createBackendChatAdapter` is the transport: it serializes skills (stripping non-JSON `execute` functions before sending), POSTs a `StudioAIRequest` to `${endpoint}/chat`, parses the `StudioAISSEEvent` SSE stream (`sseUtils.ts`), feeds text deltas into the chat UI, and applies `state-mutation` events to the local controller. `StudioAIConfig.privateMode` gates client-side, not just server-side: `pageSnapshot` (the sampled-row/numeric-stats summary), `dashboardState`, and `richContext` are all built inside one `if (!privateMode)` block — when private mode is on, none of the three is computed or sent, so the guarantee that no real row values or dashboard structure leave the client does not rest solely on the middleware honoring the flag. A `streamSettled` boolean guard plus `closeStream()`/`errorStream()` helpers ensure the stream's promise/controller settles exactly once no matter which event ends it, including a `finally`-block fallback close for a connection that ends without ever emitting a `finish` or `error` event (so the stream never hangs waiting for an event that never arrives). Because the panel supports switching threads mid-response (`StreamThreadPin`), several `sendMessage` streams can be live at once; the adapter tracks their readers in a per-adapter `Set` (`activeReaders`) rather than a single shared reference, so `stop()` cancels every live reader and one stream's cleanup can't null out another stream's reader.
- `applyStateMutation.ts` is the SSE `state-mutation` trust boundary: the incoming event is untrusted wire data (it was `JSON.parse`'d), so it is first run through `@mui/x-studio-schema`'s `parseStateMutation` validator; a malformed payload is logged and dropped (never applied, never thrown, so one bad event can't kill the stream), and only a validated mutation reaches `controller.applyExternalMutation(mutation)`. That call runs the mutation through the shared `applyMutation` reducer — the same reducer the AI middleware runs server-side, so a mutation like `addWidget` always lands on the server-chosen page regardless of what page happens to be active locally. This is the only caller in the package that passes wire-sourced data to `applyExternalMutation`; the controller's other callers construct their mutations locally and stay on the typed, non-validating path.
- `richContext.ts` builds `StudioAIRichContext` — purely-additive, client-derived signal (field statistics, recent mutations, current selection) attached to every chat request so the model has more to work with without the user typing extra detail.
- `createWidgetFromDescription.ts` calls the middleware's `/widget` endpoint ("describe a widget in English" widget creation). Its outgoing request payload honors `privateMode` independently of `studioBackendAdapter.ts`'s chat path — it is a separate request builder, so it needs its own gate: each source's `aiDescription` and field-level `aiDescription` are omitted when `config.privateMode === true`, and the `cardinality` string (built from `fieldDistinctValues` — actual distinct data values for low-cardinality fields) is not computed at all under private mode, with `privateMode` itself forwarded in the POST body so the server can also refuse to use row values. The response is untrusted wire JSON, so its `config` is run through `sanitizeServerWidgetConfig` — dropping keys invalid for the target widget kind — before the widget is committed, mirroring the validation the SSE `state-mutation` path gets from `parseStateMutation`. Despite its name, `generateInsight.ts` no longer calls an `/insight` (or `/title`) endpoint — both were removed, and insight generation now happens entirely server-side. The client-side module's only remaining job is building `buildWidgetDataSummary` (a compact, pipeline-filtered CSV-style sample + numeric-stats block for a widget) and `numericStats`, consumed by `studioBackendAdapter`'s chat requests and by `useTextWidgetAI` for text-widget generation — `StudioAIConfig.endpoint`'s only appended paths are `/chat` (streaming chat), `/approval` (tool-call approval responses), and `/widget`. `numericStats`'s min/max reduce with a loop rather than `Math.min(...values)`/`Math.max(...values)`, since the spread form throws past roughly 65k–125k elements and this runs synchronously inside every `sendMessage`'s pageSnapshot build — the same overflow hazard `aggregateNumbers` (`internals/aggregate.ts`) avoids for the same reason; its numeric-field check accepts only `field?.type === 'number'` (matching `StudioDataField['type']`'s actual member set — an `'integer'` branch would be dead code, since that string is never a valid field type). `buildWidgetDataSummary`'s aggregation calls resolve the widget's actual per-series `yAggregation`/`yAggregationByField` (mirroring `useChartWidgetData.ts`'s live-chart resolution) and apply any active rank/Top-N filter before summarizing, so the data description sent to the model matches what the chart actually renders rather than defaulting every summary to a sum over all categories. Its cross-source chart summary's own `resolveChartRowsForAggregation` call mirrors `useChartWidgetData.ts`'s call shape exactly, not an independently-drifting copy: it passes the same resolved `widgetFilters` (so an anchor-scoped filter is re-applied instead of resurrecting excluded anchor rows into the narrated numbers) and the same per-chart-type `extraFields` list (so a cross-source heatmap/funnel/sankey dimension resolves to a real value in the summary instead of `undefined`), and its widget-scoped rank-filter lookup carries the same `!f.disabled` guard `useChartWidgetData.ts`'s `widgetRankFilter` does, so a disabled Top-N filter no longer keeps truncating the AI-facing summary after the user disabled it on the rendered chart (finding 2.1). `generateInsight.ts`'s own `toPipelineState(state)` — the flat `StudioPipelineState` it hands to `createStudioPipeline` for the snapshot's L3 rows — forwards `state.doc.dashboard.globalCrossFilterMode` and `crossFilterAllPages` alongside `dataSources`/`relationships`/`expressionFields`/`filters`, matching `widgetExport.ts`'s (correct) use of the full `StudioState`; dropping either setting made the snapshot's L3 rows resolve cross-filters as if both were unset while `buildChartWidgetSummary`'s own L4 `widgetFilters` read them directly off `state.doc.dashboard`, so the two layers of the same AI-facing summary could disagree on which cross-filters were in scope. The raw-row (grid/pivot/chart-fallback) sampling path checks a candidate field's "exists in the data" membership against rows run through `enrichWithCrossSourceColumns` (the same enrichment `useWidgetRows` applies for on-screen cross-source grid columns), not the pipeline's raw pre-L2 rows — checking membership against raw rows silently excluded both an own-source expression/calculated column (which only exists after L2 enrichment) and any cross-source grid column (never enriched on this path at all) from the sample and the stats, so the model was never told about the very column a pivot/grid widget aggregates. `buildMapWidgetSummary` mirrors the rendered map's own cross-source enrichment (joining a `mapCountrySourceId`/`mapValueSourceId` field that differs from the widget's own source, via `enrichWithCrossSourceFields`) and its region-spelling normalizer (`normalizeToAlpha2`/`normalizeToStateAbbr`, chosen the same way `StudioMapWidget` chooses it) before aggregating — without both, the summary reported `'US'`/`'USA'`/`'United States'` as three separate regions while the rendered map merges them into one. `buildNumericStats` (used by the KPI/chart/map summaries and the raw-row path alike) resolves its field metadata through a shared `sourceFieldsWithExpressions(source, expressionFields)` helper — the source's own physical fields plus its own-source expression fields — mirroring `widgetExport.ts`'s `ownExpressionFields` pattern, rather than `source.fields` alone; an expression field (a calculated column or a measure) used as a KPI/chart/map value field previously got no stats line at all, even though it's exactly the field being aggregated. `selectSampleRows`' `'anomaly'` sampling mode reserves index slots for the flagged anomaly rows FIRST (up to `maxRows`), then fills any remaining budget with a stride-based sample — reserving anomalies first is what makes the "guarantees anomaly rows are included" contract actually hold, since a stride sample alone already numbers close to `maxRows` and merging stride-first (then slicing to `maxRows`) could cut off anomalies that land late in the dataset.
- `useSpeechRecognition.ts` wraps the Web Speech API for voice input into the chat composer.
- `StudioAIToolName`/`StateMutation`/`SerializableSkill`/`StudioAIState`/`StudioAIChatThread` (all re-exported from `@mui/x-studio-schema`'s `aiTypes.ts`; `studioAITools.ts` in this package is a thin re-export shim for `StudioAIToolName`) are the client-visible subset of the AI protocol; the server-only pieces (`StudioAISkill.execute`, `SkillExecuteResult`, `StudioAIDataConfig`, rate-limiting/usage types) live exclusively in `@mui/x-studio-ai-middleware`.

## Compose drawer & setup panels

`src/components/StudioComposeDrawer/` is the "add/edit widget" authoring drawer. `StudioComposeDrawer.tsx` shells the drawer; `AddWidgetView.tsx`/`WidgetTypeCard.tsx`/`WidgetInstanceList.tsx` are the kind picker; `DescribeWidgetSection.tsx` is the natural-language widget creator. Each widget kind has a setup panel registered on its `StudioWidgetDef` (`ChartSetupPanel`, `GridSetupPanel`, `KpiSetupPanel`, `MapSetupPanel`, `PivotSetupPanel`, `TextSetupPanel`, `FilterSetupPanel`), plus shared editors `FormatPanel`/`TextFormatPanel`/`GridConditionalFormatSection` and field-picker widgets (`DataSourceFieldSelect`, `FieldDetailView`, `InlineFormulaBar`).

- **Field catalog helpers** (`src/internals/fieldCatalog.ts`) — `buildFieldCatalog(dataSources, expressionFields, options?)` folds every source's physical + non-hidden expression fields into a flat `FieldCatalogEntry[]` (each entry a `StudioDataField` annotated with `sourceId`/`sourceLabel`), and `buildSourceFieldEntries(source, expressionFields, options?)` does the same for a single source. Both take an `expression` policy (`'all'`/`'non-measure'`/`'none'` — Grid's column list excludes measures; Chart/KPI value pickers include them) and are the shared fold behind the Chart/KPI/Grid/Filters field pickers. `buildFieldLabelMap` builds a flat `fieldId → label` map for labelling existing filter chips (first-writer-wins on duplicate ids across sources — a documented limitation).
- `ChartSetupPanel/` follows the same orchestrator-plus-per-type-section pattern as `StudioChartWidget/`: `ChartSetupPanel.tsx` composes the shared field pickers plus chart-type-specific section components (`GaugeConfigSection.tsx`, `ScatterConfigSection.tsx`, `FunnelConfigSection.tsx`, `HeatmapAxesSection.tsx`, `SankeyConfigSection.tsx`, `GanttFieldsSection.tsx`, `AnnotationsEditorSection.tsx`, `PieArcLabelsSection.tsx`), each reading only its own chart family's config keys so an unrelated key survives a type switch untouched. Its `analyzeChartSupport` support-check memo mirrors `useChartWidgetData.ts`'s call shape exactly, not just x/y/series: it also threads `config.scatterColorField`/`config.scatterSizeField` and a `chartTypeExtraFields` memo (the same per-chart-type dimension list described in the Data pipeline section above — `heatYField`/`funnelReachedField`/`sankeyTargetField`/the `gantt*` fields). Without these the panel validated a narrower field set than the canvas renderer did, so picking an unresolvable cross-source scatter color/size field or extra dimension (e.g. a `heatYField`) showed no warning and didn't disable the option here, while the rendered widget fell back to the "unsupported chart configuration" overlay — the authoring surface said valid, the canvas said invalid.
- **Shared cross-filter mode section** (`CrossFilterModeSection.tsx`) — the "Interactions" cross-filter-mode toggle rendered by the Chart, Grid, KPI, and Map setup panels. It takes the panel-specific `modes` list (Chart/Grid/Map offer all three `['cross-highlight', 'cross-filter', 'none']`; KPI offers only `['cross-filter', 'none']`, since a summary metric has no per-row visual to highlight) and a `defaultMode`, and normalizes a legacy-persisted `'cross-highlight'` value to display as `'cross-filter'` selected on panels that don't offer "Highlight" — a display-only normalization that does not rewrite the stored config.
- `MapSetupPanel.tsx` — geography picker (built-in + consumer-registered via `useStudioGeographies`), country/value field pickers, and the shared cross-filter section; clearing the value field also resets `mapAggregation` back to `count`, so the renderer stops applying a stale avg/min/max to synthetic per-row 1s while the panel's locked label claims "Count" (mirrors `KpiSetupPanel`'s equivalent reset). `PivotSetupPanel.tsx` — row/column/value field pickers built on `buildSourceFieldEntries`.
- **Source-switch undo folding**: every setup panel's source-change handler (`GridSetupPanel`, `KpiSetupPanel`, …) early-returns when the newly-picked source id equals the widget's current `sourceId`, so re-selecting the already-active source in the picker (a no-op MUI `Autocomplete` `onChange` still fires when the picker's freshly-mapped option/value objects differ by reference even though the selected id didn't change) is a true no-op instead of wiping every field-bound column/sort/conditional-format setting via an unwanted `clearFieldBoundGridConfig` commit. A gesture that both adopts a genuinely new source and writes a field/config value (picking a chart's X field with no source yet set, picking a cross-source filter field, switching a KPI's data source, a gauge's cross-source value-field pick) commits as ONE `updateWidget` call — `sourceId` and the field/config change folded into a single `changes` payload — rather than a separate `updateWidget` (source) followed by `updateWidgetConfig` (field). `MapSetupPanel`, `ChartSetupPanel` (including its `GaugeConfigSection`), `KpiSetupPanel`, and `FilterSetupPanel` all follow this pattern, so a single Ctrl+Z reverts the whole gesture (no source, no field, together) instead of landing on a torn intermediate state (new source, stale field) the UI never actually produced. `updateWidget` also accepts an optional `{ removeFilterIds }`, which folds a batch of `removeFilter` mutations into the SAME `commitMutations` step as the source/config change: `ChartSetupPanel`, `GridSetupPanel`, and `KpiSetupPanel` compute `collectStaleWidgetFilterIds(allFilters, widgetId, nextSourceId, fieldCatalog, relationships)` — the widget-scoped filters whose field no longer resolves against the new source — and pass their ids here, so a source switch that would otherwise strand a widget-scoped filter (which then silently excludes every row, since its field is absent from the new source) removes that filter as part of the same undo step instead of leaving the widget blank with no filter feedback to explain why.
- **Buffer-then-commit-on-blur for numeric/free-text inputs**: `GaugeConfigSection`, `GridConditionalFormatSection` (both its numeric and string-value conditional-format inputs), `ExpressionNodeEditor`, `KpiSparklineOptions`, `AnnotationsEditorSection` (label field), `FilterSetupPanel` (slider min/max/step), `ScatterConfigSection` (point radii), `PieArcLabelsSection` (min-angle), `FunnelConfigSection` (gap), `ColorInput`/`ColorSwatch` (hex text field and the native color-picker drag), `StudioWidgetEditDialog/FilterRow`'s value/between-bound inputs, and `StudioFiltersDrawer/FilterValueInput`'s numeric `between` bounds (via a dedicated `BufferedBoundInput`, matching the edit dialog's equivalent) each buffer their numeric/text inputs in local component state and validate/commit to the controller on blur (or Enter, or on a discrete selection change) rather than on every keystroke or drag frame. Committing per-keystroke through `updateWidgetConfig`/`updateFilter` on a field that requires validation/coercion (e.g. a numeric bound) could otherwise re-render the input with a coerced/reformatted value mid-type, effectively dropping the keystroke the user just made — and, for a color picker, dragging around the OS color wheel fires `onChange` continuously, which would otherwise push dozens of undo entries for one gesture.
- **Self-correcting effects commit non-undoably**: `KpiSetupPanel`'s effect that repairs an invalid stored `kpiAggregation` (e.g. left over from a prior source/field switch) commits via `controller.updateWidgetConfig(widgetId, { kpiAggregation }, { undoable: false })`, the same `{ undoable: false }` pattern `StudioDateRangeBar`'s coverage-expansion effect uses (see State management). `WidgetFilterRow` follows the identical pattern for a stored filter operator that's invalid for the filter's current field type (e.g. left over from a field switch, or authored by a host/AI call that bypassed `filterOperatorMetadata`'s UI-only allowlist): the row's displayed `activeOperator` already falls back to `operators[0]` for display, and a `{ undoable: false }` effect writes that same fallback back into `doc.filters` so the engine's applied operator matches what the row shows. A plain undoable commit fired from merely rendering the panel/row would push an unauthored undo entry every time it mounts, and undoing past it would re-commit the repair and clear the redo stack — trapping the undo stack at that point for as long as the panel/row stays open.

## Internationalization

`src/internals/localeText.ts` defines `StudioLocaleText` — an interface of every translatable string token used by the UI (drawer titles, date-range preset labels, filter-drawer strings, widget empty/error states, quick-filter-bar strings, widget-card action tooltips, chart labels, and more) — plus `DEFAULT_STUDIO_LOCALE_TEXT`, the English defaults. Both are re-exported from `internals/StudioUIConfigContext.ts` (a compatibility façade) so existing deep imports of these symbols resolve unchanged. `StudioProvider`/`Studio`'s `localeText` prop is merged shallowly over the defaults, so a consumer can override a handful of tokens without supplying the whole set.

`src/internals/StudioUIConfigContext.ts` itself owns the React context/provider/hooks for Studio's UI config (`tableSourceMode`, `featureFlags`, `localeText`, `aiConfig`, `customWidgets`, `geographies`, `onOpenFilterPanel`), plus the flat `ResolvedStudioFeatures` shape and the `resolveSubFlag` logic that unwinds nested `StudioFeatureFlags` sub-objects into top-level booleans. It re-exports the widget-registry types (`StudioWidgetRenderProps`/`StudioWidgetCapabilities`/`StudioWidgetDef`) from `./widgetRegistry` for the same compatibility reason.

`src/locales/` ships ready-made bundles: `enUS.ts` (canonical source) exports only the MUI-`xxLocale`-shaped `Localization` object (`enUS`) — the raw English text object is `DEFAULT_STUDIO_LOCALE_TEXT`, defined in `internals/localeText.ts` and re-exported from the package's main `index.ts` (not from `enUS.ts` itself). `fr.ts`, `de.ts`, `es.ts`, `ptBR.ts` each export both a raw `xxLocaleText` object and a `Localization` object (`getStudioLocalization` in `locales/utils/getStudioLocalization.ts` builds the latter from the former, matching the `components.MuiStudio.defaultProps.localeText` shape other MUI X packages use for theme-level localization). `locales/index.ts` re-exports everything; `locales.test.ts` asserts every locale bundle has the same key set as `enUS` (no missing/extra tokens).

`useStudioLocaleText()` is the hook widgets/drawers call to read the merged locale object; `useStudioFeatures()`/`useStudioUIConfig()`/`useStudioGeographies()`/`useCustomWidgetMap()` (same file, `StudioUIConfigContext.ts`) resolve the other pieces of `StudioUIConfigContext` — runtime feature flags (`ResolvedStudioFeatures`, all defaulting `true`), the full UI config object, the merged built-in + consumer-registered map geography registry, and the merged custom-widget map, respectively.

## Public API surface

- **Root components**: `Studio` (full authoring UI, imperative `StudioHandle` ref), `StudioDashboard` (embed-first, view-oriented wrapper over `Studio` that takes a pre-built `config: StudioState` + `dataAdapters` map, for displaying a live dashboard without exposing the authoring UI). On a `config` reference change, `StudioDashboard` calls `StudioHandle.loadSerializedState(config.doc)` (the persisted doc shape, run through `migrateState`/`validateStateStructure` — not a re-serialized string), logs any migration errors, and then: calls `StudioHandle.upsertDataSource()` once per entry in `config.runtime.dataSources` (`loadSerializedState` otherwise preserves whatever data sources the previous controller instance had, so the explicit re-application is what makes a `config` swap pick up the new data sources); removes any runtime source the new config dropped (`loadSerializedState` preserves the _entire_ previous `runtime.dataSources`, so a pruned source would otherwise survive forever); and re-applies the current `dataAdapters` map via `setDataSourceAdapter` for every entry. ### Server adapters (`src/server/`)

`StudioDataSourceAdapter` is the contract for wiring a data source to a remote backend instead of in-memory rows: `getRows(descriptor: StudioQueryDescriptor): Promise<StudioQueryResult>` (and an optional `submitMutation`). Two ready-made implementations:

- `createSimpleAdapter(url, options?)` — one HTTP request per `getRows` call.
- `createBatchingAdapter(url, options?)` — a DataLoader-style client-side batcher: because each widget has its own `cacheKey` (it includes `widgetId`), N widgets on a page would otherwise fire N independent requests that miss any server-side batching window. This collects all descriptors requested within a scheduling window (microtask tick by default) and POSTs them as one batch request, routing responses back to each widget by an `id` field. One loader instance is shared per endpoint URL, not per data source. It also supports automatic cross-source JOIN generation when given `dataSources`/`relationships`, mirroring `@mui/x-studio-data-middleware`'s server-side join handling.

The two adapters differ deliberately in how much they rewrite the descriptor before sending. `createBatchingAdapter` translates `StudioFilterNode`s into the middleware's `FilterPredicate`/`AggregationSpec` wire shapes (the two-way server/client partition described below) and resolves relative-date values. `createSimpleAdapter` targets a simpler host that speaks the native `StudioQueryDescriptor` directly, so it POSTs the descriptor essentially as-is — it does **not** translate to the wire `FilterPredicate` shape — but it still resolves relative-date values (`isRelativeDateValue`/`resolveRelativeDate`, `internals/filterUtils.ts`) before sending, since a relative spec (`{ relative: true, amount, unit, direction }`) is a client-only concept a remote host cannot interpret.

`createBatchingAdapter.ts`'s filter translation is a deliberate two-way split, not a best-effort one: `partitionFilterNode` walks a filter tree and, per leaf, calls `isLeafServerTranslatable` to decide whether it can be expressed as a wire `FilterPredicate` with EXACTLY the in-memory evaluator's semantics — a leaf combining its two conditions with `conjunction: 'or'` fails the check, as does one using any of the operators with no wire equivalent (`not_in`, `does_not_contain`, `starts_with`/`not_starts_with`, `ends_with`/`not_ends_with`, `is_empty`/`is_not_empty` — the last two have no `IS NULL` wire form) or one of the three substring operators (`contains`, `starts_with`, `ends_with`) that DO have an approximate `LIKE` equivalent but are kept client-side anyway because the server's `LIKE` is case-sensitive while Studio's evaluator is case-insensitive (pushing `contains` down used to map it to an unwrapped, case-sensitive `whereLike` with no `%` wildcards at all — a near-exact-match bug, not just a case mismatch). Two value-shaped cases also fail translatability regardless of operator: an empty `in: []` array (matches nothing in-memory, but the middleware drops an empty-`in` predicate on reads — matching everything, the exact inversion) and an open-ended `between` with only one bound set (unbounded in-memory, but a two-arg `whereBetween(col, [value, undefined])` on the wire — a binding error on Postgres, a silent wrong result on SQLite/MySQL). A translatable leaf (or an AND-group of them) is sent to the server; everything else — including any `logic: 'or'` group — is instead routed to `clientLeaves` and re-applied locally via `applyFilters` after the response comes back, with a dev-mode warning so an unmappable predicate degrades to client-side enforcement rather than being silently dropped or silently turned into AND. Two operators that DO stay server-side despite a subtler semantic difference are called out with their own one-time `warnAdapterDivergence` warning rather than silently diverging: `not_equals` (SQL three-valued logic excludes NULL rows; the in-memory evaluator keeps them) and `equals`/inequalities on a `date`/`datetime` field (the server compares the raw column to a bare date string while in-memory normalizes both sides, so an equality can match zero rows server-side against a DATETIME column that matches that whole day in-memory) — pushing them down is kept because routing a common, high-selectivity predicate like `not_equals` or a date bound client-side would defeat the query pushdown (and drop the filter entirely for an already-aggregated widget). A filter on an arithmetic `FunctionExpression` field (e.g. `margin = price - cost`) has no server-side column to filter on at all — `resolve()` reports `{ skip: true }` for it — and rather than dropping it from the request with no trace, the adapter calls `warnAdapterDivergence` describing which computed field and source it came from, honoring the module's "degrades to client-side, never silently dropped" contract with an explicit warning (the predicate is still not folded into the client-side residual filter list the OR-group/unmappable-operator leaves use, since raw inputs are already selected and the field gets client-side re-enrichment regardless). `count_distinct` has no distinct-count wire aggregation either, so it is still translated to a plain `count` — but `mapAggFn` calls a `warnAdapterDivergence` helper once per query build so the downgrade is visible instead of silent. A `count` aggregation itself is never pushed to the server at all: the wire protocol's `count` becomes SQL `COUNT(column)` (skips NULL measures), while Studio's `'count'` means row-count (`COUNT(*)`) semantics everywhere else in the package (see the aggregate-policy paragraph above) — so a `count`-aggregated widget instead fetches raw rows (aggregations stripped, `warnAdapterDivergence`-warned) and aggregates client-side, keeping the adapter path consistent with every in-memory widget kind. The ORDER BY clause is dropped whenever the sort field is either `skip` (a server-incompatible expression) OR `unresolved` (resolvable to no column in this source, e.g. a groupBy field 2+ hops away in the relationship graph) — checking only `skip` used to let an unresolved sort field emit `ORDER BY <nonexistent column>` and fail the whole batch entry, even though dropping just the ORDER BY would have produced usable rows. Within one batching window, each request/response pair is matched by a composite `${widgetId}::${cacheKey}` id (falling back to the bare `widgetId` only when it's unambiguous) rather than by `widgetId` alone, so two `getRows` calls for the same widget with different descriptors inside the same window can no longer have their rows cross-wired and cached under the wrong cache key. In simple (non-relationship-aware) mode, the shared per-endpoint loader reads its `fetchFn`/`batchDelayMs` from a live, refreshable config object rather than baking them into the loader's closure at creation time, so recreating an adapter at an already-registered endpoint (e.g. after an auth-token rotation) updates the shared loader instead of permanently pinning the first adapter instance's (now-stale) `fetchFn`.

## Extension points

- **New built-in widget kind**: add the kind string to `StudioWidgetKind` (`@mui/x-studio-schema`'s `baseTypes.ts` / `widgetTypes.ts`), create `components/widgets/Studio<Kind>Widget/`, add an entry to `BUILTIN_WIDGET_DEFAULTS` in `createDefaultWidget` (`@mui/x-studio-schema`'s `factories.ts`) — a missing entry fails to compile — and add an entry to `BUILTIN_WIDGET_DEFS` (`internals/builtinWidgetDefs.ts`) — the `satisfies Record<BuiltinStudioWidgetKind, StudioWidgetDef>` clause makes a missed registration a compile error.
- **New chart type**: add the schema-side plumbing described in `@mui/x-studio-schema`'s `ARCHITECTURE.md` (new `StudioChartType` literal, family interface, `StudioChartConfigByType`/`CHART_TYPE_CONFIG_KEYS` entries — all fail-closed at compile time there), then add a `render*` function and a `CHART_TYPE_DEFS` entry in `StudioChartWidget/chartTypeDefs.tsx`, and a `chartTypeRegistry` entry in `internals/chartTypeRegistry.ts` — both `satisfies Record<StudioChartType, …>` clauses make a missed entry a compile error the same way `BUILTIN_WIDGET_DEFS` does for widget kinds.
- **Custom widget kind** (app-level, no fork required): register a `StudioCustomWidgetDef` via `Studio`'s `customWidgets` prop; folded into the same registry `useWidgetDefMap()` returns, so it is rendered/dispatched identically to a built-in kind.
- **New data source backend**: implement `StudioDataSourceAdapter` directly, or use `createSimpleAdapter`/`createBatchingAdapter` against an existing endpoint (the latter also supports automatic cross-source JOIN generation when given `dataSources`/`relationships`).
- **New expression operator**: add a case to `evaluateFunctionExpression` (`utils/expressionEvaluator.ts`) — its `switch`'s exhaustiveness check (`const exhaustiveCheck: never = operator`) forces every call site to be updated.
- **New AI mutation type**: add the variant to `StateMutation` (`@mui/x-studio-schema`'s `aiTypes.ts`) and an entry to `applyMutation.ts`'s `MUTATION_HANDLERS` dispatch table (co-locating the `apply` state-transition and `label` string) — the table's mapped type requires one entry per `StateMutation` variant, so a missed entry fails to compile in both the client and the AI middleware server that share the file.
- **New locale**: add a language file under `locales/` following the `Localization`/`getStudioLocalization` shape used by `enUS.ts`, matching the full `StudioLocaleText` interface in `internals/localeText.ts`; `locales.test.ts` will fail if any token is missing.
- **A `StudioState` shape change that breaks deserialization of persisted dashboards**: bump `CURRENT_SCHEMA_VERSION` (`@mui/x-studio-schema`'s `statePersistence.ts`), add a migration keyed by the previous version, add a `statePersistence.test.ts` fixture (in the schema package) — see Persistence above. Only `doc`-partition shape changes ever need a migration; `session`/`runtime` are reconstructed on load, never persisted.
