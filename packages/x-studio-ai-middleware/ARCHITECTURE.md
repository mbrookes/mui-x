# Architecture

Internal reference for how `@mui/x-studio-ai-middleware` is put together. For install/quick-start, see [`README.md`](./README.md).

## Overview

This package is a framework-agnostic, pure-function server-side handler for the MUI X Studio AI assistant. It has no HTTP framework dependency and no LLM vendor SDK — every model call goes through raw `fetch` against an **OpenAI-compatible chat-completions endpoint** (`stream: true`, tool calling via `tools`/`tool_choice`), so any provider reachable through an OpenAI-compatible gateway/proxy works, including non-OpenAI models fronted by one.

Two independent surfaces share the same core tool logic:

- **Chat (SSE)**: `handleAIChat` → `runAgenticLoop` — a streaming, multi-turn agentic loop driven by the LLM.
- **MCP**: `buildStudioMcpServer` — exposes the same tools/state directly to any MCP client (e.g. an IDE agent), independent of the chat loop.

Both dispatch every state-mutating tool call through the same two-layer core: `executeToolOnState` (which computes the state transformation) wrapped by `toolPolicy.ts`'s authorization chokepoint. `executeToolOnState` delegates the actual state transformation to `applyMutation` — a pure reducer shared with the client via `@mui/x-studio-schema`. That reducer is the single source of truth for what a tool call does to `StudioState`; both transports (and the browser client) compute identical results from identical inputs.

Runtime dependency: `@mui/x-studio-schema` (workspace package — the shared, zero-dependency data model and mutation reducer). Dev-only dependencies: `@mui/x-chat-headless` (only for the `ChatMessage` type) and `@modelcontextprotocol/sdk` (only `buildStudioMcpServer` and its `mcp/` handlers use it functionally). Note, however, that importing the package root loads the SDK unconditionally: `src/index.ts` statically re-exports from `./mcp`, which value-imports `@modelcontextprotocol/sdk`, so even a chat-only consumer that never calls `buildStudioMcpServer` pulls the SDK in at import time. Making the SDK load lazily would require a lazy-import / subpath-export change that is intentionally not made.

## Public API surface (`src/index.ts`)

- Chat handler: `handleAIChat` (+ `StudioAIHandlerOptions`, `StudioAIContextEnricher(Args)`)
- Non-streaming handlers: `handleGenerateTitle`, `handleCreateWidget` (from `handleGenerateInsight.ts`)
- Protocol types: `StudioAIRequest`, `StudioAISSEEvent`, `StudioAISkill`, `SkillExecuteResult`, `SerializableSkill`, `StateMutation`, `MutationEnvelope`, `StudioAIToolName`, `StudioAIDataConfig`, rate-limit/usage/rich-context types
- Prompt/tools: `buildAISystemPrompt`, `serializeFieldForAI`, `sanitizeForPrompt`, `buildPageLayoutContext`, `STUDIO_AI_TOOLS`, `WIDGET_CONFIG_DESCRIPTION`
- Built-in skills: `dashboardNarratorSkill`, `insightSuggestorSkill` — the only two skills defined in `studioSkills.ts`; both are `instruction-only` (no callable tool)
- `generateFieldDescriptions`, `renderChartSvg`, `createDefaultWidget`
- Lower-level primitives for custom loops: `runAgenticLoop`, `executeToolOnState`
- Tool policy chokepoint: `computeToolEffects`, `createDefaultToolPolicy`, `createEffectsAwareToolPolicy`, `executeToolWithPolicy` (+ `ToolPolicy`, `ToolPolicyContext`, `ToolPolicyDecision`, `ToolEffectSummary`, `ExecuteToolWithPolicyResult`)
- MCP: `buildStudioMcpServer` + associated types, `createDefaultStudioState`

## Shared schema dependency: `@mui/x-studio-schema`

`@mui/x-studio-schema` (`packages/x-studio-schema`) is a separate workspace package with **zero runtime dependencies** — no React, no Node built-ins — importable from both a browser bundle (`@mui/x-studio`) and this server package. It is the single place the `StudioState` shape and its associated pure logic live, so the client and the AI middleware share one definition instead of maintaining independent copies.

`StudioState` (`stateTypes.ts`) is partitioned by lifetime into three top-level slices:

- **`doc`** (`StudioDoc`) — the user-authored dashboard document: `dashboard`, `pages`, `widgets`, `relationships`, `filters` (including session-flavoured cross-filter entries, which the reducer manipulates and which are stripped only at the persistence boundary), `expressionFields`, and optional `filterPresets`/`ai`. This is the ONLY partition that is persisted, undoable, and mutated by the shared reducer.
- **`session`** (`StudioSession`) — ephemeral UI state (`mode`, `shell`). Never persisted, never undoable, never touched by the reducer (a view↔edit switch is not a dashboard edit, so undo must never flip it).
- **`runtime`** (`StudioRuntime`) — host-injected `dataSources` (their rows are never persisted). Never undoable, never reducer-mutated (an undo must never revert live sources to stale rows).

### How this package consumes the partitions

Every structural field a tool reads or writes lives under `state.doc.*` (e.g. `state.doc.dashboard.activePageId`, `state.doc.widgets`, `state.doc.pages`, `state.doc.filters`, `state.doc.ai?.activeThreadId`), and data-source lookups go through `state.runtime.dataSources`. `applyMutation` reads and writes exclusively through `state.doc`; `session`/`runtime` pass through untouched.

- The **chat prompt builder** (`buildAISystemPrompt.ts`) reads all three: `state.doc` for pages/widgets/filters, `state.runtime.dataSources` for the data-source catalogue, and `state.session.mode` for the "Mode: view/edit" line.
- **`executeToolOnState`** reads/writes only `state.doc.*` and reads `state.runtime.dataSources`; it never writes `runtime` or `session`.
- **`get_dashboard_state`** returns `{ doc, dataSources }` where `dataSources` is `state.runtime.dataSources` projected down to AI-safe metadata (`rows`/`adapter` stripped, distinct values capped) — never raw rows, so the read cannot leak live data or defeat `privateMode`. `doc.ai` (the cross-thread AI chat history partition) is likewise reduced to per-thread metadata (`{ id, name, updatedAt, messageCount }`, no `messages`), since a thread's full transcript is not needed by the model beyond the active thread it already sees as its own message array.
- The **MCP box** (`StudioStateBox`) holds the FULL partitioned `StudioState`; handlers read `stateBox.current.doc.*` and `stateBox.current.runtime.dataSources[sourceId]`. The `studio://dashboard/state` resource does NOT emit the box verbatim: it calls the SAME `projectStateForAI(state)` helper (`executeToolOnState.ts`, a sibling of `projectDataSourceMetadata`) the `get_dashboard_state` tool calls, so the `{ doc, dataSources }` redaction contract — data sources stripped/capped, `doc.ai` reduced to thread metadata — lives in exactly one place and the two read surfaces cannot drift.

See `@mui/x-studio-schema`'s own `ARCHITECTURE.md` for the full partition design; the above is only this package's usage of it.

It exports:

- All `StudioState` data-model types: `baseTypes.ts`, `dataTypes.ts`, `widgetTypes.ts`, `expressionTypes.ts`, `stateTypes.ts`
- AI-protocol types (`aiTypes.ts`): `SerializableSkill`, `StateMutation`, `MutationEnvelope`, `createMutationEnvelope`, `StudioAIToolName`, `StudioAIRichContext` and its constituent types, and the persisted `StudioAIState`/`StudioAIChatThread` conversation types
- `createDefaultWidget`, `createWidgetId`, `createDefaultStudioState` (`factories.ts`) — shared so AI-created and UI-created widgets get identical defaults and the same collision-resistant id scheme. `createDefaultStudioState(overrides?)` seeds a fresh partitioned `StudioState`; its `overrides` are a nested bag keyed by partition (`{ doc?, session?, runtime? }`) so a field is never silently mis-routed to the wrong slice
- `STUDIO_AI_TOOL_REGISTRY`, `StudioAIToolFacts` (`aiToolRegistry.ts`) — the declarative registry of per-tool FACTS (display `title`, `destructive`/`mcpDestructiveOverride`, MCP `readOnly`/`idempotent`/`openWorld` hints, `privateModeExcluded`, `mcpSupported`) keyed by tool name. Not implementations or JSON-schema parameter definitions — only classification/availability facts. `StudioAIToolName` is the union of its keys. It is the single source both packages derive from, so `DESTRUCTIVE_TOOLS`, `MCP_UNSUPPORTED_TOOLS`, `PRIVATE_MODE_EXCLUDED_TOOLS`, `TOOL_TITLES`/`TOOL_ANNOTATIONS` can no longer disagree about one tool
- `detectAnomaliesIQR` (`anomalyDetection.ts`) — the Tukey-IQR outlier check used by `summarise_page`'s time-series anomaly detection, on both the client and the MCP `summarise_page` handler (`mcp/summarisePage.ts`)
- `truncateToPeriod`, `isoWeek` (`temporalUtils.ts`) — the date-bucketing helpers `summarise_page`'s time-series aggregation uses to group rows into day/week/month/etc. periods, imported directly by `mcp/summarisePage.ts` rather than mirrored locally
- `applyMutation`, `mutationLabel` (`applyMutation.ts`) — see below
- `getAllowedConfigKeys`/`validateConfigKeysForKind` and `getAllowedChartConfigKeys`/`validateChartConfigKeysForType` (`configKeyValidation.ts`) — write-side key allow-lists, one layer per union: per widget kind, and, one level finer, per chart type. `isWidgetOfKind`, `resolveChartType`/`isChartConfigOfType`/`isStudioChartType`/`STUDIO_CHART_TYPES` (`widgetTypeGuards.ts`) — the matching runtime narrowing/membership helpers for `StudioWidget` (by kind) and `StudioChartWidgetConfig` (by chart type). See `@mui/x-studio-schema`'s own `ARCHITECTURE.md` for the full design; see "Tool execution / state mutation model" below for how this package wires them into `executeToolOnState.ts` and `buildAISystemPrompt.ts`.

Server-only AI types (`StudioAISkill` with its `execute` function, `SkillExecuteResult`, `StudioAIDataConfig`, rate-limit/usage/enriched-context types, and the `query_data_source` data-query types) are **not** part of the shared schema — they live in this package's `models/aiTypes.ts`. `models/studioTypes.ts` and `widgetFactory.ts` are thin re-export shims over `@mui/x-studio-schema` so pre-existing internal import paths keep working without a repo-wide rename.

### `applyMutation` — the single mutation reducer

`applyMutation(state: StudioState, mutation: StateMutation): StudioState` (`packages/x-studio-schema/src/applyMutation.ts`) delegates to an internal `applyDocMutation(state.doc, mutation)` and reassembles `{ ...state, doc: nextDoc }` (returning the same `StudioState` reference untouched when the doc is unchanged, so a no-op mutation preserves reference identity; `session`/`runtime` always pass through). `applyDocMutation` dispatches through a `MUTATION_HANDLERS` table keyed by `mutation.type`, covering every `StateMutation` variant (`addPage`, `setDashboardTitle`, `addWidget`, `updateWidget`, `removeWidget`, `setWidgetLayout`, `setWidgetColSpan`, `renamePage`, `removePage`, `setActivePage`, `addFilter`, `removeFilter`, `applyBulkUpdate`, `renameAIThread`). Each entry co-locates its `apply` (a `StudioDoc → StudioDoc` transition) and `label` (human-readable log line) logic, so the two can never drift apart; the table's mapped type makes a variant missing a handler a compile error. At runtime, an unrecognized `mutation.type` is a graceful no-op rather than a throw.

Both transports use this same function for the state-transformation step:

- `executeToolOnState.ts` computes `nextState = applyMutation(state, mutation)` on the server, threading it across tool calls in the same turn and, for MCP, across the whole `StudioStateBox` session.
- The client applies the identical function inside `StudioController.applyExternalMutation` when a `state-mutation` SSE event arrives.

Notable semantics baked into the reducer:

- `removePage` performs full cleanup matching `StudioController.removePage`: it drops the page, removes every widget that lived on it, drops page-scoped filters that targeted it, and reassigns `doc.dashboard.activePageId` to another remaining page (or `''`) when the removed page was active.
- `removeWidget` drops the widget from every page's `widgetRows` (removing now-empty rows) and drops filters that only made sense while the widget existed (its own widget-scoped filters, and interactive cross-filters it emitted).
- `addWidget` takes an explicit, server-chosen target `pageId` in `mutation.args` (falling back to the applying side's active page only for legacy payloads without one) — this guarantees the widget lands on the same page the model was told about, even if the client navigates elsewhere while the model is "thinking".
- `addFilter` applies the filter verbatim, without re-stamping its scope to the applying side's active page — the filter already carries its target page/widget, chosen server-side.
- `setWidgetColSpan` clamps every span to the canvas grid (`clampSpan`, `GRID_COLS = 24`, `MIN_SPAN = 6`).
- Side effects a pure reducer cannot own — undo-stack management, title inference from live data sources, React shell selection — are intentionally **not** performed here; they stay in `StudioController` on the client.

`mutationLabel(mutation)` produces a compact human-readable label (e.g. `addWidget:chart:widget-123`, `removeFilter:filter-9`) used for the AI recent-mutation log surfaced in the system prompt's `<dashboard_context>` block and MCP's `get_recent_changes` tool. `createMutationEnvelope(mutation)` wraps a `StateMutation` into the `MutationEnvelope` shape that both transports spread into each `state-mutation` SSE event.

## Core data flow: chat request lifecycle

1. Host app parses the request body into a `StudioAIRequest` and calls `handleAIChat(body, options)`, getting back a `ReadableStream<string>` to pipe as `text/event-stream`.
2. `handleAIChat` computes the effective `allowedTools`/`privateMode`/skill set (server-side overrides — see invariant 10), creates an internal `AbortController` linked to any host-supplied `options.signal` **and** to the `ReadableStream`'s own `cancel()` callback, so a consumer calling `reader.cancel()` propagates into the agentic loop exactly like a host-triggered abort.
3. Inside the stream's `start`, `handleAIChat` best-effort runs `options.contextEnricher` (skipped if `privateMode`; failures are non-fatal, reported via `onToolError('contextEnricher', err)`), then calls `runAgenticLoop`.
4. `runAgenticLoop` drops any `server-tool` skill whose name collides with a built-in (so a built-in name resolves only to its built-in handler), builds the system prompt once (`buildAISystemPrompt`, folding in skills/richContext/enrichedContext), composes the effective `ToolPolicy` (`Policy.all(mutationBudget, hostPolicy)`), computes the effective tool list, and converts the `ChatMessage[]` history to OpenAI-style messages via `toOpenAIMessages` (`agenticLoop/openaiWire.ts`).
5. The effective tool list is `STUDIO_AI_TOOLS` filtered by `allowedTools`, gated by `data`/`pageSnapshot` presence and by `PRIVATE_MODE_EXCLUDED_TOOLS` under `privateMode`, plus any `server-tool`-mode skill schemas. Its name set is captured as `advertisedToolNames` for the dispatch-time gate.
6. For each turn (max 10 by default, or `rateLimit.maxTurnsPerRequest`): POST to `options.endpoint` with `stream: true, stream_options: { include_usage: true }`; consume the response via `parseSSE`; yield `text-delta` events as they arrive; accumulate tool-call fragments via `accumulateToolCallDeltas` keyed by index (falling back to a per-`id` synthetic index — seeded from `SYNTHETIC_INDEX_BASE` so it can never collide with a real `index: 0` — when a provider's deltas carry an `id` but never an `index`).
7. **No tool calls** → yield `message-metadata`, `usage`, `finish`, generator returns (conversation done). **Tool calls present** → the loop parses each call's `arguments` buffer and hands it (with an `argsParseFailed` flag) to `dispatchToolCall` (`agenticLoop/toolDispatch.ts`), an async generator that owns the full per-call dispatch decision and forwards its side-effect events (`state-mutation`, `tool-approval-request`) up to the loop; the loop performs the single `tool-activity` (`start`→`complete`) + tool-result pairing for every path. See "Agentic loop internals" and "Tool policy chokepoint" for the dispatch and gating detail.
8. Token budget exceeded (`usage.inputTokens + usage.outputTokens >= rateLimit.maxTokensPerRequest`) or `maxTurns` exhausted → `rateLimit.onLimitReached('tokens' | 'turns', usage)` then an `error` SSE event. An `AbortSignal` firing at any point (fetch, SSE read, or approval wait) → silent return, no `error` event.
9. `handleAIChat` encodes each yielded `StudioAISSEEvent` as `data: ${JSON.stringify(event)}\n\n`, breaking the forwarding loop on `finish`/`error`; the stream always closes in a `finally`, and the top-level `try/catch` guards `controller.enqueue` against throwing if the consumer already cancelled the stream.
10. The browser client applies `state-mutation` events to its own `StudioController` and renders `text-delta`/`tool-activity`/`tool-approval-request` events live.

## Agentic loop internals (`agenticLoop/`)

`runAgenticLoop` stays in `agenticLoop.ts`; two concerns are split into `agenticLoop/` so each stays independently testable and the security-relevant dispatch logic is isolated from the mechanical wire-format code.

- **`openaiWire.ts` — pure wire-format, zero security surface.** The OpenAI chat-completions message shapes (`OpenAIMessage` union), `toOpenAIMessages(systemPrompt, messages)` (which preserves assistant text alongside tool calls and emits a placeholder tool-result for any still-pending call so the next turn never 400s on an unmatched `tool_calls` entry), and the streamed tool-call delta accumulator (`ToolCallAccumulator`, `createToolCallAccumulator`, `accumulateToolCallDeltas`, `SYNTHETIC_INDEX_BASE`). This module does no authorization and touches no state — the split boundary is drawn so everything here is a mechanical transform that can be reasoned about without policy context.
- **`toolDispatch.ts` — approval race + per-call dispatch decision.** `waitForApproval` (the `Promise.race` of the approval callback vs. `approvalTimeoutMs` vs. the abort signal, with a cross-request duplicate-`toolCallId` guard and a `finally` that always deletes the `approvalPending` entry), `runApprovalFlow` (the single approval-pause implementation shared by the built-in and args-only paths — yields `tool-approval-request`, calls `waitForApproval`, honors `approvalFallback` when no `approvalPending` channel exists), `buildApprovalDisplayInput` (substitutes the REAL entity title from state for the model-supplied display label so the human approves against what will actually be removed), and `dispatchToolCall` itself.

`dispatchToolCall` owns the full ordered decision for one call, threading a static `ToolDispatchContext` (advertised names, policy, skills, data config, approval wiring, mutable usage counters) and returning a uniform `ToolDispatchOutcome` (`aborted` | `result`). Its order is:

1. **Parse failure** — malformed streamed `arguments` (invalid JSON) are _not_ coerced to `{}` and executed; the parse failure is fed back to the model as a tool error so it can retry, without ever running a destructive tool against wrong (empty) args.
2. **Advertised-tool gate (T1-1)** — the call's `name` is checked against `advertisedToolNames`. A call to a name outside that set (e.g. a prompt-injected `remove_page` in a read-only assistant, or `query_data_source` when no `data` config exists) is rejected with `{error: "Unknown tool: <name>"}` and never reaches `executeToolOnState` — advertisement-time filtering alone cannot be bypassed.
3. **Server-tool skill** — a matching `skillHandlers` entry is consulted args-only through the policy (`consultToolPolicyArgsOnly` with `mayMutate: true`, since a skill's `execute` may return a mutation), then run; its `mutation`/`nextState` flow through the loop the same way a built-in tool's does. A `require-approval` decision reuses `runApprovalFlow`.
4. **`query_data_source`** — consulted args-only through the policy (`mayMutate` omitted — it runs a live query but never mutates dashboard state), then dispatched through `createDataToolHandlers` (`mcp/dataTools.ts`) — the same factory the MCP transport uses — so both surfaces run identical query/validation logic. Returns a descriptive error if no `data` config was supplied.
5. **Unregistered skill** — a skill declared in `body.skills` but with no matching `skillHandlers` entry → a descriptive "no registered handler on the server" error.
6. **Built-in tool** — runs through `executeToolWithPolicy` (execute-then-gate). `denied` → `{ error }` (mutation discarded); `needs-approval` → `runApprovalFlow` (commit on approval, discard on deny/timeout/abort); `allowed` → commit immediately. A committed mutation increments `usage.committedMutations` and yields `state-mutation` (`...createMutationEnvelope(mutation)`).

In `privateMode`, `get_dashboard_state`, `list_pages`, `summarise_page`, and `query_data_source` (`PRIVATE_MODE_EXCLUDED_TOOLS`, derived from the registry's `privateModeExcluded` fact) are excluded from the advertised tool list entirely — not merely from the `<dashboard_state>` prompt block — since their output (field distinct values, widget configs, filter values, source labels, and, for `query_data_source`, live database rows) would otherwise round-trip the withheld data back to the provider as tool output. `query_data_source` is excluded even when a `data` config is present, because private mode's guarantee is precisely that no dashboard content or query result reaches the provider. Combined with the T1-1 gate, an injected call to one of these is rejected as unadvertised rather than executed and redacted after the fact.

## Tool execution / state mutation model

`executeToolOnState(toolName, input, state, customWidgets?, pageSnapshot?)` (`executeToolOnState.ts`) is a pure function: `(toolName, args, state) → { output, mutation?, nextState }`. It dispatches through `TOOL_IMPLS`, an exhaustive `{ [K in StudioAIToolName]: PureToolImpl | ExternalToolImpl }` table — one entry per tool name, enforced at compile time by the mapped type. This makes tool purity a **type**, not a convention:

- **`PureToolImpl`** — `{ effect: 'pure'; plan: (args, ctx) => ToolExecutionResult }`. A pure function of `(args, ctx)` with no I/O and no shared-state mutation, safe to call speculatively (dry-run) and discard. This is the shape `toolPolicy.ts`'s execute-then-gate chokepoint depends on. For every write tool the `plan` follows the same shape: (1) validate the referenced entity exists and return a `{ error }`/`nextState: state` no-op if it's missing; (2) build a `StateMutation`; (3) `nextState = applyMutation(state, mutation)`; (4) return `{ output, mutation, nextState }`. Read-only tools (`get_dashboard_state`, `list_pages`) skip steps 2–3 and return `nextState: state`.
- **`ExternalToolImpl`** — `{ effect: 'external' }`, no `plan`. `query_data_source` is the only member: it performs I/O (a live query) and therefore must be authorized BEFORE it runs, args-only. Its real dispatch lives in `agenticLoop/toolDispatch.ts` (chat) and `mcp/queryTools.ts` (MCP); it is intentionally unreachable through `executeToolOnState` — calling `executeToolOnState('query_data_source', …)` directly falls through to the `Unknown tool` error. The entry exists purely so `TOOL_IMPLS` is exhaustive over every `StudioAIToolName`.

`get_dashboard_state`'s pure plan returns `projectStateForAI(state)` — `{ doc, dataSources }` where the authored `doc` partition has its `ai` sub-partition reduced to per-thread metadata (`{ id, name, updatedAt, messageCount }`, transcripts removed) and `dataSources` is data-source metadata projected down to `{ id, label, tableName, aiDescription, hidden, fields, fieldDistinctValues }` with `rows`/`adapter` stripped and distinct values capped (`MAX_DISTINCT_VALUES_IN_STATE_OUTPUT`). `projectStateForAI` (`executeToolOnState.ts`, a sibling export to `projectDataSourceMetadata`) is the single home for both redactions, called by this pure plan and by the `studio://dashboard/state` MCP resource, so the two read surfaces share one output contract and cannot drift; emitting raw `StudioState` would leak live rows and cross-thread chat history into the model context.

Notable per-tool behavior:

- **`add_widget`** resolves the target page as `state.doc.dashboard.activePageId` server-side and errors (`"there is no active page"`) rather than spreading an undefined page into state. Config is layered by `buildWidgetFromArgs`: `createDefaultWidget` defaults → any matching `customWidgets[].defaultConfig` → the model-supplied `config` (highest priority), with the id minted through the shared `createDefaultWidget`/`createWidgetId`. Both `add_widget` and `apply_bulk_update`'s additions build their widget through this one helper so they cannot drift.
- **`update_widget`** applies a partial patch (`changes` + merged `config`), and validates model-supplied `unsetFields`/`unsetConfigKeys`: `unsetFields` is filtered to a fixed `CLEARABLE_WIDGET_FIELDS` allow-list (`sourceId`, `subtitle`, `titleMode`, `subtitleMode`), and `unsetConfigKeys` to keys actually present on the post-merge config.
- **`set_widget_layout`** validates the _shape_, _duplication_, and _membership_ of `rows`, in that order: it must be an array of arrays of widget-ID strings (a flat `["w1","w2"]` is rejected rather than corrupting `widgetRows`); the same id appearing in more than one cell is rejected (`"received duplicate widget IDs: …"`) before the membership check runs, since a duplicated id would otherwise place one widget in two slots and corrupt the layout; and every id must resolve to a known widget in `state.doc.widgets`. The resulting mutation carries `pageId: activePageId`.
- **`set_widget_width`** resolves `rowWidgetIds` from the active page's `widgetRows` and stamps `pageId: activePageId` into the `setWidgetColSpan` mutation. Its JSON-schema `columns` property (`minimum: 6, maximum: 24`) states the 24-column grid range of 6–24, matching the reducer's `clampSpan`. Its tool output reports the value ACTUALLY applied — read back from `nextState.doc.pages[activePageId].widgetColSpans[widgetId]` after `applyMutation` runs — rather than the raw model-supplied `columns`, so a call like `columns: 100` (clamped to 24 by the reducer) is reported as `24`, not `100`; the model's world-model always matches the state that was actually committed. Before building the mutation it also checks whether the widget lives on the active page at all: a widget found on ANOTHER page hits the reducer's orphan-span guard, which silently no-ops (`return state`), so without this check the tool would read back `null` and report `{ success: true, columns: null }` for a call that changed nothing. The check now returns an actionable error naming `set_active_page` instead, mirroring the pattern `summarise_page` and `apply_bulk_update`'s "not on the active page" skip already use; a widget on NO page yet (not-yet-placed) stays permissive.
- **`apply_bulk_update`** is a single atomic operation applying removals → additions → partial updates → optional full-page relayout (references may be given by a newly-added widget's `title`, resolved to its generated id) → column-span patches, building one `applyBulkUpdate` mutation. It emits **deltas** for widgets (`removedWidgetIds`/`addedWidgets`/`updatedWidgets`) rather than a whole-`widgets` snapshot, so a concurrent edit to a different widget while the turn runs is not reverted. Layout (`widgetRows`/`widgetColSpans`) is delta-like too, but by omission rather than by shape, and the two layout fields are no longer attached as an all-or-nothing pair: `rowsChanged` (`applied.removed > 0 || applied.added > 0 || applied.layout`) and `colSpansOnly` (`!rowsChanged && applied.colSpans > 0`) pick between three shapes (ops that were requested but skipped don't count toward either). A removal / addition / accepted `layout` op genuinely reorders or re-places rows, so `rowsChanged` ships the full turn-start `widgetRows` snapshot alongside `widgetColSpans` — the new placement IS the intended one. A batch containing only `colSpans` entries changes widths, never row placement, so it ships `widgetColSpans` ONLY, omitting `widgetRows` entirely; shipping the turn-start rows snapshot there would silently revert a concurrent client-side drag-reorder or row-reassignment that happened while the turn was running (finding 2.3 — the same lost-update class T2-4 closed for updates-only batches, one case narrower, since the tool schema explicitly invites a colSpans-only call: "Only include widgets whose width should change"). The reducer (`applyMutation.ts`'s `applyBulkUpdate.apply`) reconciles a `widgetColSpans`-present/`widgetRows`-absent payload against the page's EXISTING rows rather than wiping them, so `colSpansOnly` no longer needs to ship rows to stay safe. The spans-only branch also MERGES the wire `widgetColSpans` map onto the page's EXISTING span map (`{ ...(page.widgetColSpans ?? {}), ...clampedSpans }`) rather than replacing it wholesale (T2-2): the producer still ships a turn-start snapshot of every widget's span (only the named widget's value actually changed), and a wholesale replace silently reverted a concurrent client-side drag-resize of a DIFFERENT widget on the same page — the same lost-update shape as the `widgetRows` fix above, one field over. Merging is safe because bulk `colSpans` entries are numbers 6–24 and can never clear a span, so a merge loses nothing a replace would have kept; it only applies when `widgetRows` is absent — a `rowsChanged` payload genuinely re-places rows and ships the full intended span map alongside them, so that branch still replaces. An **updates-only** batch (only `widgetUpdates`, nothing else — `rowsChanged` and `colSpansOnly` both false) omits both fields entirely, and the reducer treats true absence of both as "layout unchanged" rather than a wipe — closing the original T2-4 gap where an updates-only bulk call always shipped the turn-start layout snapshot and silently reverted any concurrent client-side drag-reorder or width change that happened while the model was thinking. Skipped operations are collected into a `skipped` array rather than thrown. Removals are scoped to the _active_ page: a removal id that exists globally but lives on a different page is reported as `"remove <id>: not on the active page"` and left untouched. `colSpans` keys are resolved through the same `addedTitleToId` map the `layout` op uses before the range check runs, so a widget added earlier in the same batch (known to the model only by title, since its id is server-minted) can have its width set in the same call rather than the entry silently landing on an unresolved id. A `colSpans` entry outside the 6–24 range (or non-numeric) is **rejected**, not clamped — unlike `set_widget_width`'s clamp-and-report — because this handler's output reports `applied.colSpans` as a per-op count, not the per-widget applied value; clamping silently here would give the model no way to learn which width it actually got, so an out-of-range span is pushed onto `skipped` (`"colSpan <ref>: <value> is out of range (must be a number 6-24)."`, `<ref>` being the original title-or-id key the model supplied) instead. Two desync classes are also closed at the same choke points: the `layout` op rejects DUPLICATE ids across rows before the membership check runs (`"layout: duplicate widget IDs: …"`), mirroring `set_widget_layout`'s own duplicate rejection — the reducer's `dedupeLayoutRows` would otherwise silently keep the first occurrence, so an accepted-looking `layout: true` could commit a different layout than the one the model believes it set; and the `colSpans` loop checks MEMBERSHIP, not just range, against `activePageWidgetIdsAfterBatch` (the active page's widget ids after this batch's removals/additions/layout are applied) — a span keyed to a phantom widget, a widget on another page, or one removed earlier in the same batch is pushed onto `skipped` (`"colSpan <ref>: widget not found."` / `"colSpan <ref>: not on the active page."`) rather than counted in `applied.colSpans`, since the reducer's `enforceLayoutColSpans` silently prunes exactly those entries on apply.
- **`summarise_page`** on the chat path can only honor the _active_ page (only the client-provided `pageSnapshot` has live row data) — a `pageId` for a non-active page returns an actionable error telling the model to call `set_active_page` first. On the MCP path the server can query any page's sources directly, so a `pageId` argument is honored.
- **`set_widget_forecast`** validates the target is a chart widget whose `chartType` is `line` or `area` before accepting the change, coerces `periods` to a positive integer (`Number(periods)`, rejecting non-finite/non-positive values with an actionable error) rather than storing the raw model-supplied value verbatim — the tool schema declares `periods` a number, but the argument is untrusted, and a non-numeric value would both produce a structurally-broken forecast config and (before `describeWidget`'s sanitize fix) round-trip into `<dashboard_state>` unescaped. `enabled` and `showConfidenceBands` are likewise strictly validated as actual booleans (`typeof x !== 'boolean'` rejects with an actionable error) rather than trusted at their declared schema type (T2-3): the schema declares both `boolean`, but a classic LLM string-boolean slip like `enabled: "false"` is truthy in JS, so a bare truthiness check would ENABLE a forecast a call meant to DISABLE while reporting success, and a non-boolean `showConfidenceBands` (e.g. `"maybe"`) would persist a string in a `boolean`-typed config field; both now fail closed instead of silently coercing the dangerous `"false"` → `true` direction. It then emits a PARTIAL config patch carrying only `{ forecast: forecastConfig }` (via `updateWidget`'s top-level `config` arg, which the reducer shallow-merges onto the widget's LIVE config) rather than a `changes.config` replacement — `changes.config` would replace the widget's config wholesale, discarding every other config key and any concurrent edit made while the turn runs.
- **`rename_thread`** builds a `renameAIThread` mutation, stamping `args.updatedAt` once here (so server and client share the timestamp — the reducer never calls `Date.now()`) and `threadId` from `state.doc.ai?.activeThreadId` when present (so the reducer renames the thread the request belongs to). Server-side `state.doc.ai` is unset, so the reducer no-ops on the server's copy; only the client's application actually renames the thread.
- **`remove_page_filter`/`remove_widget_filter`** share one `planRemoveFilter` implementation that looks up the filter by id BEFORE mutating and returns `{ error: "Filter <id> not found." }` (`nextState: state`, no mutation) when it doesn't exist — matching every other entity-targeting tool (`remove_widget`, `remove_page`, `set_widget_width`, …). This existence check runs first because the `removeFilter` reducer is a silent no-op for an unknown id; without it the model would be told `success: true` for a call that changed nothing, with no signal to retry with a corrected id. The two tools emit identical `removeFilter` mutations keyed only by id (no page/widget scope check), so the page/widget distinction in the tool names is cosmetic — removal by id is unambiguous either way.
- **`add_widget_filter`/`add_page_filter`** validate their target exists before committing, for the same reason: `add_widget_filter` checks `state.doc.widgets[widgetId]` and `add_page_filter` checks `state.doc.pages[activePageId]`, each returning an actionable `{ error }` (`nextState: state`) instead of committing a filter scoped to a nonexistent widget/page. This keeps every entity-targeting tool in the file — additions and removals alike — on the same validate-then-mutate shape.

### Write-side config-key validation, fail-closed

Every AI-tool call site that writes untrusted, model-supplied `config` onto a widget of a known kind runs it through `@mui/x-studio-schema`'s config-key allow-lists FIRST — fail-closed, unlike `StudioController.updateWidgetConfig`'s warn-and-strip on the client (a stray key here is untrusted tool-call input, not a UI slip, so it should surface as an error the model can react to rather than silently landing a subtly-different widget). Three layers, the first two mirroring the schema package's own split and the third local to this package:

- **Widget-kind level** — the local `invalidConfigKeyError(kind, config)` wraps `validateConfigKeysForKind`. Shared by every call site that writes a known-kind widget's config: `buildWidgetFromArgs` (used by both `add_widget` and `apply_bulk_update`'s additions), `update_widget`, and `apply_bulk_update`'s updates loop — so the error wording can't drift.
- **Chart-type level, one layer finer** — the local `invalidChartConfigKeyError(patch, existingChartType)` wraps `validateChartConfigKeysForType`. It resolves the patch's EFFECTIVE chart type first — `patch.chartType` if the call supplies one, else the widget's current `chartType`, else the `'bar'` runtime default (the same rule `resolveChartType` encodes) — and validates the patch's keys against that specific family. A key can pass the kind-level check yet still fail here because it belongs to a different chart family than the effective one (e.g. `sankeyTargetField` in a patch that targets a `gauge`). Only reachable for `kind === 'chart'`, at `update_widget` and `apply_bulk_update`'s updates loop; an addition's `chartType` is freshly supplied in the same call, so `buildWidgetFromArgs`'s kind-level check plus its own chart-type check (with no fallback type) already cover it. An unrecognized `chartType` string is a hard error (`isStudioChartType` gate) — there are no custom chart types.
- **Value-shape level, orthogonal to both key checks** — key validation is a key-PRESENCE check only; it never inspects the value stored under a valid key. `invalidConfigValueError(config)` closes that gap for the small set of scalar-typed config fields the tools populate: `SCALAR_CONFIG_VALUE_TYPES` (`executeToolOnState.ts`) maps each field (e.g. `pivotShowTotals`, `dualYAxis`, `kpiTrend` → `boolean`; `barMaxCategories`, `gaugeMin`/`gaugeMax`, `scatterMinRadius`/`scatterMaxRadius` → `number`) to its expected primitive type, and any present-but-wrong-typed value (a non-boolean `pivotShowTotals`, a non-finite `gaugeMax`) fails the call with a named list of offending keys; `null`/`undefined` is treated as inert, not a violation. This closes the write-side enabler of a stored prompt-injection: a valid config key (e.g. `pivotShowTotals`) could otherwise carry an arbitrary string that later got echoed into the widget description. Shared by `buildWidgetFromArgs`, `update_widget`, and `apply_bulk_update`'s updates loop, same as the two key-level checks. Non-scalar/structured config (arrays, nested objects like `ySeries`/`forecast`) is out of scope for this table; `set_widget_forecast` coerces its own nested `periods` argument separately (see above).
- **Same-batch tracking in `apply_bulk_update`** — a widget added earlier in the same batch is not yet in `state.doc.widgets`, so the additions loop records each new widget's kind (`addedWidgetKinds`) and, for chart widgets, its `chartType` into a RUNNING `currentChartTypes` map (seeded from existing state or the addition). Critically, the updates loop keeps this map current across the WHOLE batch: after an accepted update changes a widget's `chartType`, the map is updated in place, so a later update in the same batch targeting that widget validates against the type the earlier update just set — not a stale turn-start or addition-time snapshot. Without this, changing a widget's `chartType` and then setting a key valid only for the new type in one `apply_bulk_update` call would be validated against the wrong type (falsely accepting a cross-type key or falsely rejecting a valid one).
- All three checks fail the containing operation at the granularity that call site uses: `update_widget` rejects the whole call (`{ error }`, `nextState: state`); `apply_bulk_update`'s updates loop pushes a `"update <id>: <error>"` entry onto `skipped` and continues, matching that tool's per-item skip convention.

`buildAISystemPrompt.ts`'s `describeWidget` uses the same `getAllowedChartConfigKeys`/`resolveChartType` pair on the READ side: every chart field it reports is gated by whether the widget's RESOLVED chart type's family actually owns the key (via `getAllowedChartConfigKeys`), not by mere truthiness. This is a correctness requirement, not a nicety: because `update_widget` merges config patches, a widget switched e.g. `sankey` → `gauge` legitimately retains the stale `sankeyTargetField`/`xField`; describing those leftover keys to the model would misrepresent the widget's current gauge shape. The gated description covers the full spread of chart families — bar/line/area axis and layout keys, scatter/bubble (`scatterColorField`/`scatterSizeField`), gantt (`ganttLabelField`/`ganttStartField`/`ganttEndField`/`ganttColorField`), funnel (`funnelStageSequence`/`funnelCategoryOrder`/`funnelReachedField`/label + curve/variant keys), sankey (`sankeyTargetField`/`sankeyLinkColor`/`sankeyShowValues`), heatmap (`heatYField`), pie/donut (`pieArcLabel`/`pieMaxSlices`/`pieLegendBelow`), gauge (`gaugeMin`/`gaugeMax`), plus `annotations`/`forecast`/`ySeries`/`crossFilterMode` — each surfaced only when its family owns it. Every one of these gated fields (and every other value-bearing field `describeWidget` reports — `id`/`kind`/`title`/`source`, KPI/grid/filter/pivot/map config values) is appended through the shared `pushField`/`pushQuoted` helpers rather than a hand-written template-literal `parts.push(...)`, so `sanitizeForPrompt` cannot be skipped at any individual call site — see "Key design invariants" #13. The value-shape check above is defense-in-depth for the same class of value (a wrong-typed scalar config field): it stops the malformed value from ever landing in `state`, while `describeWidget`'s structural sanitize choke point stops any value that does land there (however it got there — a crafted request body, a future call site) from breaking out of the `<dashboard_state>` block.

## Tool policy chokepoint (`toolPolicy.ts`)

`toolPolicy.ts` is the single authorization chokepoint every state-mutating tool call passes through on both transports. A `ToolPolicy` is `(ctx: ToolPolicyContext) => ToolPolicyDecision | Promise<…>`, where a decision is `{ action: 'allow' }`, `{ action: 'deny', reason }`, or `{ action: 'require-approval', reason? }`.

- **`computeToolEffects(prev, mutation, next): ToolEffectSummary`** — a pure structural diff of the pre-execution state against the reducer's `nextState`. It derives `removedWidgetIds`/`removedPageIds`/`removedFilterIds`, `orphanedWidgetIds` (a widget still in `next.doc.widgets` but referenced by no page after the change while it WAS referenced before — the `set_widget_layout` orphan case), `addedWidgetIds`/`addedPageIds`, `updatedWidgetIds` (widgets present in both whose object identity changed — relying on `applyMutation`'s immutable-update discipline), and `layoutChangedPageIds`. It re-encodes no tool-specific logic; it only observes the real before/after states, so it stays correct as reducer behavior evolves.
- **`createDefaultToolPolicy(approvalTools = DESTRUCTIVE_TOOLS)`** — `require-approval` iff the tool name is in `approvalTools`, COMPOSED with `createEffectsAwareToolPolicy()`'s orphan/removal check: even a tool that isn't itself name-listed as destructive (e.g. `set_widget_layout`, which is merely `idempotent`) still requires approval when its actual structural effect removes or orphans a widget/page/filter. Without this composition, `set_widget_layout({ rows: [] })` (or any layout omitting widgets) would pass the shape/membership checks vacuously and blank a page with zero approval — a destruction-equivalent outcome from a tool not classified destructive. The two checks are combined by hand (not via `Policy.all`, to avoid a before-use ordering issue in this file) but are equivalent to it, since the effects-aware half never returns `deny`.
- **`createEffectsAwareToolPolicy({ updatedWidgetThreshold? })`** — an independent effects-only policy: `require-approval` whenever the proposed mutation removes any widget/page/filter, orphans a widget, or (optionally) updates more than `updatedWidgetThreshold` widgets; else `allow`. It deliberately does not wrap `createDefaultToolPolicy`, so callers can compose the two; `createDefaultToolPolicy` itself now does exactly that (see above), so this function is most useful standalone inside a fully custom policy.
- **`Policy` combinators** — `Policy.all(...policies)` evaluates in order, strictest wins (deny > require-approval > allow), short-circuiting on the first `deny` so a budget check placed first denies without consulting later policies; `Policy.mutationBudget({ max, getCommitted, onExceeded, reason })` denies any call that carries a `proposed` mutation OR is flagged `mayMutate` once `getCommitted(ctx) >= max`, with a once-per-breach `onExceeded` latch; `Policy.approveDestructive` re-expresses `createDefaultToolPolicy`.

### The two chokepoint entry points

- **`executeToolWithPolicy(toolName, input, state, opts)`** — the execute-then-gate wrapper for PURE built-in tools. It calls `executeToolOnState` exactly once (the pure dry-run), derives `effects` via `computeToolEffects` when a mutation was produced, builds the `ToolPolicyContext` (with `proposed` set only for mutating tools), awaits the policy, and returns `{ kind: 'allowed' | 'denied' | 'needs-approval', … }`. It increments `usage.toolCalls` unconditionally but never touches `usage.committedMutations` — the CALLER increments that only when it actually commits (a `needs-approval` outcome might still be denied later).
- **`consultToolPolicyArgsOnly(toolName, input, state, opts)`** — the ARGS-ONLY consult for SIDE-EFFECTFUL tools that must be authorized BEFORE they run (`proposed: undefined`): server-tool skills and `query_data_source` on chat, and the read-only data tools on MCP. It performs no dry-run, increments `usage.toolCalls`, threads `mayMutate` (so a mutating-capable skill is still gated by the mutation budget), awaits the policy, and returns `allowed` | `denied` | `needs-approval`. Approval bridging is transport-specific and stays at the call site (chat's `runApprovalFlow`, MCP's `approvalHandler`).

**Purity invariant this depends on:** the execute-then-gate path is safe only because `executeToolOnState` is pure — it computes `nextState = applyMutation(...)` with no I/O and no shared-state mutation, and the real commit happens at the caller's commit point after the policy allows/approves. Any new `executeToolOnState` case (or skill-like branch) that performs a side effect DURING execution defeats the chokepoint, because the "dry run" would fire the effect before the policy runs. The `PureToolImpl`/`ExternalToolImpl` split in `executeToolOnState.ts` makes this structural: a tool that performs I/O must be declared `{ effect: 'external' }` (no `plan`), so it cannot enter the dry-run path and must go through `consultToolPolicyArgsOnly` instead.

### Chat wiring (`agenticLoop.ts` + `toolDispatch.ts`)

`runAgenticLoop` resolves the host policy as `options.toolPolicy ?? createDefaultToolPolicy()` and layers the mutation budget in front of it via `Policy.all`, threading the composed policy (plus a mutable `{ committedMutations, toolCalls }` usage object) into `dispatchToolCall` via `ToolDispatchContext`. Per built-in tool call, after the parse-failure and T1-1 gates, the call runs through `executeToolWithPolicy`: `denied` → `{ error }` (mutation discarded), `needs-approval` → `runApprovalFlow` (the `tool-approval-request` + `waitForApproval` pause/timeout/abort race, with `buildApprovalDisplayInput` substituting the real entity title), `allowed` → commit immediately. Server-tool skills and `query_data_source` consult the policy args-only (`consultToolPolicyArgsOnly`) and reuse `runApprovalFlow` on `require-approval`. A committed mutation increments `usage.committedMutations` and yields `state-mutation`; a denied/timed-out/aborted approval discards `nextState`.

- **`approvalFallback`** (`'deny'` default | `'allow'`) decides what a `require-approval` decision does when no `approvalPending` channel is configured to pause on. `'deny'` refuses the call with an actionable error, closing the previous fail-open behavior where destructive tools ran unapproved whenever a host forgot to wire `approvalPending`. `'allow'` auto-approves and additionally fires `onToolError` with a loud warning. It is exposed directly on the public `StudioAIHandlerOptions` (not only on the lower-level `runAgenticLoop` options) and forwarded by `handleAIChat`, so a host using the primary entry point can set it without dropping to the lower-level loop API.
- **Mutation budget** (`rateLimit.maxMutationsPerRequest`) — the `Policy.mutationBudget` wrapper runs BEFORE the host policy: once `committedMutations` reaches the cap, any further mutating call is denied (with a clear `{ error }`) without consulting the host policy, and `onLimitReached('mutations', usage)` fires once per breach. Unlike the token budget, this does NOT kill the stream — the loop continues, still bounded by `maxTurnsPerRequest`. Omitting the cap means no budget.
- **Server-side `allowedTools`/`privateMode`/`allowedSkills` enforcement** (`handleAIChat.ts`) — the effective allowlist is the INTERSECTION of `options.allowedTools` and `body.allowedTools` (a body omitting its list allows all, so the intersection is the server list); the effective private mode is `options.privateMode || body.privateMode` (the client can opt IN but never OUT); the effective skill set is `body.skills` filtered to `options.allowedSkills` when the host supplies it (omitting it trusts `body.skills` as-is). When all three server options are omitted, the effective values are bit-identical to the raw body values. `options.toolPolicy` is forwarded to `runAgenticLoop`.

### MCP wiring (`mcp.ts`)

Both dispatch paths in `tools/call` pass through the policy with a session-scoped `{ committedMutations, toolCalls }` usage object and a session policy of `Policy.all(mutationBudget, hostPolicy)`:

- **Read-only / side-effectful dispatch-table tools** (data queries, `render_chart`, `get_recent_changes`, and — when `data` is configured — `summarise_page`) pass an ARGS-ONLY consult (`consultToolPolicyArgsOnly`, `mayMutate` omitted since they never mutate dashboard state) and, on `require-approval`, bridge to the host's `approvalHandler` exactly like the mutation path. Only on allow/approved does the handler run.
- **State-mutating tools** (the fallthrough past the dispatch table and the `registeredToolNames` gate) run through `executeToolWithPolicy` and commit via `commitMutation` (write `stateBox.current`, increment `committedMutations`, record `recentChanges`, `sendResourceUpdated`, run `onStateChange`) ONLY on allow / approved-true. The mutating branch runs inside a **per-session mutex** (`mutationChain`): the snapshot → dry-run → policy → approval → commit sequence for a non-dispatch-table tool runs as one chained critical section, so a concurrent mutating call (e.g. one committing while this one blocks on a minutes-long approval) can't clobber this one's commit with a stale `stateBox.current`. Read-only dispatch-table tools stay concurrent — they never write the box.

- **Default policy is ALLOW-ALL**, not `createDefaultToolPolicy()`. MCP has no approval-pause channel today, so defaulting to require-approval would break every existing integration; `options.toolPolicy` defaults to `() => ({ action: 'allow' })`.
- **`approvalHandler?(ctx): Promise<boolean>`** bridges a `require-approval` decision to a host-controlled channel: `true` commits, `false` denies. When a call needs approval and no `approvalHandler` is configured, the call is denied cleanly (never thrown) with a message pointing at `StudioMcpOptions.approvalHandler`.
- **`rateLimit.maxMutationsPerSession`** — the same wrapper-before-host-policy budget as the chat side, session-scoped; further mutating calls past the cap are denied and `onLimitReached('mutations', count)` fires once per breach.
- **`denied` → `errorResult(reason)`** (a tool result flagged `isError`), not a protocol error.

## MCP surface

`mcp.ts` is a slim **composition root**: it creates the MCP `Server`, owns the session-scoped mutable state (the boxed `StudioState`, the `recentChanges` log, the `subscribedUris` set, the `sessionUsage` counters, the `mutationChain` mutex), and wires together the handler modules extracted into `mcp/`.

`buildStudioMcpServer(stateBox, options?)` uses a **boxed mutable state** (`{ current: StudioState }`, type `StudioStateBox`) shared across tool calls in a session — writing `stateBox.current = result.nextState` after a mutation makes the next tool call see the update automatically. The box holds the FULL partitioned `StudioState`: handlers read `stateBox.current.doc.*` for dashboard structure and `stateBox.current.runtime.dataSources[sourceId]` for data-source lookups (the `query_data_source`/`describe_data_source`/`get_field_values`/`compute_field_stats`/`summarise_page` sourceId validation all go through `runtime.dataSources`). Neither `get_dashboard_state` nor the `studio://dashboard/state` resource emits the box verbatim — both call the same `projectStateForAI` function (`executeToolOnState.ts`), which projects `runtime.dataSources` down to AI-safe metadata (`rows`/`adapter` stripped, distinct values capped) and reduces `doc.ai` to per-thread metadata (no `messages`), so the two surfaces can never disagree on what "state" means.

It registers:

- **`tools/list` + `tools/call`.** `tools/list` re-exposes `toolsToRegister` (the `STUDIO_AI_TOOLS` subset for this session — filtered by `MCP_UNSUPPORTED_TOOLS`, the `query_data_source`-needs-`data` gate, and `allowedTools`) plus, when `data` is supplied, the read-only data tools (`describe_data_source`/`get_field_values`/`compute_field_stats` — `mcp/toolMetadata.ts`'s `DATA_TOOL_DEFINITIONS`), and unconditionally `render_chart`/`get_recent_changes` (`EXTRA_TOOL_DEFINITIONS`) — the extra tools also gated by `allowedTools` when supplied. `tools/call` dispatches through a `Record<string, ToolHandler>` table (`toolHandlers`) built from `createDataToolHandlers(...)` plus, when `data` is present, `summarise_page`; everything else (including `get_dashboard_state`) falls through to the shared `executeToolWithPolicy` mutation path.
- **`get_dashboard_state` is intentionally NOT special-cased** in `toolHandlers`. It falls through to `executeToolWithPolicy` (read-only → allowed, no mutation), which puts it behind the policy chokepoint, unifies its output envelope with the chat path (a JSON string, not a raw object), and picks up the row-data redaction from the single pure plan in `executeToolOnState.ts`.
- **`allowedTools` gating runs before dispatch.** When supplied, `allowedTools` is the EXHAUSTIVE allow-list for the WHOLE MCP tool surface (built-in AND extra tools). `isToolAllowed(toolName)` rejects anything not listed with `Unknown tool` before either the dispatch table or the mutation path is consulted — so `allowedTools: []` disables even always-present tools like `get_dashboard_state` (mutation-path) and the extra data/chart/log tools. Names on the mutation path additionally must be in `registeredToolNames`.
- **`resources/*`** (`mcp/resources.ts`) — `studio://dashboard/state` (the authored `doc` plus data-source metadata, both projected through the shared `projectStateForAI` — never raw rows, never full `doc.ai` chat transcripts), `studio://dashboard/system-prompt` (the AI system prompt built from current state, with `contextEnricher` + distilled `buildPageLayoutContext` support), `studio://dashboard/data-health` (per-source row counts, only when `data` is configured), `studio://schema/{sourceId}` (field metadata), `studio://data/{sourceId}` (up to 20-row preview, only when `data` is configured) — with subscribe/unsubscribe and completion-based URI autocomplete. `resources/subscribe` rejects any URI `resources/read` could never serve (mirroring its unknown-URI throw) and enforces a per-session cap (`maxSubscribedUris`, default 256) so a client can't spam distinct valid-shaped URIs (e.g. `studio://schema/<garbage-N>`); re-subscribing an existing member always succeeds and immediately fires `sendResourceUpdated`. `resources/list`'s per-source `name`/`description` route the state-derived `label`/`id` through `sanitizeForPrompt` before interpolation (matching the sibling `prompts/get` handler) — MCP resource metadata is LLM-consumed text (the MCP spec positions `description` as text "for the LLM to understand the resource"), so it is a prompt-injection surface like any other, not merely a listing convenience; see invariant 13's 5th entry point. The `uri` field keeps the RAW id in both the schema and preview entries, since it is an addressable identifier `resources/read` slices back out, not LLM-consumed text.
- **Resource reads that expose the same payload as a tool are gated through the same authorization chokepoint as that tool.** Two mappings exist. (1) **Live-query reads → `query_data_source`.** `studio://data/{sourceId}` (raw row preview) and `studio://dashboard/data-health` (per-source COUNT) each run `mcp.ts`'s `authorizeResourceDataAccess` before touching `data.queryDataSource`: it checks `isToolAllowed('query_data_source')`, then runs the same `consultToolPolicyArgsOnly` args-only policy consult the dispatch-table data tools run (mapped onto the `query_data_source` tool name, since that's the tool these reads conceptually invoke), bridging to `approvalHandler` on a `require-approval` decision exactly like the mutation path. `studio://data/{sourceId}` threads its parsed `sourceId` into the consult `input` (finding 2.3) so a per-source `toolPolicy` rule or an `approvalHandler` inspecting `ctx.input` sees which source is being read; `data-health`, being a multi-source operation, is gated once without a `sourceId`. A host that excludes `query_data_source` via `allowedTools` or `toolPolicy` is honored on these resource URIs too, and the consult increments `sessionUsage.toolCalls` so a usage-aware policy doesn't undercount. (2) **Dashboard-state reads → `get_dashboard_state`.** `studio://dashboard/state`, `studio://dashboard/system-prompt`, and `studio://schema/{sourceId}` all expose a slice of the same `projectStateForAI` payload the `get_dashboard_state` tool returns (`system-prompt` renders it as prompt text; `schema/{sourceId}` serves one source's field definitions, `fieldDistinctValues`-derived `sampleValues`, and `serializeFieldForAI` string), so each runs `authorizeResourceStateAccess` (`isToolAllowed('get_dashboard_state')` + the same args-only consult) before serving — closing finding 2.1, where excluding `get_dashboard_state` from `allowedTools` blocked the tool call but left the byte-identical resource reads ungated. `studio://dashboard/system-prompt` additionally invokes the host `contextEnricher`, which runs LIVE DB queries (per-dimension row counts, finer-grained than `data-health`'s per-source COUNTs); that enrichment now passes the `authorizeResourceDataAccess` gate too (finding 2.2) — when denied, only the enrichment is skipped, the state-derived prompt is still served. `studio://schema/{sourceId}`'s `sampleValues` and `serialized` field are row-derived data (up to 8 real distinct values per field), not static metadata — the same category `MAX_DISTINCT_VALUES_IN_STATE_OUTPUT` caps and `privateModeExcluded` treats as sensitive on the chat side — which is why it needs the same gate rather than being treated as an ungated convenience read. `hidden` remains a listing-only declutter flag, not an access-control boundary, for both tools and resources — see below.
- **`prompts/*`** (`mcp/prompts.ts`) — one built-in prompt, `query_data_source_examples`, which generates example `query_data_source` invocations (a count-by-category and a sum-by-category query) tailored to the dashboard's actual configured data sources, plus `sourceId` argument autocomplete.

**`hidden` is a listing-only flag, not an access-control boundary (by design).** Sources marked `hidden` are omitted from `resources/list`; hidden _fields_ are omitted from `describe_data_source`'s enumeration and from `studio://schema/{sourceId}`. This only declutters those _listing_ surfaces. Per `@mui/x-studio-schema`'s `dataTypes.ts` (`hidden` = "hidden from the data drawer and widget config selects"), it is not an access-control flag: a hidden source read directly by id via `studio://schema/{id}` or `studio://data/{id}`, or a hidden field named explicitly in `query_data_source`'s `columns`, is served/queried unchanged — intentionally, so a legitimate but decluttered source/column (e.g. a cross-source join lookup table) stays addressable. A host that needs a hard access boundary must enforce it in its `queryDataSource` implementation (or not register the source), never rely on `hidden`.

### Data tools (`mcp/queryTools.ts`, `mcp/utilityTools.ts`, `mcp/summarisePage.ts`)

`mcp/dataTools.ts` is a thin composition façade: `createDataToolHandlers` merges `createQueryToolHandlers` (`queryTools.ts`) and `createUtilityToolHandlers` (`utilityTools.ts`) into one six-key record that `mcp.ts` spreads into its dispatch table, and it re-exports `createSummarisePageHandler` and `resolveSource`. The chat transport imports the same `createDataToolHandlers` factory for `query_data_source`, so both surfaces run the identical pipeline.

- **`queryTools.ts`** — `resolveSource(stateBox, sourceId)` validates a `sourceId` against `runtime.dataSources` (and its `tableName`) BEFORE building a query, returning a transport-neutral error (no `studio://` hint, since the chat transport also uses it) that names `get_dashboard_state` as the discovery path. The four handlers (`query_data_source`, `describe_data_source`, `get_field_values`, `compute_field_stats`) each return a descriptive error when `data` is unconfigured, clamp `limit`, and defer to `resolveSource`. `get_field_values`'s `limit` is clamped the SAME way `query_data_source`'s is (finding 2.1): truncated and clamped to `[1, 200]` via `Math.min(Math.max(1, truncated || fallback), cap)` — a non-numeric/zero/`NaN` value (falsy after truncation) falls back to the default of 50, while a _negative_ value (truthy, e.g. `-1`) skips the fallback and is instead floored to `1` by the `Math.max` — so a NaN/negative/zero value can no longer reach the host as `LIMIT NaN`/`LIMIT 0`, closing the below-bound gap left when only the upper bound was enforced, though a negative `limit` now returns a single row rather than the page-50 default. Its tool schema (`mcp/toolMetadata.ts`) documents the cap ("Default 50, capped at 200") so a client asking for more gets an honest description of what it will actually receive. `query_data_source` never writes SQL — it forwards structured `columns`/`filters`/`aggregations`/`having`/`orderBy`/`limit`/`offset` to `data.queryDataSource`, but not before clamping the two numeric bounds: `limit` is truncated and clamped to `[1, maxQueryRows]` via the same `Math.min(Math.max(1, truncated || fallback), cap)` shape — a non-numeric/zero/`NaN` value (e.g. a model-supplied `"all"`) falls back to `maxQueryRows`, matching the schema's documented "Default 1000", while a _negative_ value (e.g. `-1`) is truthy and skips that fallback, instead flooring to `1` via `Math.max` — and `offset` is coerced to a non-negative integer (negative/`NaN`/non-numeric collapses to `0`) rather than forwarded as-is; both transports share this clamp since MCP `tools/call` and the chat loop's `query_data_source` dispatch resolve to the same `createDataToolHandlers` factory. This closes a gap where an untrusted `limit`/`offset` could reach the host's `queryDataSource` implementation unclamped and surface a raw driver error (e.g. `LIMIT NaN`) instead of one of this layer's actionable, model-recoverable errors. `describe_data_source` runs sample-rows + per-field numeric stats concurrently; `get_field_values` also best-effort renders a bar chart of the top values.
- **`utilityTools.ts`** — `render_chart` (pure `renderChartSvg`, returning base64 + raw SVG text) and `get_recent_changes` (the session-scoped `recentChanges` log). Neither touches a data source. `render_chart`'s args are model output and therefore untrusted: `renderChartSvg` validates/coerces `width`/`height` (finite, positive, capped) and each `colors` entry (a strict hex pattern, falling back to the default palette per-entry on a mismatch) before any renderer interpolates them into an SVG attribute position — text content (titles, labels, series names) is separately escaped via `esc()`.
- **`summarisePage.ts`** — `createSummarisePageHandler` (registered only when `data` is configured). It queries every widget's source concurrently (`Promise.all`, each call individually bounded by `withTimeout`), computes numeric stats and a CSV excerpt, and — for time-series chart widgets — runs a GROUP BY aggregation plus `detectAnomaliesIQR` to flag anomalous periods (trimming the first/last bucket, which are commonly partial and produce false-positive low outliers). Per-widget results are written into a pre-sized, index-addressed array (`results[i]`) so the final summary preserves page/layout order regardless of which query settles first. `truncateToPeriod` and `detectAnomaliesIQR` are imported directly from `@mui/x-studio-schema` — the same zero-dependency functions the client uses. `ANOMALY_SAFE_AGGREGATIONS` (`sum`/`count` only) gates the anomaly path — summing per-period `avg`/`min`/`max` into a combined bucket is not mathematically meaningful, so those aggregations skip anomaly detection — and `ANOMALY_CHART_TYPES` (`bar`, `bar-stacked`, `bar-100`, `line`) gates which chart types are eligible for the time-series path at all. Blended charts (a `ySeries` entry from a foreign source) are also skipped.

## Skills

`studioSkills.ts` defines exactly two built-in skills, both `mode: 'instruction-only'` (a prompt fragment with no callable tool — the model reads `<dashboard_state>` and composes a plain-text response):

- **`dashboardNarratorSkill`** — triggers on "walk me through", "explain", "describe", or "give an overview of" the dashboard. Produces a business-stakeholder-friendly narrative: purpose, each widget by title/type, active filters, and a closing summary sentence.
- **`insightSuggestorSkill`** — triggers on "what's interesting?", "any insights?", requests for notable/unusual observations. Suggests 2–4 specific, numbered observations grounded in the actual widgets/fields present, ending with a note on what additional data could deepen the analysis.

Apps can register additional skills of any `StudioAISkill` mode (`instruction-only`, `server-tool` with an `execute` function, or `client-handler`) by passing them through `StudioAIConfig.skills` (serialized as `SerializableSkill` over the wire) and, for `server-tool` skills, through `StudioAIHandlerOptions.skillHandlers` so the agentic loop can invoke `execute` server-side. A `server-tool` skill whose name collides with a built-in `STUDIO_AI_TOOLS` name is dropped (from both the request `skills` and the host `skillHandlers`) before the advertised list, prompt, and dispatch context are built, so a built-in name always resolves only to its built-in handler.

Since a skill's `name`/`mode` are sanitized on the way into the prompt but its `promptFragment` is interpolated as trusted model-instruction prose (`buildSkillSection`), two defenses guard the higher-trust system region a fragment lands in: `handleAIChat`'s optional `options.allowedSkills` drops any body-supplied skill whose name isn't vetted before its fragment ever reaches the prompt builder (see invariant 10), and `buildAISystemPrompt.ts`'s `neutralizeSkillBoundary` replaces any `</skill`-style closing tag inside a surviving fragment with `&lt;/skill` so it can never terminate its own `<skill>` block early — defense-in-depth for the tag framing on top of the allow-list.

## Tool registry: `STUDIO_AI_TOOLS`

`studioAITools.ts` declares `STUDIO_AI_TOOLS` as a single `as const` array of OpenAI-compatible `{ type: 'function', function: { name, description, parameters } }` entries — the same array is passed as the `tools` field of every chat-completion request and re-exposed (mapped into MCP's `Tool` shape) by `buildStudioMcpServer`'s `tools/list` handler. There is exactly one registry; both transports read from it, so adding a tool is a one-file change to be available everywhere.

`STUDIO_AI_TOOL_NAMES` is the array of registered names, derived at runtime from `STUDIO_AI_TOOLS`. `StudioAIToolName` (the type consumers use for `allowedTools`) lives in `@mui/x-studio-schema`, derived as the union of `STUDIO_AI_TOOL_REGISTRY`'s keys — deriving it from the server tool array would invert the schema package's dependency direction (the client needs `StudioAIToolName` without depending on this server package). The registry carries only classification facts, not the JSON-schema parameter definitions, so the two cannot be derived from each other; `studioAITools.ts` therefore ends with a compile-time mutual-assignability check (`AssertMutuallyAssignable<AdvertisedToolName, StudioAIToolName>`) asserting the registry's key set exactly matches the tool names advertised in `STUDIO_AI_TOOLS` — adding a tool to one without a matching registry entry is a TypeScript compile error rather than a silent drift.

`studioAITools.ts` also exports `DESTRUCTIVE_TOOLS: ReadonlySet<StudioAIToolName>` (`remove_page`, `remove_widget`, `apply_bulk_update`) — built by filtering `STUDIO_AI_TOOL_REGISTRY` on its `destructive` fact. `mcp/toolMetadata.ts`'s `annotationsFromFacts` derives each tool's MCP `destructiveHint` from the same entry — `facts.mcpDestructiveOverride ?? facts.destructive` — where `mcpDestructiveOverride` marks `remove_page_filter`/`remove_widget_filter` destructive on MCP even though they aren't chat-approval-gated (MCP clients have no separate confirmation step and the tool permanently deletes an entity). The chat approval gate reads from `DESTRUCTIVE_TOOLS` (`createDefaultToolPolicy()`'s default `approvalTools`), so the chat gate and the MCP annotations both trace to one registry source and can't drift.

`mcp/toolMetadata.ts`'s `TOOL_TITLES` and `TOOL_ANNOTATIONS` are typed as `Record<McpToolName, …>`, where `McpToolName = StudioAIToolName | McpExtraToolName` (the five MCP-only tools: `describe_data_source`, `get_field_values`, `compute_field_stats`, `render_chart`, `get_recent_changes`). Their `StudioAIToolName`-member entries are built from `STUDIO_AI_TOOL_REGISTRY` (`builtInToolTitles()`/`builtInToolAnnotations()`), spread together with the hand-written `EXTRA_TOOL_TITLES`/`EXTRA_TOOL_ANNOTATIONS`. Typing against the real tool-name union means a missing entry for a real tool, or a phantom entry for a tool that doesn't exist, is a compile error; this caught two real bugs (`list_pages` was missing, so `tools/list` emitted `title: undefined`; `get_current_date` was a phantom entry).

`query_data_source` is a single `STUDIO_AI_TOOLS` member dispatched identically on both transports through `createDataToolHandlers` (`mcp/queryTools.ts`). Its only per-transport difference is gating: both require a `data` config, and the chat loop additionally excludes it under `privateMode` (MCP has no private-mode concept).

Per-transport tool availability still differs by design in a few cases:

- **`summarise_page`** — advertised in the chat loop only when a `pageSnapshot` was provided (or the host explicitly opts in via `allowedTools`), because live row data is otherwise only available client-side. In MCP it is unconditionally listed, but its handler only queries live data when `options.data` is configured — without `data` it falls through to `executeToolOnState`, which returns a descriptive client-side-limitation error.
- **`get_dashboard_state`** and **`summarise_page`**'s _output contracts_ are aligned across transports, but their _availability gating_ intentionally differs — a deliberate contract difference, not a bug.

## Key design invariants

1. **Pure function / dependency injection** — no framework imports, no globals; endpoint, apiKey, callbacks, and abort signal are all passed as options. Don't add a hard HTTP framework or vendor SDK dependency here.
2. **Immutable state threading** — `StudioState` is never mutated in place; every tool call returns a new `nextState` (via `applyMutation`), threaded through subsequent tool calls in the same turn and across an MCP session via `StudioStateBox`.
3. **One core, two transports** — `executeToolOnState`, `STUDIO_AI_TOOLS`, `applyMutation`, `buildAISystemPrompt`, the `createDataToolHandlers` data-tool factory, and the `toolPolicy.ts` chokepoint are shared verbatim between the chat loop and the MCP server. Adding or changing a tool means editing `executeToolOnState.ts` + `studioAITools.ts` once, not per-transport.
4. **Cacheable static prompt prefix** — `STUDIO_AI_INSTRUCTIONS` in `buildAISystemPrompt.ts` is a module-level constant so providers can prompt-cache it as a stable prefix; don't make it depend on request-specific data.
5. **Errors never abort the stream** — top-level exceptions become an `{type:'error'}` SSE event (stream still closes cleanly); per-tool exceptions are caught and surfaced to the model as `{error: message}` tool output so it can recover, rather than killing the loop.
6. **Best-effort enrichment** — `contextEnricher` failures are logged and swallowed; the chat proceeds without enrichment rather than failing the whole request.
7. **Bounded pauses, not indefinite waits** — the tool-approval pause (`waitForApproval` in `agenticLoop/toolDispatch.ts`) always races the approval promise against an abort signal and a timeout, guards against a duplicate `toolCallId` across concurrent requests, and always cleans up its `approvalPending` map entry, so an abandoned client can never leak server resources or hang a stream forever.
8. **Single semantic authority for mutations** — `applyMutation` in `@mui/x-studio-schema` is the one implementation of every `StateMutation`'s effect; the server-threaded state and the client-applied state cannot disagree because they run the same code.
9. **Advertisement is not authorization** — a tool being filtered out of the model-facing tool list (`allowedTools`, `privateMode`, data/snapshot gating) must also be rejected at dispatch time if called anyway. `dispatchToolCall` checks `advertisedToolNames` (T1-1) and `mcp.ts`'s `tools/call` checks `isToolAllowed`/`registeredToolNames` before running anything — a filtered tool that somehow gets called is never executed on the strength of the filter alone.
10. **Body `privateMode`/`allowedTools`/`skills` are client-asserted; the host enforces server-side via options** — the body fields are read straight off the client-supplied `StudioAIRequest`. For a hard server-side guarantee, `StudioAIHandlerOptions.allowedTools`/`privateMode`/`allowedSkills` are the built-in overrides: the effective allowlist is the INTERSECTION of `options.allowedTools` and `body.allowedTools`; the effective private mode is `options.privateMode || body.privateMode` (client can opt in, never out); and, when `options.allowedSkills` is set, every body-supplied skill whose `name` isn't in it is dropped before its `promptFragment` ever reaches `buildAISystemPrompt` (omitting the option preserves the current behavior of trusting `body.skills` as-is). A skill's `promptFragment` is otherwise trusted model-instruction prose interpolated into the higher-trust system region, so `allowedSkills` is the only lever a host has to vet it short of denying skills entirely. Alternatively (or additionally) a host can supply a `toolPolicy` that denies per call, or withhold the capability entirely (do not pass a `data` option). When both server options and a custom policy are omitted, the effective values are bit-identical to the raw body values. Treat the _body_ fields as request-shaping hints; the _options_ fields (and `toolPolicy`) are the server-enforced trust boundary.
11. **Execute-then-gate depends on tool purity** — the policy chokepoint's dry-run is only safe because pure tools (`PureToolImpl`) perform no side effect during execution. A side-effectful tool must be declared `{ effect: 'external' }` and authorized args-only (`consultToolPolicyArgsOnly`) BEFORE it runs; it must never masquerade as a dry-run through `executeToolWithPolicy`.
12. **Config-key writes are fail-closed** — untrusted model-supplied `config` is validated against the widget-kind and chart-type allow-lists before any mutation is built; an invalid key rejects (chat) or skips (bulk-update) the operation rather than being silently stripped. This deliberately contrasts with the client controller's warn-and-strip convention, because tool-call input is untrusted rather than a UI slip.
13. **Every state-derived string interpolated into an LLM-consumed text surface is sanitized before interpolation — closed across the five entry points known today, not just the agentic-loop system prompt.** (See "Scope, corrected" below: this class of gap was found and closed in a new entry point in four consecutive review rounds (five entry points total, one round surfacing two at once). The next round (iteration 9) re-swept every file in the package — including several never named in a prior fix — specifically hunting for a sixth entry point, and found none: the first clean round for this invariant. It did surface two things worth tracking separately, neither a sixth instance of this exact class: a marginal injection-hygiene residual inside an already-covered entry point (`prompts/get`'s unknown-`sourceId` error echoed the full configured-source-id list raw; now routed through `sanitizeForPrompt` alongside its sibling call in the same file — see "Scope, corrected"), and, in a related but distinct area, an authorization-parity gap rather than an injection gap (T2-1: `studio://schema/{sourceId}` served row-derived sample values without the `get_dashboard_state` gate its sibling resources already had — see the MCP resources section). Treat "closed" as a statement about the entry points enumerated here and the outcome of the most recent sweep, not a standing guarantee against a sixth — this exact class, and the adjacent authorization-parity class, should both be re-swept at the start of every future review round.) "LLM-consumed text surface" is deliberately broader than "prompt": it also covers MCP tool/resource/prompt _metadata_ a client places into its own model's context (e.g. `resources/list`'s `name`/`description`), not only text this package assembles into its own system prompt. Widget titles, field ids/labels/descriptions, distinct data values, config values (chart type, forecast periods, pivot/grid/map/KPI/filter config scalars), filter values, skill names, layout column-span suffixes (in both `buildDashboardState` and `buildRichContextBlock`), row-count values, enrichment notes, and MCP resource `name`/`description` metadata are all ultimately attacker-influenceable (e.g. a value read back through `query_data_source` from a poisoned data source, a `richContext`/`enrichedContext` field that is client-supplied but typed as a number, or a config scalar that passed key-presence validation but was never value-checked). `buildAISystemPrompt.ts`'s `sanitizeForPrompt()` is the choke point: every such value is escaped (`<`/`>` neutralized) before it lands inside a tagged prompt region (`<dashboard_state>`, `<dashboard_context>`, `<server_context>`, `<skill>`) or an LLM-consumed metadata field, so a hostile value can never structurally close the block early and inject instructions into the trusted prompt/metadata that follows. In `describeWidget`, this is enforced STRUCTURALLY, not by convention: every value-bearing field is appended through the `pushField`/`pushQuoted` helpers, whose only stringifier is `sanitizeForPrompt`, so no call site can interpolate a raw value into the widget description. This holds literally even for values typed `number`: `sanitizeForPrompt(value: unknown)` accepts any value (stringifying internally), so callers route numbers through it directly — `richContext.fieldStats`' `min`/`max`/`mean`/`distinctCount`/`sampledRows`, `richContext.pageLayout`'s per-widget `colSpan` in the `<dashboard_context>` block, and `enrichedContext.rowCounts`' per-value counts are all routed through it alongside their (already-sanitized) sibling key/label, rather than being assumed safe by virtue of their declared type — so a hand-crafted request body cannot smuggle a closing tag into any of these `number`-typed fields. This is in addition to, not instead of, the static "treat it as data" instruction in the prompt's Security Rules. A client-supplied skill `promptFragment` (`buildSkillSection`) is a deliberate exception to full sanitization — it is meant to be model-instruction prose, so its body is not escaped — but `neutralizeSkillBoundary` still replaces any `</skill`-style closing tag inside it with `&lt;/skill`, so a fragment can never terminate its own `<skill>` block early; `allowedSkills` (invariant 10) is the primary server-side lever for untrusted fragments, and this is defense-in-depth for the tag framing.

    **Scope, corrected:** an earlier revision of this invariant described the choke point as unconditionally "fully closed," but that claim was true only of `buildAISystemPrompt.ts`'s agentic-loop system prompt. The package has four other entry points that build LLM-consumed text independently: two one-shot, non-agentic LLM calls — `generateFieldDescriptions.ts` (generates `aiDescription` text from a data source's fields) and `handleGenerateInsight.ts`'s `handleCreateWidget` (drafts a widget from a natural-language description) — the MCP `prompts/get` builder in `mcp/prompts.ts` (`query_data_source_examples`, which returns `role: 'assistant'`/`role: 'user'` messages an MCP client splices straight into its LLM conversation), and `mcp/resources.ts`'s `resources/list` handler (the per-source `name`/`description` fields listed for MCP clients, which the MCP spec positions as text "for the LLM to understand the resource"). All four interpolated state-derived source/field `label`/`id` values (and, in `generateFieldDescriptions`, live DB `sampleValues` — the canonical attacker-influenceable input) raw, with no call through `sanitizeForPrompt` and no tagged region at all. `generateFieldDescriptions` was the most severe gap: its output is stored and merged into every subsequent chat system prompt, making an unsanitized sample value a **stored, second-order** injection channel rather than a same-turn one; `mcp/prompts.ts` was a high-trust instruction position (assistant-role output an MCP client splices into its own conversation); `mcp/resources.ts`'s `resources/list` was the last one found, and — unlike the other three — is metadata rather than prompt/message text, which is exactly why it had been missed: the invariant's prior wording ("prompt-building entry point") didn't obviously cover it. All four now route every interpolated value through `sanitizeForPrompt` (`resources/list` keeps the `uri` field's id raw, since a URI is an addressable identifier the read handler parses back out, not LLM-consumed text), and the three prompt/message-building ones additionally wrap the data in a tagged region (`<fields>`/`<data_sources>`/`<data_source_examples>`) with an explicit "treat as data" instruction, and — `generateFieldDescriptions` only — length-cap each sample value (100 chars) before interpolation, matching the pattern `buildAISystemPrompt.ts` already used. The invariant now holds across all five entry points in the package; a future one-shot LLM call, MCP prompt, or MCP tool/resource metadata field added to this package must route its interpolated state through `sanitizeForPrompt` the same way, since there is no shared helper that enforces this across entry points structurally the way `pushField`/`pushQuoted` does within `describeWidget`. **This is a recurring bug class, not a one-time gap:** four consecutive review rounds have each found exactly one not-yet-covered entry point — `buildAISystemPrompt.ts` closed first, then `generateFieldDescriptions.ts`/`handleCreateWidget` in the next round, then `mcp/prompts.ts` in the round after that, then `mcp/resources.ts`'s `resources/list` in this round — every time immediately after the invariant had been declared "fully closed," and the entry point widened in kind each time it recurred (prompt text → stored/derived prompt text → MCP message content → MCP metadata). Nothing in the package's structure stops a sixth entry point (a new one-shot LLM helper, a new MCP prompt or resource, a new skill mode, a dynamic `tools/list` description) from being added without going through `sanitizeForPrompt`; the fix is procedural (route new interpolation through the choke point) rather than structural (there is no compile-time or lint-time check that a new text- or metadata-building function does so), so this invariant's "closed" status should be re-verified, not assumed, at the start of every future review round — and that re-verification should explicitly sweep MCP tool/resource/prompt metadata, not only prompt-builder source files, since that is precisely the category the 5th instance came from.

    **Iteration 9 update:** that re-verification happened, on every file in the package (including several never named in a prior fix: `mcp/utilityTools.ts`, `mcp/queryTools.ts`, `mcp/summarisePage.ts`, `mcp/toolMetadata.ts`, `mcp/helpers.ts`, `mcp/types.ts`, `widgetConfigMeta.ts`, `buildPageLayoutContext.ts`, `studioSkills.ts`, `agenticLoop/openaiWire.ts`, `parseSSE.ts`), and found no sixth entry point — the first clean round for this invariant. It did find one residual inside an already-covered entry point: `mcp/prompts.ts`'s `prompts/get` sanitizes the example blocks' source ids (closed in the round above) but had not sanitized the SAME ids when they appear in its unknown-`sourceId` error prose (`Unknown sourceId: "…". Available: …`) — free-form text many MCP clients splice back into the model conversation. Both the requested id and the "Available" list now route through `sanitizeForPrompt` (T2-5), for symmetry with `resources/list`. Separately (not this invariant's class, but found in the same sweep of the MCP surface): `studio://schema/{sourceId}` was serving `fieldDistinctValues`-derived `sampleValues` and the `serializeFieldForAI` string — row-derived data, not static metadata — without the `get_dashboard_state` authorization gate its sibling `studio://dashboard/state`/`system-prompt` resources already had; a host excluding `get_dashboard_state` could recover that data anyway via `resources/list` + per-source `studio://schema/<id>` reads. Fixed by running the same `authorizeStateAccess` gate (T2-1; see the MCP resources section). Neither finding reopens this invariant's "five entry points, four rounds" tally; both are noted here because they sit in the same neighborhood (MCP-surfaced, state-derived text/data reaching an untrusted consumer) and the next review round should keep sweeping it.

## Extension points

- **New built-in tool**: add a `StateMutation` variant (if it changes state) to `@mui/x-studio-schema`'s `StateMutation` union and a handler in `applyMutation`'s `MUTATION_HANDLERS`, a `TOOL_IMPLS` entry in `executeToolOnState.ts` (`{ effect: 'pure', plan }` for a pure tool, or `{ effect: 'external' }` for a side-effectful one authorized args-only), a schema entry in `studioAITools.ts` (`STUDIO_AI_TOOLS`), and an entry in `STUDIO_AI_TOOL_REGISTRY` (`aiToolRegistry.ts` in `@mui/x-studio-schema`) — its keys define `StudioAIToolName`, so the compile-time drift guard fails until the registry and `STUDIO_AI_TOOLS` agree — and, if it needs LLM-facing docs, an entry in `widgetConfigMeta.ts`. `mcp/toolMetadata.ts`'s `Record<McpToolName, …>` typing derives its built-in entries straight from the registry, so a registry entry is all that's needed there. If the tool is destructive, set `destructive: true` on its registry entry — the one fact both transports derive from. It's then automatically available to both the chat loop and MCP.
- **New skill**: add a `StudioAISkill` to `studioSkills.ts` (`mode: 'instruction-only'`, or a callable `server-tool` skill with an `execute` function passed via `skillHandlers`).
- **New widget kind's AI-facing config**: update `widgetConfigMeta.ts` (`WIDGET_KIND_DESCRIPTIONS` + the per-kind config lines) — the single place that keeps the `add_widget`/`update_widget` tool schemas and the system prompt's widget docs in sync — and add the kind's `describeWidget` branch in `buildAISystemPrompt.ts`.
- **New chart type's AI-facing config**: add the chart-type-level plumbing described in `@mui/x-studio-schema`'s `ARCHITECTURE.md` (new `StudioChartType` literal, family interface, `CHART_TYPE_CONFIG_KEYS` entry — all fail-closed at compile time there), then add a line to `widgetConfigMeta.ts`'s `CHART_TYPE_DOCS` so the system prompt's `## Chart Types` reference describes it, and the field(s) to `describeWidget`'s gated read block. The `CHART_TYPE_DOCS` array is a plain array with only a comment reminder, not compile-enforced, so it's easy to forget.
- **Custom agentic loop**: `runAgenticLoop` and `executeToolOnState` are exported directly for hosts that want to build their own loop instead of using `handleAIChat`.
