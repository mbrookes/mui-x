# Vega-Lite → MUI X Charts: support matrix and gaps

This document tracks what the wrapper translates natively, what renders with a visible approximation, and what cannot be expressed with `@mui/x-charts` components in any tier. The wrapper depends on `@mui/x-charts-premium` (which re-exports Pro and MIT): Premium-covered marks render with a watermark until a license key is set. Runtime code reports the same information per-spec through the `onGaps` prop as `TranslationGap` objects.

## Severity levels

- **✅ supported** — feature translates to native x-charts behavior.
- **⚠️ partial/approximated** — feature renders with a visible approximation or reduced functionality.
- **✅ supported (Premium)** — translates natively via `@mui/x-charts-pro`/`-premium` components (watermarked without a license key).
- **❌ unsupported (all tiers)** — no x-charts equivalent in any tier.

## Gap origin: whose limitation is it?

Every `TranslationGap` also carries an `origin` (stamped from its `code` — see `X_CHARTS_LIMITATION_CODES` in `src/gaps/index.ts`) that separates two fundamentally different reasons a spec didn't translate cleanly:

- **`origin: 'vega-lite'` — actual remaining gaps.** The Vega-Lite feature is not translated by this wrapper (out of scope, or simply not implemented yet). Closing one means teaching the wrapper a new Vega-Lite feature. These are the gaps that measure wrapper coverage.
- **`origin: 'x-charts'` — x-charts limitations worked around.** The spec is understood, but `@mui/x-charts` cannot render it natively, so the wrapper **approximates** it (e.g. a gradient fill collapsed to a solid color, `mark.opacity` baked into an rgba series color) or renders it through a **custom overlay** built on the public `useXScale`/`useYScale` hooks. These are limits of the render target, not wrapper omissions; closing one means x-charts gaining the capability (or the workaround improving).

The x-charts-origin gap codes are: `encoding:shape`, `mark:point-square-shape`, `mark:point-size-approximation`, `mark:point-styling`, `mark:point-transparent`, `mark:trail-width`, `mark:strokedash-legend-swatch`, `mark:stack-order-explicit-domain`, `encoding:opacity`, `encoding:opacity-field-unsupported`, `mark:bar-corner-radius`, `mark:bar-corner-radius-conflict`, `mark:bar-corner-radius-per-corner`, `mark:bar-size`, `mark:gradient-fill`, `mark:rect-opacity`, `mark:rect-stroke`, `mark:rect-ranged`, `mark:interpolate-approximate`, `mark:interpolate-unsupported`, `scale:band-padding`, `scale:nice-count`, `scale:zero-approximation`, `scale:temporal-point-approximation`, `encoding:color-legend-config-ignored`, `resolve:independent-scale`, `mark:boxplot-custom-overlay`, `mark:errorbar-custom-overlay`, `mark:errorband-custom-overlay`, `mark:image-custom-overlay`, `mark:text-custom-overlay`, `mark:line-continuous-x-custom-overlay`, `mark:area-continuous-x-custom-overlay`, `mark:line-closed-polygon-custom-overlay`, `mark:tick-custom-overlay`, `mark:rule-segment-custom-overlay`, `axis:labelExpr-multiline`, `mark:bar-continuous-range-custom-overlay`, `mark:bar-continuous-range-color-legend`, `mark:bar-category-ranged-custom-overlay`, `mark:rect-ranged-custom-overlay`, `mark:rect-ranged-color-legend`, `mark:point-geo-projected-custom-overlay`, `mark:point-geo-color-legend`, `mark:rule-geo-projected-custom-overlay`, `mark:line-geo-projected-custom-overlay`, `mark:text-geo-projected-custom-overlay`.

**Custom-overlay marks report an `ignored`/`x-charts` gap even though they render correctly.** The `boxplot`/`errorbar`/`errorband`/`text`/`image` marks and `x`→`x2`/`y`→`y2` span rules render through the custom overlay pipeline (`src/overlays`, plain SVG surface children on `useXScale`/`useYScale`); a 1D `tick` strip plot and a `line`/`area` over a continuous quantitative x render as `segments`/`band` overlays. None of these have a native x-charts series/plot behind them, so each reports a `mark:*-custom-overlay` gap (see the code list above) — this is what tells a consumer (and the demo gallery) that a chart with zero _other_ gaps still isn't 100% native rendering. These don't count against Vega-Lite coverage (the spec itself translated fine) — closing one means x-charts gaining a native primitive for that mark, not the wrapper learning new syntax.

**Still worked around fully silently (no gap at all):** a static `mark.opacity`/`fillOpacity` is baked into the resolved series color as an rgba alpha, and an id-keyed choropleth is colored by joining the `lookup` values onto each feature and bridging the feature `id` into `properties.name` (x-charts joins map shapes only by name). These are internal data/styling adjustments with no visible tradeoff to report — the rendered chart is indistinguishable from one that didn't need the adjustment.

## x-charts limitations worked around (custom components & shims)

The wrapper is a strict consumer of the **public** `@mui/x-charts(-pro/-premium)` API — it never patches the charts library. Where x-charts has no native primitive for a Vega-Lite feature, the wrapper renders it through a custom SVG overlay or a small shim built on public hooks. The net diff to `packages/x-charts`, `-pro`, and `-premium` across this whole effort is **zero** (verified: `git diff --stat <effort-base>..HEAD -- packages/x-charts/ packages/x-charts-pro/ packages/x-charts-premium/` is empty).

### One x-charts library bug discovered (fixed in the wrapper, not the library)

Fitting an `albersUsa` choropleth crashed with `projection.rotate is not a function`. Root cause is in the **charts library**: `getDefaultTranslation` (`x-charts-pro`/`-premium` `internals/plugins/useGeoProjection/projection.utils.ts`) calls `projection.rotate(...)` **unconditionally** while fitting a map, but composite projections such as `geoAlbersUsa` expose no `rotate` method.

- An earlier commit patched the library (`projection.rotate?.(...)`), then **reverted it** — patching the shipping charts lib defeats the point of a wrapper that must compose the public API.
- The wrapper now works around it without touching the library (`marks/geoshape.ts` `albersUsaWithRotateShim`): for the `albersUsa` projection it passes a **pre-built `geoAlbersUsa()` instance with a chainable no-op `rotate` shim** instead of the named string, so the provider's unconditional `projection.rotate(...)` fit call succeeds. `CompiledGeo.projection` was widened (`compile/context.ts`) to carry a projection instance for this. Rotation is meaningless for a composite projection, so the no-op is behaviorally correct.
- This remains a genuine **x-charts library limitation** (a fix belongs upstream in `getDefaultTranslation`); it is listed here so it is not lost.

They render correctly and emit **no** gap — they are not counted against Vega-Lite coverage.

## Vega-Lite default alignment

To read like the reference renderer rather than the ambient MUI theme, the wrapper reproduces these Vega-Lite defaults (all land in the wrapper — never the charts library):

- **Categorical palette (`compile/vegaDefaults.ts`, `compile/index.ts`).** With no `scale.scheme`/`range`, a color-split uses Vega's `tableau10`; a single uncolored mark uses its first swatch (`#4c78a8`, steel blue). A `tick` overlay and an `errorband` fill — which are custom overlays, not auto-colored x-charts series — default to that same first palette color instead of the theme's black/grey.
- **Exact scheme swatches (`compile/vegaDefaults.ts` `VEGA_CATEGORICAL_SCHEMES`).** Named categorical schemes (`tableau10`/`tableau20`, `category10`/`20`/`20b`/`20c`, `set1`/`2`/`3`, `accent`, `dark2`, `paired`, `pastel1`/`2`) resolve to the literal hex arrays Vega ships, so scheme-driven charts match color-for-color. A domain longer than the palette cycles it (modulo) rather than bleeding into the chart default palette.
- **Ordered ramp for a sequential scheme on a discrete field (`compile/color.ts` `sampleDiscreteSchemeRamp`).** A sequential/multi-hue scheme (`magma`/`inferno`/`plasma`/`viridis`/`cividis`, the single-hue `blues`/`greens`/`oranges`/`purples`/`reds`, ColorBrewer multi-stop names, `turbo`/`rainbow`/`sinebow`) on a nominal/ordinal color field now **samples an ordered ramp across the domain** (real dark→light progression) instead of cycling a fixed multi-hue palette — this is what makes the CO2 chart's decade lines read as a magma gradient. The perceptual schemes carry real multi-stop hex; single-hue schemes interpolate between their two endpoints; `turbo`/`rainbow`/`sinebow` resolve to an _ordered_ two-endpoint `strawberrySky` approximation. Only `spectral` (and any scheme resolved without a data-derived domain) still falls back to the older cycling `strawberrySky` swatches.
- **Legend/series ordering (`compile/color.ts`).** A nominal/ordinal color legend is ordered ascending by value when the spec gives no explicit `scale.domain` or channel `sort` (Vega's default), instead of first-seen data order.
- **Stack geometry (`marks/bar.ts`, `marks/lineArea.ts`).** Vega stacks in descending order of the color value, so the first legend category sits at the top of the stack. **Bars** now reproduce this for _both_ an ascending data-derived domain and an explicit custom-ordered `scale.domain`: the series are sorted descending by the color value (`compareStackValuesDesc` in `marks/bar.ts`), keeping colors domain-indexed, so no gap is emitted. **Line/area** stacks reproduce it for a data-derived domain via `stackOrder: 'reverse'`, but an explicit custom `scale.domain` still can't be matched (x-charts ties an area stack's draw order to the series order) and reports `mark:stack-order-explicit-domain` (`partial`, x-charts origin) — colors and totals are unaffected; only the vertical segment sequence may differ.
- **Gridlines (`compile/scales.ts`).** Continuous (non-band/point) axes show gridlines by default, matching Vega; discrete axes don't, unless `axis.grid` says otherwise.
- **Plot-area view border (`VegaLiteChart.tsx` `PlotBorder`).** Vega-Lite draws a light border around the plotting area (`config.view.stroke`, default `#ddd`). The wrapper reproduces it with a `<rect>` around the drawing area (`useDrawingArea`, `crispEdges`, non-interactive) on every cartesian chart, unless `config.view.stroke` is `null`/`false`/`transparent`/`''`. This is what "closes" a chart whose grid runs in only one direction (a bar chart's horizontal-only gridlines) into the full frame Vega shows.
- **Axis & legend typography (`compile/scales.ts`).** Vega-Lite's defaults are reproduced over the MUI theme: 10px pure-black tick labels, an 11px bold black axis title, and 10px legend labels — instead of x-charts' 12px/16px 87%-ink defaults — so the chart reads like the reference rather than the ambient theme.
- **Every discrete tick label, rotated when cramped (`compile/scales.ts` `SHOW_ALL_DISCRETE_LABELS`; `VegaLiteChart.tsx`).** A discrete axis shows a label for _every_ band (via `tickLabelInterval`), matching Vega, instead of x-charts' overlap-hiding `'auto'`; when the labels would collide they rotate rather than drop.
- **Series legend title (`VegaLiteChart.tsx`).** A color-split legend is titled with the color field's name (or the field def's `title`), drawn above the legend, mirroring Vega-Lite's legend title (x-charts has no per-legend title slot).
- **Shared layer encoding merged per channel property (`normalize/index.ts` `mergeEncoding`).** A layer's encoding is merged over the parent's **one level deeper than a channel** — a shared top-level `x: {type, title, axis}` plus a layer `x: {field}` resolves to `x: {type, title, axis, field}`, so an inherited axis title/type/scale survives (e.g. the CO2 chart's "Year into Decade" title lives on the shared `x` while the field lives on each layer). A plain channel-level override would have dropped it.
- **`timeUnit` axis labels (`compile/scales.ts`).** A `__timeUnit_<unit>_` axis is labeled by its unit (month → `Jan`, yearmonth → `Jan 2012`, quarter → `Q1`, day → `Mon`, …) rather than a raw locale date string.
- **Axis auto-sizing (`compile/scales.ts`).** Axes carry `width`/`height: 'auto'` so x-charts sizes them to their tick labels; without it, long category names and large numbers ellipsize (`Glabron` → `Gla…`, `20,000` → `20,0…`). Auto-sizing is stripped inside trellis cells (`VegaLiteChart.tsx`), where the fixed per-cell margin governs alignment.
- **Selection-bound opacity (`compile/index.ts` `staticMarkOpacity`).** An `opacity` encoding whose `condition` is bound to a selection is rendered at the condition's value, mirroring Vega's `empty: "all"` default (an untouched selection matches everything). This keeps interactive-legend-style charts fully opaque instead of collapsing to the unselected `value` fallback.
- **Binned y-axis orientation (`compile/scales.ts`).** A binned quantitative y-axis (`__bin_*` synthetic column) is reversed so the lowest bin sits at the bottom — Vega-Lite draws a binned range low-to-high bottom-up. Categorical band axes (nominal/ordinal, including numeric ordinals like `age`) keep x-charts' first-at-top order, matching Vega there too.
- **Binned axis titles (`transforms/encoding.ts`).** A binned field's axis/legend title is suffixed with `(binned)` (`temp_max` → `temp_max (binned)`), as Vega-Lite does, unless the spec sets an explicit title.
- **Facet value order & sizing (`facet/index.ts`).** Wrapping-facet values are ordered ascending by default (Vega-Lite's default), and each cell is sized to a Vega-like per-cell target so the grid grows to fit its cells rather than squishing them into a small total. A `columns` count is read from the facet channel def (`encoding.facet.columns`) as well as the top level.
- **Bubble size legend (`VegaLiteChart/SizeLegend.tsx`).** A scatter `size` field has no native x-charts legend, so the shell draws representative hollow circles + value labels (radii taken from the compiled `sizeMap`) beside the chart, titled from the `size` channel ("Count of Records", etc.).
- **View sizing (`VegaLiteChart.tsx` `resolveVegaViewSize`; `facet/index.ts` `vegaCellSize`).** When no `width`/`height` prop is given, each view is sized the way Vega-Lite sizes it: a numeric spec size is used verbatim; a discrete band/point axis — or an explicit `{step}` — uses step-based sizing (`step × categoryCount`, default step 20); a binned axis and continuous axes use a default view size. The perpendicular axis space is added on top so the _plot_ (not the surface) matches the reference's plot. Trellis cells size the same way from the inner cell spec, and the grid grows to fit its cells rather than dividing a fixed total. An explicit `width`/`height` prop still overrides all of this. **A facet/concat/repeat child's own default plot dimension (`facet/index.ts`'s `VEGA_DEFAULT_VIEW`) is 200px** — a bare `vega-lite` compile of a genuinely unconstrained top-level view resolves this to 300px, but that isn't what the reference actually renders: the gallery's reference always calls `vega-embed`'s `embed()` with an explicit `{width: 440, height: 340}` (see `GalleryPage.tsx`), and under that constraint a composed child's continuous axis default is 200px — confirmed by instantiating `vega-embed`'s real `embed()` (not just the `vega-lite` compiler) with those options and reading the resulting Vega view's internal `*_width`/`*_height` signals, across a facet operator, a `concat` grid, a `vconcat`, and a wrapping facet.
- **Rounded ("nice") axis domains for overlay-only geometry (`compile/index.ts` `applyOverlayDomains`).** An axis whose range must stretch to fit overlay-only geometry (an errorband above its line, a boxplot's whiskers/outliers) is rounded to the same clean tick values `d3.scaleLinear(...).nice()`/Vega would pick (e.g. a CI band ending at exactly `40`, a box plot at `2500–6500`), instead of the series extent padded by a flat 5% — which produced arbitrary-looking bounds that also didn't match the reference.
- **A `stack: 'center'` (silhouette) y field is exempt from the `zero` pin (`compile/scales.ts`).** The `scale.zero` default approximation (pinning the domain to include 0 for all-positive raw field data) assumes an unstacked or zero-baseline stack; a center/silhouette stack's rendered values are genuinely negative for the lower half, so pinning the axis min to 0 there squeezed the whole stream into half its real vertical range and clipped the peaks (`interactive_legend`'s streamgraph).
- **`rect` band scales default to no inter-cell padding (`compile/scales.ts`).** A heatmap's cells now tile edge to edge by default (Vega-Lite's own `rect` band default), matching the reference instead of showing visible gaps between cells; a `bar` sharing the same band scale (e.g. a text/point label layer over the same cells) still gets x-charts' own default gap.
- **`config.axis.grid` is honored as a chart-wide default (`compile/scales.ts`).** A spec-level `config.axis.grid: true`/`false` now sets the default for both axes (a per-field `encoding.<channel>.axis.grid` still overrides it), matching Vega-Lite — previously only the per-field override was read, so a spec relying on the config-level default silently kept x-charts' own grid default instead.
- **`point`/`circle`/`square` marks default to 0.7 opacity (`compile/index.ts` `staticMarkOpacity`).** Vega-Lite's own mark config gives these three (and `tick`) a 0.7 opacity out of the box so overlapping scatter/bubble points stay visible; an explicit `mark.opacity`/`fillOpacity`/`encoding.opacity` still overrides it. (`tick`'s own rendering path doesn't consume this — ticks keep full opacity.)
- **A literal opaque-white gradient stop reads as "fade to transparent" (`marks/lineArea.ts` `buildMarkGradient`).** Vega-Lite's own gradient-area examples often fade to a literal `"white"` stop — a trick that only reads as "fading to nothing" against a plain white page. Rendered inside a themed card (including dark mode), that stop would instead paint an opaque white patch. A pure-white, fully-opaque stop is reinterpreted as a transparent version of the nearest solid stop instead, so the fade is a true alpha gradient that reads correctly on any background.
- **A bare array of primitive values as `data.values` OR a named dataset (`normalize/index.ts` `resolveRows`, `wrapPrimitiveRows`).** Vega-Lite wraps `data.values: [12, 23, 47]` into one-field records keyed `data` (`{data: 12}`, …) so `encoding.field: "data"` resolves; the wrapper now mirrors that instead of handing mark compilers primitive "rows" with no properties to read a field from (`arc_radial`'s inline data). The same wrapping now also applies when the bare primitive array reaches a unit via a **named dataset** (`data: {name: ...}` + `datasets`) rather than inline `data.values` — previously only the inline path wrapped it, so `layer_line_window`'s `datasets.falcon`/`.square` (each a bare array of numbers) reached a `calculate: "1000/datum.data"` transform with `datum.data` always `undefined` (the row was the raw number itself, not `{data: <number>}`), silently nulling every derived value and rendering nothing.
- **Pie/donut default `outerRadius` matches the surface, not x-charts' own conservative auto-fit (`VegaLiteChart.tsx`).** A pie/arc series with no explicit `mark.outerRadius` now defaults to `min(surfaceWidth, surfaceHeight) / 2` — the same full-bleed sizing Vega-Lite itself uses — instead of x-charts' own auto-fit, which reserved more margin than necessary and rendered visibly smaller than the reference at the same surface size.
- **Continuous/piecewise color legend direction & length (`marks/rect.ts`, `VegaLiteChart.tsx`).** `encoding.color.legend.direction`/`gradientLength` on a heatmap's color field size and orient its gradient legend bar (Vega-Lite defaults to a vertical bar unless a spec asks for `"horizontal"` explicitly); previously only vertical was ever drawn, ignoring both. A geoshape choropleth's own continuous/piecewise legend also now defaults its length to Vega-Lite's real `config.legend.gradientLength` (200px) instead of x-charts' much shorter default, which read as a squashed sliver next to a full-height map.
- **A facet channel's inline `timeUnit` is applied before partitioning (`facet/index.ts`).** A `row`/`column`/`facet` channel (or the `facet` operator's equivalents) with `timeUnit: 'hours'`/`'month'`/etc. now facets on the truncated bucket value, matching Vega-Lite — previously it partitioned on the raw per-row timestamp, producing one near-empty cell per distinct raw value (8759 cells instead of 24 for an hour-of-day facet over a year of hourly data) instead of one cell per bucket; besides mis-rendering the trellis entirely, compiling thousands of spurious cells was combinatorially slow (`trellis_area_seattle`).
- **A `lookup` transform's topojson secondary data is converted to one row per feature (`transforms/lookup.ts`, `normalize/index.ts` `extractTopojsonFeatureRows`).** A `from.data.format.type: 'topojson'` secondary dataset (a common "choropleth via lookup" pattern — joining map geometry onto a primary table by id) now gets the same topology→GeoJSON conversion applied to primary geoshape data, exploded to one row per Feature (keyed by its `id`) so the lookup can actually match — previously the raw Topology object reached the lookup's row-array logic directly and crashed (`geo_repeat`, `geo_trellis`, `interactive_geo_facet_species`).
- **An explicit `scale.type: "point"` can't override a bar/rect/boxplot/errorbar mark's band requirement (`compile/scales.ts`).** These marks derive their width/summary geometry from a band scale; x-charts has no way to draw them on a point scale at all. An explicit point scale on such a channel now falls back to band (with a `scale:point-forced-band` `partial` gap) instead of reaching x-charts with no band width to draw from and crashing (`histogram_nonlinear`).
- **A `line`/`trail` mark with `interpolate: "linear-closed"` draws a closed, filled polygon (`marks/lineArea.ts`, `overlays/Polygon.tsx`).** Vega-Lite treats this interpolation as a hand-drawn shape, not an ordinary polyline: the mark's `fill` paints the closed area and the points are connected in row order (never x-sorted) with the path closed back to the first point. x-charts has no such series, so this now renders through a new `{kind: 'polygon'}` custom overlay (`mark:line-closed-polygon-custom-overlay`, `ignored`) instead of falling into the plain continuous-x line overlay, which drew an open, unfilled, x-sorted polyline — visible as stray colored line segments with no fill (`ternary`'s background wedges).
- **An identity color/fill/stroke field (`scale: null`) uses each row's raw value as the literal color (`compile/color.ts`).** Vega-Lite's `scale: null` is an escape hatch for a field that already holds CSS/hex color strings (typically computed by an earlier `calculate` transform): the raw value IS the color, with no domain/range/legend involved. Previously every distinct raw value was treated as its own categorical domain entry and assigned an arbitrary palette color instead of its own literal value (and always drew hollow markers, since a `point` mark's default `filled: false` was never overridden by an explicit `fill` channel) — now such a field reports `identity: true` (no gap; this is fully supported), and an explicit `fill` channel is always treated as filled regardless of the mark-type default (`ternary`'s city markers).
- **A static `mark.stroke` alongside a solid fill draws a distinct marker outline (`marks/point.ts`, `VegaLiteChart/HollowScatterMarker.tsx`).** A `point`/`circle` mark with both a fill (static or field-driven) and an explicit `mark.stroke` now renders a filled circle with that stroke as its border color/width, via a new `markerStroke` map fed to the same custom scatter-marker slot the hollow-marker styling uses — previously `mark.stroke` was read only for `tick` marks and silently dropped elsewhere.
- **The bubble-size `zAxis` domain defaults to zero, not the data minimum (`marks/point.ts`).** Vega-Lite defaults `zero: true` for non-positional continuous scales (`size`, `opacity`, …), so the size domain starts at 0 unless the spec opts out with an explicit `scale.zero: false`. Anchoring at the data minimum instead shrank the smallest bubble toward radius 0 whenever the data didn't already start near zero (`ternary`'s `TotalLevel` bubbles, ranging 81–545, collapsed the smallest few cities to barely-visible dots).
- **A `mark.dx`/`mark.dy` text-mark offset may be a per-row signal expression, not just a constant (`marks/textMark.ts`).** Vega-Lite allows `{expr: 'datum.someField'}` here (e.g. a `calculate`-derived offset that varies per row); only a literal number was previously read, so an expression offset silently fell back to no offset at all — a text mark relying on it to clear an overlapping marker rendered directly on top instead (`ternary`'s city labels, offset ±15px via `datum.dy_val`).
- **A multi-line `title.text` array is now joined and rendered (`normalize/index.ts` `titleText`).** Vega-Lite's title `text` may be a string array (one entry per rendered line); only a plain string was previously read, so an array-form title (with no other unsupported property) was silently dropped entirely instead of falling back to at least its first line (`ternary`'s chart title).
- **`config.axis.disable` hides every axis by default (`compile/scales.ts`).** A chart-wide `config.axis.disable: true` now suppresses each axis's line, ticks, labels, title, and default grid, matching the per-channel `axis: null` behavior already supported — previously only `config.axis.grid` was read from the config object, so a spec relying on `disable` still rendered fully-labeled axes the reference never draws (`ternary`, whose axes exist only to place its marks). A channel's own explicit `axis` config still overrides the chart-wide default, same as Vega-Lite.
- **Custom overlays produced before any series-contributing layer render behind the native plots, not on top of them (`compile/index.ts`, `VegaLiteChart.tsx`).** The shell can only stack overlays as one group before the plot components and one group after — it can't interleave per-layer the way a real z-order would — so overlays are now split by whether they came from a layer before or after the first layer that contributes a native series, and the "before" group renders first. Previously every overlay rendered in a single group _after_ every plot regardless of source layer, so an early background-only layer (the ternary chart's filled wedges, layer 0–6) painted over a later series layer's markers (layer 9's city points) instead of sitting behind them. An errorband layered under a following line (a common composite-marks idiom) benefits the same way, now genuinely drawing behind its line instead of merely appearing to via translucency.
- **A field-based `strokeDash` (with no color/fill/stroke field) still splits a line/area layer into one series per distinct value (`marks/lineArea.ts`).** Vega-Lite groups a line mark on any "detail"-like channel, not just color; previously the layer had no split field at all in this case, so every row across every distinct `strokeDash` value was bucketed into a single series, overwriting whichever row's value landed at a shared x index last (`line_strokedash`'s 5 stock symbols collapsed into one garbled line). Each group now gets its own dash pattern (cycling a default range confirmed against vega-embed's real rendering: solid, then increasingly dashed/dotted) while sharing the same single default line color (an explicit color is now forced here — `compile/index.ts`'s per-series auto-palette assignment otherwise only makes sense for a single uncolored series, and would give each dash-split line its own distinct color instead). The legend now shows correctly (each series gets a `label`), though its swatch is a plain solid line (`mark:strokedash-legend-swatch`, `ignored`/x-charts) since x-charts' legend swatches have no per-entry dash pattern.
- **Per-series line stroke styling (`mark.strokeWidth`/`strokeDash`) now actually renders (`marks/lineArea.ts`, `VegaLiteChart.tsx`).** This was always compiled but never worked: the wrapper targeted a CSS selector (`.MuiLineElement-root[data-series-id=…]`) via a fictitious per-series `sx` property that neither matches any class x-charts' `LineChart` actually renders (the real class, confirmed via `lineClasses.ts`, is `MuiLineChart-line`) nor is `sx` itself a property x-charts' line series recognizes at all — the value was silently dropped every time, confirmed empirically via computed-style inspection in a live render. Fixed by exposing a `lineStyle` map (keyed by series id) at the compiled-chart level and having the shell feed it through `<LinePlot slotProps={{line: (ownerState) => lineStyle[ownerState.seriesId]}}>`, which resolves per series (via `ownerState.seriesId`) and forwards arbitrary SVG props straight to the real `<path>` — the same per-series-override pattern already used for the scatter marker slot.
- **A `repeat`'s own top-level `transform` runs before the repeat expands (`facet/index.ts` `planRepeat`).** A spec-level `transform` array that's a sibling of `repeat`/`spec` is shared preprocessing that must apply to the rows once, before partitioning — already handled correctly for `facet`/`row`/`column` via `transformedRootRows`, but `planRepeat` called the untransformed `resolveRootRows` directly, so a `repeat.layer` spec relying on a root `pivot`/`aggregate`/etc. silently repeated over the raw, untransformed rows instead (`line_color_halo`, whose `pivot` reshape never ran, leaving every repeated layer with no matching field to plot).
- **Auto-assigned palette colors skip series that already have an explicit color (`compile/index.ts`).** The per-series auto-palette pass previously indexed `palette[rawSeriesIndex % palette.length]`, so a spec mixing explicitly-colored series (e.g. a static-white halo line) among auto-colored ones consumed a palette slot for the pre-colored series too, shifting every later auto-colored series onto the wrong (skipped/odd) swatch. A separate counter now advances only for series actually needing a color, matching Vega-Lite's own sequential assignment (`line_color_halo`'s per-symbol lines landing on the correct Tableau10 colors instead of every other slot).
- **A `timeUnit`-qualified filter predicate truncates both sides before comparing (`transforms/filter.ts`, `transforms/timeUnit.ts`).** A field predicate like `{field, timeUnit: 'year', range: [2006, 2007]}` previously compared the _raw_ field value against the plain comparator numbers — for a formatted date string this is a lexicographic string comparison against a number that (via `String.localeCompare`) evaluates the same regardless of the actual date, so a `range` filter's `>=`/`<=` pair could both resolve to the same, date-independent answer and drop every row (`line_conditional_axis` rendered with no line at all, just its axes). The field is now truncated via `resolveTimeUnit` (the same truncation the `timeUnit` transform/encoding path already used) and each comparator value is converted to its equivalent synthetic date via the new `unitValueToDate` (mirroring Vega-Lite's own `dateTimeToExpr({[unit]: value})` predicate compilation), so both sides become directly comparable timestamps. Only falls back to the old raw-value comparison (with its `partial` gap) for shapes `unitValueToDate` can't build a single-field date from — a composite unit, `day`/`dayofyear`/`week`, or `valid`.
- **The `calculate` expression evaluator now supports `log`/`pow` (`transforms/calculate.ts`).** Vega's own `log`/`pow` functions weren't in the allow-listed function set, so any expression using them (`"log(datum.x)/log(10)"`, a common log-base-10 change-of-base idiom, and `"pow(10, datum.bin)"`) threw an `UnsupportedExpressionError` and left the target field `null` for every row — silently breaking any downstream `bin`/positional channel reading it, not just producing an approximation (`histogram_log`'s entire `log(x) → bin → pow(10, bin)` pipeline evaluated to `null`, leaving the bar mark with zero rows to draw).
- **An unaggregated `x2`/`y2` field survives an aggregate's implicit group-by (`transforms/encoding.ts` `GROUPING_CHANNELS`).** An encoding-level aggregate (e.g. `y: {aggregate: 'count'}`) groups rows by every other non-aggregated positional/grouping channel field so each output row keeps its category — but `x2`/`y2` weren't in that grouping-channel list, so a plain (non-aggregate) `x2`/`y2` field was silently dropped from every grouped-output row instead of surviving alongside its `x`/`y` group. This broke any ranged-bar-with-a-count spec (`histogram_log`'s `x`/`x2` bin edges paired with `y: {aggregate: 'count'}` lost the `x2` field entirely, leaving no range to draw).
- **A `bar` mark with BOTH positional channels continuous draws through a custom `rects` overlay (`marks/bar.ts`, `overlays/Rects.tsx`).** Vega-Lite's own bar mark can draw a genuine "ranged bar on a continuous domain" — e.g. a log-scaled `x` paired with an `x2` twin for explicit (non-uniform) bin edges, and a plain quantitative `y` count — but x-charts' `bar`/`rangeBar` series always need one categorical/band dimension to draw from, so neither could render this at all (`mark:bar-missing-axes`, since neither axis is categorical). Detected as a distinct case (both axes continuous, exactly one `2`-twin present, no color split) and drawn instead as plain `<rect>`s positioned by the real `useXScale`/`useYScale` at render time — so a log-scaled axis still spaces the bars correctly — reporting an honest `mark:bar-continuous-range-custom-overlay` (`ignored`/x-charts) gap (`histogram_log`, previously rendering with zero bars, just its axes).
- **A continuous-x `line`/`trail` mark's zero:true default now pins its y domain too (`marks/lineArea.ts`, `compile/index.ts` `applyOverlayDomains`).** Vega-Lite's line-mark default zeroes the y-axis the same as bar/area, and `applyOverlayDomains` already implements this — but only by checking native `series` array entries for `type: 'line'`/`'bar'`; a **continuous-x** line (no index-aligned category domain, so it renders through the `segments` overlay instead of a native series — see the Marks table's `line` row) was invisible to that check, so its y-axis fit the data extent instead of zeroing. The overlay is now tagged (`lineMarkZeroBaseline`) so the same zero-pinning logic recognizes it (`layer_point_line_regression`/`layer_point_line_loess`'s y-axis previously started around the data minimum, e.g. `2`, instead of `0` like the reference).
- **`data.sequence` generates rows from a numeric range (`normalize/index.ts` `resolveSequenceRows`).** Vega-Lite's `data.sequence: {start, stop, step, as}` generator (d3/JS `range()` semantics: `start` inclusive, `stop` exclusive, a negative `step` counting down) was entirely unimplemented — a spec relying on it for its data (rather than `values`/`url`/a named dataset) silently resolved to zero rows and no gap at all. Now generates the row set directly (capped at 100,000 rows, `partial`/`data:sequence-truncated` if hit), reporting an honest `unsupported`/`data:sequence-invalid` gap only for a sequence whose `step` sign can never reach `stop` (`sequence_line_fold`, previously rendering completely blank).
- **The `calculate` expression evaluator now supports `sin`/`cos` (`transforms/calculate.ts`).** A second, independent blocker for the same spec as above: once `data.sequence` produced rows, its `sin(x)`/`cos(x)` derived fields still evaluated to `null` for every row (an `UnsupportedExpressionError`, same failure mode as the earlier missing `log`/`pow`), leaving nothing for the line mark to plot.
- **A continuous-x `line`/`trail` mark's segments overlay now accepts a categorical y (`marks/lineArea.ts` `groupContinuousPoints`).** Vega-Lite's "bump chart" pattern (continuous/quantitative x, ordinal/nominal y — e.g. ranking builds by pass/fail/skip over time) has no index-aligned category domain on x, so it must render through the same continuous-x `segments` overlay as a numeric-y line; previously that path forced every y value through `toNumber`, so a categorical y silently dropped every row (0 numeric-x points survive) instead of rendering. The overlay's point type now keeps the raw category value for a categorical y, resolved to a pixel position by the band scale at render time (`scalePosition` in `overlays/scaleUtils.ts` already centers within a band scale generically, so no overlay-rendering change was needed) (`line_bump`, previously rendering completely blank).
- **A `bar` mark with BOTH `x`/`x2` AND `y`/`y2` explicit spans draws a genuine per-row rect (`marks/bar.ts` `compileFullyRangedRects`).** The existing continuous-range `rects` overlay only handled one twinned axis with an implied zero baseline on the other (`histogram_log`'s log-scaled bin edges); a spec with both axes twinned — a true per-row rectangle with no implied baseline on either side (`bar_heatlane`'s heat-lane cells, each spanning an explicit horsepower bin AND an explicit count band) — fell through to the generic `mark:bar-missing-axes` gap instead, rendering nothing. Generalized to a third case reusing the same overlay mechanism. This also surfaced the `rects` overlay's `!color.splitField` restriction: `bar_heatlane`'s per-cell color encoding would otherwise still have reported unsupported even once the geometry worked, so a color split now resolves genuinely per row instead (each `OverlayRectItem` already carries its own `fill`, unlike a native series which needs one color for the whole series), cycling the chart's default palette when no explicit scheme/range is given and reporting the missing color-legend honestly via a new `mark:bar-continuous-range-color-legend` (`ignored`/x-charts) gap.
- **A "global"/1D `errorband` (no category channel at all) spans the full continuous domain of the sibling axis instead of reporting missing axes (`marks/errorBar.ts`).** Vega-Lite's composite error marks don't always group by a category: `layer_scatter_errorband_1D_stdev_global_mean`'s errorband layer encodes only `y` (`Miles_per_Gallon`) — no `x` anywhere, not even a shared root encoding — meaning ONE interval is computed over every row and drawn spanning the whole plot width, not grouped per category. The wrapper's axis-resolution previously conflated "the shared, chart-wide x-axis has some field" (inherited from the sibling scatter layer) with "this layer defines a category channel", and unconditionally required `categoryAxis.categories` (a band/point scale) to proceed — so a genuinely continuous span-axis (no categories at all) always fell through to `mark:errorbar-missing-axes`, even though the value channel and a perfectly good continuous axis to span both resolved correctly. Detected via a new check (`isGlobalBand`: this layer's own merged encoding defines only the value channel, and the shared axis for the other channel is continuous with a real field but no categories) and rendered as a flat two-point `band` (start/end taken from that field's own data extent, same lower/upper at both ends) — reusing the existing `band` overlay mechanism entirely unchanged. Deliberately NOT extended to a global `errorbar`: Vega-Lite positions that whisker at the plot's pixel center, not a data value derivable from `compileSpec` alone, so that shape still reports the honest missing-axes gap.
- **An explicit `size` scale `domain`/`range` is honored instead of silently recomputed from the data extent (`marks/point.ts`).** The bubble-size block previously derived its domain purely from the field's own min/max and hardcoded the radius range to `[0, 11]`, ignoring an explicit `scale.domain`/`scale.range` entirely — with no gap reported, so a spec deliberately widening/narrowing the size mapping (`dynamic_color_legend`, `interactive_seattle_weather`) silently rendered with the wrong bubble sizes instead. A two-number `domain` now sets `zAxis[0].min`/`.max` directly (falling back to the old data-extent/`zero` behavior otherwise), and a two-number `range` (Vega-Lite's `size` scale outputs marker _area_, not radius) converts each endpoint through `sqrt(area / π)` into the continuous `sizeMap`'s radius range. A **discretizing** size scale (`quantile`/`quantize`/`threshold`) is now implemented directly rather than falling back to this continuous path — see the dedicated bullet below. A `range` endpoint that isn't a plain number (e.g. `{expr: 'pow(earthquakeSize, 3)'}`, a signal bound to an interactive parameter) reports `encoding:size-scale-range-unsupported` (`partial`) and also falls back to the default range, instead of silently misinterpreting the expression object as a number.
- **The bar/line `zero: true` domain default never pins a log-scaled axis to 0 (`compile/index.ts` `applyOverlayDomains`).** A log scale can never include 0 (`log(0)` is undefined) — Vega-Lite itself requires `scale.zero: false` there regardless of mark type — but the zero-baseline pin (added for bar/area/line series, and for a continuous-x line's `segments` overlay) applied unconditionally, feeding `d3.scaleLog` an invalid `[0, max]` domain. `d3` degrades silently rather than throwing, so the chart didn't crash — it just rendered as a totally blank plot with no visible axis ticks at all (`layer_line_window`'s log-scaled fps axis). The zero-pin now short-circuits whenever the axis's `scaleType` is `'log'`.
- **A `hconcat`/`vconcat`/`concat` spec's own top-level `transform` now runs before any cell sees the rows (`facet/index.ts` `planConcat`).** Every sibling composition path (`facet`/`row`/`column`, the `facet` operator, `repeat`) already applied the spec-level `transform` array once via `transformedRootRows` before partitioning/repeating; `planConcat` was the one path still calling the untransformed `resolveRootRows` directly. A concatenated spec relying on a root `calculate`/`filter`/`aggregate`/etc. therefore saw the raw, untransformed rows in every cell — silently wrong (but plausible-looking) values with no gap reported (`vconcat_weather`'s two charts both aggregated over every location instead of just Seattle), or a cell with nothing to plot at all (`point_quantile_quantile`, `concat_population_pyramid`, both rendering completely blank).
- **A layer's own literal `{value: N}` positional encoding is honored ahead of the chart-wide field-based axis (`marks/point.ts`, `marks/textMark.ts`).** Vega-Lite's positional `value` encoding is a plot-area **pixel** offset, not a data value (used for annotation-style marks pinned to a fixed row/column regardless of the data domain — e.g. `parallel_coordinate`'s three fixed label/tick rows at pixel `0`/`150`/`300`). A `tick`/`text` layer whose own `x`/`y` encoding is such a value def (typically inherited down from a parent layer group's shared encoding) was previously always resolved through `ctx.x`/`ctx.y` — the chart-wide, field-based axis, usually inherited from an unrelated sibling layer — scattering every row across that axis' whole range instead of pinning them all to the one intended pixel row. A literal value def now resolves to a new `OverlayPixelPosition` (`{pixel: N}`) that `scalePosition` (`overlays/scaleUtils.ts`) recognizes and passes through unchanged, bypassing the data scale entirely, instead of being (mis)coerced through it.
- **A `tick` mark's explicit `mark.size` (its length in pixels) is honored instead of always being derived from the categorical-axis bandwidth (`marks/point.ts`, `overlays/Segments.tsx`).** Vega-Lite's `tick` mark `size` is a length in pixels (unlike point/circle's area-like `size`) — `parallel_coordinate`'s ticks set an explicit `size: 8` so a short, narrow tick doesn't visually collide with the adjacent value label — but the wrapper's degenerate-segment tick renderer always computed its own expansion length from a fraction of the categorical axis's bandwidth, ignoring `mark.size` entirely. An explicit size now flows through as `OverlaySegment.tickLength`, which `Segments.tsx` uses verbatim in place of its bandwidth-ratio default when present.
- **A bracket-indexed array field path (e.g. `"ranges[2]"`) now resolves to a row's array element instead of always reading `undefined` (`compile/fieldTypes.ts` `resolveFieldPath`).** Vega-Lite's field-path grammar allows a field reference into a nested/array-valued property (`facet_bullet`'s bullet-chart idiom reads each row's `ranges`/`measures`/`markers` array fields by index: `ranges[2]`, `measures[0]`, …) — every row-value lookup across the wrapper (`marks/bar.ts`, `marks/point.ts`'s axis-value resolution, `compile/scales.ts`'s domain computation, `compile/fieldTypes.ts`'s type inference) did a plain `row[field]` property read, which never matches a literal key like `"ranges[2]"` — every value silently resolved to `undefined`/`null` and the marks were dropped with **no gap raised at all** (`facet_bullet` rendered completely blank across all 5 facet rows). A shared resolver now parses a compound field path (dot and/or bracket-index segments) and walks the row; a bare top-level field name (the overwhelming common case) is still a single direct property read with no parsing overhead.
- **Several bar/tick layers sharing one continuous axis each resolve their OWN field, not the shared axis' single representative field (`marks/bar.ts`, `marks/point.ts`).** A composite "bullet chart" layers 5-6 marks (background range bands, measure bars, a marker tick) that all share one x-axis but each draws its value from its own distinct field — `ctx.x`/`ctx.y` (the chart-wide resolved axis) only carries one representative field for the whole shared axis, so `compileBarMark`'s `valueField` and `point.ts`'s tick `resolveAxisValue` both read that SAME field for every layer regardless of each layer's own encoding, silently drawing every bar/tick at the same value with **no gap raised**. Both now prefer this layer's own resolved field (via `fieldOf(encoding.x/y)`, or an explicit tick-only field override threaded through `resolveCandidates`), falling back to the shared axis' field only when this layer's own encoding has none of its own (e.g. an aggregate/bin channel, whose renamed output field only the shared axis reliably reflects).
- **A boxplot's `mark.box: false` now genuinely hides the box (IQR rectangle) sub-mark (`marks/boxplot.ts`, `overlays/BoxPlot.tsx`).** The box/median/rule/ticks/outliers sub-marks were previously treated asymmetrically: `median`/`rule`/`ticks`/`outliers` already supported `false` to hide that piece (`OverlayBoxSubMark | false`), but `box` was hardcoded as the overlay's "primary glyph" and reported an `ignored` gap instead — even though nothing about the custom overlay actually required drawing it (the whiskers/median/outliers already render as independent SVG elements, not derived from the box rect). `box` now carries the same `OverlayBoxSubMark | false` type as its siblings, and `BoxPlot.tsx` simply skips the `<rect>` when it's `false`, leaving the rest of the glyph to render normally, matching Vega-Lite's own composite-mark semantics with no approximation and no gap.
- **A discretizing (`quantile`/`quantize`/`threshold`) `size` scale is now implemented directly instead of always falling back to the continuous sqrt scale (`marks/point.ts` `buildDiscretizingSizeMap`).** These Vega-Lite scale types bucket a field's domain into a fixed number of bands, each with its own explicit size — a shape `@mui/x-charts`' `sizeMap` already expresses natively via a `{type: 'piecewise', thresholds, sizes}` config (a plain `d3.scaleThreshold`), so this was a missing case, not an actual x-charts limitation. `threshold`'s `scale.domain` is read verbatim as the band boundaries (one fewer entry than `range`); `quantize` slices `[domainMin, domainMax]` into equal-WIDTH bands; `quantile` slices the field's actual sorted data values into equal-COUNT bands via the same linear-interpolation `quantile()` helper backing the `median`/`q1`/`q3` aggregate ops. Each band's `range` entry (a symbol area, per Vega-Lite's `size` semantics) converts to a marker radius the same way the continuous case's endpoints do (`r = sqrt(area / π)`). A malformed `range` (not a plain array of ≥2 numbers) or, for `threshold`, a malformed `domain` (not exactly `range.length - 1` numbers) still falls back to the default continuous scale with an honest `partial` gap explaining why, instead of either silently misreading it or blanket-refusing every discretizing scale regardless of whether it was well-formed. `concat_bar_scales_discretize`'s own point/circle marks still don't render — a separate, pre-existing `mark:point-missing-axis` gap, since each panel encodes only `y` (no `x` at all) and x-charts' scatter series needs both — but the size-scale mapping itself is now correct wherever a point mark's positional channels do resolve.
- **A discrete axis `sort` by another field or encoding channel now actually ranks the domain instead of always degrading to ascending (`compile/scales.ts` `applySort`/`resolveSortField`/`sortKeyForCategory`).** Vega-Lite supports two "sort by value" shapes beyond a plain `ascending`/`descending`/explicit-array sort: an object `{field, op, order}` (rank by an aggregate of another field), and a compact channel-shorthand string (`"x"`/`"-x"`/`"color"`/…, `-` prefix for descending) that ranks by another encoding channel's own value. Both previously fell straight through to a blanket `scale:sort-by-field` gap regardless of whether they were well-formed and resolvable. The object form now aggregates every row sharing each category via the existing `evaluateAggregate` helper (the same one backing the `aggregate` transform); the channel-shorthand form resolves the referenced channel's field from the shared unit encoding — already rewritten by the encoding-transform pass, so a channel-level `aggregate` (e.g. `bar_aggregate_sort_by_encoding`'s `x: {aggregate: 'sum', field: 'people'}`) is already collapsed to one row per category by the time this runs, needing no separate aggregation of its own. A sort that still can't be resolved (no `field`, or a channel name nothing in the chart actually encodes) keeps the honest `scale:sort-by-field` `partial` gap and falls back to data order, same as before.
- **A `lookup` transform's `from.data.name` (a named secondary dataset) now resolves instead of always reporting an `unsupported` gap (`transforms/lookup.ts`, `normalize/index.ts`).** Named datasets were already resolved for the chart's PRIMARY data source (a spec's own inline `datasets` map merged with the host-provided `datasets` prop), but that merged map was a private local inside `normalizeSpec`, never exposed — so a `lookup` transform referencing one by name had no way to look it up, even though the exact same rows were available elsewhere in the pipeline for the main data. The merge is now exposed as `NormalizedSpec.datasets` and threaded through `applyTransforms`/`applyLookupTransform`, so `from.data.name` resolves the same way the primary data source's `data.name` does (inline `values` still wins if a spec somehow gives both); a named topojson secondary dataset reuses the same feature-per-row conversion inline topojson `values` already got. Only `url` (a genuine remote fetch) remains an unsupported gap; a name absent from both the spec's own `datasets` and the host-provided `datasets` prop still reports `transform:lookup-named-dataset` and passes rows through with defaults, same as before.

| `loess`         | ✅ supported               | `transforms/loess.ts`. Full LOESS (Cleveland's algorithm): a tricube-weighted linear fit at each point over its `span` (`max(2, ceil(bandwidth · n))`, default `bandwidth: 0.3`) nearest x-neighbors, refined by two bisquare-weighted robustness iterations. Groups with fewer than 3 valid points pass through unsmoothed (no gap — too little data to fit, not a translation failure).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `impute`        | ❌ unsupported (all tiers) | Missing-value imputation has no x-charts equivalent. Workaround: impute before passing data.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `flatten`       | ❌ unsupported (all tiers) | Nested array flattening has no x-charts equivalent. Workaround: flatten before passing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `sample`        | ❌ unsupported (all tiers) | Stochastic row sampling has no x-charts equivalent. Workaround: sample before passing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `quantile`      | ✅ supported               | `transforms/quantile.ts`. Per-group quantile curves reusing the shared linear-interpolation `quantile()` helper (the same one behind the `median`/`q1`/`q3` aggregate ops). `probs` defaults to a generated series from `step` (default `0.01`): `step/2, step/2 + step, …` while `< 1`. Groups with no numeric values emit nothing (not a gap — an empty curve for an empty group is expected).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

All of the remaining `KNOWN_UNSUPPORTED_TRANSFORMS` (`transforms/index.ts`: `sample`, `stack`, `impute`, `flatten`) plus any other unrecognized top-level transform key report `transform:<kind>` as an `unsupported` gap and are skipped, leaving downstream rows unmodified by that step.

## Scales & axes

### Scale types

`compile/scales.ts` `resolveChannelAxis` resolves positional (x/y) scales. Temporal data on a continuous-friendly mark (line/area/point/tick) defaults to a continuous `time`/`utc` scale, so points are spaced by real date distance. It falls back to a discrete band/point scale over the sorted date domain (with a `partial` gap, `scale:temporal-point-approximation`) for occurrence/band marks (`bar`/`rect`/`boxplot`/`errorbar`/`rule` — the `BAND_SCALE_MARKS` set), an explicit discrete `scale.type`, or a non-ascending `sort`.

| Scale type                                           | Status       | Notes                                                                                                                                                                                                                                                                                                                                   |
| :--------------------------------------------------- | :----------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `linear`                                             | ✅ supported | Default for quantitative axes.                                                                                                                                                                                                                                                                                                          |
| `log`                                                | ✅ supported | Logarithmic scale.                                                                                                                                                                                                                                                                                                                      |
| `pow`                                                | ⚠️ partial   | Scale type maps through, but `scale.exponent` is declared in the `VegaScale` type and never read by `resolveChannelAxis` — the x-charts default exponent is always used, not the spec's value.                                                                                                                                          |
| `sqrt`                                               | ✅ supported | Square-root scale.                                                                                                                                                                                                                                                                                                                      |
| `symlog`                                             | ✅ supported | Scale type maps through, and a numeric `scale.constant` (the symlog linear-region constant) is now forwarded to the x-charts symlog `constant` (`compile/scales.ts`); it is read only on `symlog`, ignored for other scale types.                                                                                                       |
| `time` / `utc`                                       | ✅ supported | Continuous time scale (`scaleType: 'time'`) by default on continuous-friendly marks; `min`/`max` come from `scale.domain` (`domainMin`/`domainMax` and `{unionWith}` object domains are ignored — `partial`). Falls back to a discrete band/point scale for occurrence marks / explicit discrete type / non-ascending sort (see above). |
| `band`                                               | ✅ supported | Categorical; used by default for occurrence marks — `bar`/`rect`/`boxplot`/`errorbar`/`rule` (`BAND_SCALE_MARKS` via `channelNeedsBandScale` in `compile/scales.ts`).                                                                                                                                                                   |
| `point`                                              | ✅ supported | Categorical; used by default for non-bar marks.                                                                                                                                                                                                                                                                                         |
| `ordinal`                                            | ✅ supported | An explicit `scale.type: 'ordinal'` maps to x-charts' `band` scale (`explicitDiscreteScaleType`), matching Vega's own convention that an ordinal position scale is a band scale. | Unsupported types (e.g., `sequential`, custom names) | ⚠️ partial   | An unrecognized `scale.type` string falls back to `linear` with a `partial` gap (`scale:<type>`) — the chart still renders (with the wrong scale semantics), it does not drop the axis.                                                                                                                                                 |

## Known remaining visual approximations

These render but don't yet match the reference pixel-for-pixel. They are limitations of the current wrapper/render target, not silent failures, and are listed so they aren't lost:

- **Concat views don't share scales.** A marginal-histogram concat (`concat_marginal_histograms`) positions its top/right histograms beside the heatmap and sizes each leaf's default plot dimension the same way Vega-Lite does (`facet/index.ts`'s `VEGA_DEFAULT_VIEW = 200`, matching every child view's real compiled size under `vega-embed`'s constrained rendering), so a shared plot width/height lines the panels up in the common case — but Vega-Lite still literally shares one _scale instance_ (and thus one exact domain) across concat cells, which this wrapper doesn't do; a concat whose cells would otherwise need genuinely different plot sizes to align (rather than the same default) can still drift.
- **Text over a continuous-x axis.** A `text` mark layered on a continuous quantitative x (e.g. the CO2 chart's end-of-line decade labels, positioned at an `argmin`/`argmax` of the x field) is not placed — the text overlay resolves positions against a discrete category axis, so continuous-x labels are dropped. The line itself renders correctly.
- **A trellis's shared right-side histogram can render with no visible bars.** `concat_marginal_histograms`' right-side marginal histogram (a `bar` mark with a binned `y` and an aggregated `x`) renders its axes but no bars — pre-existing, reproduces identically with `VEGA_DEFAULT_VIEW` at both 200 and 300, so it isn't a sizing regression; likely a transposed-axis case `marks/bar.ts` doesn't fully handle. Not yet root-caused.
- **Facet domain includes empty categories / excludes null.** A wrapping facet derives its cell values from the data's distinct field values, so an empty category can still get a (blank) cell while a `null`-valued group is dropped — the reference sometimes does the opposite (`trellis_scatter`'s `null` vs `NC-17` panels).
- **Continuous color legend has no interior tick marks.** x-charts' `ContinuousColorLegend` only draws min/max labels at the ends of the gradient bar; Vega-Lite's own continuous legend also draws evenly-spaced interior ticks (e.g. `10.0%`/`20.0%` along a choropleth's rate legend). The gradient bar itself (color, direction, length) matches; the interior tick marks would need a custom legend component to add, which no gallery chart currently has.
- **`wheat_wages` (7-layer bar + area/line + ranged-rect timeline) is much improved but not pixel-perfect.** The bar histogram, area, and line layers now render correctly, and the monarch-reign highlight rects resolve against the shared band scale (see the `rect` mark's ranged-rect support above). The x-axis is still denser/less legible than the reference — it's forcing a ~250-year continuous year domain onto a discrete band scale (one tick per distinct year value in the data, not an evenly-spaced continuous tick set) — and the monarch-timeline rect labels are visually cramped. This is a separate, deeper band-vs-continuous-axis approximation beyond the scope of the ranged-rect fix itself.
- **`airport_connections`'s flight-path rules render every route instead of just the hovered one.** Its `rule` layer's `transform` filters to a point-selection parameter (an interactive "show only this airport's routes on hover" pattern); the filter transform can't evaluate a selection-parameter predicate and fails open (`filter:unsupported-shape`, keeping every row) rather than the empty/hover-scoped set Vega-Lite's own reference shows before any interaction. The `rule`/`point` marks themselves now translate and position correctly (see the geo-projected marks row above) — this is a pre-existing, separate limitation in the filter transform's handling of selection predicates, not specific to geo rules.
- **`parallel_coordinate`'s top (max-value) label row shows minor rendering fringing at the exact plot boundary.** Now that the tick/text value-def fix (above) correctly pins the top row to pixel `0` — the literal top edge of the plotting area — a vertically-centered label sitting exactly on that boundary renders with some antialiasing/edge artifacting the reference doesn't show (the reference draws it into the surrounding margin, unclipped). The mid/min rows (pixel `150`/`300`, safely inside the plot) render cleanly. This looks like an inherent edge-of-domain rendering nuance rather than anything the wrapper's own overlay compilation controls, and wasn't chased further given the "never edit `x-charts` core" boundary.
- **`facet_bullet`'s layered range/measure/marker bars render grouped (offset side by side) instead of fully overlaid on the same row.** Now that the bracket-index field-path and per-layer field fixes (above) make every layer resolve its own correct value, all 6 layers per facet row share one synthetic single-category axis — Vega-Lite's `layer` composition draws each independently on the exact same plot rectangle, back-to-front by z-order (a wide light-gray range band, a narrower medium-gray band, a narrower dark-gray band, then the two measure bars, then the tick), producing the classic bullet-chart look of one bar overlaid on the widest. x-charts' native `bar`/`rangeBar` series instead auto-offset multiple series sharing one category band side by side (grouped-bar semantics), so the wrapper currently renders 6 parallel bars stacked down the row rather than 6 concentric bars on top of each other. The values, colors, and axis domain are all correct; only this z-order-overlay-vs-offset-group layout differs. Fixing this would need a way to force multiple bar series onto the exact same band position (or a custom-overlay fallback for this specific "several bar layers, one shared synthetic category" shape), which is a distinct, deeper change beyond the scope of the field-resolution fixes above.

## How gaps are reported at runtime

When the wrapper encounters untranslatable Vega-Lite features, it collects them as `TranslationGap` objects and returns them via the `onGaps` prop. Each gap has a `code` (e.g., `mark:geoshape`, `encoding:facet`), a human-readable `message` (often including workarounds and tier pointers), a `severity` (unsupported/partial/ignored), and optionally a `path` into the input spec (e.g., `layer[0].encoding.color`).

Example usage:

```tsx
import { VegaLiteChart } from '@mui/x-charts-vega';

const spec = {
  mark: 'point',
  encoding: {
    x: { field: 'a', type: 'quantitative' },
    y: { field: 'b', type: 'quantitative' },
    shape: { field: 'c', type: 'nominal' },
  },
};

const [gaps, setGaps] = useState([]);

<VegaLiteChart spec={spec} onGaps={setGaps} />;

// gaps[0].code === 'encoding:shape'
// gaps[0].severity === 'ignored'
// gaps[0].origin === 'x-charts'   // x-charts scatter markers are visually uniform
```

Render gaps as warnings in your UI, or use them to fall back to a different visualization. The wrapper always attempts a best-effort render even when gaps are present.
