# Architecture

Internal reference for how `@mui/x-studio-ai-middleware` is put together. For install/quick-start, see [`README.md`](./README.md).

## Overview

This package is a framework-agnostic, pure-function server-side handler for the MUI X Studio AI assistant. It has no HTTP framework dependency and no LLM vendor SDK — every model call goes through raw `fetch` against an **OpenAI-compatible chat-completions endpoint** (`stream: true`, tool calling via `tools`/`tool_choice`), so any provider reachable through an OpenAI-compatible gateway/proxy works, including non-OpenAI models fronted by one.

Two independent surfaces share the same core tool logic:

- **Chat (SSE)**: `handleAIChat` → `runAgenticLoop` — a streaming, multi-turn agentic loop driven by the LLM.
- **MCP**: `buildStudioMcpServer` — exposes the same tools/state directly to any MCP client (e.g. an IDE agent), independent of the chat loop.

Both dispatch every state-mutating tool call through the same two-layer core: `executeToolOnState` (which computes the state transformation) wrapped by `toolPolicy.ts`'s authorization chokepoint. `executeToolOnState` delegates the actual state transformation to `applyMutation` — a pure reducer shared with the client via `@mui/x-studio-schema`. That reducer is the single source of truth for what a tool call does to `StudioState`; both transports (and the browser client) compute identical results from identical inputs.

Runtime dependency: `@mui/x-studio-schema` (workspace package — the shared, zero-dependency data model and mutation reducer). Dev-only dependencies: `@mui/x-chat-headless` (only for the `ChatMessage` type) and `@modelcontextprotocol/sdk` (only `buildStudioMcpServer` and its `mcp/` handlers use it functionally). Note, however, that importing the package root loads the SDK unconditionally: `src/index.ts` statically re-exports from `./mcp`, which value-imports `@modelcontextprotocol/sdk`, so even a chat-only consumer that never calls `buildStudioMcpServer` pulls the SDK in at import time. Making the SDK load lazily would require a lazy-import / subpath-export change that is intentionally not made.

## Public API surface (`src/index.ts`)

- Chat handler: `handleAIChat` (+ `StudioAIHandlerOptions`, `StudioAIContextEnricher(Args)`)
- Non-streaming handlers: `handleGenerateTitle`, `handleCreateWidget` (from `handleGenerateInsight.ts`)
- Protocol types: `StudioAIRequest`, `StudioAISSEEvent`, `StudioAISkill`, `SkillExecuteResult`, `SerializableSkill`, `StateMutation`, `MutationEnvelope`, `StudioAIToolName`, `StudioAIDataConfig`, rate-limit/usage/rich-context types
- Prompt/tools: `buildAISystemPrompt`, `serializeFieldForAI`, `sanitizeForPrompt`, `buildPageLayoutContext`, `STUDIO_AI_TOOLS`, `WIDGET_CONFIG_DESCRIPTION`
- Built-in skills: `dashboardNarratorSkill`, `insightSuggestorSkill` — the only two skills defined in `studioSkills.ts`; both are `instruction-only` (no callable tool)
- `generateFieldDescriptions`, `renderChartSvg`, `createDefaultWidget`
- Lower-level primitives for custom loops: `runAgenticLoop`, `executeToolOnState`, `PendingApproval` (the `approvalPending` map's value type — a resolver bound to the AI chat thread it was raised under, shared by `StudioAIHandlerOptions.approvalPending` and `AgenticLoopOptions.approvalPending`, updated in lockstep with `toolDispatch.ts`'s `waitForApproval` when its shape changes), `isApprovalThreadIdAuthorized` (the thread-binding check a host's approval-resolution route should reuse rather than hand-roll — denies a resolution when the pending entry has a `threadId` but the resolving request's is missing or mismatched)
- Tool policy chokepoint: `computeToolEffects`, `createDefaultToolPolicy`, `createEffectsAwareToolPolicy`, `executeToolWithPolicy`, `Policy` (the composable decision combinators), `consultToolPolicyArgsOnly` (the args-only authorization consult custom loops use to gate a side-effectful tool BEFORE it runs) (+ `ToolPolicy`, `ToolPolicyContext`, `ToolPolicyDecision`, `ToolEffectSummary`, `ExecuteToolWithPolicyResult`) — `Policy`/`consultToolPolicyArgsOnly` are now exported from the package root so a host composing policies or gating a custom loop needs no forbidden deep import
- MCP: `buildStudioMcpServer` + associated types, `createDefaultStudioState`

## Shared schema dependency: `@mui/x-studio-schema`

`@mui/x-studio-schema` (`packages/x-studio-schema`) is a separate workspace package with **zero runtime dependencies** — no React, no Node built-ins — importable from both a browser bundle (`@mui/x-studio`) and this server package. It is the single place the `StudioState` shape and its associated pure logic live, so the client and the AI middleware share one definition instead of maintaining independent copies.

`StudioState` (`stateTypes.ts`) is partitioned by lifetime into three top-level slices:

- **`doc`** (`StudioDoc`) — the user-authored dashboard document: `dashboard`, `pages`, `widgets`, `relationships`, `filters` (including session-flavoured cross-filter entries, which the reducer manipulates and which are stripped only at the persistence boundary), `expressionFields`, and optional `filterPresets`/`ai`. This is the ONLY partition that is persisted, undoable, and mutated by the shared reducer.
- **`session`** (`StudioSession`) — ephemeral UI state (`mode`, `shell`). Never persisted, never undoable, never touched by the reducer (a view↔edit switch is not a dashboard edit, so undo must never flip it).
- **`runtime`** (`StudioRuntime`) — host-injected `dataSources` (their rows are never persisted). Never undoable, never reducer-mutated (an undo must never revert live sources to stale rows).

### How this package consumes the partitions

Every structural field a tool reads or writes lives under `state.doc.*` (e.g. `state.doc.dashboard.activePageId`, `state.doc.widgets`, `state.doc.pages`, `state.doc.filters`, `state.doc.ai?.activeThreadId`), and data-source lookups go through `state.runtime.dataSources`. `applyMutation` reads and writes exclusively through `state.doc`; `session`/`runtime` pass through untouched.

- The **chat prompt builder** (`buildAISystemPrompt.ts`) reads all three: `state.doc` for pages/widgets/filters, `state.runtime.dataSources` for the data-source catalogue, and `state.session.mode` for the "Mode: view/edit" line.
- **`executeToolOnState`** reads/writes only `state.doc.*` and reads `state.runtime.dataSources`; it never writes `runtime` or `session`.
- **`get_dashboard_state`** returns `{ doc, dataSources }` where `dataSources` is `state.runtime.dataSources` projected down to AI-safe metadata (`rows`/`adapter` stripped, distinct values capped) — never raw rows, so the read cannot leak live data or defeat `privateMode`. `doc.ai` (the cross-thread AI chat history partition) is likewise reduced to per-thread metadata (`{ id, name, updatedAt, messageCount }`, no `messages`), since a thread's full transcript is not needed by the model beyond the active thread it already sees as its own message array.
- The **MCP box** (`StudioStateBox`) holds the FULL partitioned `StudioState`; handlers read `stateBox.current.doc.*` and `stateBox.current.runtime.dataSources[sourceId]`. The `studio://dashboard/state` resource does NOT emit the box verbatim: it calls the SAME `projectStateForAI(state)` helper (`executeToolOnState.ts`, a sibling of `projectDataSourceMetadata`) the `get_dashboard_state` tool calls, so the `{ doc, dataSources }` redaction contract — data sources stripped/capped, `doc.ai` reduced to thread metadata — lives in exactly one place and the two read surfaces cannot drift.

See `@mui/x-studio-schema`'s own `ARCHITECTURE.md` for the full partition design; the above is only this package's usage of it.

It exports:

- All `StudioState` data-model types: `baseTypes.ts`, `dataTypes.ts`, `widgetTypes.ts`, `expressionTypes.ts`, `stateTypes.ts`
- AI-protocol types (`aiTypes.ts`): `SerializableSkill`, `StateMutation`, `MutationEnvelope`, `createMutationEnvelope`, `StudioAIToolName`, `StudioAIRichContext` and its constituent types, and the persisted `StudioAIState`/`StudioAIChatThread` conversation types
- `createDefaultWidget`, `createWidgetId`, `createDefaultStudioState` (`factories.ts`) — shared so AI-created and UI-created widgets get identical defaults and the same collision-resistant id scheme. `createDefaultStudioState(overrides?)` seeds a fresh partitioned `StudioState`; its `overrides` are a nested bag keyed by partition (`{ doc?, session?, runtime? }`) so a field is never silently mis-routed to the wrong slice
- `STUDIO_AI_TOOL_REGISTRY`, `StudioAIToolFacts` (`aiToolRegistry.ts`) — the declarative registry of per-tool FACTS (display `title`, `destructive`/`mcpDestructiveOverride`, MCP `readOnly`/`idempotent`/`openWorld` hints, `privateModeExcluded`, `mcpSupported`) keyed by tool name. Not implementations or JSON-schema parameter definitions — only classification/availability facts. `StudioAIToolName` is the union of its keys. It is the single source both packages derive from, so `DESTRUCTIVE_TOOLS`, `MCP_UNSUPPORTED_TOOLS`, `PRIVATE_MODE_EXCLUDED_TOOLS`, `TOOL_TITLES`/`TOOL_ANNOTATIONS` can no longer disagree about one tool
- `detectAnomaliesIQR` (`anomalyDetection.ts`) — the Tukey-IQR outlier check used by `summarise_page`'s time-series anomaly detection, on both the client and the MCP `summarise_page` handler (`mcp/summarisePage.ts`)
- `truncateToPeriod`, `isoWeek` (`temporalUtils.ts`) — the date-bucketing helpers `summarise_page`'s time-series aggregation uses to group rows into day/week/month/etc. periods, imported directly by `mcp/summarisePage.ts` rather than mirrored locally
- `applyMutation`, `mutationLabel` (`applyMutation.ts`) — see below
- `getAllowedConfigKeys`/`validateConfigKeysForKind` and `getAllowedChartConfigKeys`/`validateChartConfigKeysForType` (`configKeyValidation.ts`) — write-side key allow-lists, one layer per union: per widget kind, and, one level finer, per chart type. `isWidgetOfKind`, `resolveChartType`/`isChartConfigOfType`/`isStudioChartType`/`STUDIO_CHART_TYPES` (`widgetTypeGuards.ts`) — the matching runtime narrowing/membership helpers for `StudioWidget` (by kind) and `StudioChartWidgetConfig` (by chart type). See `@mui/x-studio-schema`'s own `ARCHITECTURE.md` for the full design; see "Tool execution / state mutation model" below for how this package wires them into `executeToolOnState.ts` and `buildAISystemPrompt.ts`.

Server-only AI types (`StudioAISkill` with its `execute` function, `SkillExecuteResult`, `StudioAIDataConfig`, rate-limit/usage/enriched-context types, and the `query_data_source` data-query types) are **not** part of the shared schema — they live in this package's `models/aiTypes.ts`. `models/studioTypes.ts` and `widgetFactory.ts` are thin re-export shims over `@mui/x-studio-schema` so pre-existing internal import paths keep working without a repo-wide rename.

### `applyMutation` — the single mutation reducer

`applyMutation(state: StudioState, mutation: StateMutation): StudioState` (`packages/x-studio-schema/src/applyMutation.ts`) delegates to an internal `applyDocMutation(state.doc, mutation)` and reassembles `{ ...state, doc: nextDoc }` (returning the same `StudioState` reference untouched when the doc is unchanged, so a no-op mutation preserves reference identity; `session`/`runtime` always pass through). `applyDocMutation` dispatches through a `MUTATION_HANDLERS` table keyed by `mutation.type`, covering every `StateMutation` variant (`addPage`, `setDashboardTitle`, `addWidget`, `updateWidget`, `removeWidget`, `setWidgetLayout`, `setWidgetColSpan`, `renamePage`, `removePage`, `setActivePage`, `addFilter`, `removeFilter`, `applyBulkUpdate`, `renameAIThread`). Each entry co-locates its `apply` (a `StudioDoc → StudioDoc` transition) and `label` (human-readable log line) logic, so the two can never drift apart; the table's mapped type makes a variant missing a handler a compile error. At runtime, an unrecognized `mutation.type` is a graceful no-op rather than a throw.

Both transports use this same function for the state-transformation step:

- `executeToolOnState.ts` computes `nextState = applyMutation(state, mutation)` on the server, threading it across tool calls in the same turn and, for MCP, across the whole `StudioStateBox` session.
- The client applies the identical function inside `StudioController.applyExternalMutation` when a `state-mutation` SSE event arrives.

Notable semantics baked into the reducer:

- `removePage` performs full cleanup matching `StudioController.removePage`: it drops the page, removes every widget that lived on it, drops page-scoped filters that targeted it, and reassigns `doc.dashboard.activePageId` to another remaining page (or `''`) when the removed page was active.
- `removeWidget` drops the widget from every page's `widgetRows` (removing now-empty rows) and drops filters that only made sense while the widget existed (its own widget-scoped filters, and interactive cross-filters it emitted).
- `addWidget` takes an explicit, server-chosen target `pageId` in `mutation.args` (falling back to the applying side's active page only for legacy payloads without one) — this guarantees the widget lands on the same page the model was told about, even if the client navigates elsewhere while the model is "thinking".
- `addFilter` applies the filter verbatim, without re-stamping its scope to the applying side's active page — the filter already carries its target page/widget, chosen server-side.
- `setWidgetColSpan` clamps every span to the canvas grid (`clampSpan`, `GRID_COLS = 24`, `MIN_SPAN = 6`).
- Side effects a pure reducer cannot own — undo-stack management, title inference from live data sources, React shell selection — are intentionally **not** performed here; they stay in `StudioController` on the client.

`mutationLabel(mutation)` produces a compact human-readable label (e.g. `addWidget:chart:widget-123`, `removeFilter:filter-9`) used for the AI recent-mutation log surfaced in the system prompt's `<dashboard_context>` block and MCP's `get_recent_changes` tool. `createMutationEnvelope(mutation)` wraps a `StateMutation` into the `MutationEnvelope` shape that both transports spread into each `state-mutation` SSE event.

## Core data flow: chat request lifecycle

1. Host app parses the request body into a `StudioAIRequest` and calls `handleAIChat(body, options)`, getting back a `ReadableStream<string>` to pipe as `text/event-stream` (a nullish `body` is defaulted to `{}` before the top-level destructure so this call itself never throws synchronously — the resulting empty shape is still caught by the body-shape validation in step 3 below, which runs inside the stream and reports it as a normal SSE error rather than a constructor-time exception).
2. `handleAIChat` creates an internal `AbortController` linked to any host-supplied `options.signal` **and** to the `ReadableStream`'s own `cancel()` callback, so a consumer calling `reader.cancel()` propagates into the agentic loop exactly like a host-triggered abort. The listener it registers on `options.signal` is explicitly removed — in both the stream's `finally` and in `cancel()` — rather than left to `{ once: true }` alone: `{ once: true }` only unregisters a listener once the signal actually FIRES, so a host that reuses one long-lived `AbortSignal` across many `handleAIChat` requests would otherwise accumulate one never-firing listener per request that outlives its own stream, a slow listener-accumulation leak. The effective `allowedTools`/`privateMode` overrides AND the effective skill set are deliberately NOT computed here — all three are deferred into the stream's `start()`, after validation runs (see step 3; findings F1 for `allowedTools`/`privateMode` and the earlier iter-27 relocation for skills).
3. Inside the stream's `start`, `handleAIChat` first validates the minimal request shape it's about to dereference downstream (`validateStudioAIRequestBody`: `body.messages` must be an array AND every entry must itself carry a `parts` array — the shape `toOpenAIMessages`/`agenticLoop/openaiWire.ts`'s `msg.parts.flatMap` actually iterate, so an OpenAI-shaped `{ role, content }` message with no `parts` is rejected here rather than crashing the first time the loop serializes it — and `body.dashboardState.doc`'s `dashboard`/`pages`/`widgets`/`filters` fields must all be present — the fields `toOpenAIMessages` iterates, `buildAISystemPrompt` reads (`filters.filter(...)` once an active page resolves), and `runAgenticLoop`'s `snapshotPageId` resolution (`initialState.doc.dashboard.activePageId`) dereference). A malformed body — `dashboardState` missing `doc`, a hand-built partial `StudioState` missing one of those four `doc` fields, or a `messages` entry missing `parts` — short-circuits with one actionable `MUI X Studio:`-prefixed `{type:'error'}` SSE event instead of surfacing later as an opaque native `TypeError` ("Cannot read properties of undefined" / "msg.parts.flatMap is not a function") once the loop actually dereferences the missing field. `validateStudioAIRequestBody` now also validates each `parts` ARRAY ELEMENT, not just that `parts` itself is an array (Tier 3 finding 2): every element must be an object carrying a string `type`, and a `dynamic-tool` element must additionally carry a `toolInvocation.toolCallId` string and, when present, a string `toolInvocation.toolName` (iteration 29, finding F5: `toOpenAIMessages` reads `toolName` into an OpenAI `function.name`, so a non-string value would otherwise be serialized into a malformed message and rejected by the provider with an opaque 400 when replaying history, instead of surfacing here as a clean validation error — only its TYPE is enforced, since it is optional on the wire) — the shapes `agenticLoop/openaiWire.ts`'s `toOpenAIMessages` dereferences (`p.type`, `p.toolInvocation.toolCallId`/`toolName`) when replaying history to the LLM. A malformed element (`null`, or a `dynamic-tool` part missing `toolInvocation`) previously slipped past the shallow "is `parts` an array" check and only surfaced later as that same class of opaque `TypeError`, deep inside `toOpenAIMessages` rather than at this entry gate. The check is still deliberately shallow (only the shapes that would otherwise crash), not full schema validation. The validator additionally requires `dashboardState.session` and `dashboardState.runtime.dataSources` to be present (finding F2, Tier 3) — `buildAISystemPrompt`'s `buildDashboardState` destructures `state.session.mode`/`state.runtime.dataSources` and `executeToolOnState.ts`'s `projectStateForAI` does `Object.entries(state.runtime.dataSources)`, so a body supplying a valid `doc` but omitting `session`/`runtime` previously passed validation and only crashed once the first prompt was built. Each present `dashboardState.runtime.dataSources[id]` entry is itself now shape-validated too (Iteration 30): a string `id`, a string `label`, and an array `fields` are required, since `describeSource` (`buildAISystemPrompt.ts`) unconditionally filters `source.fields` — a malformed entry previously threw an unprefixed native `TypeError` the first time the system prompt was built, masked by the outer `try`/`catch` into a generic error rather than this file's actionable `MUI X Studio:`-prefixed convention. It likewise now requires `allowedTools`, when present, to be an array of strings (rather than a bare string that `agenticLoop.ts`'s `.includes(...)` would silently treat as a substring match instead of exact tool-name membership) and `customWidgets`, when present, to be an array (a non-array value previously threw inside `buildWidgetFromArgs` the first time a widget-creating tool call read it) — the two related F2 gaps. Each `customWidgets` ELEMENT is now also validated as a plain object with a string `kind` (iteration 29, finding F4): a malformed element (`null`, or one without a `kind`) previously surfaced only as a raw `TypeError` swallowed by an outer try/catch deep in `buildAISystemPrompt.ts`'s widget-listing loop / `buildWidgetFromArgs`, rather than the actionable `MUI X Studio:`-prefixed error every other malformed field gets. It also now requires `body.pageSnapshot`, when present, to be a string (iteration 28, finding F6, Tier 3): a truthy non-string `pageSnapshot` both enables the `summarise_page` tool advertisement AND is returned VERBATIM as that tool's output, so a non-string value would land as non-string `content` in the next OpenAI turn message and be rejected by the provider with an opaque 400 — the validator turns that into a clean, actionable SSE error frame instead. It also now bounds `body.messages` itself (iteration 29, finding F2): an array over `MAX_REQUEST_MESSAGES` (1000) entries, or whose entries sum past `MAX_REQUEST_MESSAGES_TOTAL_CHARS` (2,000,000) serialized characters, is REJECTED up front (not truncated, which could silently drop the user's latest message), since the history is serialized into the first LLM request with no length/size bound of its own and the per-turn budgets are checked only after a turn completes. It also now validates `body.skills`: `undefined`, or an array of objects each carrying a string `name` — anything else is rejected with an actionable error (finding F1) rather than reaching the `effectiveSkills` computation below. Only AFTER this validation succeeds does `handleAIChat` compute the server-side overrides — `effectiveSkills`, and now `effectiveAllowedTools`/`effectivePrivateMode` too (the server-side allow-list / private-mode enforcement — see invariant 10). All three are computed here, inside `start()`, rather than before the stream was even constructed. `effectiveSkills` was relocated in iteration 27; `effectiveAllowedTools`/`effectivePrivateMode` are relocated in iteration 28 (finding F1, Tier 2) for the exact same reason: the intersection `options.allowedTools.filter((t) => body.allowedTools.includes(t))` previously ran at the top of `handleAIChat`, before validation and before the stream existed, so a truthy non-array `body.allowedTools` (`{}`, `42`, `true` — whose `.includes(...)` is `undefined`) threw a synchronous `TypeError` straight out of `handleAIChat`, violating its "always returns a stream, never throws" contract. Now the validator's "`allowedTools`, when present, must be an array of strings" check (an F2 gap above) always runs first, and a malformed value surfaces as a normal `{type:'error'}` SSE event. Downstream, `buildAISystemPrompt.ts`'s rich-context renderer (`buildRichContextBlock`) applies the same defense-in-depth stance to the client-supplied `richContext` fields it consumes (`pageLayout.rows`/`crossFilters`, `fieldStats`, `recentMutations`, `omitted`): `richContext` is only NOMINALLY typed `StudioAIRichContext`, so each section is now checked to actually be the array/plain-object shape expected before being read, and a malformed section is skipped/omitted from the rendered block entirely instead of throwing a raw `TypeError` mid-prompt-build. It then caps the validated client-supplied `dashboardState` via `capIncomingDashboardState` (iteration 29, finding F2 — see "closing the remaining persisted token-bomb caps" below; as of Iteration 30 this also caps `runtime.dataSources`, and as of Iteration 32 each widget/page/data-source's own `.id` field plus each page's `widgetRows`/`widgetColSpans` layout) BEFORE the state is used anywhere, and caps `richContext`/`customWidgets` via `capIncomingRichContext`/`capIncomingCustomWidgets` at the same chokepoint (Iteration 30 — see below), best-effort runs `options.contextEnricher` on the capped `dashboardState`/`richContext` (skipped if `privateMode`; failures are non-fatal, reported via `onToolError('contextEnricher', err)`), then calls `runAgenticLoop` with the capped `dashboardState`/`customWidgets`/`richContext`, with the capped state as the loop's starting `currentState`.
4. `runAgenticLoop` drops any `server-tool` skill whose name collides with a built-in (so a built-in name resolves only to its built-in handler), builds the system prompt once (`buildAISystemPrompt`, folding in skills/richContext/enrichedContext), composes the effective `ToolPolicy` (`Policy.all(mutationBudget, toolCallBudget, hostPolicy)`), computes the effective tool list, and converts the `ChatMessage[]` history to OpenAI-style messages via `toOpenAIMessages` (`agenticLoop/openaiWire.ts`).
5. The effective tool list is `STUDIO_AI_TOOLS` filtered by `allowedTools`, gated by `data`/`pageSnapshot` presence and by `PRIVATE_MODE_EXCLUDED_TOOLS` under `privateMode`, plus any `server-tool`-mode skill schemas. Its name set is captured as `advertisedToolNames` for the dispatch-time gate.
6. For each turn (max 10 by default, or `rateLimit.maxTurnsPerRequest`): POST to `options.endpoint` with `stream: true, stream_options: { include_usage: true }`, the fetch itself bounded by a 120s `withTimeout` wrap (`LLM_FETCH_TIMEOUT_MS`) so a hung/overloaded gateway that never resolves can't block the turn — and therefore the whole SSE stream — indefinitely; consume the response via `parseSSE`, which now ALSO bounds the read loop itself with a 60s idle timeout (`LLM_STREAM_IDLE_TIMEOUT_MS`, reset on every chunk received) — the fetch-level timeout only ever covered time-to-first-byte, so a connection that sent some bytes then stalled mid-stream (all the turn's own budgets already inert once headers arrive) previously hung indefinitely; a timeout here cancels the reader, which aborts the underlying fetch per the Streams/Fetch spec, and the read loop's `try/finally` now also cancels the reader on every OTHER exit path (a thrown error, or the caller's `for await` `break`-ing early), not just normal completion. `handleGenerateTitle`/`handleCreateWidget`/`generateFieldDescriptions.ts`'s LLM fetches now reuse this same `LLM_FETCH_TIMEOUT_MS` wrap too — previously only the main chat loop had any fetch timeout at all, so those paths could hang indefinitely on a stalled provider. The fetch-level timeout only ever bounds the wait for HEADERS to arrive, though — a gateway that sends headers (a non-2xx status, or a 2xx it then never finishes) and then stalls the BODY would previously hang the read forever even with the fetch itself timed out. Every body read that happens after headers arrive is now wrapped in the same `withTimeout`/`LLM_FETCH_TIMEOUT_MS` pattern: `agenticLoop.ts`'s non-2xx error branch (`response.text()`, falling back to `statusText` if the timeout or a genuine read error fires), and both `generateFieldDescriptions.ts` and `handleGenerateInsight.ts`'s `handleGenerateTitle`/`handleCreateWidget` calls (their error-body `response.text()` reads and their success-body `response.json()` reads alike) — closing a class of hang where a gateway that sends headers then stalls the body left every one of these non-streaming call sites stuck indefinitely. `parseSSE`'s own idle-timeout (below) is the equivalent protection for the STREAMING chat path's body; read each chunk's `choice.delta` defensively as `choice.delta ?? {}`, since a finish-reason-only chunk — real behavior on some OpenAI-compatible gateways — can omit the `delta` key entirely, and reading it unguarded previously threw a raw `TypeError` mid-stream instead of degrading gracefully; yield `text-delta` events as they arrive; accumulate tool-call fragments via `accumulateToolCallDeltas` keyed by index (falling back to a per-`id` synthetic index — seeded from `SYNTHETIC_INDEX_BASE` so it can never collide with a real `index: 0` — when a provider's deltas carry an `id` but never an `index`). Per-turn usage is captured **from the last usage-bearing chunk** (assign-from-last-seen), not summed across chunks, then folded into the cumulative `usage` once at turn end (T3-4b): the OpenAI contract emits usage once in the final chunk, but some gateways repeat a CUMULATIVE usage on every chunk, and summing those would multiply the true token count by the chunk count and trip `maxTokensPerRequest` far too early. After accumulation, any tool call the provider left un-id'd (the accumulator seeds `id: ''`) is given a synthetic id via `crypto.randomUUID()` (T3-5, hardened from an earlier `call-${turn}-${idx}` scheme) so two un-id'd calls in one turn stay independently addressable — otherwise both would address as `toolCallId: ''` and the second would be wrongly rejected by the approval-dispatch duplicate guard. Unlike the sequential scheme, a `randomUUID()` id is also unguessable: this same id becomes the key into the shared `approvalPending` map for destructive tools (see "Agentic loop internals" below), so a predictable, enumerable id would let anyone who observed a few requests predict — and resolve or deny — another in-flight request's pending approval.
7. **No tool calls** → yield `message-metadata`, `usage`, `finish`, generator returns (conversation done). **Tool calls present** → the loop parses each call's `arguments` buffer and hands it (with an `argsParseFailed` flag) to `dispatchToolCall` (`agenticLoop/toolDispatch.ts`), an async generator that owns the full per-call dispatch decision and forwards its side-effect events (`state-mutation`, `tool-approval-request`) up to the loop; the loop performs the single `tool-activity` (`start`→`complete`) + tool-result pairing for every path. See "Agentic loop internals" and "Tool policy chokepoint" for the dispatch and gating detail.
8. Token budget exceeded (`usage.inputTokens + usage.outputTokens >= rateLimit.maxTokensPerRequest`) or `maxTurns` exhausted → `rateLimit.onLimitReached('tokens' | 'turns', usage)` then an `error` SSE event. An `AbortSignal` firing at any point (fetch, SSE read, or approval wait) → silent return, no `error` event. **Known limitation, documented in a comment at the check rather than fixed:** this budget is only as good as the usage data the provider actually sends — `usage.inputTokens`/`usage.outputTokens` are populated entirely from `stream_options: { include_usage: true }` chunks (step 6), so a gateway that omits usage chunks altogether leaves them at their initial value and the check silently never trips; the only remaining bound on spend in that case is `maxTurnsPerRequest` (and, for tool calls, `maxMutationsPerRequest`/`maxToolCallsPerRequest`). No client-side token estimation (e.g. a tokenizer over `currentMessages`) is implemented as a fallback — that would be the full fix, but is out of scope here.
9. `handleAIChat` encodes each yielded `StudioAISSEEvent` as `data: ${JSON.stringify(event)}\n\n`, breaking the forwarding loop on `finish`/`error`; the stream always closes in a `finally`, and the top-level `try/catch` guards `controller.enqueue` against throwing if the consumer already cancelled the stream.
10. The browser client applies `state-mutation` events to its own `StudioController` and renders `text-delta`/`tool-activity`/`tool-approval-request` events live.

## Agentic loop internals (`agenticLoop/`)

`runAgenticLoop` stays in `agenticLoop.ts`; two concerns are split into `agenticLoop/` so each stays independently testable and the security-relevant dispatch logic is isolated from the mechanical wire-format code.

- **`openaiWire.ts` — pure wire-format, zero security surface.** The OpenAI chat-completions message shapes (`OpenAIMessage` union), `toOpenAIMessages(systemPrompt, messages)` (which preserves assistant text alongside tool calls and emits a placeholder tool-result for any still-pending call so the next turn never 400s on an unmatched `tool_calls` entry), and the streamed tool-call delta accumulator (`ToolCallAccumulator`, `createToolCallAccumulator`, `accumulateToolCallDeltas`, `SYNTHETIC_INDEX_BASE`, `POSITIONAL_INDEX_BASE`). Two hardenings guard the accumulator against real gateway quirks: a delta that carries NEITHER an `index` NOR an `id` falls back to its position in the chunk's `tool_calls` array, offset by `POSITIONAL_INDEX_BASE` (disjoint from both a real 0-based `index` and an id-keyed synthetic index, so the positional fallback can't collide with either and wrongly merge two distinct calls' fragments); and a gateway that resends a tool call's COMPLETE function name on every chunk (instead of streaming it incrementally) is detected — an incoming name fragment identical to what's already accumulated is treated as a repeat and not appended again, so the name doesn't come out duplicated/mangled (e.g. `remove_pageremove_page`). **Known limitation, accepted as a best-effort tradeoff (not a bug):** this equality check cannot distinguish a genuine resend from a genuinely incremental fragment that happens to be textually identical to the prefix accumulated so far (e.g. a name streamed as two identical halves, `"aa"` + `"aa"`) — the second fragment would be wrongly dropped as a "repeat." The wire carries no resend flag or expected-total-length hint that would let this be resolved precisely, and no registered `STUDIO_AI_TOOLS` name has a self-repeating shape at any plausible chunk boundary, so this never misfires in practice; it is documented at the check rather than fixed. This module does no authorization and touches no state — the split boundary is drawn so everything here is a mechanical transform that can be reasoned about without policy context. The accumulator's per-tool-call `arguments` buffer is bounded by `MAX_TOOL_CALL_ARGS_BUFFER_CHARS` (1,000,000): a delta that would push it over the ceiling errors out cleanly instead of letting a misbehaving gateway grow the buffer without limit across an unbounded number of chunks. The NUMBER of distinct tool-call slots the accumulator may hold in one turn is separately bounded by `MAX_TOOL_CALLS_PER_TURN` (1,000, finding T2-1, iteration 25): `accumulateToolCallDeltas` throws once a delta would mint a slot past the cap (an update to an already-minted slot never counts against it), following the same convention as `MAX_TOOL_CALL_ARGS_BUFFER_CHARS`/`MAX_TURN_TEXT_BUFFER_CHARS` — a gateway streaming deltas for an unbounded number of distinct indices would otherwise grow this process's memory, and the dispatch loop's per-entry work (two `tool-activity` SSE events plus a tool-result message per call), without limit within a single turn. `agenticLoop.ts` mirrors `toOpenAIMessages`'s text-preservation on the way IN, not only on replay: it buffers each turn's streamed `delta.content` fragments into `turnTextBuffer` and uses that buffer — instead of hardcoding `content: null` — as the `content` of the assistant message it appends alongside that turn's `tool_calls`, so a turn that streams both commentary and tool calls keeps the model's own text in the conversation being built, matching what `toOpenAIMessages` already did for a fully-replayed request history. `turnTextBuffer` carries the same class of bound (`MAX_TURN_TEXT_BUFFER_CHARS`, 2,000,000), one ceiling per accumulation buffer in the streaming pipeline (line buffer, tool-call-args buffer, per-turn text buffer), each erroring out rather than growing unboundedly if a gateway misbehaves.
- **`toolDispatch.ts` — approval race + per-call dispatch decision.** `waitForApproval` (the `Promise.race` of the approval callback vs. `approvalTimeoutMs` vs. the abort signal, with a cross-request duplicate-`toolCallId` guard and a `finally` that always deletes the `approvalPending` entry) now stores a `PendingApproval` (`{ resolve, threadId? }`) in the `approvalPending` map instead of a bare resolver callback: `threadId` is the request's `state.doc.ai?.activeThreadId` — the same identity `rename_thread` (`executeToolOnState.ts`) already stamps onto mutations — captured once per request and threaded down from `runAgenticLoop` alongside `snapshotPageId`. This lets a host's approval-resolution endpoint refuse a resolution presented for the wrong conversation instead of trusting a bare `toolCallId` alone, closing a gap where a predictable synthetic id let anyone who could guess or observe an id resolve or deny another request's pending approval. `threadId` is optional — a host that hasn't wired thread-id passthrough into its own approval UI can still resolve by id alone, unchanged from before — but once an entry DOES carry a `threadId`, the resolving request MUST present a matching one: the exported `isApprovalThreadIdAuthorized(entry, threadId)` helper (Tier 3 finding 5) denies the resolution when `entry.threadId` is set but the request's `threadId` is missing OR mismatched, closing a gap where the naive `entry.threadId !== undefined && threadId !== undefined && entry.threadId !== threadId` shape (previously hand-rolled at each call site) degraded to a silent no-op the moment a resolving request simply omitted `threadId` — bypassing thread-binding entirely rather than failing closed. `isApprovalThreadIdAuthorized` is wired into `toolDispatch.ts` itself, the `@example` in `handleAIChat.ts`'s `approvalPending` doc comment, and the real `/approval` route in `examples/x-studio-dev-server/src/routes/ai.ts`, so no host is left hand-rolling the bypassable version. `runApprovalFlow` (the single approval-pause implementation shared by the built-in and args-only paths — yields `tool-approval-request`, calls `waitForApproval`, honors `approvalFallback` when no `approvalPending` channel exists), `buildApprovalEffectsSummary` (T2-2 — derives an optional `ApprovalEffectsSummary` from a proposed mutation's `ToolEffectSummary` and the pre-mutation state: `willRemoveWidgets`/`willRemovePages`/`willOrphanWidgets` each carrying the entity's CURRENT title, `willRemoveFilters` ids, and `updatedWidgetCount`, all present only when non-empty; returns `undefined` when there are no structural effects). `dispatchToolCall` attaches this summary to the built-in path's `tool-approval-request` SSE event (via the new optional `effects` field on that event, `models/protocol.ts`), so a human approving a layout-affecting/removing op sees the real structural impact instead of an opaque widget-id matrix — parallel to the `effects` the MCP transport already forwards to its `approvalHandler`. Also `buildApprovalDisplayInput` (substitutes the REAL entity title from state for the model-supplied display label so the human approves against what will actually be removed — exported and reused by the MCP transport's `bridgeApproval` as of the fourteenth review's finding T2-A, so an MCP host that renders `ctx.input.widgetTitle` in its confirmation UI can no longer be tricked into approving a removal under a spoofed title, exactly as on chat), and `dispatchToolCall` itself.

`dispatchToolCall` owns the full ordered decision for one call, threading a static `ToolDispatchContext` (advertised names, policy, skills, data config, approval wiring, mutable usage counters) and returning a uniform `ToolDispatchOutcome` (`aborted` | `result`). Its order is:

1. **Parse failure** — malformed streamed `arguments` (invalid JSON) are _not_ coerced to `{}` and executed; the parse failure is fed back to the model as a tool error so it can retry, without ever running a destructive tool against wrong (empty) args. This return happens before either policy-consult chokepoint runs, so it bumps `ctx.usage.toolCalls` itself before returning — otherwise a model stuck emitting invalid JSON could retry unboundedly without ever tripping `maxToolCallsPerRequest`, since every other dispatch path only gets counted via `executeToolWithPolicy`/`consultToolPolicyArgsOnly`.
2. **Advertised-tool gate (T1-1)** — the call's `name` is checked against `advertisedToolNames`. A call to a name outside that set (e.g. a prompt-injected `remove_page` in a read-only assistant, or `query_data_source` when no `data` config exists) is rejected with `{error: "Unknown tool: <name>"}` and never reaches `executeToolOnState` — advertisement-time filtering alone cannot be bypassed. Same accounting as the parse-failure path above: this also happens before any policy consult, so it likewise bumps `ctx.usage.toolCalls` before returning, so a flood of hallucinated/injected unadvertised-tool calls can't dispatch for free against the tool-call budget.
3. **Server-tool skill** — a matching `skillHandlers` entry is consulted args-only through the policy (`consultToolPolicyArgsOnly` with `mayMutate: true`, since a skill's `execute` may return a mutation), then run under a 15s `withTimeout` wrap (`SERVER_TOOL_TIMEOUT_MS`) — the same duration and rationale as `query_data_source`'s own timeout (step 4 below) — so a hanging host-registered `execute()` (e.g. one awaiting a stuck external API call) can't block the whole agentic-loop turn indefinitely; its `mutation`/`nextState` flow through the loop the same way a built-in tool's does. A `require-approval` decision reuses `runApprovalFlow`.
4. **`query_data_source`** — consulted args-only through the policy (`mayMutate` omitted — it runs a live query but never mutates dashboard state), then dispatched through `createDataToolHandlers` (`mcp/dataTools.ts`) — the same factory the MCP transport uses — so both surfaces run identical query/validation logic (including `resolveSource`'s `allowedTables` enforcement, see "Data tools" below). The live query itself is bounded by a 15s `withTimeout` wrap (`QUERY_DATA_SOURCE_TIMEOUT_MS`), matching `mcp/summarisePage.ts`'s existing convention for bounding per-query calls, so a slow/hung DB call can't block the turn indefinitely. Returns a descriptive error if no `data` config was supplied — and, as of iteration 29 (finding F1), ALSO fails closed with a descriptive error when a `data` config IS present but `data.allowedTables` is `undefined`, refusing to resolve any source before the handlers run: on this transport the data-source catalog descends from the client-supplied request body, so a table can't be resolved safely without the host declaring an allowlist (an array, or the explicit `'*'` opt-out — see "Data tools" below). When the handler's result comes back flagged `isError`, its text is parsed for a human-readable message via `extractToolErrorMessage` (a small helper extracted for this purpose) inside its OWN try/catch, isolated from the surrounding `catch (queryErr)` that wraps the whole dispatch: today `errorResult` (`mcp/helpers.ts`) always returns JSON, but a future or misbehaving handler could return plain non-JSON error text, and parsing it inline in the outer catch would let a `JSON.parse` failure masquerade as — and overwrite — the tool's real error instead of falling back to the raw text.
5. **Unregistered skill** — a skill declared in `body.skills` but with no matching `skillHandlers` entry → a descriptive "no registered handler on the server" error. Same accounting as the parse-failure/advertised-tool-gate paths above (finding F3): this was previously the one early-return that didn't bump `ctx.usage.toolCalls` before returning, letting a declared-but-unhandled skill tool be retried for free against the budget; it now increments `ctx.usage.toolCalls` for the same reason its siblings do.
6. **Built-in tool** — runs through `executeToolWithPolicy` (execute-then-gate). `denied` → `{ error }` (mutation discarded); `needs-approval` → `runApprovalFlow` (commit on approval, discard on deny/timeout/abort); `allowed` → commit immediately. A committed mutation increments `usage.committedMutations` and yields `state-mutation` (`...createMutationEnvelope(mutation)`).

In `privateMode`, `get_dashboard_state`, `list_pages`, `summarise_page`, and `query_data_source` (`PRIVATE_MODE_EXCLUDED_TOOLS`, derived from the registry's `privateModeExcluded` fact) are excluded from the advertised tool list entirely — not merely from the `<dashboard_state>` prompt block — since their output (field distinct values, widget configs, filter values, source labels, and, for `query_data_source`, live database rows) would otherwise round-trip the withheld data back to the provider as tool output. `query_data_source` is excluded even when a `data` config is present, because private mode's guarantee is precisely that no dashboard content or query result reaches the provider. Combined with the T1-1 gate, an injected call to one of these is rejected as unadvertised rather than executed and redacted after the fact.

## Tool execution / state mutation model

`executeToolOnState(toolName, input, state, customWidgets?, pageSnapshot?, snapshotPageId?)` (`executeToolOnState.ts`) is a pure function: `(toolName, args, state) → { output, mutation?, nextState }`. `snapshotPageId` (the active page captured at request time, threaded from `runAgenticLoop`/`toolDispatch` and `executeToolWithPolicy`) lets `summarise_page` compare the requested page against the snapshot's own page identity rather than the mutated threaded active page (finding 2-2, see below). It dispatches through `TOOL_IMPLS`, an exhaustive `{ [K in StudioAIToolName]: PureToolImpl | ExternalToolImpl }` table — one entry per tool name, enforced at compile time by the mapped type. This makes tool purity a **type**, not a convention:

- **`PureToolImpl`** — `{ effect: 'pure'; plan: (args, ctx) => ToolExecutionResult }`. A pure function of `(args, ctx)` with no I/O and no shared-state mutation, safe to call speculatively (dry-run) and discard. This is the shape `toolPolicy.ts`'s execute-then-gate chokepoint depends on. For every write tool the `plan` follows the same shape: (1) validate the referenced entity exists and return a `{ error }`/`nextState: state` no-op if it's missing; (2) build a `StateMutation`; (3) `nextState = applyMutation(state, mutation)`; (4) return `{ output, mutation, nextState }`. Read-only tools (`get_dashboard_state`, `list_pages`) skip steps 2–3 and return `nextState: state`.
- **`ExternalToolImpl`** — `{ effect: 'external' }`, no `plan`. `query_data_source` is the only member: it performs I/O (a live query) and therefore must be authorized BEFORE it runs, args-only. Its real dispatch lives in `agenticLoop/toolDispatch.ts` (chat) and `mcp/queryTools.ts` (MCP); it is intentionally unreachable through `executeToolOnState` — calling `executeToolOnState('query_data_source', …)` directly falls through to the `Unknown tool` error. The entry exists purely so `TOOL_IMPLS` is exhaustive over every `StudioAIToolName`.

`get_dashboard_state`'s pure plan returns `projectStateForAI(state)` — `{ doc, dataSources }` where the authored `doc` partition has its `ai` sub-partition reduced to per-thread metadata (`{ id, name, updatedAt, messageCount }`, transcripts removed) and `dataSources` is data-source metadata projected down to `{ id, label, tableName, aiDescription, hidden, fields, fieldDistinctValues }` with `rows`/`adapter` stripped and distinct values capped (`MAX_DISTINCT_VALUES_IN_STATE_OUTPUT`). `projectStateForAI` (`executeToolOnState.ts`, a sibling export to `projectDataSourceMetadata`) is the single home for both redactions, called by this pure plan and by the `studio://dashboard/state` MCP resource, so the two read surfaces share one output contract and cannot drift; emitting raw `StudioState` would leak live rows and cross-thread chat history into the model context.

Notable per-tool behavior:

- **`add_widget`** resolves the target page as `state.doc.dashboard.activePageId` server-side and errors (`"there is no active page"`) rather than spreading an undefined page into state. Config is layered by `buildWidgetFromArgs`: `createDefaultWidget` defaults → any matching `customWidgets[].defaultConfig` → the model-supplied `config` (highest priority), with the id minted through the shared `createDefaultWidget`/`createWidgetId`. Both `add_widget` and `apply_bulk_update`'s additions build their widget through this one helper so they cannot drift. Every model-supplied stored title — dashboard, page, and widget (`buildWidgetFromArgs`, `add_page`, `set_dashboard_title`, `rename_page`, `update_widget`, and `apply_bulk_update`'s `widgetUpdates[].title`) — is capped at the write source to `MAX_TITLE_LENGTH = 200` via the shared `capTitle` helper (T3-3): these strings are re-interpolated into `<dashboard_state>` on every future request, so an unbounded title is a persistent token bomb that `sanitizeForPrompt` neutralizes for markup but not for size; the cap is larger than `rename_thread`'s 40-char limit because dashboard/widget titles are legitimately longer, but still bounded. `apply_bulk_update`'s title write was the last of these six sites to route through `capTitle` — it previously wrote `String(update.title)` verbatim, the one gap in an otherwise-uniform convention.
- **`update_widget`** applies a partial patch (`changes` + the RAW `args.config` patch), and validates model-supplied `unsetFields`/`unsetConfigKeys`: `unsetFields` is filtered to a fixed `CLEARABLE_WIDGET_FIELDS` allow-list (`sourceId`, `subtitle`, `titleMode`, `subtitleMode`), and `unsetConfigKeys` to keys actually present on the post-merge config. A `config: null` (JSON `null`, distinct from `undefined`) is normalized to **absent** up front (T3-1) rather than passed into the config-key validators, whose `Object.keys(null)`/`Object.hasOwn(null, …)` would otherwise throw a raw, unactionable `TypeError` — matching every sibling path (`buildWidgetFromArgs`'s `?? {}`, the bulk loop's truthiness gate, the reducer's non-record-config-is-absent rule). The mutation ships the raw `args.config` patch (`configPatch`), NOT a pre-merged full-config snapshot — matching `apply_bulk_update`/`set_widget_forecast` (finding 2-1). The reducer key-by-key merges the raw patch onto the LIVE widget, so a concurrent user edit to a DIFFERENT config key survives; shipping the merged snapshot would re-assert every pre-existing key at its turn-start value and silently clobber that edit. A locally-merged config is still computed, but used ONLY for the `unsetConfigKeys` presence filter (which must test against the post-merge config), never as the mutation payload.
- **`set_widget_layout`** validates the _count_, _shape_, _duplication_, and _membership_ of `rows`, in that order: the row COUNT is capped at `MAX_LAYOUT_ROWS = 200` (iteration 28, finding F3) — an over-cap array is REJECTED rather than truncated, since a truncated layout would silently orphan every widget beyond the cap, and an unbounded row array is re-flattened/re-validated on every call and, once committed, re-described in `<dashboard_state>` on every future request (the same token-bomb class the other caps guard); it must then be an array of arrays of widget-ID strings (a flat `["w1","w2"]` is rejected rather than corrupting `widgetRows`); the same id appearing in more than one cell is rejected (`"received duplicate widget IDs: …"`) before the membership check runs, since a duplicated id would otherwise place one widget in two slots and corrupt the layout; and every id must resolve to a known widget in `state.doc.widgets`. Each of the three id-list error strings (duplicate / unknown / foreign-page ids) now interpolates its offending ids through the shared `joinIdsForError` helper, which truncates to the first `MAX_IDS_IN_ERROR = 10` with a "…N more" suffix (iteration 28, finding F3) so a model sending hundreds of bad ids can't echo the whole list back as an unbounded response bomb. The resulting mutation carries `pageId: activePageId`.
- **`set_widget_width`** resolves `rowWidgetIds` from the active page's `widgetRows` and stamps `pageId: activePageId` into the `setWidgetColSpan` mutation. Its JSON-schema `columns` property (`minimum: 6, maximum: 24`) states the 24-column grid range of 6–24, matching the reducer's `clampSpan`. It now **coerces and validates `columns` at the write source** (T2-3), mirroring `set_widget_forecast.periods`: `null` is the documented reset (clears the span), a numeric value is `Number()`-coerced and `Math.trunc`-ed, and a **non-numeric** value (a string-boolean/string-number slip like `"12"`) fails closed with an actionable "must be a number between 6 and 24 (or null to reset)" error rather than falling through the bare cast to the reducer's `clampSpan`, which treats any non-finite input as `MIN_SPAN` (6) and would silently commit the minimum width while reporting `{ success: true, columns: 6 }`. Its tool output reports the value ACTUALLY applied — read back from `nextState.doc.pages[activePageId].widgetColSpans[widgetId]` after `applyMutation` runs — rather than the raw model-supplied `columns`, so a call like `columns: 100` (clamped to 24 by the reducer) is reported as `24`, not `100`; the model's world-model always matches the state that was actually committed. Before building the mutation it also checks whether the widget lives on the active page at all: a widget found on ANOTHER page hits the reducer's orphan-span guard, which silently no-ops (`return state`), so without this check the tool would read back `null` and report `{ success: true, columns: null }` for a call that changed nothing. The check now returns an actionable error naming `set_active_page` instead, mirroring the pattern `summarise_page` and `apply_bulk_update`'s "not on the active page" skip already use; a widget on NO page yet (not-yet-placed) stays permissive.
- **`apply_bulk_update`** is a single atomic operation applying removals → additions → partial updates → optional full-page relayout (references may be given by a newly-added widget's `title`, resolved to its generated id) → column-span patches, building one `applyBulkUpdate` mutation. It emits **deltas** for widgets (`removedWidgetIds`/`addedWidgets`/`updatedWidgets`) rather than a whole-`widgets` snapshot, so a concurrent edit to a different widget while the turn runs is not reverted. Layout (`widgetRows`/`widgetColSpans`) is delta-like too, but by omission rather than by shape, and the two layout fields are no longer attached as an all-or-nothing pair: `rowsChanged` (`applied.removed > 0 || applied.added > 0 || applied.layout`) and `colSpansOnly` (`!rowsChanged && applied.colSpans > 0`) pick between three shapes (ops that were requested but skipped don't count toward either). A removal / addition / accepted `layout` op genuinely reorders or re-places rows, so `rowsChanged` ships the full turn-start `widgetRows` snapshot alongside `widgetColSpans` — the new placement IS the intended one. A batch containing only `colSpans` entries changes widths, never row placement, so it ships `widgetColSpans` ONLY, omitting `widgetRows` entirely; shipping the turn-start rows snapshot there would silently revert a concurrent client-side drag-reorder or row-reassignment that happened while the turn was running (finding 2.3 — the same lost-update class T2-4 closed for updates-only batches, one case narrower, since the tool schema explicitly invites a colSpans-only call: "Only include widgets whose width should change"). The reducer (`applyMutation.ts`'s `applyBulkUpdate.apply`) reconciles a `widgetColSpans`-present/`widgetRows`-absent payload against the page's EXISTING rows rather than wiping them, so `colSpansOnly` no longer needs to ship rows to stay safe. The producer now ships **only the spans this batch actually changed** in the colSpans-only branch (T2-1), tracked in a separate `changedSpans` record as entries are accepted, rather than the full turn-start snapshot of every widget's span the `colSpans` local holds. This is the producer-side complement to the reducer's own merge (T2-2, `applyMutation.ts`'s `applyBulkUpdate` merges `{ ...(page.widgetColSpans ?? {}), ...incoming }` onto the page's existing spans): even with that merge, shipping the whole turn-start snapshot would re-assert the stale span of a widget this batch never touched, reverting a concurrent client-side drag-resize of a DIFFERENT widget on the same page — the same lost-update shape as the `widgetRows` fix above, one field over. Shipping only the changed entries is safe because bulk `colSpans` entries are numbers 6–24 and can never clear a span; it only applies when `widgetRows` is absent — a `rowsChanged` payload genuinely re-places rows and ships the full intended span map (`colSpans`) alongside them, so that branch still sends the whole snapshot. An **updates-only** batch (only `widgetUpdates`, nothing else — `rowsChanged` and `colSpansOnly` both false) omits both fields entirely, and the reducer treats true absence of both as "layout unchanged" rather than a wipe — closing the original T2-4 gap where an updates-only bulk call always shipped the turn-start layout snapshot and silently reverted any concurrent client-side drag-reorder or width change that happened while the model was thinking. Skipped operations are collected into a `skipped` array rather than thrown. Removals are scoped to the _active_ page: a removal id that exists globally but lives on a different page is reported as `"remove <id>: not on the active page"` and left untouched. `colSpans` keys are resolved through the same `addedTitleToId` map the `layout` op uses before the range check runs, so a widget added earlier in the same batch (known to the model only by title, since its id is server-minted) can have its width set in the same call rather than the entry silently landing on an unresolved id. A `colSpans` entry outside the 6–24 range (or non-numeric) is **rejected**, not clamped — unlike `set_widget_width`'s clamp-and-report — because this handler's output reports `applied.colSpans` as a per-op count, not the per-widget applied value; clamping silently here would give the model no way to learn which width it actually got, so an out-of-range span is pushed onto `skipped` (`"colSpan <ref>: <value> is out of range (must be a number 6-24)."`, `<ref>` being the original title-or-id key the model supplied) instead. Two desync classes are also closed at the same choke points: the `layout` op rejects DUPLICATE ids across rows before the membership check runs (`"layout: duplicate widget IDs: …"`), mirroring `set_widget_layout`'s own duplicate rejection — the reducer's `dedupeLayoutRows` would otherwise silently keep the first occurrence, so an accepted-looking `layout: true` could commit a different layout than the one the model believes it set; and the `colSpans` loop checks MEMBERSHIP, not just range, against `activePageWidgetIdsAfterBatch` (the active page's widget ids after this batch's removals/additions/layout are applied) — a span keyed to a phantom widget, a widget on another page, or one removed earlier in the same batch is pushed onto `skipped` (`"colSpan <ref>: widget not found."` / `"colSpan <ref>: not on the active page."`) rather than counted in `applied.colSpans`, since the reducer's `enforceLayoutColSpans` silently prunes exactly those entries on apply. Three further orphan/shape hazards are closed at the same site (findings 2-3, 2-4): (a) each of the three op arrays — `widgetRemovals`/`widgetAdditions`/`widgetUpdates` — is now **shape-validated** (`Array.isArray` plus per-element checks: removals must be strings, additions/updates must be plain records carrying the required string `kind`+`title` / `widgetId`) before iteration, just as the `layout` op already was, so a mis-shaped value (`widgetRemovals: "w1"`, `{}`, `[null]`) yields a descriptive `skipped` entry and is treated as empty instead of `for…of`-ing over characters or throwing a raw `TypeError`; (b) when the batch also carries a layout or non-empty colSpans op that resolves added-widget refs BY TITLE, a SECOND addition sharing a title is skipped (`addedTitleToId` is last-write-wins, so the ref would resolve to only one and the other would land in `doc.widgets` referenced by no page — an invisible orphan that still persists/serializes/survives undo, reported as `applied.added` success); (c) an accepted `layout` op that leaves any widget added in the same batch **unplaced** is rejected (`"layout: widgets added in this batch are not placed in the layout: …"`) — a layout op REPLACES the active page's rows wholesale, so an added-but-unplaced widget would be the same invisible orphan, reported as `applied.added` + `layout:true` success. Each of the five array/record args is independently size-capped (iteration 28, finding F2, Tier 2): `widgetRemovals`/`widgetAdditions`/`widgetUpdates`/`colSpans` at `MAX_BULK_UPDATE_OPS = 200` (entries beyond the cap are dropped and a `"…only the first 200 were processed. Split the rest into a separate apply_bulk_update call."` note is pushed onto `skipped`), and the `layout` op's row count at `MAX_LAYOUT_ROWS = 200` (finding F3) — but `layout` REJECTS the whole op when over-cap rather than truncating, since a layout op replaces the page wholesale and a truncated one would orphan every widget past the cap (the standalone `set_widget_layout` guard applies the same rule). Without these per-arg caps a single bulk call — which counts as just ONE mutation against `maxMutationsPerRequest` — could mint unbounded persisted widgets via `widgetAdditions`, a PERSISTENT token bomb since every widget is re-described in `<dashboard_state>` on every future request, plus unbounded diff work in `computeToolEffects`. The layout op's four id-list `skipped` messages (duplicate / unknown / foreign-page / unplaced-added ids) route through the same `joinIdsForError` truncation (`MAX_IDS_IN_ERROR = 10`) `set_widget_layout` uses (finding F3), and the whole `skipped` array is itself truncated to `MAX_SKIPPED_IN_OUTPUT = 20` entries (+ a `"…and N more"` marker) via `truncateSkipped` before it is echoed in the tool result (finding F2), since each rejected op appends to `skipped` and the array is echoed back verbatim.
- **`summarise_page`** on the chat path can only honor the page the client-provided `pageSnapshot` covers, whose identity is captured ONCE at request time as `snapshotPageId` (the active page when the request began) and threaded through the tool-plan context. The plan compares the requested `pageId` against `snapshotPageId`, **not** the threaded `state.doc.dashboard.activePageId` (finding 2-2): a same-turn `set_active_page(pageB)` mutates the threaded active page mid-turn, so comparing against it would let a `set_active_page(pageB)` + `summarise_page(pageB)` sequence pass the guard and return page A's snapshot narrated as page B. On a mismatch the error tells the model to send a NEW message (the snapshot cannot be rebuilt for another page within the turn), rather than to call `set_active_page` — it falls back to the threaded active page only for legacy callers that don't thread `snapshotPageId`. On the MCP path the server can query any page's sources directly, so a `pageId` argument is honored (and `summarisePage.ts`'s widget-row lookup is now `Object.hasOwn`-guarded, for parity with the pageId/sourceId guards, so a widget-row id naming an `Object.prototype` member resolves to absent rather than an inherited function).
- **`set_widget_forecast`** validates the target is a chart widget whose `chartType` is `line` or `area` before accepting the change, coerces `periods` to a positive integer (`Number(periods)`, rejecting non-finite/non-positive values with an actionable error) rather than storing the raw model-supplied value verbatim — the tool schema declares `periods` a number, but the argument is untrusted, and a non-numeric value would both produce a structurally-broken forecast config and (before `describeWidget`'s sanitize fix) round-trip into `<dashboard_state>` unescaped. `enabled` and `showConfidenceBands` are likewise strictly validated as actual booleans (`typeof x !== 'boolean'` rejects with an actionable error) rather than trusted at their declared schema type (T2-3): the schema declares both `boolean`, but a classic LLM string-boolean slip like `enabled: "false"` is truthy in JS, so a bare truthiness check would ENABLE a forecast a call meant to DISABLE while reporting success, and a non-boolean `showConfidenceBands` (e.g. `"maybe"`) would persist a string in a `boolean`-typed config field; both now fail closed instead of silently coercing the dangerous `"false"` → `true` direction. It then emits a PARTIAL config patch carrying only `{ forecast: forecastConfig }` (via `updateWidget`'s top-level `config` arg, which the reducer shallow-merges onto the widget's LIVE config) rather than a `changes.config` replacement — `changes.config` would replace the widget's config wholesale, discarding every other config key and any concurrent edit made while the turn runs.
- **`rename_thread`** rejects a missing/non-string OR whitespace-only `name` (it checks the `trim()`ed value, not just `!name` — a `"   "` is a truthy non-empty string that would otherwise commit an empty thread title, finding T3-3), then builds a `renameAIThread` mutation, stamping `args.updatedAt` once here (so server and client share the timestamp — the reducer never calls `Date.now()`) and `threadId` from `state.doc.ai?.activeThreadId` when present (so the reducer renames the thread the request belongs to). Server-side `state.doc.ai` is unset, so the reducer no-ops on the server's copy; only the client's application actually renames the thread.
- **`remove_page_filter`/`remove_widget_filter`** share one `planRemoveFilter` implementation that looks up the filter by id BEFORE mutating and returns `{ error: "Filter <id> not found." }` (`nextState: state`, no mutation) when it doesn't exist — matching every other entity-targeting tool (`remove_widget`, `remove_page`, `set_widget_width`, …). This existence check runs first because the `removeFilter` reducer is a silent no-op for an unknown id; without it the model would be told `success: true` for a call that changed nothing, with no signal to retry with a corrected id. The two tools emit identical `removeFilter` mutations keyed only by id (no page/widget scope check), so the page/widget distinction in the tool names is cosmetic — removal by id is unambiguous either way.
- **`add_widget_filter`/`add_page_filter`** validate their target exists before committing, for the same reason: `add_widget_filter` checks `state.doc.widgets[widgetId]` and `add_page_filter` checks `state.doc.pages[activePageId]`, each returning an actionable `{ error }` (`nextState: state`) instead of committing a filter scoped to a nonexistent widget/page. This keeps every entity-targeting tool in the file — additions and removals alike — on the same validate-then-mutate shape. Both tools also cap their model-supplied `field`/`sourceId` (via `capString`, to `MAX_FILTER_STRING_LENGTH = 200`) and `value` (via `capFilterValue` — a string is capped the same way, an array such as an `in` list is truncated to `MAX_FILTER_VALUE_ARRAY_LENGTH = 50` entries, a plain object's retained key COUNT is likewise capped at `MAX_FILTER_VALUE_OBJECT_KEYS = 50` (iteration 29, finding F3 — the object branch previously recursed over every key with no count cap, so an object-typed value with thousands of short keys was persisted and re-interpolated verbatim), other JSON-serializable shapes pass through unchanged) before building the mutation — the same token-bomb class `capTitle`/`MAX_TITLE_LENGTH` guards against above, since `buildAISystemPrompt.ts` re-interpolates every active filter's `field`/`value` into the `<dashboard_state>` "Active Filters" block on every subsequent request, so an unbounded filter value would otherwise persist as a growing token cost across the whole conversation.

### Write-side config-key validation, fail-closed

Every AI-tool call site that writes untrusted, model-supplied `config` — and, since Iteration 31, any `customWidgets[].defaultConfig` a widget's config is merged with, which is equally untrusted request-body content rather than a trusted server default — onto a widget of a known kind runs it through `@mui/x-studio-schema`'s config-key allow-lists FIRST — fail-closed, unlike `StudioController.updateWidgetConfig`'s warn-and-strip on the client (a stray key here is untrusted tool-call input, not a UI slip, so it should surface as an error the model can react to rather than silently landing a subtly-different widget). Three layers, the first two mirroring the schema package's own split and the third local to this package:

- **Widget-kind level** — the local `invalidConfigKeyError(kind, config)` wraps `validateConfigKeysForKind`. Shared by every call site that writes a known-kind widget's config: `buildWidgetFromArgs` (used by both `add_widget` and `apply_bulk_update`'s additions), `update_widget`, and `apply_bulk_update`'s updates loop — so the error wording can't drift. As of Iteration 31, `buildWidgetFromArgs` runs this check — and the chart-type and value-shape checks below — against the MERGE of a matching `customWidgets[].defaultConfig` and the model-supplied `config` (the latter taking precedence), not just the latter alone: `defaultConfig` is shaped directly by `body.customWidgets`, so a chart-only key smuggled into e.g. a `grid` widget's `defaultConfig` previously bypassed the same fail-closed key/value validation the model-supplied `config` was already subject to. `defaultConfig` is run through `capConfigStringValues` before the merge, same as `config`.
- **Chart-type level, one layer finer** — the local `invalidChartConfigKeyError(patch, existingChartType)` wraps `validateChartConfigKeysForType`. It resolves the patch's EFFECTIVE chart type first — `patch.chartType` if the call supplies one, else the widget's current `chartType`, else the `'bar'` runtime default (the same rule `resolveChartType` encodes) — and validates the patch's keys against that specific family. A key can pass the kind-level check yet still fail here because it belongs to a different chart family than the effective one (e.g. `sankeyTargetField` in a patch that targets a `gauge`). Only reachable for `kind === 'chart'`, at `update_widget` and `apply_bulk_update`'s updates loop; an addition's `chartType` is freshly supplied in the same call, so `buildWidgetFromArgs`'s kind-level check plus its own chart-type check (with no fallback type) already cover it. An unrecognized `chartType` string is a hard error (`isStudioChartType` gate) — there are no custom chart types.
- **Value-shape level, orthogonal to both key checks** — key validation is a key-PRESENCE check only; it never inspects the value stored under a valid key. `invalidConfigValueError(config)` closes that gap for the small set of scalar-typed config fields the tools populate: `SCALAR_CONFIG_VALUE_TYPES` (`executeToolOnState.ts`) maps each field (e.g. `pivotShowTotals`, `dualYAxis`, `kpiTrend` → `boolean`; `barMaxCategories`, `gaugeMin`/`gaugeMax`, `scatterMinRadius`/`scatterMaxRadius` → `number`) to its expected primitive type, and any present-but-wrong-typed value (a non-boolean `pivotShowTotals`, a non-finite `gaugeMax`) fails the call with a named list of offending keys; `null`/`undefined` is treated as inert, not a violation. This closes the write-side enabler of a stored prompt-injection: a valid config key (e.g. `pivotShowTotals`) could otherwise carry an arbitrary string that later got echoed into the widget description. Shared by `buildWidgetFromArgs`, `update_widget`, and `apply_bulk_update`'s updates loop, same as the two key-level checks. Non-scalar/structured config (arrays, nested objects like `ySeries`/`forecast`) is out of scope for this table; `set_widget_forecast` coerces its own nested `periods` argument separately (see above). **Scope decision on string-ENUM config values (finding T2-5, deliberately deferred):** string-enum config fields (`barLayout`, `chartSortBy`/`chartSortDirection`, `heatColorScheme`/`heatLegendPosition`/`heatSortDirection`, `funnelVariant`/`funnelCurve`/`funnelLabelFormat`, `crossFilterMode`, `pieArcLabel`, `kpiSparklinePlotType`/`kpiTrendComparison`, `filterWidgetType`, aggregation fields, …) are NOT added to `SCALAR_CONFIG_VALUE_TYPES` and are not value-validated. This was evaluated and deferred rather than mechanically extended: unlike `operator` (backed by the exported `STUDIO_FILTER_OPERATORS`) or `chartType` (backed by `STUDIO_CHART_TYPES`), the MAJORITY of these enums are declared as **inline union literals** on the config interfaces in `@mui/x-studio-schema/widgetTypes.ts` (e.g. `chartSortBy?: 'category' | 'value' | 'natural'`) with no exported named type or runtime list to `satisfies`-lock against. A hand-copied allow-list per field would therefore be a second, un-pinned source of truth that silently drifts when the schema union changes — precisely the anti-pattern the `satisfies`-locked `VALID_FIELD_TYPES`/`STUDIO_FILTER_OPERATORS`/`BUILTIN_WIDGET_KINDS` gates were built to avoid — and the correct fix belongs upstream (export a `satisfies`-locked runtime list per enum from the schema package, the way it now exports `STUDIO_FILTER_OPERATORS`), out of scope for this unit's ai-middleware-only edit. Each such value is individually low-stakes (a bad enum falls back to the renderer's default) and the read-side `sanitizeForPrompt` choke point already neutralizes the injection vector, so no invalid enum value can escape `<dashboard_state>`; this is a correctness-nicety gap, not a safety one.
- **Same-batch tracking in `apply_bulk_update`** — a widget added earlier in the same batch is not yet in `state.doc.widgets`, so the additions loop records each new widget's kind (`addedWidgetKinds`) and, for chart widgets, its `chartType` into a RUNNING `currentChartTypes` map (seeded from existing state or the addition). Critically, the updates loop keeps this map current across the WHOLE batch: after an accepted update changes a widget's `chartType`, the map is updated in place, so a later update in the same batch targeting that widget validates against the type the earlier update just set — not a stale turn-start or addition-time snapshot. Without this, changing a widget's `chartType` and then setting a key valid only for the new type in one `apply_bulk_update` call would be validated against the wrong type (falsely accepting a cross-type key or falsely rejecting a valid one).
- All three checks fail the containing operation at the granularity that call site uses: `update_widget` rejects the whole call (`{ error }`, `nextState: state`); `apply_bulk_update`'s updates loop pushes a `"update <id>: <error>"` entry onto `skipped` and continues, matching that tool's per-item skip convention.
- **Widget-`kind` validation (finding T2-4)** — `buildWidgetFromArgs` validates the model-supplied `kind` against the CLOSED, locally-knowable set `BUILTIN_WIDGET_KINDS ∪ customWidgets[].kind` BEFORE building anything. `BUILTIN_WIDGET_KINDS` is a `satisfies readonly BuiltinStudioWidgetKind[]` list with an `AssertAllBuiltinKindsListed` compile-time completeness lock (same pattern as `STUDIO_FILTER_OPERATORS`/`STUDIO_CHART_TYPES`), so a new built-in kind that isn't listed fails the build. This is load-bearing beyond a cosmetic "unrenderable widget" guard: `validateConfigKeysForKind` returns `[]` (unrestricted) for an unknown kind and the chart-level check only runs for the exact string `'chart'`, so an unknown kind like `"Chart"` (capitalization slip) or `"table"` would ALSO bypass every config-key check above — the `kind` is the unvalidated key that selects which allow-list applies. Rejected with an error naming the valid kinds (chat) / skipped (`apply_bulk_update`).
- **`fieldType` filter-arg validation (finding T2-3)** — `add_page_filter`/`add_widget_filter` validate the optional `fieldType` hint through the shared `resolveFieldType`, backed by `VALID_FIELD_TYPES` (a `satisfies Record<NonNullable<StudioDataField['type']>, true>` allow-list — exhaustive against the schema union), mirroring the sibling `operator` gate in the same tools. An absent value is legal (the hint is dropped to `undefined`); a present but unknown value (a classic `"text"`-for-`"string"` slip, or a non-string) fails the call rather than persisting verbatim into `StudioFilterState.fieldType` and shipping a broken filter editor.
- **Filter-`operator` validation via the shared schema export (schema finding T2-1, consumer half)** — `invalidFilterOperatorError` now consumes `@mui/x-studio-schema`'s exported `isStudioFilterOperator`/`STUDIO_FILTER_OPERATORS` (the same compile-time-locked list the schema-side `addFilter` wire boundary in `parseStateMutation.ts` validates against) instead of a hand-copied `VALID_FILTER_OPERATORS` object literal. The AI-tool boundary and the persistence/wire boundary can no longer disagree about which operators are legal — one source of truth, deleted the second.
- **Prototype-member entity-id hardening (finding T2-1)** — every model-supplied entity-id lookup in the executor goes through `Object.hasOwn` (`getWidget`/`getPage` helpers, `hasOwnEntity` for membership filters), matching the reducer's own `Object.hasOwn` discipline in `applyMutation.ts`. A bare `state.doc.widgets[id]` resolves a prototype-member key (`"constructor"`, `"__proto__"`, `"toString"`) to a truthy INHERITED function via the prototype chain, so the executor's "validate-then-mutate" existence checks would pass while the hardened reducer no-ops — reporting `success: true` for a call that changed nothing (budget/SSE/persistence-hook pollution + a model/actual-state desync) and, for `add_widget_filter` (whose `addFilter` reducer applies the filter verbatim with no widget-existence check), actually COMMITTING a persisted dangling filter. The `set_widget_forecast`/`apply_bulk_update` widget reads and the sibling `sourceId`/`pageId`/`focusedWidgetId` lookups in `mcp/queryTools.ts`, `mcp/resources.ts`, `mcp/summarisePage.ts`, `buildAISystemPrompt.ts`, and `agenticLoop/toolDispatch.ts` are hardened in the same pass for consistency (several previously failed safe only by accident — e.g. a `!source.tableName` follow-on check).

`buildAISystemPrompt.ts`'s `describeWidget` uses the same `getAllowedChartConfigKeys`/`resolveChartType` pair on the READ side: every chart field it reports is gated by whether the widget's RESOLVED chart type's family actually owns the key (via `getAllowedChartConfigKeys`), not by mere truthiness. This is a correctness requirement, not a nicety: because `update_widget` merges config patches, a widget switched e.g. `sankey` → `gauge` legitimately retains the stale `sankeyTargetField`/`xField`; describing those leftover keys to the model would misrepresent the widget's current gauge shape. The gated description covers the full spread of chart families — bar/line/area axis and layout keys, scatter/bubble (`scatterColorField`/`scatterSizeField`), gantt (`ganttLabelField`/`ganttStartField`/`ganttEndField`/`ganttColorField`), funnel (`funnelStageSequence`/`funnelCategoryOrder`/`funnelReachedField`/label + curve/variant keys), sankey (`sankeyTargetField`/`sankeyLinkColor`/`sankeyShowValues`), heatmap (`heatYField`), pie/donut (`pieArcLabel`/`pieMaxSlices`/`pieLegendBelow`), gauge (`gaugeMin`/`gaugeMax`), plus `annotations`/`forecast`/`ySeries`/`crossFilterMode` — each surfaced only when its family owns it. Every one of these gated fields (and every other value-bearing field `describeWidget` reports — `id`/`kind`/`title`/`source`, KPI/grid/filter/pivot/map config values) is appended through the shared `pushField`/`pushQuoted` helpers rather than a hand-written template-literal `parts.push(...)`, so `sanitizeForPrompt` cannot be skipped at any individual call site — see "Key design invariants" #13. The value-shape check above is defense-in-depth for the same class of value (a wrong-typed scalar config field): it stops the malformed value from ever landing in `state`, while `describeWidget`'s structural sanitize choke point stops any value that does land there (however it got there — a crafted request body, a future call site) from breaking out of the `<dashboard_state>` block.

`sankey` is now covered across the LLM-facing chart-type surface, closing a gap where the chart-type existed in the schema but the AI docs never advertised it: `widgetConfigMeta.ts`'s `WIDGET_KIND_DESCRIPTIONS` chart line, `KIND_CONFIG_LINES` (`sankey: xField (source node), sankeyTargetField (target node), yField (flow value); optional sankeyLinkColor/sankeyShowValues`), the `chartType` enum in that same line, and `CHART_TYPE_DOCS`, plus the chart-type table in `buildAISystemPrompt.ts`'s static instructions — so the write-facing surfaces now agree with `describeWidget`'s read side (which already gated the sankey keys) on the full built-in chart set.

**Iteration 22: closing the remaining persisted token-bomb caps.** A handful of model-writable string fields were previously uncapped in length and, since they land in persisted `doc` state, got re-echoed into `<dashboard_state>` on every SUBSEQUENT request — a stored cost/latency bomb, not merely a one-turn one. `executeToolOnState.ts`'s new `capConfigStringValues()` caps every string-typed value inside a model-supplied widget `config` object at the same `MAX_FILTER_STRING_LENGTH` constant the existing filter-value cap already uses (reused, not reinvented), wired into all three write sites (`buildWidgetFromArgs`, `update_widget`'s `configArg`, `apply_bulk_update`'s per-update `config`); a new `capSourceId()` applies the identical treatment to widget `sourceId` at the same three sites. `capFilterValue()` is now recursive (bounded to depth 5): it previously only truncated a filter value ARRAY's length, leaving an oversized string/object nested inside an element uncapped. Separately, `mcp/queryTools.ts`/`mcp/resources.ts` MCP data-query handlers now wrap their underlying query in the same `withTimeout` pattern `mcp/summarisePage.ts` already used (15s), and `compute_field_stats` rejects a `fields` array over `MAX_COMPUTE_FIELD_STATS_FIELDS` (50) rather than running unbounded per-field aggregation. As of a later Tier 3 fix (finding 4), this is no longer a standalone `.length` comparison: `fields` is routed through the same `validateQueryArrayArg` helper `query_data_source`'s five array arguments already use — `toolName` is now threaded through that helper so its error message names whichever tool actually rejected the call, rather than always saying `query_data_source` — closing the gap where a non-array `fields` value with its own `.length` property (e.g. a bare string) slipped past the old size-only check. Its per-element check was then folded into the shared `validateAndCapStringArrayElements` helper `query_data_source`'s `columns` uses (iteration 28, finding F4): a non-string entry (e.g. a number or nested object) is still rejected instead of being forwarded verbatim as an aggregation `column`, and an oversized-but-valid field id is now ALSO truncated to `MAX_FILTER_STRING_LENGTH` — the string-length cap this path previously lacked, unlike `columns`.

**Iteration 29: capping the INITIAL client-supplied state and message history (finding F2).** Every `cap*` helper above runs only when an AI tool MUTATES state — but the very first request's `dashboardState` comes straight off the client `body` and, before this fix, reached `<dashboard_state>` with only `sanitizeForPrompt` applied (which neutralizes `<`/`>` but neither truncates length nor counts entries). So a client could post thousands of pages/widgets/filters — each with an oversized title or a megabyte-scale filter value — and blow the system prompt up unbounded on turn one, before any per-tool cap or `maxMutationsPerRequest` could apply, and before `maxTokensPerRequest` (checked only AFTER a turn completes, and a documented no-op when a gateway omits usage chunks) could ever catch it. `executeToolOnState.ts`'s new `capIncomingDashboardState(state)` closes this by running the incoming dashboard title, pages, widgets, and filters through the SAME write-source helpers the mutation paths use — `capTitle`, `capSourceId`, `capConfigStringValues`, `capFilterValue`, `MAX_FILTER_STRING_LENGTH` — plus generously-sized count caps `MAX_STATE_PAGES` (200) / `MAX_STATE_WIDGETS` (1000) / `MAX_STATE_FILTERS` (500), returning a shallow-cloned state (the input is not mutated). It is applied once at the top of `handleAIChat`'s stream `start()`, AFTER validation but BEFORE the state feeds context enrichment or the agentic loop, and the capped snapshot is what the loop threads forward as its starting `currentState` (so subsequent mutations build on the bounded state too). Non-interpolated `doc` sub-partitions (`relationships`/`expressionFields`/`filterPresets`/`ai`) and the `session` partition pass through unchanged (at the time of this finding, so did `runtime` — closed in Iteration 30 below). The same finding also bounds the client-supplied `body.messages` array in the request validator — `MAX_REQUEST_MESSAGES` (1000, count) and `MAX_REQUEST_MESSAGES_TOTAL_CHARS` (2,000,000, total chars) — REJECTED (not truncated, which could silently drop the user's latest message) with an actionable error, since the conversation history is serialized into the first LLM request by `toOpenAIMessages` with no length/size bound of its own and the per-turn token/turn budgets are checked only after a turn completes. (The related `capFilterValue` object-key-count cap, `MAX_FILTER_VALUE_OBJECT_KEYS`, is finding F3 — see the `add_page_filter`/`add_widget_filter` note above.)

**Iteration 30: capping `runtime.dataSources`, `richContext`, and `customWidgets` in the first-turn prompt.** Iteration 29's `capIncomingDashboardState` bounded `doc.dashboard`/`doc.pages`/`doc.widgets`/`doc.filters` on the incoming `dashboardState`, but claimed `session`/`runtime` were passed through unchanged — that was unsafe for `runtime.dataSources` specifically, since `buildAISystemPrompt.ts`'s `describeSource`/`serializeFieldForAI` interpolate every data-source entry (and every field's `label`/`aiDescription`/`format`) into the SAME first-turn `<dashboard_state>` block with only `sanitizeForPrompt`'s angle-bracket escaping, which neutralizes markup but never bounds size or count. A client posting e.g. 100,000 fabricated data sources, each with megabyte-sized strings, would reach the very first LLM request unbounded, before any per-tool-call cap could apply. `capIncomingDashboardState` now also runs `state.runtime.dataSources` through new `capDataSources`/`capDataSource`/`capDataSourceField` helpers: `MAX_STATE_DATA_SOURCES` (500) caps the number of source entries, `MAX_STATE_DATA_SOURCE_FIELDS` (500) caps the number of `fields` per source, and each source's `label`/`aiDescription` and each field's `label`/`aiDescription`/`format` are truncated to `MAX_TITLE_LENGTH` (200, the same bound already applied to dashboard/page/widget titles). Source and field `id`s were left untouched by this pass, consistent with how widget/page ids were handled elsewhere in this function at the time — a shared gap Iteration 32 below closes for the SOURCE `id` (and for widget/page `id`s) via the new `capEntityId`; each field's own `id` is still passed through untouched.

`richContext` and `customWidgets` are two sibling request fields with the identical gap: both are client-supplied and interpolated into that same first system prompt (`buildRichContextBlock`'s shape-checked sections, and the custom-widget listing loop) with no count/length bound of their own — `StudioAIRichContext`'s own doc comment had assumed the CLIENT would stay under a token budget, which was never actually enforced server-side. `handleAIChat.ts` adds `capIncomingRichContext`/`capIncomingCustomWidgets`, invoked at the same request-handling chokepoint as `capIncomingDashboardState` — inside the stream's `start()`, before either value reaches `options.contextEnricher` or `runAgenticLoop`. `capIncomingRichContext` caps `fieldStats` key count (`MAX_RICH_CONTEXT_FIELD_STATS`, 500), `pageLayout.rows` (`MAX_RICH_CONTEXT_LAYOUT_ROWS`, 200) and each row's cells (`MAX_RICH_CONTEXT_ROW_CELLS`, 50), `pageLayout.crossFilters` (`MAX_RICH_CONTEXT_CROSS_FILTERS`, 200), `recentMutations` (`MAX_RICH_CONTEXT_RECENT_MUTATIONS`, 200), and `omitted` (`MAX_RICH_CONTEXT_OMITTED`, 50) — mirroring, not replacing, `buildRichContextBlock`'s existing shape guards: a malformed (non-array/non-plain-object) section is left alone for that renderer to skip as it already does, and only an otherwise-well-shaped section had its count bounded here (Iteration 31 below additionally bounds the LENGTH of individual string fields inside each retained element). `capIncomingCustomWidgets` caps the array itself at `MAX_REQUEST_CUSTOM_WIDGETS` (200) and, per entry, the `label`/`description` string length (`MAX_REQUEST_STRING_LENGTH`, 200, `kind` capped identically as of Iteration 31 below) and the `defaultConfig` key count (`MAX_CUSTOM_WIDGET_CONFIG_KEYS`, 200). Both capped values replace the raw request fields everywhere downstream — `options.contextEnricher`'s `richContext` argument, and `runAgenticLoop`'s `customWidgets` parameter and the `AgenticLoopOptions.richContext` passed alongside it.

A related Tier-3 crash-resilience gap closed in the same change: `validateStudioAIRequestBody` already checked that `runtime.dataSources` was a map, but not the shape of any individual entry, so a malformed entry (e.g. missing `fields`) threw an unprefixed native `TypeError` out of `describeSource` the first time the system prompt was built — masked by `handleAIChat`'s outer `try`/`catch` into a generic error rather than this file's actionable `MUI X Studio:`-prefixed convention. The validator now checks each `dashboardState.runtime.dataSources[id]` entry has a string `id`, a string `label`, and an array `fields`, returning a proper `MUI X Studio:`-prefixed validation error otherwise — the same shape-check convention already applied to `doc.pages`/`doc.widgets`/`doc.filters`/`messages[].parts` above.

**Iteration 31: closing the length/allowlist gaps the count-cap passes above left behind.** A fresh architecture review found four sibling instances of the same class: a count cap (or key-allowlist) had been added everywhere for prompt-injection/token-bomb defense, but each of these four fields only got it on SOME write paths, not all.

- **`buildWidgetFromArgs` validates the MERGE of `customWidgets[].defaultConfig` and `args.config`, not just `args.config`.** Previously the kind-level, chart-type-level, and value-shape checks (see "Write-side config-key validation, fail-closed" above) ran only against the AI-supplied `config`, on the theory that `customDef?.defaultConfig` was a trusted server-side default. That theory doesn't hold: `StudioCustomWidgetDef` (and therefore every `customWidgets[].defaultConfig`) is shaped directly by `body.customWidgets`, capped only for length/count by `capIncomingCustomWidgets` (never key/value validated) — so it is exactly as untrusted as `args.config`, and a chart-only key (e.g. `chartType`) or a wrong-typed scalar (e.g. a string `pivotShowTotals`) smuggled into a `grid`/`pivot` widget's `defaultConfig` previously landed on the widget unchecked. `defaultConfig` is now capped via `capConfigStringValues` before the merge (same treatment `args.config` already got), then the merged config — `defaultConfig` spread first, `aiConfig` taking precedence — is what `invalidConfigKeyError`/`invalidConfigValueError`/`invalidChartConfigKeyError` actually validate; a key/value carried only by `defaultConfig` now fails the call (chat) / skips the op (`apply_bulk_update`'s additions) exactly like one carried only by `aiConfig` always did.
- **`capConfigStringValues` (Iteration 22) now also bounds array- and nested-object-typed config values, not just scalar strings.** `describeWidget` echoes a chart widget's `ySeries`/`annotations`/`funnelCategoryOrder`/`funnelStageSequence`, a grid widget's `columns`, and a nested single-object value like `forecast` in FULL into `<dashboard_state>` on every future request — exactly the persistent token-bomb class the existing scalar-string cap already covered, just one shape over. A new `MAX_CONFIG_ARRAY_LENGTH` constant (reusing `MAX_FILTER_VALUE_ARRAY_LENGTH`'s 50-entry convention rather than inventing a new bound) truncates any array-typed config value to 50 entries, and a new `capShallowConfigValue` helper caps each retained array ELEMENT — a string element (e.g. a `funnelCategoryOrder` entry) directly, a plain-object element (e.g. a `ySeries`/`columns` entry) on every one of ITS string-typed properties — at the existing `MAX_FILTER_STRING_LENGTH` (200); the same helper is applied directly to a nested single-object config VALUE (`forecast`), capping properties like `forecast.method`. One level deep was assumed sufficient here, on the theory that config values/elements are flat records never further nested — Iteration 32 below found two real counter-examples (`customConfig` and `gridConditionalFormats[].style`) and made `capShallowConfigValue` recurse to `MAX_CONFIG_VALUE_DEPTH` (4) instead.
- **`capIncomingCustomWidgets` now also length-caps `kind`** (`MAX_REQUEST_STRING_LENGTH`, 200) — previously only `label`/`description` were capped, even though `kind` is echoed into the system prompt exactly like `label`: once in the custom-widget listing, and again, for a widget actually created with that kind, in every subsequent `<dashboard_state>` via `describeWidget`'s `kind` field.
- **`capIncomingRichContext` now also caps the LENGTH of individual string fields inside every already-count-capped array/record**, not just the element counts: `fieldStats` entry values (`type`/`min`/`max`/`mean`/`distinctCount`/`sampledRows`, via a new `capFieldStatEntry` helper — these are nominally `number`/enum but `richContext` is unchecked client JSON, so a crafted body could smuggle an oversized string into any of them), `pageLayout.pageId`, each `pageLayout.rows` cell's `widgetId`/`kind`/`title`/`chartType`/`colSpan` (via a new `capLayoutWidgetCell` helper), and each `pageLayout.crossFilters` entry's `sourceWidgetId`/`field`/`scope` (via a new `capCrossFilterEdge` helper) — all capped to `MAX_REQUEST_STRING_LENGTH` (200) via the existing `capRequestString`. This closes the gap relative to the sibling `recentMutations[].label`, which already went through `capRequestString` and was the one field in this section correctly capped both ways. One field was still missed by this pass — the `fieldStats` entry KEY (the field name itself), capped only in COUNT — which Iteration 32 below routes through `capRequestString` too.

Tests for all four fixes (plus the array/nested-object `capConfigStringValues` generalization) were added to `executeToolOnState.test.ts`, `buildAISystemPrompt.test.ts`, and `handleAIChat.test.ts`.

**Iteration 32: the fields the previous cap passes still left unbounded — entity `.id`s, page layout, nested config values, `handleCreateWidget`'s `sources`, `fieldStats` keys, and `resolveSource`'s `sourceId`.** Another architecture review over the same defensive surface found five remaining holes. Three are Tier 1 (a client-controlled value reaching an LLM-consumed surface with no length/count bound at all), two Tier 2.

- **Tier 1 — `capIncomingDashboardState` now caps each entity's own `.id` field and the page's layout matrix.** Iterations 29/30 capped entity COUNTS (`MAX_STATE_PAGES`/`MAX_STATE_WIDGETS`/`MAX_STATE_DATA_SOURCES`) and the free-text `title`/`label`/`aiDescription`/`config`/`sourceId` strings, but an entity's `.id` is a field SEPARATE from its map key, and `buildAISystemPrompt.ts` echoes that field verbatim regardless — `pushField('id', widget.id)`, `sanitizeForPrompt(page.id)`, `sanitizeForPrompt(source.id)` — while `sanitizeForPrompt` escapes `<`/`>` and never truncates. A new `capEntityId` helper (bounded by `MAX_ENTITY_ID_LENGTH`, which reuses `MAX_FILTER_STRING_LENGTH`'s 200 rather than inventing a constant for the same class of short id string) now runs on every widget, page, and `runtime.dataSources` entry. The same gap existed one field over on `page.widgetRows`: `<dashboard_state>`'s "## Layout" block iterates the active page's rows with no bound of its own, so a matrix repeating one widget id millions of times was echoed in full on the very FIRST request — before any tool-call cap or `maxTokensPerRequest` could apply, and with no `set_widget_layout` write path involved to hit that tool's existing `MAX_LAYOUT_ROWS` rejection. A new `capPageWidgetRows` helper bounds the row count (`MAX_STATE_LAYOUT_ROWS`, aliasing `MAX_LAYOUT_ROWS` = 200 — the same bound the write path already enforced, now applied to the incoming-state READ path), the cells per row (`MAX_STATE_LAYOUT_ROW_CELLS` = 50 — a single pathological row is just as unbounded as too many rows), and each retained cell id's length (`capEntityId`); `page.widgetColSpans` is bounded to `MAX_STATE_WIDGET_COL_SPANS` entries (aliasing `MAX_STATE_WIDGETS` = 1000, since a well-formed span map never legitimately carries more entries than there are widgets). Unlike `set_widget_layout`, this path TRUNCATES rather than rejects: it runs on the read path, where there is no caller to report a validation error back to.
- **Tier 1 — `capShallowConfigValue` recurses up to `MAX_CONFIG_VALUE_DEPTH` (4) instead of stopping one level deep.** Iteration 31's "config values/elements are flat records, never further nested" assumption had two real counter-examples: `StudioSharedWidgetConfig.customConfig` (arbitrary consumer JSON, valid on EVERY widget kind) and `StudioGridConfig.gridConditionalFormats[].style.backgroundColor`/`color` (one level past what the old cap inspected). Both keys pass `validateConfigKeysForKind` unmodified, so they are persisted as-is and echoed back to the model on every subsequent `get_dashboard_state` via `projectStateForAI` — the same persistent token-bomb class `capTitle`/`capFilterValue` guard against, just deeper. The helper now takes a `depth` parameter and, at every level, length-caps strings (`MAX_FILTER_STRING_LENGTH`), bounds arrays to `MAX_CONFIG_ARRAY_LENGTH` and objects to `MAX_FILTER_VALUE_OBJECT_KEYS`, and recurses into their entries; values past the depth budget are left as-is, the same bounded-work trade-off `capFilterValue`'s `MAX_FILTER_VALUE_DEPTH` already makes rather than recursing forever on a pathologically deep structure. One latent bug was caught while making this change: `capConfigStringValues`'s array branch was written `value.slice(…).map(capShallowConfigValue)`, and `Array.prototype.map` invokes its callback with `(element, index, array)` — passing the now-two-parameter helper directly would silently feed the array INDEX in as `depth`, so every element past index 3 would skip capping entirely. It is wrapped in an arrow function (`.map((entry) => capShallowConfigValue(entry))`) so each element starts its own recursion at `depth = 0`, with a comment at the call site and a regression test asserting EVERY `gridConditionalFormats` element (not just index 0) is capped.
- **Tier 1 — `handleCreateWidget` (`handleGenerateInsight.ts`) gets the request-size caps its sibling entry point already had.** `handleCreateWidget` is a separate, client-facing public handler from `handleAIChat`, and `CreateWidgetRequest.sources` is fully client-controlled and interpolated into its system prompt — but none of `handleAIChat.ts`'s `capIncomingRichContext`/`capIncomingCustomWidgets`-style caps applied to it, so the `sourceLines` build had no count cap and no string cap of any kind (`sanitizeForPrompt`, already applied there, bounds markup but not size). A new `capCreateWidgetSources` helper caps `sources.length` (`MAX_CREATE_WIDGET_SOURCES` = 200), each source's `fields.length` (`MAX_CREATE_WIDGET_SOURCE_FIELDS` = 500), and every `sources[].id`/`label` and `fields[].id`/`type`/`label` string (`capCreateWidgetString`, reusing the imported `MAX_FILTER_STRING_LENGTH` = 200). It runs at the top of the handler, before the prompt is built, and the capped array replaces `request.sources` for the rest of the function.
- **Tier 2 — `capIncomingRichContext` now caps `fieldStats` entry KEYS, not just entry counts and values.** Iteration 30 capped the entry COUNT (`MAX_RICH_CONTEXT_FIELD_STATS`) and Iteration 31 capped each entry's VALUES (`capFieldStatEntry`), but the key itself — the field name, arbitrary client JSON — was never bounded, and `buildRichContextBlock` echoes it verbatim with no length bound of its own. Each key now runs through the existing `capRequestString` (`MAX_REQUEST_STRING_LENGTH` = 200), which only touches strings, so it is a no-op guard for the always-string keys `Object.entries` yields.
- **Tier 2 — `resolveSource`'s `sourceId` is type-checked, non-empty-checked, and length-capped (`mcp/queryTools.ts`).** It was the one argument in that file guarded by nothing but a caller-side falsy check, while every sibling (`field`, `filters[].field`, `columns[]`, `aggregations[].column`, `fieldId`, …) was both type- and length-validated — and its failure path echoed the raw value into the `Unknown data source: "…"` error string returned to the model. The parameter is now typed `unknown` and validated at the single chokepoint all four data-query tools funnel through (rather than duplicated at four call sites): a non-string/empty value returns an actionable `sourceId must be a non-empty string, received <type>` error naming the discovery tools, and an oversized string is truncated to `MAX_FILTER_STRING_LENGTH` BEFORE the `Object.hasOwn` lookup, the error message, and the `checkAllowedTable` call. See the `queryTools.ts` bullet under "Data tools" for the full behavior.

Each fix's failure scenario has a regression test: oversized widget/page/source `.id` and oversized `widgetRows`/`widgetColSpans` in `executeToolOnState.test.ts` (which also covers deeply-nested `customConfig`/`gridConditionalFormats` strings and the `.map` index/depth mix-up), an oversized `sources` array/field list/strings in `handleGenerateInsight.test.ts`, a long `fieldStats` key in `handleAIChat.test.ts`, and non-string/empty/oversized `sourceId`s in `mcp/dataTools.test.ts`.

## Tool policy chokepoint (`toolPolicy.ts`)

`toolPolicy.ts` is the single authorization chokepoint every state-mutating tool call passes through on both transports. A `require-approval` decision's optional `reason` (e.g. why THIS destructive call needs sign-off) is now threaded all the way through to the client instead of being silently dropped in transit: `ExecuteToolWithPolicyResult`/`ConsultToolPolicyArgsOnlyResult`'s `needs-approval` variants carry it, it's included in the `tool-approval-request` SSE event (`models/protocol.ts` gained an optional `reason` field), and it's included in the no-approval-channel fallback denial message — previously an approval-denial's stated reason never reached the model, so it couldn't adjust its next attempt. A `ToolPolicy` is `(ctx: ToolPolicyContext) => ToolPolicyDecision | Promise<…>`, where a decision is `{ action: 'allow' }`, `{ action: 'deny', reason }`, or `{ action: 'require-approval', reason? }`.

- **`computeToolEffects(prev, mutation, next): ToolEffectSummary`** — a pure structural diff of the pre-execution state against the reducer's `nextState`. It derives `mutationType` (the mutation's own `type`) plus `removedWidgetIds`/`removedPageIds`/`removedFilterIds`, `orphanedWidgetIds` (a widget still in `next.doc.widgets` but referenced by no page after the change while it WAS referenced before — the `set_widget_layout` orphan case), `addedWidgetIds`/`addedPageIds`, `updatedWidgetIds` (widgets present in both whose object identity changed — relying on `applyMutation`'s immutable-update discipline), and `layoutChangedPageIds`. It re-encodes no tool-specific logic; it only observes the real before/after states, so it stays correct as reducer behavior evolves. `mutationType` is optional on `ToolEffectSummary` and present only when a real mutation was diffed: a `require-approval` decision synthesized for a non-mutating built-in call (see `executeToolWithPolicy` below) omits it rather than fabricating an unrelated real mutation type as a placeholder — it previously always reported `'setDashboardTitle'` regardless of what was actually being approved, which was misleading to any approval UI that displays it (display-only, so not a security issue, but still wrong information).
- **`createDefaultToolPolicy(approvalTools = DESTRUCTIVE_TOOLS)`** — `require-approval` iff the tool name is in `approvalTools`, COMPOSED with `createEffectsAwareToolPolicy()`'s orphan/removal check: even a tool that isn't itself name-listed as destructive (e.g. `set_widget_layout`, which is merely `idempotent`) still requires approval when its actual structural effect removes or orphans a widget/page/filter. Without this composition, `set_widget_layout({ rows: [] })` (or any layout omitting widgets) would pass the shape/membership checks vacuously and blank a page with zero approval — a destruction-equivalent outcome from a tool not classified destructive. The two checks are combined by hand (not via `Policy.all`, to avoid a before-use ordering issue in this file) but are equivalent to it, since the effects-aware half never returns `deny`.
- **`createEffectsAwareToolPolicy({ updatedWidgetThreshold? })`** — an independent effects-only policy: `require-approval` whenever the proposed mutation removes any widget/page/filter, orphans a widget, or (optionally) updates more than `updatedWidgetThreshold` widgets; else `allow`. It deliberately does not wrap `createDefaultToolPolicy`, so callers can compose the two; `createDefaultToolPolicy` itself now does exactly that (see above), so this function is most useful standalone inside a fully custom policy.
- **`Policy` combinators** — `Policy.all(...policies)` evaluates in order, strictest wins (deny > require-approval > allow), short-circuiting on the first `deny` so a budget check placed first denies without consulting later policies; `Policy.mutationBudget({ max, getCommitted, onExceeded, reason })` denies any call that carries a `proposed` mutation OR is flagged `mayMutate` once `getCommitted(ctx) >= max`, with a once-per-breach `onExceeded` latch; `Policy.toolCallBudget({ max, getCalls, onExceeded, reason })` denies EVERY further call — mutating or read-only — once `getCalls(ctx) > max` (strictly greater-than, since both chokepoints increment `usage.toolCalls` BEFORE consulting the policy, so the call being gated is already counted), closing the gap where `maxTurnsPerRequest`/`maxMutationsPerRequest` bounded LLM round-trips and committed mutations but left a single turn free to carry an unbounded number of tool calls (e.g. hundreds of live `query_data_source` queries); `Policy.approveDestructive` re-expresses `createDefaultToolPolicy`.

### The two chokepoint entry points

- **`executeToolWithPolicy(toolName, input, state, opts)`** — the execute-then-gate wrapper for PURE built-in tools. It increments `usage.toolCalls` unconditionally, then runs a cheap PRE-CHECK (finding T2-1, iteration 25): it consults `opts.policy` once with `proposed: undefined` and `phase: 'pre-check'` before the dry run runs at all, and short-circuits with `denied` on a `deny` decision — safe because a `deny` here can only come from a budget-style check that doesn't need `proposed` (the effects-aware/name-based policies never deny outright), so a call the tool-call/mutation budget was always going to reject no longer pays the full dry-run cost (e.g. `projectStateForAI` + stringify for `get_dashboard_state`). An `allow`/`require-approval` pre-check outcome is NOT acted on — only the real dry-run can supply the `result`/`effects` those outcomes must carry — so execution falls through unchanged to calling `executeToolOnState` exactly once (the pure dry-run), deriving `effects` via `computeToolEffects` when a mutation was produced, building the `ToolPolicyContext` (with `proposed` set only for mutating tools, and `phase: 'final'`) and re-consulting the policy with the real `proposed` value, returning `{ kind: 'allowed' | 'denied' | 'needs-approval', … }`. `phase` (Tier 3 finding 1) is what lets a host policy tell the pre-check consult apart from this real one: for a non-mutating tool both consults present the identical `proposed: undefined` shape, so a policy that keys `deny` off `!ctx.proposed` — a plausible "deny all args-only/side-effectful calls" catch-all — could not otherwise distinguish a budget-only pre-check (which should be treated as such and not denied for reasons that only make sense once the real shape of the call is known) from the consult whose decision is actually acted on. It never touches `usage.committedMutations` — the CALLER increments that only when it actually commits (a `needs-approval` outcome might still be denied later).
- **`consultToolPolicyArgsOnly(toolName, input, state, opts)`** — the ARGS-ONLY consult for SIDE-EFFECTFUL tools that must be authorized BEFORE they run (`proposed: undefined`, `phase: 'final'` — this is always the genuine, decision-acted-on consult, never a budget-only pre-check): server-tool skills and `query_data_source` on chat, and the read-only data tools on MCP. It performs no dry-run, increments `usage.toolCalls`, threads `mayMutate` (so a mutating-capable skill is still gated by the mutation budget), awaits the policy, and returns `allowed` | `denied` | `needs-approval`. Approval bridging is transport-specific and stays at the call site (chat's `runApprovalFlow`, MCP's `approvalHandler`). On MCP, the raw-row-returning data tools (`describe_data_source`, `get_field_values`, `compute_field_stats`) consult the policy — and bridge approval — under the `query_data_source` name with `sourceId` threaded, mirroring the raw-row RESOURCE path's `authorizeResourceDataAccess` (fourteenth review, finding T2-B), so a host `toolPolicy` that denies `query_data_source` for a sensitive source governs every raw-row surface uniformly; these tools stay advertised/allow-listed under their own names (only the policy-consult tool name is remapped). `summarise_page` is remapped the same way but **source-agnostically** (fifteenth review, finding T2-α): it fans out live `queryDataSource` calls across every widget source on the page (up to 5 real sample rows per widget, plus stats and GROUP BY anomaly aggregates), so it has no single `sourceId` — its consult routes under `query_data_source` with no source threaded, exactly mirroring the multi-source `studio://dashboard/data-health` resource, so a blanket / by-name `query_data_source` deny gates it.

**Purity invariant this depends on:** the execute-then-gate path is safe only because `executeToolOnState` is pure — it computes `nextState = applyMutation(...)` with no I/O and no shared-state mutation, and the real commit happens at the caller's commit point after the policy allows/approves. Any new `executeToolOnState` case (or skill-like branch) that performs a side effect DURING execution defeats the chokepoint, because the "dry run" would fire the effect before the policy runs. The `PureToolImpl`/`ExternalToolImpl` split in `executeToolOnState.ts` makes this structural: a tool that performs I/O must be declared `{ effect: 'external' }` (no `plan`), so it cannot enter the dry-run path and must go through `consultToolPolicyArgsOnly` instead.

### Chat wiring (`agenticLoop.ts` + `toolDispatch.ts`)

`runAgenticLoop` resolves the host policy as `options.toolPolicy ?? createDefaultToolPolicy()` and layers the mutation budget AND a total tool-call budget in front of it via `Policy.all` (`Policy.mutationBudget` then `Policy.toolCallBudget`, strictest-wins), threading the composed policy (plus a mutable `{ committedMutations, toolCalls }` usage object) into `dispatchToolCall` via `ToolDispatchContext`. Per built-in tool call, after the parse-failure and T1-1 gates, the call runs through `executeToolWithPolicy`: `denied` → `{ error }` (mutation discarded), `needs-approval` → `runApprovalFlow` (the `tool-approval-request` + `waitForApproval` pause/timeout/abort race, with `buildApprovalDisplayInput` substituting the real entity title), `allowed` → commit immediately. Server-tool skills and `query_data_source` consult the policy args-only (`consultToolPolicyArgsOnly`) and reuse `runApprovalFlow` on `require-approval`. A committed mutation increments `usage.committedMutations` and yields `state-mutation`; a denied/timed-out/aborted approval discards `nextState`.

- **`approvalFallback`** (`'deny'` default | `'allow'`) decides what a `require-approval` decision does when no `approvalPending` channel is configured to pause on. `'deny'` refuses the call with an actionable error, closing the previous fail-open behavior where destructive tools ran unapproved whenever a host forgot to wire `approvalPending`. `'allow'` auto-approves and additionally fires `onToolError` with a loud warning. It is exposed directly on the public `StudioAIHandlerOptions` (not only on the lower-level `runAgenticLoop` options) and forwarded by `handleAIChat`, so a host using the primary entry point can set it without dropping to the lower-level loop API.
- **Mutation budget** (`rateLimit.maxMutationsPerRequest`) — the `Policy.mutationBudget` wrapper runs BEFORE the host policy: once `committedMutations` reaches the cap, any further mutating call is denied (with a clear `{ error }`) without consulting the host policy, and `onLimitReached('mutations', usage)` fires once per breach. Unlike the token budget, this does NOT kill the stream — the loop continues, still bounded by `maxTurnsPerRequest`. Omitting the cap means no budget.
- **Tool-call budget** (`rateLimit.maxToolCallsPerRequest`, default `50` via `DEFAULT_MAX_TOOL_CALLS_PER_REQUEST`) — the `Policy.toolCallBudget` wrapper, layered the same way (before the host policy, via `Policy.all`): once `usage.toolCalls` exceeds the cap, EVERY further tool call in the request — not just mutating ones — is denied, and `onLimitReached('toolCalls', usage)` fires once per breach. Same non-fatal behavior as the mutation budget: the stream isn't killed, only the offending call is refused. This is what actually bounds a single turn requesting an unbounded number of tool calls (e.g. a flood of read-only `query_data_source` queries), which neither `maxTurnsPerRequest` nor `maxMutationsPerRequest` constrains on their own.
- **Server-side `allowedTools`/`privateMode`/`allowedSkills` enforcement** (`handleAIChat.ts`) — the effective allowlist is the INTERSECTION of `options.allowedTools` and `body.allowedTools` (a body omitting its list allows all, so the intersection is the server list); the effective private mode is `options.privateMode || body.privateMode` (the client can opt IN but never OUT); the effective skill set, when the host supplies `options.allowedSkills`, is each allowlisted NAME resolved against `options.skillHandlers` (matched by `name`) — the body's own `promptFragment`/`tool` are never used, only its `name` as a selector, and a name with no matching `skillHandlers` entry is dropped (finding T1-1, iteration 25 — filtering by name alone still let a body-supplied fragment through under an allowlisted name). Omitting `allowedSkills` trusts `body.skills` as-is, content included. When all three server options are omitted, the effective values are bit-identical to the raw body values. `options.toolPolicy` is forwarded to `runAgenticLoop`.

### MCP wiring (`mcp.ts`)

Both dispatch paths in `tools/call` pass through the policy with a session-scoped `{ committedMutations, toolCalls }` usage object and a session policy of `Policy.all(mutationBudget, toolCallBudget, hostPolicy)` — the same two-layer-before-host-policy budget composition the chat transport uses (see "Chat wiring" above), so a session that dispatches an unbounded number of read-only calls (e.g. hundreds of `query_data_source` live queries) is bounded even though none of them are mutations:

- **Read-only / side-effectful dispatch-table tools** (data queries, `render_chart`, `get_recent_changes`, and — when `data` is configured — `summarise_page`) pass an ARGS-ONLY consult (`consultToolPolicyArgsOnly`, `mayMutate` omitted since they never mutate dashboard state) and, on `require-approval`, bridge to the host's `approvalHandler` exactly like the mutation path. Only on allow/approved does the handler run. The raw-row data tools consult under `query_data_source` with `sourceId` threaded, and `summarise_page` — which returns raw rows fanned out across the whole page — consults under `query_data_source` source-agnostically (finding T2-α; see the policy-consult section above); the rest consult under their own name.
- **State-mutating tools** (the fallthrough past the dispatch table, the `READ_ONLY_NO_MUTEX_TOOLS` check below, and the `registeredToolNames` gate) run through `executeToolWithPolicy` and commit via `commitMutation` (write `stateBox.current`, increment `committedMutations`, record `recentChanges`, `sendResourceUpdated`, run `onStateChange`) ONLY on allow / approved-true. The mutating branch runs inside a **per-session mutex** (`mutationChain`): the snapshot → dry-run → policy → approval → commit sequence for a non-dispatch-table tool runs as one chained critical section, so a concurrent mutating call (e.g. one committing while this one blocks on a minutes-long approval) can't clobber this one's commit with a stale `stateBox.current`. Read-only dispatch-table tools stay concurrent — they never write the box. Because the approval wait itself runs _inside_ this critical section, `bridgeApproval` (below) races the host's `approvalHandler` against a bounded timeout rather than awaiting it indefinitely — otherwise a stalled approval UI (a closed tab, a dropped connection) would hang not just this call but every subsequent mutating call queued behind it in the mutex for the rest of the session.
- **`get_dashboard_state`/`list_pages`/`summarise_page`'s no-`data`-configured path** are registered (non-dispatch-table) tools marked `readOnly: true` in `STUDIO_AI_TOOL_REGISTRY`, but they are no longer routed through the mutating branch above. `READ_ONLY_NO_MUTEX_TOOLS` is checked before the generic mutation fallthrough and, on a match, dispatches through `runReadOnlyTool` instead: same `executeToolWithPolicy` policy chokepoint and approval bridge as the mutating path, but it never acquires `mutationChain` and never writes `stateBox.current` — since a read-only tool's `plan` always returns `nextState` as the SAME object reference it was given (`executeToolOnState.ts`), there is nothing to commit, no subscriber notification to send, and no `committedMutations` bump. Previously both tools fell all the way through to the mutating branch and were serialized behind its mutex like any state-changing call — including behind another in-flight call paused for minutes on a human approval — even though the registry already marked them `readOnly`; that contradicted the documented read-only concurrency contract this same section describes for dispatch-table tools. `READ_ONLY_NO_MUTEX_TOOLS` is now DERIVED from `STUDIO_AI_TOOL_REGISTRY`'s `readOnly` fact rather than a hand-maintained set (finding T3-2, iteration 25): the previous hand-listed set covered only `get_dashboard_state`/`list_pages` and missed `summarise_page`, which IS `readOnly: true` in the registry but is normally reached through the dispatch table's `handler` branch (`createSummarisePageHandler`, wired only when `data` is configured) before this set is ever consulted — except when `data` is absent, where it has no dispatch handler and falls through here, so without the derivation its "client-side limitation" response was wrongly serialized behind the mutation mutex (and any in-flight approval pause) instead of bypassing it like its read-only siblings.

- **Default policy is ALLOW-ALL**, not `createDefaultToolPolicy()`. MCP has no approval-pause channel today, so defaulting to require-approval would break every existing integration; `options.toolPolicy` defaults to `() => ({ action: 'allow' })`.
- **`approvalHandler?(ctx): Promise<boolean>`** bridges a `require-approval` decision to a host-controlled channel: `true` commits, `false` denies. When a call needs approval and no `approvalHandler` is configured, the call is denied cleanly (never thrown) with a message pointing at `StudioMcpOptions.approvalHandler`. The bridge (`bridgeApproval`) races `approvalHandler`'s promise against `StudioMcpOptions.approvalTimeoutMs` (default `120_000`, matching the chat transport's `waitForApproval` timeout) — MCP has no per-call `AbortSignal` to race the way the chat transport does, so only the timeout half of that pattern applies here, but it's just as necessary: a timed-out approval resolves to a clean deny (an actionable message naming `approvalTimeoutMs`) instead of leaving the awaited promise — and, transitively, the mutex-serialized queue of mutating calls behind it — hanging forever.
- **`rateLimit.maxMutationsPerSession`** — the same wrapper-before-host-policy budget as the chat side, session-scoped; further mutating calls past the cap are denied and `onLimitReached('mutations', count)` fires once per breach. Read-only calls never count against it.
- **`rateLimit.maxToolCallsPerSession`** — layered alongside `maxMutationsPerSession` via the same `Policy.all`, session-scoped: once this many total `tools/call` invocations (mutating OR read-only) are reached, EVERY further call in the session is denied, and `onLimitReached('toolCalls', count)` fires once per breach. This is what actually bounds a session that dispatches an unbounded number of read-only calls — `maxMutationsPerSession` alone does not, since it only ever counts committed mutations. Omitting either budget means no cap for that dimension (current default).
- **`denied` → `errorResult(reason)`** (a tool result flagged `isError`), not a protocol error.

## MCP surface

`mcp.ts` is a slim **composition root**: it creates the MCP `Server`, owns the session-scoped mutable state (the boxed `StudioState`, the `recentChanges` log, the `subscribedUris` set, the `sessionUsage` counters, the `mutationChain` mutex), and wires together the handler modules extracted into `mcp/`.

`buildStudioMcpServer(stateBox, options?)` uses a **boxed mutable state** (`{ current: StudioState }`, type `StudioStateBox`) shared across tool calls in a session — writing `stateBox.current = result.nextState` after a mutation makes the next tool call see the update automatically. The box holds the FULL partitioned `StudioState`: handlers read `stateBox.current.doc.*` for dashboard structure and `stateBox.current.runtime.dataSources[sourceId]` for data-source lookups (the `query_data_source`/`describe_data_source`/`get_field_values`/`compute_field_stats`/`summarise_page` sourceId validation all go through `runtime.dataSources`). Neither `get_dashboard_state` nor the `studio://dashboard/state` resource emits the box verbatim — both call the same `projectStateForAI` function (`executeToolOnState.ts`), which projects `runtime.dataSources` down to AI-safe metadata (`rows`/`adapter` stripped, distinct values capped) and reduces `doc.ai` to per-thread metadata (no `messages`), so the two surfaces can never disagree on what "state" means.

It registers:

- **`tools/list` + `tools/call`.** `tools/list` re-exposes `toolsToRegister` (the `STUDIO_AI_TOOLS` subset for this session — filtered by `MCP_UNSUPPORTED_TOOLS`, the `query_data_source`-needs-`data` gate, and `allowedTools`) plus, when `data` is supplied, the read-only data tools (`describe_data_source`/`get_field_values`/`compute_field_stats` — `mcp/toolMetadata.ts`'s `DATA_TOOL_DEFINITIONS`), and unconditionally `render_chart`/`get_recent_changes` (`EXTRA_TOOL_DEFINITIONS`) — the extra tools also gated by `allowedTools` when supplied. `tools/call` dispatches through a `Record<string, ToolHandler>` table (`toolHandlers`) built from `createDataToolHandlers(...)` plus, when `data` is present, `summarise_page`; `get_dashboard_state`/`list_pages` dispatch through the dedicated `runReadOnlyTool` path (see "MCP wiring" above); everything else falls through to the shared `executeToolWithPolicy` mutation path.
- **`get_dashboard_state`/`list_pages` are not entries in `toolHandlers`**, but they are no longer left to fall all the way through to the generic mutating branch either: `tools/call` checks `READ_ONLY_NO_MUTEX_TOOLS` first and, on a match, dispatches through `runReadOnlyTool`, which still puts the call behind the policy chokepoint, unifies its output envelope with the chat path (a JSON string, not a raw object), and picks up the row-data redaction from the single pure plan in `executeToolOnState.ts` — exactly as the old mutation-path fallthrough did — but skips `mutationChain` and the `stateBox.current` write-back, since a read-only call has nothing to commit.
- **`allowedTools` gating runs before dispatch.** When supplied, `allowedTools` is the EXHAUSTIVE allow-list for the WHOLE MCP tool surface (built-in AND extra tools). `isToolAllowed(toolName)` rejects anything not listed with `Unknown tool` before either the dispatch table or the mutation path is consulted — so `allowedTools: []` disables even always-present tools like `get_dashboard_state` (mutation-path) and the extra data/chart/log tools. Names on the mutation path additionally must be in `registeredToolNames`.
- **`resources/*`** (`mcp/resources.ts`) — `studio://dashboard/state` (the authored `doc` plus data-source metadata, both projected through the shared `projectStateForAI` — never raw rows, never full `doc.ai` chat transcripts), `studio://dashboard/system-prompt` (the AI system prompt built from current state, with `contextEnricher` + distilled `buildPageLayoutContext` support), `studio://dashboard/data-health` (per-source row counts, only when `data` is configured), `studio://schema/{sourceId}` (field metadata), `studio://data/{sourceId}` (up to 20-row preview, only when `data` is configured) — with subscribe/unsubscribe and completion-based URI autocomplete. `resources/subscribe` rejects any URI `resources/read` could never serve (mirroring its unknown-URI throw) and enforces a per-session cap (`maxSubscribedUris`, default 256) so a client can't spam distinct valid-shaped URIs (e.g. `studio://schema/<garbage-N>`); re-subscribing an existing member always succeeds and immediately fires `sendResourceUpdated`. `resources/list`'s per-source `name`/`description` route the state-derived `label`/`id` through `sanitizeForPrompt` before interpolation (matching the sibling `prompts/get` handler) — MCP resource metadata is LLM-consumed text (the MCP spec positions `description` as text "for the LLM to understand the resource"), so it is a prompt-injection surface like any other, not merely a listing convenience; see invariant 13's 5th entry point. The `uri` field keeps the RAW id in both the schema and preview entries, since it is an addressable identifier `resources/read` slices back out, not LLM-consumed text.
- **Resource reads that expose the same payload as a tool are gated through the same authorization chokepoint as that tool.** Two mappings exist. (1) **Live-query reads → `query_data_source`.** `studio://data/{sourceId}` (raw row preview) and `studio://dashboard/data-health` (per-source COUNT) each run `mcp.ts`'s `authorizeResourceDataAccess` before touching `data.queryDataSource`: it checks `isToolAllowed('query_data_source')`, then runs the same `consultToolPolicyArgsOnly` args-only policy consult the dispatch-table data tools run (mapped onto the `query_data_source` tool name, since that's the tool these reads conceptually invoke), bridging to `approvalHandler` on a `require-approval` decision exactly like the mutation path. Both resolve their source directly rather than through `resolveSource`, so both also run `checkAllowedTable` (`mcp/helpers.ts`) against the resolved `tableName` — the same `allowedTables` allowlist `resolveSource` applies for `query_data_source` — before issuing the query, closing the gap where a source resolving outside the allowlist could still be read via these two resources even with `allowedTables` configured. `studio://data/{sourceId}` threads its parsed `sourceId` into the consult `input` (finding 2.3) so a per-source `toolPolicy` rule or an `approvalHandler` inspecting `ctx.input` sees which source is being read; `data-health`, being a multi-source operation, is gated once without a `sourceId`. A host that excludes `query_data_source` via `allowedTools` or `toolPolicy` is honored on these resource URIs too, and the consult increments `sessionUsage.toolCalls` so a usage-aware policy doesn't undercount. (2) **Dashboard-state reads → `get_dashboard_state`.** `studio://dashboard/state`, `studio://dashboard/system-prompt`, and `studio://schema/{sourceId}` all expose a slice of the same `projectStateForAI` payload the `get_dashboard_state` tool returns (`system-prompt` renders it as prompt text; `schema/{sourceId}` serves one source's field definitions, `fieldDistinctValues`-derived `sampleValues`, and `serializeFieldForAI` string), so each runs `authorizeResourceStateAccess` (`isToolAllowed('get_dashboard_state')` + the same args-only consult) before serving — closing finding 2.1, where excluding `get_dashboard_state` from `allowedTools` blocked the tool call but left the byte-identical resource reads ungated. `studio://dashboard/system-prompt` additionally invokes the host `contextEnricher`, which runs LIVE DB queries (per-dimension row counts, finer-grained than `data-health`'s per-source COUNTs); that enrichment now passes the `authorizeResourceDataAccess` gate too (finding 2.2) — when denied, only the enrichment is skipped, the state-derived prompt is still served. `studio://schema/{sourceId}`'s `sampleValues` and `serialized` field are row-derived data (up to 8 real distinct values per field), not static metadata — the same category `MAX_DISTINCT_VALUES_IN_STATE_OUTPUT` caps and `privateModeExcluded` treats as sensitive on the chat side — which is why it needs the same gate rather than being treated as an ungated convenience read. `hidden` remains a listing-only declutter flag, not an access-control boundary, for both tools and resources — see below.
- **`prompts/*`** (`mcp/prompts.ts`) — one built-in prompt, `query_data_source_examples`, which generates example `query_data_source` invocations (a count-by-category and a sum-by-category query) tailored to the dashboard's actual configured data sources, plus `sourceId` argument autocomplete. `prompts/get`'s content generation for `query_data_source_examples` runs the SAME `authorizeStateAccess` gate (`isToolAllowed('get_dashboard_state')` + args-only policy consult + approval bridge, wired in `mcp.ts` to the same `authorizeResourceStateAccess` function `studio://schema/{id}` uses) before serving, since it returns a per-source schema slice (source id/label, the first categorical and first numeric field's id/label, `defaultAggregationFn`) — a strict subset of the `get_dashboard_state` payload (finding T2-2). Without this gate a host excluding `get_dashboard_state` via `allowedTools` (including `allowedTools: []`) or denying it via `toolPolicy` still leaked that slice through `prompts/get`, and the read never incremented `sessionUsage.toolCalls`. `prompts/list` and `completion/complete` stay ungated by design, parity with `resources/list`.

**`hidden` is a listing-only flag, not an access-control boundary (by design).** Sources marked `hidden` are omitted from `resources/list`; hidden _fields_ are omitted from `describe_data_source`'s enumeration and from `studio://schema/{sourceId}`. This only declutters those _listing_ surfaces. Per `@mui/x-studio-schema`'s `dataTypes.ts` (`hidden` = "hidden from the data drawer and widget config selects"), it is not an access-control flag: a hidden source read directly by id via `studio://schema/{id}` or `studio://data/{id}`, or a hidden field named explicitly in `query_data_source`'s `columns`, is served/queried unchanged — intentionally, so a legitimate but decluttered source/column (e.g. a cross-source join lookup table) stays addressable. A host that needs a hard access boundary must enforce it in its `queryDataSource` implementation (or not register the source), never rely on `hidden`.

### Data tools (`mcp/queryTools.ts`, `mcp/utilityTools.ts`, `mcp/summarisePage.ts`)

`mcp/dataTools.ts` is a thin composition façade: `createDataToolHandlers` merges `createQueryToolHandlers` (`queryTools.ts`) and `createUtilityToolHandlers` (`utilityTools.ts`) into one six-key record that `mcp.ts` spreads into its dispatch table, and it re-exports `createSummarisePageHandler` and `resolveSource`. The chat transport imports the same `createDataToolHandlers` factory for `query_data_source`, so both surfaces run the identical pipeline.

- **`queryTools.ts`** — `resolveSource(stateBox, sourceId, allowedTables?)` validates a `sourceId` against `runtime.dataSources` (and its `tableName`) BEFORE building a query, returning a transport-neutral error (no `studio://` hint, since the chat transport also uses it) that names `get_dashboard_state` as the discovery path. The `sourceId` parameter itself is typed `unknown` and validated at this single chokepoint (Iteration 32) rather than at each of the four call sites: every caller only ever did a bare truthiness check (`!sourceId`), so a truthy NON-string (an object, a number) previously sailed through to the `Object.hasOwn` lookup verbatim, and an unbounded string sailed into the `Unknown data source: "…"` message echoed straight back to the model. A non-string/empty value now fails with an actionable `sourceId must be a non-empty string, received <type>` error naming `get_dashboard_state`/`studio://dashboard/state` as the recovery path, and an oversized one is truncated to `MAX_FILTER_STRING_LENGTH` before both the lookup and the error — the same bound `capSourceId` applies to a PERSISTED widget `sourceId`, and the treatment every sibling arg in the file (`field`, `filters[].field`, `columns[]`, `fieldId`, …) already had. Validating that `sourceId` exists in the catalog is not the same as proving the resulting `tableName` is one the caller should be allowed to query: on the CHAT transport the catalog descends from the client-supplied `dashboardState`, so a hostile caller can fabricate a `runtime.dataSources` entry whose `tableName` points at an arbitrary table the host's DB connection can reach (the MCP transport doesn't share this gap — its state box is server-held, never request-supplied). The `allowedTables` parameter, threaded from `StudioAIDataConfig.allowedTables` (`models/aiTypes.ts`, now typed `string[] | '*'`), closes this: when set to an ARRAY, a resolved `tableName` outside the allowlist is rejected here, before any query is built. As of iteration 29 (finding F1) the chat transport no longer merely _documents_ this boundary for hosts that skip `allowedTables` — it **fails closed by default**: `dispatchToolCall`'s `query_data_source` branch (`agenticLoop/toolDispatch.ts`) refuses to resolve ANY source when `allowedTables` is `undefined`, returning an actionable tool-error that instructs the host to configure it, rather than trusting the client-supplied `runtime.dataSources` catalog to name a safe table. A host that genuinely wants no restriction must now say so EXPLICITLY with the literal `'*'` sentinel — a greppable, deliberate opt-out (e.g. a trusted dev/demo setup, or a host whose own `queryDataSource` re-derives the physical table server-side and ignores `params.tableName`) rather than an accidental fail-open by omission. The MCP transport (server-held state, never request-supplied) is deliberately unaffected: an omitted `allowedTables` still means "no restriction" there, since its dispatch never routes through the chat branch and its state box can't be fabricated by a caller — a fundamentally different trust boundary. `checkAllowedTable` (`mcp/helpers.ts`) understands both new forms: `'*'` and `undefined` each return `null` (permit), but the `undefined`-permits path is only ever reached from the trusted MCP/server-held read paths, because the chat dispatch site refuses first when `allowedTables` is omitted. The check itself is extracted into a standalone `checkAllowedTable(sourceId, tableName, allowedTables)` helper (`mcp/helpers.ts`) that `resolveSource` calls, so the same allowlist logic (and identical denial-message shape) is available to the three sibling raw-row read paths that resolve a `tableName` from `runtime.dataSources` and query it directly rather than going through `resolveSource`: `summarise_page`'s per-widget queries, the `studio://dashboard/data-health` resource, and the `studio://data/{id}` resource (see below) — each now runs `checkAllowedTable` before its own `data.queryDataSource` call, closing the gap where those three paths could reach an out-of-allowlist table even with `allowedTables` configured. The four handlers (`query_data_source`, `describe_data_source`, `get_field_values`, `compute_field_stats`) each return a descriptive error when `data` is unconfigured, clamp `limit`, and defer to `resolveSource`. `get_field_values`'s `limit` is clamped the SAME way `query_data_source`'s is (finding 2.1): truncated and clamped to `[1, 200]` via `Math.min(Math.max(1, truncated || fallback), cap)` — a non-numeric/zero/`NaN` value (falsy after truncation) falls back to the default of 50, while a _negative_ value (truthy, e.g. `-1`) skips the fallback and is instead floored to `1` by the `Math.max` — so a NaN/negative/zero value can no longer reach the host as `LIMIT NaN`/`LIMIT 0`, closing the below-bound gap left when only the upper bound was enforced, though a negative `limit` now returns a single row rather than the page-50 default. Its tool schema (`mcp/toolMetadata.ts`) documents the cap ("Default 50, capped at 200") so a client asking for more gets an honest description of what it will actually receive. `query_data_source` never writes SQL — it forwards structured `columns`/`filters`/`aggregations`/`having`/`orderBy`/`limit`/`offset` to `data.queryDataSource`, but not before clamping the two numeric bounds: `limit` is truncated and clamped to `[1, maxQueryRows]` via the same `Math.min(Math.max(1, truncated || fallback), cap)` shape — a non-numeric/zero/`NaN` value (e.g. a model-supplied `"all"`) falls back to `maxQueryRows`, matching the schema's documented "Default 1000", while a _negative_ value (e.g. `-1`) is truthy and skips that fallback, instead flooring to `1` via `Math.max` — and `offset` is coerced to a non-negative integer (negative/`NaN`/non-numeric collapses to `0`) rather than forwarded as-is; both transports share this clamp since MCP `tools/call` and the chat loop's `query_data_source` dispatch resolve to the same `createDataToolHandlers` factory. This closes a gap where an untrusted `limit`/`offset` could reach the host's `queryDataSource` implementation unclamped and surface a raw driver error (e.g. `LIMIT NaN`) instead of one of this layer's actionable, model-recoverable errors. Its five array-typed arguments — `columns`/`filters`/`aggregations`/`having`/`orderBy` — are each validated by `validateQueryArrayArg` (finding T2-3, iteration 25) before any of them reach `data.queryDataSource`: a non-array value is REJECTED (not coerced) with an actionable error naming the argument, and an array over `MAX_QUERY_ARRAY_LENGTH` (reusing `compute_field_stats`'s existing 50-entry convention rather than inventing a tool-specific bound) is rejected with a "split the request" message, closing the gap where these five arrays were cast and forwarded unvalidated while `compute_field_stats`'s own `fields` array already had this exact protection. `filters[].value`/`value2` are additionally routed through the now-exported `capFilterValue` (`executeToolOnState.ts`) before forwarding — the same recursive, depth-bounded cap `add_page_filter`/`add_widget_filter` already apply to a PERSISTED filter's value — closing the gap where a `query_data_source` filter (forwarded live to `data.queryDataSource` rather than persisted) could carry an unbounded string/array value that `checkAllowedTable`'s table allowlist does nothing to bound. `describe_data_source` runs sample-rows + per-field numeric stats concurrently, fanning out one aggregation query per numeric field (min/max/avg/sum/count); that fan-out is now capped at `MAX_DESCRIBE_DATA_SOURCE_NUMERIC_FIELDS`, reusing `compute_field_stats`'s own `MAX_COMPUTE_FIELD_STATS_FIELDS` (50) since both bound "how many per-field aggregation queries can one tool call issue in a single `Promise.all`" — but unlike `compute_field_stats` (whose `fields` list is model-supplied and can simply be rejected for the model to retry smaller), `describe_data_source`'s numeric-field set is derived from the source's own schema, so there's no smaller request to retry with: the fan-out is truncated to the first N numeric fields in schema order and the response notes the truncation, rather than rejecting the call outright, leaving `compute_field_stats` with an explicit `fields` list as the recovery path for the rest. `get_field_values` also best-effort renders a bar chart of the top values. `validateQueryArrayArg` only ever checked array-ness and overall length, never individual ELEMENTS (finding F4, Tier 2): `columns`'s elements are now validated + capped by `validateAndCapStringArrayElements` (a non-string entry is rejected outright; an oversized string is truncated, not rejected) and `filters`/`aggregations`/`having`/`orderBy`'s elements by `validateAndCapRecordArrayElements` (a non-object entry is rejected; each entry's NAMED string-typed fields — `filters[].field`/`operator`, `aggregations[].column`/`func`/`alias`, `having[].alias`/`operator`, `orderBy[].column`/`direction` — must themselves be strings, and are rejected if they are an object/array/number, since a mis-typed column name is not recoverable by truncation), closing the gap where an object/multi-megabyte-string element reached `data.queryDataSource` verbatim as a nonsensical column name or an unbounded value. `MAX_FILTER_STRING_LENGTH` is exported from `executeToolOnState.ts` for this reuse rather than duplicated. `validateAndCapRecordArrayElements` originally validated the named fields but then spread `{ ...record }` verbatim to forward the entry — so any UNLISTED key carrying an unbounded string reached `data.queryDataSource` uncapped; it now instead projects a fresh record capping EVERY string-typed value (listed or not) to `MAX_FILTER_STRING_LENGTH`, leaving non-string values (numbers such as `having`'s `value`, booleans) untouched (iteration 28, finding F5, Tier 3). `compute_field_stats`'s `fields` argument — which was previously element-type-checked by a hand-rolled `findIndex` scan but NOT length-capped, unlike `columns` — now runs through that same `validateAndCapStringArrayElements` helper after its `validateQueryArrayArg` array-ness/length check, so a non-string field id is rejected and an oversized-but-valid one is truncated to `MAX_FILTER_STRING_LENGTH`, matching `columns` (iteration 28, finding F4, Tier 2). `get_field_values.fieldId` was previously only truthiness-checked, so a truthy non-string (an object/number) reached `data.queryDataSource` verbatim; it is now required to be a non-empty string and capped at the same `MAX_FILTER_STRING_LENGTH` bound.
- **`utilityTools.ts`** — `render_chart` (pure `renderChartSvg`, returning base64 + raw SVG text) and `get_recent_changes` (the session-scoped `recentChanges` log). Neither touches a data source. `render_chart`'s args are model output and therefore untrusted: `renderChartSvg` validates/coerces `width`/`height` (finite, positive, capped) and each `colors` entry (a strict hex pattern, falling back to the default palette per-entry on a mismatch) before any renderer interpolates them into an SVG attribute position — text content (titles, labels, series names) is separately escaped via `esc()`. `renderChartSvg`'s `sanitizeInput` choke point also caps the NUMBER of entries accepted in the `data`/`xLabels`/`series` arrays, and each per-series `values` array, at `MAX_CHART_ARRAY_LENGTH` (1,000, Tier 3 finding 3) — matching the `MAX_QUERY_ARRAY_LENGTH` convention `query_data_source`/`compute_field_stats` already use elsewhere in the package — throwing an actionable "split the request" error rather than letting one tool call turn into unbounded SVG-generation work and an unbounded response payload. `MAX_CHART_ARRAY_LENGTH` only ever bounded the entry COUNT, though — each individual text field (a `data[*].label`, `series[*].name`, `xLabels` entry, or the chart `title`) stayed unbounded until `sanitizeText`/`sanitizeOptionalText` also began truncating each to `MAX_CHART_TEXT_LENGTH = 200` (iteration 28, finding F7), since a single multi-megabyte label is the same unbounded-work/response-payload class one oversized array is. `get_recent_changes` bounds its own response independently of how large the caller-injected `recentChanges` array is: it honors an optional `limit` clamped to `[1, MAX_RECENT_CHANGES_RESPONSE]` (50), returns the most-recent slice, and — only when truncating — prepends a `{ label, at }` sentinel noting how many older entries were omitted, so a host that raises its own buffer cap can't blow past this layer's response-size bound.
- **`summarisePage.ts`** — `createSummarisePageHandler` (registered only when `data` is configured). It queries every widget's source concurrently (`Promise.all`, each call individually bounded by `withTimeout`), computes numeric stats and a CSV excerpt, and — for time-series chart widgets — runs a GROUP BY aggregation plus `detectAnomaliesIQR` to flag anomalous periods (trimming the first/last bucket, which are commonly partial and produce false-positive low outliers). This per-widget anomaly-aggregation query's `limit` is `Math.min(20_000, maxQueryRows)` (Tier 3 finding 6) rather than a hardcoded `20000`: `createSummarisePageHandler` now threads an optional `maxQueryRows` deps field (mirroring `QueryToolDeps.maxQueryRows`, and falling back to `DEFAULT_MAX_QUERY_ROWS = 1000` — the same default `mcp.ts` uses for `query_data_source` — when a caller omits it), so this query respects whatever bound the host actually configured instead of always querying up to 20,000 rows regardless. Each per-widget query resolves its source directly (not through `resolveSource`), so it now also runs `checkAllowedTable` (`mcp/helpers.ts`) against the resolved `tableName` before querying, applying the same `allowedTables` allowlist `query_data_source` enforces. Per-widget results are written into a pre-sized, index-addressed array (`results[i]`) so the final summary preserves page/layout order regardless of which query settles first. The per-widget fan-out itself had no cap on widget COUNT (finding F5, Tier 3): it is now truncated at `MAX_SUMMARISE_PAGE_WIDGETS` (50), reusing the same convention as `MAX_COMPUTE_FIELD_STATS_FIELDS`/`MAX_DESCRIBE_DATA_SOURCE_NUMERIC_FIELDS` rather than a tool-specific bound — truncated (not rejected), like `describe_data_source`'s numeric-field fan-out, since a page's widget count isn't something the caller can retry smaller; the summary covers the first N widgets in layout order and the output notes the truncation. `truncateToPeriod` and `detectAnomaliesIQR` are imported directly from `@mui/x-studio-schema` — the same zero-dependency functions the client uses. `ANOMALY_SAFE_AGGREGATIONS` (`sum`/`count` only) gates the anomaly path — summing per-period `avg`/`min`/`max` into a combined bucket is not mathematically meaningful, so those aggregations skip anomaly detection — and `ANOMALY_CHART_TYPES` (`bar`, `bar-stacked`, `bar-100`, `line`) gates which chart types are eligible for the time-series path at all. Blended charts (a `ySeries` entry from a foreign source) are also skipped. The generated markdown returned as this tool's output is itself an LLM-consumed text surface (finding T3-3, iteration 25): the per-widget heading (`widget.title || source.label`), each field's `label` in the stats line and the CSV header row, and every CSV cell value (live, attacker-influenceable row data) now route through `sanitizeForPrompt` before interpolation — the same choke point `buildAISystemPrompt.ts` uses — closing a gap where this tool's summary text was assembled from state- and row-derived strings without going through it (see invariant 13). The "page not found" error's caller-supplied `pageId` is likewise now routed through `sanitizeForPrompt` before interpolation (finding F6), matching this same sanitize-before-interpolate convention — previously it was the one string in this file's output interpolated unsanitized.

## Skills

`studioSkills.ts` defines exactly two built-in skills, both `mode: 'instruction-only'` (a prompt fragment with no callable tool — the model reads `<dashboard_state>` and composes a plain-text response):

- **`dashboardNarratorSkill`** — triggers on "walk me through", "explain", "describe", or "give an overview of" the dashboard. Produces a business-stakeholder-friendly narrative: purpose, each widget by title/type, active filters, and a closing summary sentence.
- **`insightSuggestorSkill`** — triggers on "what's interesting?", "any insights?", requests for notable/unusual observations. Suggests 2–4 specific, numbered observations grounded in the actual widgets/fields present, ending with a note on what additional data could deepen the analysis.

Apps can register additional skills of any `StudioAISkill` mode (`instruction-only`, `server-tool` with an `execute` function, or `client-handler`) by passing them through `StudioAIConfig.skills` (serialized as `SerializableSkill` over the wire) and, for `server-tool` skills, through `StudioAIHandlerOptions.skillHandlers` so the agentic loop can invoke `execute` server-side. A `server-tool` skill whose name collides with a built-in `STUDIO_AI_TOOLS` name is dropped (from both the request `skills` and the host `skillHandlers`) before the advertised list, prompt, and dispatch context are built, so a built-in name always resolves only to its built-in handler.

Since a skill's `name`/`mode` are sanitized on the way into the prompt but its `promptFragment` is interpolated as trusted model-instruction prose (`buildSkillSection`), two defenses guard the higher-trust system region a fragment lands in: `handleAIChat`'s optional `options.allowedSkills` resolves each allowlisted body-supplied NAME against the host's own `options.skillHandlers` registry and uses THAT definition — never the body's own `promptFragment`/`tool` (see invariant 10; finding T1-1, iteration 25, closed a bypass where filtering by name alone still let a body-supplied fragment through under an allowlisted name) — before anything reaches the prompt builder, and `buildAISystemPrompt.ts`'s `neutralizeSkillBoundary` replaces any `</skill`-style closing tag inside a surviving fragment with `&lt;/skill` so it can never terminate its own `<skill>` block early — defense-in-depth for the tag framing on top of the allow-list.

## Tool registry: `STUDIO_AI_TOOLS`

`studioAITools.ts` declares `STUDIO_AI_TOOLS` as a single `as const` array of OpenAI-compatible `{ type: 'function', function: { name, description, parameters } }` entries — the same array is passed as the `tools` field of every chat-completion request and re-exposed (mapped into MCP's `Tool` shape) by `buildStudioMcpServer`'s `tools/list` handler. There is exactly one registry; both transports read from it, so adding a tool is a one-file change to be available everywhere.

`STUDIO_AI_TOOL_NAMES` is the array of registered names, derived at runtime from `STUDIO_AI_TOOLS`. `StudioAIToolName` (the type consumers use for `allowedTools`) lives in `@mui/x-studio-schema`, derived as the union of `STUDIO_AI_TOOL_REGISTRY`'s keys — deriving it from the server tool array would invert the schema package's dependency direction (the client needs `StudioAIToolName` without depending on this server package). The registry carries only classification facts, not the JSON-schema parameter definitions, so the two cannot be derived from each other; `studioAITools.ts` therefore ends with a compile-time mutual-assignability check (`AssertMutuallyAssignable<AdvertisedToolName, StudioAIToolName>`) asserting the registry's key set exactly matches the tool names advertised in `STUDIO_AI_TOOLS` — adding a tool to one without a matching registry entry is a TypeScript compile error rather than a silent drift.

`studioAITools.ts` also exports `DESTRUCTIVE_TOOLS: ReadonlySet<StudioAIToolName>` (`remove_page`, `remove_widget`, `apply_bulk_update`) — built by filtering `STUDIO_AI_TOOL_REGISTRY` on its `destructive` fact. `mcp/toolMetadata.ts`'s `annotationsFromFacts` derives each tool's MCP `destructiveHint` from the same entry — `facts.mcpDestructiveOverride ?? facts.destructive` — where `mcpDestructiveOverride` marks `remove_page_filter`/`remove_widget_filter` destructive on MCP so an MCP client (which surfaces `destructiveHint` in its own confirmation UI) flags the permanent deletion. The override no longer implies the op is chat-unguarded: the composed chat default policy DOES gate these filter removals, via `createEffectsAwareToolPolicy`'s `removedFilterIds` check — a removal that deletes a filter requires approval even though the tool name is not in `DESTRUCTIVE_TOOLS` (the earlier "aren't chat-approval-gated" comment was stale and has been corrected in `toolMetadata.ts`). The chat approval gate reads from `DESTRUCTIVE_TOOLS` (`createDefaultToolPolicy()`'s default `approvalTools`) composed with the effects-aware check, so the chat gate and the MCP annotations both trace to one registry source and can't drift.

`mcp/toolMetadata.ts`'s `TOOL_TITLES` and `TOOL_ANNOTATIONS` are typed as `Record<McpToolName, …>`, where `McpToolName = StudioAIToolName | McpExtraToolName` (the five MCP-only tools: `describe_data_source`, `get_field_values`, `compute_field_stats`, `render_chart`, `get_recent_changes`). Their `StudioAIToolName`-member entries are built from `STUDIO_AI_TOOL_REGISTRY` (`builtInToolTitles()`/`builtInToolAnnotations()`), spread together with the hand-written `EXTRA_TOOL_TITLES`/`EXTRA_TOOL_ANNOTATIONS`. Typing against the real tool-name union means a missing entry for a real tool, or a phantom entry for a tool that doesn't exist, is a compile error; this caught two real bugs (`list_pages` was missing, so `tools/list` emitted `title: undefined`; `get_current_date` was a phantom entry).

`query_data_source` is a single `STUDIO_AI_TOOLS` member dispatched identically on both transports through `createDataToolHandlers` (`mcp/queryTools.ts`). Its only per-transport difference is gating: both require a `data` config, and the chat loop additionally excludes it under `privateMode` (MCP has no private-mode concept).

Per-transport tool availability still differs by design in a few cases:

- **`summarise_page`** — advertised in the chat loop only when a `pageSnapshot` was provided (or the host explicitly opts in via `allowedTools`), because live row data is otherwise only available client-side. In MCP it is unconditionally listed, but its handler only queries live data when `options.data` is configured — without `data` it falls through to `executeToolOnState`, which returns a descriptive client-side-limitation error.
- **`get_dashboard_state`** and **`summarise_page`**'s _output contracts_ are aligned across transports, but their _availability gating_ intentionally differs — a deliberate contract difference, not a bug.

## Key design invariants

1. **Pure function / dependency injection** — no framework imports, no globals; endpoint, apiKey, callbacks, and abort signal are all passed as options. Don't add a hard HTTP framework or vendor SDK dependency here.
2. **Immutable state threading** — `StudioState` is never mutated in place; every tool call returns a new `nextState` (via `applyMutation`), threaded through subsequent tool calls in the same turn and across an MCP session via `StudioStateBox`.
3. **One core, two transports** — `executeToolOnState`, `STUDIO_AI_TOOLS`, `applyMutation`, `buildAISystemPrompt`, the `createDataToolHandlers` data-tool factory, and the `toolPolicy.ts` chokepoint are shared verbatim between the chat loop and the MCP server. Adding or changing a tool means editing `executeToolOnState.ts` + `studioAITools.ts` once, not per-transport.
4. **Cacheable static prompt prefix** — `STUDIO_AI_INSTRUCTIONS` in `buildAISystemPrompt.ts` is a module-level constant so providers can prompt-cache it as a stable prefix; don't make it depend on request-specific data.
5. **Errors never abort the stream** — top-level exceptions become an `{type:'error'}` SSE event (stream still closes cleanly); per-tool exceptions are caught and surfaced to the model as `{error: message}` tool output so it can recover, rather than killing the loop.
6. **Best-effort enrichment** — `contextEnricher` failures are logged and swallowed; the chat proceeds without enrichment rather than failing the whole request. Also bounded by `CONTEXT_ENRICHER_TIMEOUT_MS` (15s, finding T2-2, iteration 25) on both transports — `handleAIChat.ts` and `mcp/resources.ts`'s `studio://dashboard/system-prompt` resource both wrap the call in `withTimeout` and treat a timeout the same as a thrown error, so a hung enrichment DB query degrades to "no enrichment" rather than stalling the response.
7. **Bounded pauses, not indefinite waits** — the tool-approval pause (`waitForApproval` in `agenticLoop/toolDispatch.ts`) always races the approval promise against an abort signal and a timeout, guards against a duplicate `toolCallId` across concurrent requests, and always cleans up its `approvalPending` map entry, so an abandoned client can never leak server resources or hang a stream forever.
8. **Single semantic authority for mutations** — `applyMutation` in `@mui/x-studio-schema` is the one implementation of every `StateMutation`'s effect; the server-threaded state and the client-applied state cannot disagree because they run the same code.
9. **Advertisement is not authorization** — a tool being filtered out of the model-facing tool list (`allowedTools`, `privateMode`, data/snapshot gating) must also be rejected at dispatch time if called anyway. `dispatchToolCall` checks `advertisedToolNames` (T1-1) and `mcp.ts`'s `tools/call` checks `isToolAllowed`/`registeredToolNames` before running anything — a filtered tool that somehow gets called is never executed on the strength of the filter alone.
10. **Body `privateMode`/`allowedTools`/`skills` are client-asserted; the host enforces server-side via options** — the body fields are read straight off the client-supplied `StudioAIRequest`. For a hard server-side guarantee, `StudioAIHandlerOptions.allowedTools`/`privateMode`/`allowedSkills` are the built-in overrides: the effective allowlist is the INTERSECTION of `options.allowedTools` and `body.allowedTools`; the effective private mode is `options.privateMode || body.privateMode` (client can opt in, never out); and, when `options.allowedSkills` is set, a body-supplied skill's `name` is used **only as a selector**, never as a content source: each allowlisted name is resolved against `options.skillHandlers` (matched by `name` — the same host-registered registry the agentic loop already consults to run `server-tool` skills' `execute`), and that server-authored definition — its `promptFragment` and, for `server-tool` mode, its `tool` schema — is what actually reaches `buildAISystemPrompt`; the body's own `promptFragment`/`tool` are never used, and a name with no matching `skillHandlers` entry is dropped rather than falling back to the body's content (omitting `allowedSkills` preserves the current behavior of trusting `body.skills` as-is, content included). **Fixed in finding T1-1 (iteration 25):** the previous version of this invariant filtered `body.skills` by `name` alone, which did NOT prevent a request from pairing an allowlisted `name` with its own hostile `promptFragment`/`tool` — the name passed the check while the attacker's own content rode through unchanged, a full bypass of the allow-list's intent. A skill's `promptFragment` is otherwise trusted model-instruction prose interpolated into the higher-trust system region, so `allowedSkills` (now paired with `skillHandlers`) is the only lever a host has to vet it short of denying skills entirely. Alternatively (or additionally) a host can supply a `toolPolicy` that denies per call, or withhold the capability entirely (do not pass a `data` option). When both server options and a custom policy are omitted, the effective values are bit-identical to the raw body values. Treat the _body_ fields as request-shaping hints; the _options_ fields (and `toolPolicy`) are the server-enforced trust boundary.
11. **Execute-then-gate depends on tool purity** — the policy chokepoint's dry-run is only safe because pure tools (`PureToolImpl`) perform no side effect during execution. A side-effectful tool must be declared `{ effect: 'external' }` and authorized args-only (`consultToolPolicyArgsOnly`) BEFORE it runs; it must never masquerade as a dry-run through `executeToolWithPolicy`.
12. **Config-key writes are fail-closed** — untrusted model-supplied `config` is validated against the widget-kind and chart-type allow-lists before any mutation is built; an invalid key rejects (chat) or skips (bulk-update) the operation rather than being silently stripped. This deliberately contrasts with the client controller's warn-and-strip convention, because tool-call input is untrusted rather than a UI slip.
13. **Every state-derived string interpolated into an LLM-consumed text surface is sanitized before interpolation — closed across the five entry points known today, not just the agentic-loop system prompt.** (See "Scope, corrected" below: this class of gap was found and closed in a new entry point in four consecutive review rounds (five entry points total, one round surfacing two at once). The next round (iteration 9) re-swept every file in the package — including several never named in a prior fix — specifically hunting for a sixth entry point, and found none: the first clean round for this invariant. It did surface two things worth tracking separately, neither a sixth instance of this exact class: a marginal injection-hygiene residual inside an already-covered entry point (`prompts/get`'s unknown-`sourceId` error echoed the full configured-source-id list raw; now routed through `sanitizeForPrompt` alongside its sibling call in the same file — see "Scope, corrected"), and, in a related but distinct area, an authorization-parity gap rather than an injection gap (T2-1: `studio://schema/{sourceId}` served row-derived sample values without the `get_dashboard_state` gate its sibling resources already had — see the MCP resources section). Treat "closed" as a statement about the entry points enumerated here and the outcome of the most recent sweep, not a standing guarantee against a sixth — this exact class, and the adjacent authorization-parity class, should both be re-swept at the start of every future review round.) "LLM-consumed text surface" is deliberately broader than "prompt": it also covers MCP tool/resource/prompt _metadata_ a client places into its own model's context (e.g. `resources/list`'s `name`/`description`), not only text this package assembles into its own system prompt. Widget titles, field ids/labels/descriptions, distinct data values, config values (chart type, forecast periods, pivot/grid/map/KPI/filter config scalars), filter values, skill names, layout column-span suffixes (in both `buildDashboardState` and `buildRichContextBlock`), row-count values, enrichment notes, and MCP resource `name`/`description` metadata are all ultimately attacker-influenceable (e.g. a value read back through `query_data_source` from a poisoned data source, a `richContext`/`enrichedContext` field that is client-supplied but typed as a number, or a config scalar that passed key-presence validation but was never value-checked). `buildAISystemPrompt.ts`'s `sanitizeForPrompt()` is the choke point: every such value is escaped (`<`/`>` neutralized) before it lands inside a tagged prompt region (`<dashboard_state>`, `<dashboard_context>`, `<server_context>`, `<skill>`) or an LLM-consumed metadata field, so a hostile value can never structurally close the block early and inject instructions into the trusted prompt/metadata that follows. In `describeWidget`, this is enforced STRUCTURALLY, not by convention: every value-bearing field is appended through the `pushField`/`pushQuoted` helpers, whose only stringifier is `sanitizeForPrompt`, so no call site can interpolate a raw value into the widget description. This holds literally even for values typed `number`: `sanitizeForPrompt(value: unknown)` accepts any value (stringifying internally), so callers route numbers through it directly — `richContext.fieldStats`' `min`/`max`/`mean`/`distinctCount`/`sampledRows`, `richContext.pageLayout`'s per-widget `colSpan` in the `<dashboard_context>` block, and `enrichedContext.rowCounts`' per-value counts are all routed through it alongside their (already-sanitized) sibling key/label, rather than being assumed safe by virtue of their declared type — so a hand-crafted request body cannot smuggle a closing tag into any of these `number`-typed fields. This is in addition to, not instead of, the static "treat it as data" instruction in the prompt's Security Rules. A client-supplied skill `promptFragment` (`buildSkillSection`) is a deliberate exception to full sanitization — it is meant to be model-instruction prose, so its body is not escaped — but `neutralizeSkillBoundary` still replaces any `</skill`-style closing tag inside it with `&lt;/skill`, so a fragment can never terminate its own `<skill>` block early; `allowedSkills` (invariant 10) is the primary server-side lever for untrusted fragments, and this is defense-in-depth for the tag framing.

    **Scope, corrected:** an earlier revision of this invariant described the choke point as unconditionally "fully closed," but that claim was true only of `buildAISystemPrompt.ts`'s agentic-loop system prompt. The package has four other entry points that build LLM-consumed text independently: two one-shot, non-agentic LLM calls — `generateFieldDescriptions.ts` (generates `aiDescription` text from a data source's fields) and `handleGenerateInsight.ts`'s `handleCreateWidget` (drafts a widget from a natural-language description) — the MCP `prompts/get` builder in `mcp/prompts.ts` (`query_data_source_examples`, which returns `role: 'assistant'`/`role: 'user'` messages an MCP client splices straight into its LLM conversation), and `mcp/resources.ts`'s `resources/list` handler (the per-source `name`/`description` fields listed for MCP clients, which the MCP spec positions as text "for the LLM to understand the resource"). All four interpolated state-derived source/field `label`/`id` values (and, in `generateFieldDescriptions`, live DB `sampleValues` — the canonical attacker-influenceable input) raw, with no call through `sanitizeForPrompt` and no tagged region at all. `generateFieldDescriptions` was the most severe gap: its output is stored and merged into every subsequent chat system prompt, making an unsanitized sample value a **stored, second-order** injection channel rather than a same-turn one; `mcp/prompts.ts` was a high-trust instruction position (assistant-role output an MCP client splices into its own conversation); `mcp/resources.ts`'s `resources/list` was the last one found, and — unlike the other three — is metadata rather than prompt/message text, which is exactly why it had been missed: the invariant's prior wording ("prompt-building entry point") didn't obviously cover it. All four now route every interpolated value through `sanitizeForPrompt` (`resources/list` keeps the `uri` field's id raw, since a URI is an addressable identifier the read handler parses back out, not LLM-consumed text), and the three prompt/message-building ones additionally wrap the data in a tagged region (`<fields>`/`<data_sources>`/`<data_source_examples>`) with an explicit "treat as data" instruction, and — `generateFieldDescriptions` only — length-cap each sample value (100 chars) before interpolation, matching the pattern `buildAISystemPrompt.ts` already used. The invariant now holds across all five entry points in the package; a future one-shot LLM call, MCP prompt, or MCP tool/resource metadata field added to this package must route its interpolated state through `sanitizeForPrompt` the same way, since there is no shared helper that enforces this across entry points structurally the way `pushField`/`pushQuoted` does within `describeWidget`. **This is a recurring bug class, not a one-time gap:** four consecutive review rounds have each found exactly one not-yet-covered entry point — `buildAISystemPrompt.ts` closed first, then `generateFieldDescriptions.ts`/`handleCreateWidget` in the next round, then `mcp/prompts.ts` in the round after that, then `mcp/resources.ts`'s `resources/list` in this round — every time immediately after the invariant had been declared "fully closed," and the entry point widened in kind each time it recurred (prompt text → stored/derived prompt text → MCP message content → MCP metadata). Nothing in the package's structure stops a sixth entry point (a new one-shot LLM helper, a new MCP prompt or resource, a new skill mode, a dynamic `tools/list` description) from being added without going through `sanitizeForPrompt`; the fix is procedural (route new interpolation through the choke point) rather than structural (there is no compile-time or lint-time check that a new text- or metadata-building function does so), so this invariant's "closed" status should be re-verified, not assumed, at the start of every future review round — and that re-verification should explicitly sweep MCP tool/resource/prompt metadata, not only prompt-builder source files, since that is precisely the category the 5th instance came from.

    **Iteration 9 update:** that re-verification happened, on every file in the package (including several never named in a prior fix: `mcp/utilityTools.ts`, `mcp/queryTools.ts`, `mcp/summarisePage.ts`, `mcp/toolMetadata.ts`, `mcp/helpers.ts`, `mcp/types.ts`, `widgetConfigMeta.ts`, `buildPageLayoutContext.ts`, `studioSkills.ts`, `agenticLoop/openaiWire.ts`, `parseSSE.ts`), and found no sixth entry point — the first clean round for this invariant. It did find one residual inside an already-covered entry point: `mcp/prompts.ts`'s `prompts/get` sanitizes the example blocks' source ids (closed in the round above) but had not sanitized the SAME ids when they appear in its unknown-`sourceId` error prose (`Unknown sourceId: "…". Available: …`) — free-form text many MCP clients splice back into the model conversation. Both the requested id and the "Available" list now route through `sanitizeForPrompt` (T2-5), for symmetry with `resources/list`. Separately (not this invariant's class, but found in the same sweep of the MCP surface): `studio://schema/{sourceId}` was serving `fieldDistinctValues`-derived `sampleValues` and the `serializeFieldForAI` string — row-derived data, not static metadata — without the `get_dashboard_state` authorization gate its sibling `studio://dashboard/state`/`system-prompt` resources already had; a host excluding `get_dashboard_state` could recover that data anyway via `resources/list` + per-source `studio://schema/<id>` reads. Fixed by running the same `authorizeStateAccess` gate (T2-1; see the MCP resources section). Neither finding reopens this invariant's "five entry points, four rounds" tally; both are noted here because they sit in the same neighborhood (MCP-surfaced, state-derived text/data reaching an untrusted consumer) and the next review round should keep sweeping it.

    **Iteration 25 update (finding T3-3):** a much later round found an instance of this exact class in `mcp/summarisePage.ts` — a file the iteration 9 sweep above had already named and cleared. The gap was in a different shape than any of the five enumerated entry points: not a prompt/message builder or MCP listing metadata, but a TOOL'S OWN OUTPUT — `summarise_page`'s generated markdown, which the agentic loop feeds straight back to the model as that call's tool result on both transports, making it just as much an "LLM-consumed text surface" as a prompt region even though it never passes through `buildAISystemPrompt.ts` at all. The per-widget heading (`widget.title || source.label`), field labels in the stats line and CSV header, and every CSV cell value (live row data read back from the widget's own data source) were interpolated raw; all now route through `sanitizeForPrompt` before interpolation, matching every other entry point's convention. This reinforces the standing warning above: a sixth (or here, effectively a re-opened) entry point can surface in a file previously swept clean, in a shape (tool output, not prompt/metadata) the invariant's own wording had not yet had to consider — the class is "any LLM-consumed text surface," and enumerating today's instances is not a substitute for re-sweeping with that full breadth in mind every round.

## Extension points

- **New built-in tool**: add a `StateMutation` variant (if it changes state) to `@mui/x-studio-schema`'s `StateMutation` union and a handler in `applyMutation`'s `MUTATION_HANDLERS`, a `TOOL_IMPLS` entry in `executeToolOnState.ts` (`{ effect: 'pure', plan }` for a pure tool, or `{ effect: 'external' }` for a side-effectful one authorized args-only), a schema entry in `studioAITools.ts` (`STUDIO_AI_TOOLS`), and an entry in `STUDIO_AI_TOOL_REGISTRY` (`aiToolRegistry.ts` in `@mui/x-studio-schema`) — its keys define `StudioAIToolName`, so the compile-time drift guard fails until the registry and `STUDIO_AI_TOOLS` agree — and, if it needs LLM-facing docs, an entry in `widgetConfigMeta.ts`. `mcp/toolMetadata.ts`'s `Record<McpToolName, …>` typing derives its built-in entries straight from the registry, so a registry entry is all that's needed there. If the tool is destructive, set `destructive: true` on its registry entry — the one fact both transports derive from. It's then automatically available to both the chat loop and MCP.
- **New skill**: add a `StudioAISkill` to `studioSkills.ts` (`mode: 'instruction-only'`, or a callable `server-tool` skill with an `execute` function passed via `skillHandlers`).
- **New widget kind's AI-facing config**: update `widgetConfigMeta.ts` (`WIDGET_KIND_DESCRIPTIONS` + the per-kind config lines) — the single place that keeps the `add_widget`/`update_widget` tool schemas and the system prompt's widget docs in sync — and add the kind's `describeWidget` branch in `buildAISystemPrompt.ts`.
- **New chart type's AI-facing config**: add the chart-type-level plumbing described in `@mui/x-studio-schema`'s `ARCHITECTURE.md` (new `StudioChartType` literal, family interface, `CHART_TYPE_CONFIG_KEYS` entry — all fail-closed at compile time there), then add a line to `widgetConfigMeta.ts`'s `CHART_TYPE_DOCS` so the system prompt's `## Chart Types` reference describes it, and the field(s) to `describeWidget`'s gated read block. The `CHART_TYPE_DOCS` array is a plain array with only a comment reminder, not compile-enforced, so it's easy to forget.
- **Custom agentic loop**: `runAgenticLoop` and `executeToolOnState` are exported directly for hosts that want to build their own loop instead of using `handleAIChat`.

`executeToolOnState.test.ts` has one `describe` per tool, verifying both the JSON `output` contract and the resulting `nextState` — including the `set_widget_layout` shape/membership validation, `apply_bulk_update`'s cross-page removal rejection and same-batch config-key validation, the two-layer (kind + chart-type) fail-closed config-key rejection, and the `pageId`/`threadId` stamping.

`toolPolicy.test.ts` has one `describe` per exported primitive: `computeToolEffects`, `createDefaultToolPolicy`, `createEffectsAwareToolPolicy`, `executeToolWithPolicy`, `consultToolPolicyArgsOnly`, and the `Policy.all`/`Policy.mutationBudget` combinators (strictest-wins ordering, deny short-circuit, once-per-breach `onExceeded` latch).

`mcp.test.ts` drives `buildStudioMcpServer` by pulling registered request handlers off the constructed `Server` and invoking them — `describe('buildStudioMcpServer', …)` (tools/resources/tool-calls/prompts), `describe('… context for MCP clients', …)` (the `get_recent_changes` log and the system-prompt resource's cross-filter-graph content), and `describe('… tools/call allowedTools gating (T1-3)', …)` (a `STUDIO_AI_TOOLS` member excluded via `allowedTools` is rejected before dispatch, including `get_dashboard_state`/`summarise_page`). `mcp/dataTools.test.ts` unit-tests `createDataToolHandlers` and `createSummarisePageHandler` directly (bypassing the `Server` plumbing), and `mcp/resources.test.ts` covers the resource handlers including the subscription cap. `src/__tests__/mcp.integration.test.ts` separately checks the same surface through the real MCP protocol machinery.
