# Architecture review

Independent technical-debt review of `@mui/x-studio`, covering the UI/component layer and the internals/state layer. This is a ground-up review against the current code (not a diff against a prior report — the previous review's findings were all implemented and that report has been deleted). Findings are organized in this project's four-tier taxonomy: Tier 1 (correctness/security bugs), Tier 2 (structural duplication), Tier 3 (God-files/cohesion), Tier 4 (testing gaps).

**Headline verdict**: the cache layer (L1–L3), join-key unification (outside one L2 exception), filter scoping, and persistence are in genuinely good shape — well-designed per-entry dependency tracking, consistently applied, and well-tested. The real debt clusters around: date-range preset resolution, the widget column-span unit system (two incompatible unit systems coexist), the L4 chart cache's dependency tracking, and — in the UI layer — a handful of concrete correctness bugs (a broken `config`-prop reload, a chart cross-highlight rendering bug, a grid highlight bug) alongside the expected accumulation of i18n gaps and duplicated UI logic.

---

## Tier 1 — Correctness bugs

### Internals/state

**1. HIGH — KPI widget-level date-range presets are silently never applied.** `StudioController.setWidgetDateRange` (`src/store/StudioController.ts:1028-1072`) stores non-custom presets with `value: null` and `scope: { kind: 'widget', widgetId }`, with a comment claiming `resolveDateRangePresets` computes fresh dates at query time. But `resolveDateRangePresets` (`src/internals/filterUtils.ts:24-49`) only resolves filters with `scope.kind === 'dashboard-date-range'` — a widget-scoped preset passes through unresolved with `value: null`, then `isConditionComplete('between', null)` (`filterUtils.ts:327-330`) evaluates false and the filter is dropped as incomplete. The KPI shows all-time values regardless of the chosen preset. The trend/sparkline path (`kpiUtils.ts:82-124`'s `extractDateRange`) has the identical gate and is independently broken the same way. `KpiSetupPanel.tsx:397-441` genuinely calls `setWidgetDateRange` with non-custom presets, so this is reachable in the product. Zero tests exist for `setWidgetDateRange` anywhere in the package. **Fix**: resolve any filter carrying a non-custom `dateRangePreset` regardless of `scope.kind`, in both `resolveDateRangePresets` and `extractDateRange`; add controller + pipeline tests for widget-scoped presets.

**2. HIGH — Widget col-span written in two incompatible unit systems (12-col vs 24-col).** The live canvas is a 24-column grid (`canvasGridConstants.ts`'s `GRID_COLS = 24`); the drag-resize handle commits via `StudioController.setAdjacentWidgetColSpans` (`:586-619`) in 24-col units, and `StudioCanvas.tsx:381` renders `pct = (span / GRID_COLS) * 100`. But three other writers of the same `widgetColSpans` record use 12-col semantics with a 3-12 clamp and `total > 12` rebalance: `StudioController.setWidgetColSpan` (`:489-508`), `setWidgetColSpanInRow` (`:537-580`), and — critically — the shared reducer's `setWidgetColSpan` handler (`packages/x-studio-schema/src/applyMutation.ts:187-240`), which backs the AI `set_widget_width` tool (whose description tells the model "valid values are 3-12"). Concrete failure: a user drag-resizes a row to 10/14 (24-unit); the AI then calls `set_widget_width(columns: 6)` — clamped to 6, rebalanced against a 14-unit sibling under a 12-unit ceiling, producing stored spans that render as roughly half the row left empty. `setWidgetColSpan`/`setWidgetColSpanInRow` have no production call sites (only the AI path and tests exercise the 12-col system). **Fix**: pick one unit system (24, since that's what renders), update the clamp/rebalance in `applyMutation.ts` and the AI tool description, delete or fix the two unused controller methods, and add a round-trip test asserting drag-resize and AI-resize agree on `GRID_COLS`.

**3. MEDIUM — L4 chart cache (`rcfaCache`) misses two row dependencies, serving stale chart data after a source refresh.** `resolveChartRowsForAggregation` (`src/internals/chartSupport.ts:271-421`) keys its cache on `widgetRows × anchorRows × configKey` and validates `relationships` and expression-field refs, but `resolveRowsAtGrain` (`grainResolution.ts`) reads two categories of rows the cache doesn't track: (a) the M:N junction anchor path (`:128-143`) merges the _remote_ endpoint's rows, which aren't part of `anchorRows`, so refreshing the remote source leaves the cache key unchanged and serves stale remote fields; (b) the same-source/many-to-one anchor path (`:74-92, 182-188`) pulls x/series display fields from other related sources via `enrichRowsWithRelatedFields`, and since `anchorRows === widgetRows` in that case, refreshing the _other_ related source never invalidates the cache. `resolvedRowsCache` solved the identical class of problem with a `collectJoinedSourceIds` out-param; the L4 cache's fix (per its own comment block) was incomplete. **Fix**: apply the same `collectJoinedSourceIds` pattern to `resolveRowsAtGrain`, storing and checking every foreign source's row reference in the cache entry; add staleness tests mirroring `resolvedRowsCache.test.ts`'s foreign-rows-refresh cases (currently absent here).

**4. MEDIUM — `JoinFieldExpression` joins bypass the shared `normalizeJoinKey` policy.** `utils/expressionEvaluator.ts` builds its join index and does lookups with raw, non-normalized values (around lines 107, 127, 300), unlike every other cross-source join in the pipeline (L3 semi-joins, L4 re-anchoring, display columns, grid dedup), which all go through `normalizeJoinKey` specifically to handle numeric-FK-vs-string-PK relationships. A join-field-expression column over such a relationship silently yields `null`, and downstream aggregations count zeros — while the identical relationship works correctly in the grid/filter/chart paths. **Fix**: key the join index by `normalizeJoinKey(...)` in all three spots; add a mixed-type test alongside `joinKeys.test.ts`.

**5. MEDIUM — L4 re-anchoring ignores filters applied to the anchor source.** In the many-to-one anchor branch (`grainResolution.ts:161-208`), anchor rows are the _full_ set of the anchor source's rows, filtered only by FK membership in the (L3-filtered) widget rows — so a page filter on the anchor source itself (e.g. a widget on `customers` with `y = orders.amount` and a page filter `orders.status = 'complete'`) narrows which customers survive in L3, but L4's re-expansion then re-joins _all_ of each surviving customer's orders, including ones the filter excluded. The M:N branch has the same shape. May be an intentional semi-join semantic, but it isn't documented or golden-tested either way. **Fix**: re-apply the anchor-source-owned filters after re-anchoring, or deliberately document and golden-fixture the semi-join behavior.

**6. LOW-MEDIUM — Removing a widget leaves its emitted cross-filter active.** `StudioController.removeWidget` (`:653-661`) cleans `widget`- and `interactive`-scope filters but not `cross-filter`-scope filters whose `sourceWidgetId` is the removed widget. The schema reducer's `removeWidget` handler has the identical gap. Deleting a chart while its click-driven cross-filter is active leaves the whole page filtered by a filter whose owner no longer exists. **Fix**: add the cross-filter predicate to both cleanup lists; test alongside the existing interactive-filter-cleanup coverage.

**7. LOW — Cache-key fingerprint collapses `Date` values.** `sortedStringify` (`resolvedRowsCache.ts:56-67`) serializes any `Date` as `'{}'` (`Object.keys(date)` is empty), so two filters differing only by a `Date` object value share a cache fingerprint. Currently latent (filter values are strings/plain objects in practice) but one adapter or chart-click away from being live. **Fix**: add a `Date → toISOString()` branch, mirroring `normalizeJoinKey`.

**8. LOW — Empty-dashboard edge cases in `StudioController`.** `addWidget`/`removeWidget`/`duplicateWidget` dereference `state.pages[activePageId]` unguarded, and `removePage` can legitimately leave `activePageId = ''` after removing the last page — the next `addWidget` throws a raw `TypeError` rather than a guarded no-op or MUI X error. Separately, `undo()`/`redo()` don't rewind `mutationLog`, so `getRecentMutations()` can report actions to the AI that the user has since undone.

### UI/components

**9. HIGH — `StudioDashboard`'s `config` prop reload is a silent no-op.** `components/Studio/StudioDashboard.tsx:153-158` calls `innerRef.current?.loadSerializedState(JSON.stringify(config))`, passing a **string**. `migrateState`'s `validateStateStructure` rejects anything where `typeof state !== 'object'`, so the call always fails and the result is discarded — only the initial mount (via `initialState`) actually works. Even fixed, `loadSerializedState` re-injects the _old_ controller's `dataSources`, so a new config's data sources would still be ignored unless `StudioDashboard` explicitly upserts them. Zero tests exist for this component. **Fix**: pass the config object directly (not stringified), handle/log the `MigrationResult`, upsert `config.dataSources`, and add a regression test — this is exactly the kind of bug a "change `config` prop → new state visible" test would catch.

**10. HIGH/MEDIUM — Single-series line/area cross-highlight "ghost" renders at full opacity.** In `StudioChartWidget.tsx`, the single-series line ghost (~line 2712) and area ghost (~line 2846) set an explicit `color: lineColor` on the ghost series while relying on a `colors={[`${lineColor}40`, lineColor]}` array for the intended 25% alpha. x-charts resolves `series.color ?? colors[i]`, so the explicit `color` wins and the ghost renders at full opacity in the same color as the active series — the cross-highlight baseline becomes visually indistinguishable from the highlighted data. The sibling seriesField-line and multi-Y ghost paths do this correctly (`color: `${...}40``). Existing chart tests mock every `@mui/x-charts` component as a prop-spy, so they structurally can't catch this rendering-level bug. **Fix**: set `color: `${lineColor}40`` (or `30` for area) directly on the ghost series and drop the misleading `colors` override; add a browser-mode smoke test asserting real rendered opacity.

**11. MEDIUM — Grid cross-highlight dims every row when the data source has no `id` column.** `StudioGridWidget.tsx`'s `highlightedRowIds` (lines 176-185) collects `row.id` from raw filtered rows — `undefined` for id-less sources — while rendered rows get synthetic ids indexed into a _different_ filtered-rows baseline. `getRowClassName` then finds no match and dims every row. Id-less sources are an explicitly supported case (that's why the synthetic-id fallback exists), so this is reachable. **Fix**: build the highlight set from row object references (shared across both baselines via the pipeline caches) rather than from `row.id`.

**12. MEDIUM — SSE stream ending without a `finish` event leaves the chat panel hung.** `studioBackendAdapter.ts:387-402`: if the server closes the connection mid-response (proxy timeout, restart), `parseSSEStream` returns without the `ReadableStream` ever being closed, so the UI stays in a streaming state indefinitely. Relatedly, `processEvent` never returns `false` to stop on `finish`/`error`, so an event arriving after `finish` would enqueue on an already-closed controller and throw. **Fix**: close the controller if not already closed after the stream resolves; return `false` from `processEvent` on `finish`/`error`.

**13. LOW — Chat thread races and ID collisions.** `StudioChatPanel.tsx`'s `handleMessagesChange` closes over `activeThreadId`; switching threads (or creating a new one) mid-stream can write the old thread's messages into the newly active thread. Thread/message IDs are `Date.now()`-based and collision-prone. **Fix**: capture the thread ID at stream start; use a counter or UUID suffix for IDs.

**14. LOW — KPI fixed-period trend skips grain anchoring and measure fields.** `StudioKpiWidget.tsx:320-371`'s fixed-period branch aggregates from widget-grain rows directly, while the headline value uses grain-anchored rows — a cross-source value field is double-counted across both trend windows, and a measure expression field silently yields 0. The filter-based branch (`:444-470`) handles both cases correctly. **Fix**: route fixed-period rows through the same aggregation/measure-evaluation logic as the headline value.

**15. LOW — Pie selection-highlight index mismatch.** `StudioChartWidget.tsx:1838`: `selectedDataIndices` is computed against one label ordering while rendered arcs come from a different one when a highlight is active, so an own-selection plus incoming-cross-filter combination can highlight the wrong arc.

**16. LOW — `DefaultLoadingOverlay` hardcodes a white scrim** (`StudioWidgetCard.tsx:139`, `rgba(255,255,255,0.6)`) — visibly wrong in dark mode. Use `alpha(theme.palette.background.paper, 0.6)`.

**17. LOW — Cross-page widget move leaks `widgetColSpans`.** `StudioCanvas.tsx`'s `handleDrop` (~252-266) removes the moved widget from the source page's `widgetRows` but leaves its entry in the source page's `widgetColSpans`, which can resurface if the widget is later moved back.

**18. LOW — Inconsistent cross-filter toggle equality.** `StudioChartWidget.tsx:499`'s single-click toggle uses strict equality while the multi-select path three lines away uses `crossFilterValueEquals` — a `Date`-derived value stored as an ISO string can fail to toggle off on re-click.

Security spot-check (UI layer): nothing concerning — `privateMode` correctly suppresses rich context and page snapshots at the points checked, skills/custom widgets are stripped to serializable fields before POST, and no unsafe HTML injection was found in the reviewed surfaces.

## Tier 2 — Structural duplication

### Internals/state

**1. HIGH — `StudioController` methods and the shared `applyMutation` reducer are drifting twin implementations.** The shared reducer eliminated client/server drift, but the controller's hand-written methods are a _third_ implementation of the same mutations, and they've already diverged: `removeWidget` clears orphaned singleton `widgetColSpans` and shell selection on the controller side but not in the reducer; neither cleans cross-filters (Tier-1 #6 above — a bug now duplicated in two places); `setWidgetLayout` validates unknown/orphaned IDs on the controller but the reducer applies rows verbatim; span clamping exists three times (controller ×2, schema `clampSpan`) with the Tier-1 #2 unit bug baked into all three. **Fix**: make controller methods delegate to `MUTATION_HANDLERS[...].apply` (wrapping with UI-only extras — shell selection, title inference, undo labels) or extract the shared state-transform bodies into the schema package. A fix applied to only one side today is a silent regression on the other.

**2. MEDIUM — Per-cell aggregation semantics implemented four times with divergent null handling.** `aggregateByField`, `aggregateByTwoFields`/`aggregateMultipleSeries` (sharing a `CellAcc` accumulator), `aggregateHeatmap`, and `gridSummary`'s `aggregateGridValue` each treat null/non-numeric values differently — the same `avg` over the same column with nulls can yield three different numbers depending on widget kind. The non-numeric-y → fall-back-to-count behavior also exists in two of the four but not the third. **Fix**: fold `aggregateByField`/`aggregateHeatmap` onto the shared `CellAcc` accumulator, make the null policy an explicit parameter, and document any intentional grid-vs-chart difference.

**3. MEDIUM — Date-range preset resolution duplicated (and is where Tier-1 #1 lives).** `filterUtils.resolveDateRangePresets`, `kpiUtils.extractDateRange`, and the server-adapter translation layer each re-implement preset → concrete-range logic; the two client copies already disagree about which filter scopes they resolve, which _is_ the widget-preset bug above. The controller separately contains three near-identical date-range-filter builder methods. **Fix**: one shared `resolveDateRangePreset(filter)` helper used by all consumers; one `buildDateRangeFilter(...)` factory in the controller.

**4. LOW — Four copies of the filter-partitioning loop in `context/selectors.ts`.** `selectPartitionedFilters`, `selectPartitionedBaseFilters`, and two per-page factory variants are the same partition-plus-reference-stability logic copy-pasted with two toggles. One of them additionally keeps its memo in module-level globals shared across all `<Studio>` instances. **Fix**: one parameterized factory; remove or deprecate the unused module-level globals.

**5. Good, no action** — the chart-vs-grid fan-out topology split remains cleanly separated and well-defended (`grainResolution`'s docstring explicitly names `gridGrouping.symmetricAggregate` as the fan-in counterpart, both share the same join-key/relationship-index utilities, and `fanOutGolden.test.ts` pins the divergent behavior scenario-by-scenario). No new duplication has crept in here.

### UI/components

**6. The shared `filterOperatorMetadata.ts` module is already drifting on the localization axis.** It exists specifically to stop the widget-edit-dialog and filters-drawer operator pickers from diverging, but only `StudioWidgetEditDialog/FilterRow.tsx` resolves labels through it — the filters drawer's `getOperators` still returns raw hardcoded English labels, so the `filterOperator_*` locale tokens (with fr/de/es/ptBR translations) are simply unused there. **Fix**: have the drawer's `getOperators` resolve through `getOperatorLabel(..., localeText, ...)` too.

**7. `summarizeFilter` is a second, unlocalized filter-description implementation**, hardcoding English strings and calling `getOperatorLabel` without locale text — consumed by the quick-filter-bar chips, the drawer row summaries, and the KPI tooltip subtitle, so filter descriptions are untranslatable across four surfaces despite full locale infrastructure existing. A widget-card rank-chip label separately re-derives its own hardcoded English strings. **Fix**: thread `localeText` through `summarizeFilter`; add the missing tokens.

**8. `StudioWidgetCardActionsOverlay.tsx`'s edit-mode and view-mode toolbars duplicate ~150 lines of near-identical button logic** (export, expand, insight menu, anomaly toggle/explain, AI refresh — including a hardcoded string repeated verbatim in both copies), with `tabIndex` handling already subtly diverging between them. **Fix**: extract shared per-action button components.

**9. `isRecomputing` is computed independently in two places with different definitions** — `useWidgetRows.ts` excludes adapter-backed widgets from the flag, `StudioWidgetCard.tsx` computes its own version that doesn't, showing a loading overlay for widgets whose recompute is actually a server fetch already signalled by `isLoading`. **Fix**: have the card consume the row hook's flag rather than recomputing it.

**10. Intra-file repetition in `StudioChartWidget.tsx`** (feeds the Tier-3 decomposition below): six near-identical densify/align memos for bar-chart variants, repeated ghost-context construction across three bar paths, repeated click/highlight-handler and legend-slot blocks (~8×), and a field-definition lookup (`dataSource?.fields.find(...) ?? expressionFields.find(...)`) repeated ~10× that should be one `resolveFieldDef(fieldId)` helper.

**11. Anomaly-annotation sentinel knowledge duplicated** — `StudioChartWidget.tsx` re-derives "is this an anomaly annotation" from the annotation's id/label format rather than importing a predicate from the module that owns that format.

**12. i18n gaps beside a complete locale system**: hardcoded English strings remain in the canvas empty-state, several chart-type "unconfigured" hints, the `'Other'` chart-bucket label, tooltip `'(filtered out)'` text, widget-card kind-fallback titles, the entire chat-panel UI chrome (thread labels, tool labels, send/stop button text), the widget-card-actions-overlay refresh label and insight-menu items, and a widget-preview `alt`/label string that interpolates an English word. `locales.test.ts` only guarantees key-set parity, not that any surface actually renders translated output under a non-English locale — so all of the above pass CI today.

**13. Public API defect**: `src/index.ts` exports `normalizeGridColumn` — a function — inside a `export type { ... }` block, making `import { normalizeGridColumn } from '@mui/x-studio'` a type-only export that's undefined at runtime.

## Tier 3 — God-files / cohesion

### Internals/state

1. **`store/StudioController.ts`** (~1,630 lines, ~45 methods) — mostly homogeneous commit-a-new-state methods, which is fine, but also embeds layout-rebalancing math, a rank-filter policy, three date-range filter builders, and session restore. Extracting the date-range builders (Tier-2 #3) and removing the dead 12-col span methods (Tier-1 #2) would remove ~250 lines and the two most drift-prone areas without an architectural change.
2. **`internals/chartUtils.ts`** is a legacy 4-line re-export barrel of `filterUtils`/`dataSourceGraph`/`temporalUtils`/`chartAggregation`, still imported by four core internals files — it hides the real dependency locations (`resolveRows` actually lives in `dataSourceGraph`; `normalizeDataSourceRows` lives, oddly, in `temporalUtils.ts`) and its name doesn't describe its contents. Point the four imports at the real modules and delete the barrel.
3. **`models/*.ts` deep shims over-export** — each deep shim (`models/baseTypes.ts`, `dataTypes.ts`, etc.) does `export * from '@mui/x-studio-schema'`, so a deep import of any one of them surfaces the _entire_ schema surface. Harmless at runtime, misleading in practice; scope each shim to its named module, or migrate remaining deep imports to `../models` and delete the shims.
4. **`StudioProvider`'s default `featureFlags = {}`** creates a fresh object per render when the prop is omitted, defeating the `uiConfig` memo and churning `StudioUIConfigContext` for every consumer on every provider render. Hoist a module-level `EMPTY_FLAGS` constant.
5. **`useWidgetRows.usedFieldIds` is derived from _all_ `state.filters`**, not just the filters that can reach a given widget — any filter anywhere (other pages, other widgets) that introduces a new field changes this widget's cache key, undercutting the package's "unrelated edits never recompute" design. Restrict to the already-computed partitioned filter buckets for this widget.

### UI/components

1. **`StudioChartWidget.tsx`** (~3,070 lines) — the existing extraction (gauge/scatter/mixed/funnel/gantt/sankey delegated to per-type files) proves the pattern works, but the split isn't finished. What remains inline is three more coherent, extractable units: pie/donut (~430 lines, including two-ring mode and "Other" grouping — already has its own cross-highlight context to carry state across a file boundary), the three bar-chart paths (~850 lines, sharing ~70% of their config), and line/area (~500 lines). Heatmap's data shaping already lives in a separate module (`chartShapes/heatmap.ts`) but its rendering is still inline — the cheapest remaining extraction. What would remain is a genuinely cohesive ~500-line orchestrator (shared hook, hover/selection state, dispatch). The file has its own scar tissue documenting this ("Capture local copy to avoid TDZ in valueFormatter closures") — symptoms of a 2,100-line function body sharing one scope.
2. **`ChartSetupPanel.tsx`** (~1,327 lines, single component) — chart-type-specific field sections (heatmap axes, funnel config, gantt fields, scatter color/size, sankey target, annotations editor) are independent and should become per-type section components, mirroring how the widget itself was decomposed.
3. **`StudioChatPanel.tsx`** (~1,283 lines) mixes eight concerns (tool icon/label maps, send-button slot, message actions/metadata, reasoning display, suggestion generation, voice-input wiring, and thread management doing raw `controller.setState` writes). Most pieces are already module-level components, making this a low-risk split; thread management deserves its own hook (also where the Tier-1 #13 race should be fixed).
4. **`StudioKpiWidget.tsx`** — a single 330-line `useMemo` computes value, sparkline, and two trend algorithms. Extracting pure `kpiUtils` functions would also make the Tier-1 #14 gap unit-testable.
5. **Acceptable but worth watching**: `StudioWidgetCard.tsx` (~792 lines), `GridSetupPanel.tsx` (~780 lines, same pattern as `ChartSetupPanel` but milder), `StudioWidgetCardActionsOverlay.tsx` (~644 lines, fixable via the Tier-2 #8 dedup).
6. **In good shape, no action needed**: `StudioCanvas` and its drag/resize modules, `StudioFilterWidget` + controls, the already-extracted chart renderers, `StudioFiltersDrawer`'s 16-file decomposition, `StudioDataDrawer`, `Studio.tsx`/`StudioContent.tsx`, `StudioWidgetEditDialog`, and `useChartWidgetData.ts` (long but cohesive).

## Tier 4 — Testing gaps

Coverage in `internals/` is genuinely strong — every cache has invalidation tests, sync/async parity is tested, and golden fixtures pin the fan-out semantics. The UI layer's gaps are more about missing coverage on newer/larger components than about testing philosophy. Ranked by value:

1. **`StudioController`'s date-range surface has zero tests anywhere** — no test exercises `setWidgetDateRange`, `setDashboardDateRange`, or `setDashboardDateRangeAll`, which is exactly why Tier-1 #1 survived undetected.
2. **Col-span methods have zero direct tests** (`setWidgetColSpan`, `setWidgetColSpanInRow`, `setAdjacentWidgetColSpans`) — a single "drag units and AI units agree with `GRID_COLS`" test would have caught Tier-1 #2.
3. **`rcfaCache` staleness for untracked foreign sources is untested** — existing tests cover expression-field/relationship invalidation but not a refresh of the M:N remote source or a display-field-only related source (Tier-1 #3).
4. **`StudioDashboard.tsx` has zero tests** — the highest-value UI gap, since a basic "change `config` prop → new state visible" test would have caught Tier-1 #9 directly.
5. **`StudioChatPanel.tsx` has zero tests** (1,283 lines): thread create/switch/persistence, message write-back, suggestion generation, voice/composer sync.
6. **Filter presets and page-removal edge cases are untested**: `saveFilterPreset`/`applyFilterPreset`/`deleteFilterPreset`/`renameFilterPreset`, `removePage`'s active-page reassignment, and the `activePageId = ''` edge case (Tier-1 #8).
7. **Setup panels beyond `ChartSetupPanel` are largely untested** — Grid/Kpi/Map/Pivot/Filter/Format panels (~2,400 combined lines) have no tests, despite writing directly to widget config.
8. **Canvas drag-drop reducer is untested** — no test exercises `handleDrop`, so cross-page widget moves and the col-span leak (Tier-1 #17) are unguarded; extracting `handleDrop`'s pure computation and testing it directly would close this.
9. **Mock-boundary blind spot**: `StudioChartWidget.test.tsx` mocks every `@mui/x-charts` component as a prop-spy, which is fine for config assertions but structurally cannot catch integration bugs in how x-charts actually interprets those props — exactly where the ghost-opacity bug (Tier-1 #10) lives. A small number of browser-mode smoke tests asserting real rendered SVG attributes would close this class of gap.
10. **Filter widget controls**: only `ToggleControl` is tested; `MultiSelectControl`, `DateRangeControl`, and `SliderControl` are not.
11. **Locale routing is untested beyond key-set parity** — nothing renders a surface under a non-English locale and asserts translated output, which is why the Tier-2 #6/#12 gaps pass CI today.
12. **`generateInsight.ts`** (~656 lines, pure and cheap to test) and **`countryUtils.ts`** (~964 lines of pure geography-name mapping) have no tests despite feeding every AI insight / map-region rendering respectively.
13. Minor: `aggregateByTwoFields` with a non-numeric y-field is untested (where the Tier-2 #2 divergence lives); `useWidgetRows`'s deferred-value/`isRecomputing` paths lack even a smoke test.

## Summary

Top three actions by impact, in order: fix the widget-scoped date-range preset gap (Tier-1 #1 — a broken user-facing feature with a clear root cause and no test coverage); reconcile the two column-span unit systems (Tier-1 #2 — actively corrupts layouts when the AI and manual drag paths are both used on the same dashboard); and close the L4 chart-cache dependency-tracking gap using the same `collectJoinedSourceIds` pattern already proven in `resolvedRowsCache` (Tier-1 #3). Beyond that, unifying `StudioController`'s hand-written mutation methods with the shared `applyMutation` reducer (Tier-2 #1) would resolve the largest source of ongoing drift risk in one motion, since several Tier-1 bugs above already stem from the same fix existing in one implementation but not its twin.
