# Architecture

Internal reference for how `@mui/x-studio-data-middleware` is put together. For install/quick-start, see [`README.md`](./README.md).

## Overview

`@mui/x-studio-data-middleware` is a framework-agnostic (no HTTP framework imports), driver-agnostic (no literal `import ... from 'knex'` in source — `db` is duck-typed as `any` and only called through Knex's chainable builder API) server middleware. It turns a batch of widget query/mutation descriptors sent by an MUI X Studio dashboard into parameterized SQL, executed through a host-supplied Knex instance, with multi-tenant row-level security and a two-plane (data + tier) caching system.

Two pure entry points:

- `handleBatchQuery(body, claims, options)` — reads. Routes each widget query through the cheapest adequate execution tier (`client` / `server` / `db`) and caches results.
- `handleMutation(body, claims, options)` — writes (insert/update/delete). Enforces tenant-safety invariants and invalidates the read cache.

Everything else in the package exists to support those two functions. The host application is responsible for parsing the HTTP request body, calling `extractSecurityClaims()` to obtain verified claims, providing a configured Knex instance, and writing the returned response object back to the HTTP response.

**Tenancy is a required, explicit, fail-closed decision.** Both option shapes carry a mandatory `tenancy: TenancyConfig` — either `{ mode: 'multi-tenant', tenantColumn }` or `{ mode: 'single-tenant' }`. There is no default and no silent-omission path: a deployment cannot express "I forgot to configure a tenant column" and thereby fall into an unscoped, cross-tenant-leaking query. This is the correct posture for a multi-tenant security boundary — the unsafe state (no tenant predicate) must be impossible to reach by leaving a field unset; it can only be reached by explicitly declaring `single-tenant`. `compileSecurityPolicy` (the single place tenancy is interpreted) turns the declaration into a `CompiledSecurityPolicy` whose `tenancy.mode === 'multi-tenant'` is the one unambiguous tenancy check used everywhere.

## Core data flow

### Read path — `handleBatchQuery(body, claims, options)`

0. **Security policy compiled once** — before any validation or query building, `compileSecurityPolicy({ tenancy, securityColumns, columnAllowlist })` (`security/compileSecurityPolicy.ts`) resolves the row-level-security column names for every table into a single `CompiledSecurityPolicy` (`forPrimaryTable`/`forJoinedTable`/`digest`/`tenancy`) and computes its `digest` once. The same `policy` object is threaded into every widget's cache-key generation, preflight, and tier execution — no enforcement site re-runs the `perTable[table] ?? default` resolution chain itself.
1. **Table allowlist** ("Zero-Knowledge Rule"): every `widget.table` plus all `widget.joins[].table` is checked against `options.schemaAllowlist` via the shared `assertTablesAllowed()` (`shared/assertTablesAllowed.ts`), **per widget inside `processWidget`'s `try`** (thirteenth review, finding 2.1). A widget naming a non-allowlisted table yields that widget's `{ error }` result and never builds a query, while well-formed sibling widgets on the same page still resolve — upholding the per-widget error-isolation invariant instead of failing the whole batch on one bad descriptor. (The write path's `handleMutation` still rejects the whole request on a table violation — see below — since a mutation batch is not a set of independent read widgets.)
2. **Column-reference validation + resolution, once per widget** — for every widget, `validateQueryPlan(descriptor, columnAllowlist)` (`security/validateQueryPlan.ts`) runs, in order:
   - `validateHavingAliases()` (`shared/columnValidation.ts`) **unconditionally** (independent of whether a column allowlist is configured): `having[].alias` must match a declared `aggregations[].alias`, a `having` clause on a widget with no `aggregations` at all is rejected, and each `having[].value` must be a **finite number** (the documented HAVING contract is numeric-only). This is what stops HAVING from reaching arbitrary raw columns, and the value-shape check fails closed at the validation stage with a per-widget error rather than letting a non-scalar value (array/object/`undefined`) expand into malformed SQL or an opaque driver error at `applyHaving`'s `havingRaw('FUNC(??) op ?', …)` — parity with the filter path's scalar/`in`/`between`/`like` guards.
   - `validateAggregationAliases()` (`shared/columnValidation.ts`) **unconditionally**: every `aggregations[].alias` must match the safe `[A-Za-z0-9_-]+` identifier charset (see invariant 5 below).
   - `validateOutputAliases()` (module-private to `validateQueryPlan.ts`) **unconditionally**: for every projection `columns[]` entry whose logical id resolves (via `resolveAlias`) to a _different_ physical column — i.e. it will become an `outputAlias` on the plan — the logical id itself must match the same `[A-Za-z0-9_-]+` charset as `agg.alias`, checked against the single `SAFE_ALIAS_PATTERN` regex **exported from** `shared/columnValidation.ts` and imported here (previously a byte-identical module-private duplicate in each file — a charset tightened in one place couldn't silently drift out of sync with the other). This closes the one client-controlled identifier token that reaches an interpolated `db.raw('?? as ??', [physical, outputAlias])` without a charset check; a direct (non-renamed) column reference never reaches the alias position and is skipped. The charset **includes the hyphen**: the x-studio client mints expression-field logical ids as `expr-<timestamp>-<counter>` (e.g. `expr-order-country`) and sends them verbatim as the `columns[]`/`outputAlias` value, so a hyphen-excluding charset wrongly rejected _every_ join expression-field widget. The hyphen stays injection-safe because both alias positions are Knex identifier-escaped — the output alias via `db.raw('?? as ??', …)`, the aggregation alias via Knex object-form `query.sum({ [alias]: col })` — so it becomes a quoted identifier exactly like an underscore; genuinely dangerous tokens (`;`, spaces, quotes, parens) remain rejected.
   - `validateOrderByDirections()` (module-private to `validateQueryPlan.ts`) **unconditionally**: every `orderBy[].direction` must match `asc`/`desc` (case-insensitive). The direction token is interpolated straight into Knex's `.orderBy(col, direction)` clause rather than through a `?`/`??` binding, and the TypeScript `'asc' | 'desc'` type is not a runtime guarantee — the wire value can be any string/number/object — so it is constrained fail-closed, mirroring `SAFE_OPERATORS` and `SAFE_ALIAS_PATTERN`.
   - `validateDescriptorColumns()` (`shared/columnValidation.ts`), only when `options.columnAllowlist` is supplied: checks `columns`, `filters[].column`, `orderBy[].column`, `aggregations[].column`, and both sides of every `joins[].on` pair against the allowlist via the shared `checkColumnAgainstAllowlist()`, resolving each reference through `resolveAlias(descriptor, column)` first. An `orderBy[].column` that names a declared `aggregations[].alias` (e.g. ordering by a `total_revenue` aggregation alias rather than a physical column) is skipped by this check — an aggregation alias is never going to appear in a host's column allowlist, which only lists physical columns, and the alias is separately charset-validated by `validateAggregationAliases()`; this mirrors `buildPlan`'s identical `aggAliasSet.has(ob.column)` exclusion below. For a join `on` pair, the **left** side is validated against the primary table and the **right** side against the **joined** table (`join.table`) — matching the pair convention (`[primaryColumn, joinedColumn]`) so an unqualified right-side column is checked against the allowlist for the table Knex actually resolves it against at execution time, not the primary table. This check is **fail-closed**: if a referenced table has no entry in `columnAllowlist` at all, the request is rejected (a table can opt out of column checking by listing `['*']`). The same `checkColumnAgainstAllowlist()` helper is reused, unmodified, by the write path's `validateMutation()`.

     `validateQueryPlan` then resolves every column reference **once** into a `ValidatedQueryPlan` — a boundary object of pre-resolved, branded `ColumnRef`s (`table`, `joins`, `filters`, `columns`, `aggregations`, `orderBy`) carrying no `columnAliases` map and no raw logical names. Finally, when a `columnAllowlist` is configured but a widget declares no projection columns and no aggregations, it synthesizes an explicit projection from the allowlist (see `synthesizeProjectionFromAllowlist` under "Query path in detail") so Knex never emits `SELECT *` and returns un-allowlisted columns. `resolveAlias` (`shared/columnValidation.ts`) is the **one** place a logical column/field ID is resolved to its physical SQL column via `descriptor.columnAliases`, but `buildSecureQuery` (queryBuilder.ts) and `execute.ts` (SELECT/ORDER BY/aggregations) never call it themselves — they read the already-resolved `ColumnRef`s off the plan, so validation and execution structurally cannot resolve a reference differently. The `columnAliases` lookup is gated by `Object.prototype.hasOwnProperty.call` before reading (matching `applyHaving`'s own-property-gated opMap): a client-supplied `column` naming an inherited `Object.prototype` member (`"constructor"`, `"toString"`, `"__proto__"`, …) resolves to the literal `column` string, never to the truthy inherited value, which would otherwise defeat the `?? column` fallback and let a non-string `ColumnRef` reach the allowlist check or a Knex builder call. `checkColumnAgainstAllowlist`'s `allowlist[table]` lookup (and `synthesizeProjectionFromAllowlist`'s equivalent) is gated the same way, so a client-qualified table name resolving to an inherited member is treated as "no entry" and rejected fail-closed instead of bypassing the allowlist check. This validation+resolution step runs synchronously **inside each widget's `processWidget` `try` block** (thirteenth review, finding 2.1), so a validation error (unsafe alias, non-`asc`/`desc` ORDER BY direction, HAVING-alias, or column-allowlist violation) becomes that widget's `{ error }` result and never executes a query — isolated to the offending widget rather than rejecting the whole batch, matching how an unsupported filter operator or aggregation func already isolates inside `executeForTier`. Because every resolution path funnels through `resolveAlias` and `checkColumnAgainstAllowlist` validates whatever physical column comes out, an alias can only ever relabel a column the caller could already reach — never escalate past the allowlist (pinned end-to-end in `handler.test.ts`'s column-allowlist cases, across columns/filters/join.on, and in `validateQueryPlan.test.ts`'s alias-resolution-parity suite).

3. Each widget in the batch is processed **in parallel** (`Promise.all`) via `processWidget()`, threading the widget's `ValidatedQueryPlan` and the request-wide `CompiledSecurityPolicy`, with **per-widget error isolation** — a failed widget returns `{ id, rows: [], tier: 'db', rowCount: 0, error }` rather than failing the whole batch. Per widget:
   - Compute `cacheKey = generateCacheKey(claims, descriptor, undefined, policy.digest)` — folding the compiled policy's `digest` into the HMAC'd security profile so two nodes/deployments running a differently-resolved security policy (e.g. mid-rollout, tightening a `perTable` scope or locking down a `columnAllowlist`) never share a cache entry for the same claims (see `generateCacheKey` below). This call runs **inside** `processWidget`'s `try` block (seventh review, finding 2.3): `generateCacheKey` throws when no HMAC secret is configured (`CACHE_HMAC_SECRET`/`JWT_SECRET` both unset), and every widget-scoped operation must honor the per-widget error-isolation invariant — before this fix the call ran ahead of the `try`, so a missing-secret throw rejected the whole batch's `Promise.all` instead of producing this widget's `{ error }` result.
   - **Data cache check**: on a hit, return the cached rows immediately, echoing back the `tier` stored on the cache entry (falls back to `'server'` for entries written without a `tier` field — this avoids silently reporting a `'client'`-tier result as `'server'`), and echoing the `rowCount` persisted on the cache entry (falling back to `cached.rows.length` for entries written without `rowCount`) — see `CacheEntry` under "Caching layer" below. The `cacheProvider.get()` call is wrapped in its own `try`/`catch`: a throwing cache backend (e.g. Redis down) is treated as a miss — logged via `console.warn` and falling through to the DB — rather than failing the widget, since the cache sits in front of, not instead of, the authoritative DB read.
   - On a miss, call `decideTierWithCache()` (see Tier decision below), which runs `runPreflight(db, claims, descriptor, policy, plan)` on its own cache miss, to determine `'client' | 'server' | 'db'`.
   - `executeForTier(db, claims, descriptor, tier, policy, plan)` (`router/execute.ts`) builds and runs the real query via `buildSecureQuery()`: `'client'`/`'server'` tiers return raw filtered rows (SELECT/ORDER BY/LIMIT); `'db'` tier pushes a GROUP BY/aggregate query down to the database. Both tiers table-qualify unqualified ORDER BY columns (matching how SELECT/GROUP BY are already qualified) to avoid ambiguous-column errors under joins; an ORDER BY targeting an aggregation alias is left unqualified since it isn't a physical column. All three tier branches gate the LIMIT clause on `queryPlan.limit !== undefined` rather than truthiness, so a client-supplied `limit: 0` (a legitimate "return zero rows" request) actually limits to zero rows instead of being treated as "no limit" and returning every scoped row.
   - For aggregation descriptors, the reported `rowCount` is overridden to the actual number of result groups (the tier decision itself bypasses COUNT(\*) for aggregations — see below).
   - Results are written into the data cache together with the `rowCount` that produced them whenever `tier !== 'db'` **or the descriptor has no aggregations** — i.e. every `'client'`/`'server'` result, plus a non-aggregation `'db'`-tier result (routed there only because its preflight `COUNT(*)` exceeded `serverMemoryTier`, but still a plain, reusable raw-row slice — the same shape `'client'`/`'server'` return). Only a true aggregation push-down (grouped/aggregated rows, always tier `'db'`) is left uncached. Cache writes are tagged with the primary table name **and** every joined table name — tagging only the primary table would leave a joined result stale until TTL after a mutation to the joined table. Persisting `rowCount` on the entry (rather than only `rows`) is what lets a later cache hit report the same total as the original cold miss instead of the (possibly limit-truncated) `rows.length`. The `cacheProvider.set()` call is likewise wrapped in its own `try`/`catch`: the rows are already fetched from the DB by this point, so a write failure logs a warning and returns the (uncached) result rather than discarding already-successful work.
4. Returns `{ pageId, results }`.

### Tier decision (`router/tierDecision.ts`)

`decideTierWithCache()` is the single source of truth for routing:

1. **Aggregation queries** (`descriptor.aggregations?.length > 0`) are forced to tier `'db'` immediately — no COUNT(\*), no tier-cache read or write. The row count is irrelevant once the result is a set of aggregated groups rather than raw rows.
2. Otherwise, a **tier-cache hit** short-circuits: the cached `rowCount` is reused, skipping `runPreflight`, but the **tier itself is re-derived** from that `rowCount` via `tierFromRowCount(cached.rowCount, thresholds)` against the CALLER's current `thresholds` rather than trusting the cached `tier` field verbatim (seventh review, finding 2.4). `thresholds` is folded into neither the tier-cache key nor the policy digest, so a cached entry may have been written under a different threshold config (mid-rollout change, or a different node in a cluster during a deploy); re-deriving at read time makes a cached decision reinterpretable under the reader's own config with no key change and no extra I/O — only `cached.tier` was stale-prone, since `cached.rowCount` is still the true preflight count. The `tierCacheProvider.get()` call is wrapped in its own `try`/`catch`: a throwing tier-cache backend (e.g. Redis down) is treated as a miss — logged via `console.warn` and falling through to the preflight `COUNT(*)` — rather than failing the widget, mirroring the data cache's `get` guard in `handler.ts` (see the read-path step above) and closing the one gap where that posture didn't yet hold (finding 2.1). Before this fix, `decideTierWithCache` awaited `tierCacheProvider.get()`/`.set()` bare, so a down tier-cache backend was only caught by `processWidget`'s outer catch-all and turned into a per-widget **error result** — for every non-aggregation widget, even though the DB itself was healthy and the preflight could have run; aggregation widgets were immune only because they bypass the tier cache entirely (step 1).
3. On a **tier-cache miss**, `runPreflight()` (`router/preflight.ts`) runs a `COUNT(*)` through `buildSecureQuery()` (full security + user-filter predicates applied, no SELECT/columns) and `tierFromRowCount()` maps it to a tier using `DEFAULT_THRESHOLDS = { client: 10_000, server: 100_000 }` (overridable via `options.thresholds.clientTier` / `serverMemoryTier`). When a `tierCacheTtlMs` was given, the decision is persisted to the tier cache; when it was omitted, the decision is computed but not written back. The `tierCacheProvider.set()` call is likewise wrapped in its own `try`/`catch`: the tier decision is already computed by this point, so a write failure logs a warning and returns the (uncached) decision rather than discarding already-completed work (finding 2.1, mirroring the data cache's `set` guard).

### Write path — `handleMutation(body, claims, options)`

0. **Security policy compiled once for the whole batch** — `compileSecurityPolicy({ tenancy, securityColumns, columnAllowlist })` runs once at the top of `handleMutation`, before the table-allowlist check. The resulting `policy` (a `CompiledSecurityPolicy`) is threaded into `validateMutation()` and every builder call for every mutation in the batch, so the tenant/region/department resolution chain runs once per batch rather than once per mutation per builder.
1. Same upfront table-allowlist check across all mutations, via the same shared `assertTablesAllowed()` used by the read path (rejects the whole request on violation).
2. Each mutation is processed **sequentially** — a `for...await` loop in `handleMutation()`, not `Promise.all` — via `processMutation()`, with per-item error isolation (`{ id, ok: false, error }` on failure — doesn't abort the batch). Running in array order (rather than concurrently) makes a batch like `[insert row, update that row]` deterministic: the update observes the insert's effect instead of racing it. Batch sizes are small in practice, so this trades a small amount of latency for correctness.
   - `validateMutation(descriptor, claims, { writableColumns, columnAllowlist, policy })`: `update`/`delete` **must** carry at least one `where` predicate (insert is exempt) — prevents accidental full-table mutations. It resolves the table's security columns via `resolvePrimaryCols()` (a thin wrapper over `toCompiledSecurityPolicy(policy).forPrimaryTable(table)`, so a direct unit-test caller may pass raw `SecurityPolicyOptions` instead of a pre-compiled policy), rejects any table-qualified `values` key via `rejectQualifiedValueKeys()`, then calls `validateSecurityColumnValues()` (rejects a client-supplied tenant column outright, and rejects a client-supplied region/department value outside the caller's `regionIds`/`department` claims — a region-5 caller cannot stamp a row into region 6). For `insert` specifically, it additionally calls `resolveInsertScopeStamps()` purely for its fail-closed throw (see below) — a region/department-restricted caller cannot omit the column and mint an out-of-scope row. `where[].column` is validated against `columnAllowlist` (when supplied) and `values` keys against `writableColumns`, both via the shared fail-closed `checkColumnAgainstAllowlist()`.
   - Dispatch to `buildInsertMutation` / `buildUpdateMutation` / `buildDeleteMutation` via a `switch (descriptor.operation)`, each taking the same `policy` (or raw `SecurityPolicyOptions`) instead of a loose `(tenancy, securityColumns)` pair. The switch's `default` arm is unreachable in practice (`descriptor.operation` is validated against exactly `['insert', 'update', 'delete']` earlier in `processMutation`) but is not dead code: it assigns `descriptor.operation` to a `never`-typed local, so the build fails to compile if a new operation is ever added to the `MutationDescriptor['operation']` union without a corresponding `case` here, then throws a defensive "Unreachable mutation operation" error at runtime as a backstop.
   - On success, `cacheProvider.deleteByTag(descriptor.table)` evicts every cached read result tagged with that table — this is the entire cache-invalidation story; there is no manual invalidation endpoint. When `options.cacheProvider` is omitted, `handleMutation` falls back to the SAME process-wide default cache singleton (`cache/defaultProviders.ts`'s `getDefaultCache()`) that `handleBatchQuery` populates by default, so a zero-config host — one that passes no `cacheProvider` to either handler — still observes its own writes instead of the read path caching into a singleton the write path can't reach. The cache call itself is best-effort: a throwing `deleteByTag` is caught and logged rather than flipping an already-committed mutation's result to `ok: false` (which would risk a client retry inserting a duplicate row).
3. Returns `{ results }`.

## Shared predicate / security-predicate model (`src/shared/predicates.ts`)

This module is the single source of truth for row-level security and structured-filter translation, used identically by both the read path (`router/queryBuilder.ts`'s `buildSecureQuery`) and the write path (`mutations/mutationBuilder.ts`'s `buildUpdateMutation`/`buildDeleteMutation`).

- **`SAFE_OPERATORS`** — a `Set` of the only filter operators ever translated to SQL: `eq`, `neq`, `in`, `lt`, `lte`, `gt`, `gte`, `like`, `between`. An operator outside this set always throws, on both reads and writes — never silently dropped.
- **`resolvePrimarySecurityColumns(table, config, resolvedTenantColumn)`** — resolves the tenant/region/department column names for a query's _primary_ table. The tenant column is `perTable[table]?.tenant ?? resolvedTenantColumn`, where `resolvedTenantColumn` is derived from the required `TenancyConfig` (`tenancy.tenantColumn` for multi-tenant, `undefined` for single-tenant); region/department fall back to hardcoded `region_id` / `department`.
- **`resolveJoinSecurityColumns(table, config, resolvedTenantColumn)`** — resolves security columns for a _joined_ table. Joined tables are scoped **by default** (fail-closed): a joined table with no `securityColumns.perTable[table]` entry **inherits the primary table's resolved tenant/region/department column names**, so an unregistered join cannot silently fan out to every tenant's rows (the concrete leak: a tenant-filtered primary `LEFT JOIN`ed on a non-unique key like `region_id` pulling in other tenants' rows). A per-table entry (a `SecurityColumnOverride`) overrides individual column names for a table using a different convention, distinguishing **three** intents per dimension via the shared `resolveDimension()` helper: a `string` renames the column, `undefined`/absent inherits the default, and `null` **drops just that one dimension** while the others (crucially, tenant) still apply — e.g. `perTable.audit_log = { region: null, department: null }` keeps the inherited tenant predicate for a joined table that carries `tenant_id` but has no region/department column, instead of forcing a region/department-restricted caller onto the whole-table opt-out below. A genuinely shared/lookup table with no tenant column at all (e.g. a country-codes table) **opts out entirely** with the whole-entry `perTable[table] = null` sentinel, which returns `undefined` (no predicate for any dimension) — a table joins fully unscoped only when the host explicitly declares it shared.
- **`applySecurityPredicates(query, table, claims, securityColumns, mode)`** — applies `WHERE table.tenant = claims.tenantId`, `WHERE table.region IN claims.regionIds`, and `WHERE table.department = claims.department` for whichever dimensions have a configured column name and a claim. The department dimension gates on `claims.department !== undefined` (not truthiness): an empty-string `department` claim is a defined (if unusual) scope, not "unscoped," so it always emits a real predicate — `claims.department === ''` used to be indistinguishable from "no department scoping" (both falsy), which silently failed open (a caller whose department claim happened to be `''` would see/affect every department in its tenant). This mirrors the region dimension's `undefined`-vs-`[]` distinction described next. Called **before** any user-supplied filter/WHERE in every caller, so it can never be overridden or AND-ed away. Region scope distinguishes `regionIds === undefined` (this deployment is not region-scoped → no predicate) from `regionIds === []` (the caller is authorized for **zero** regions), mirroring the empty-`in` convention of `applyPredicate` via the `mode` parameter: on `'read'` an empty `regionIds` emits `whereIn(col, [])` (Knex renders `1 = 0`, matching zero rows — **not** dropped, which would fail open); on `'write'` it **throws** rather than silently widening the mutation. The `region IN (...)` list itself includes **both** the numeric `regionIds` claim values **and** their string form (`claims.regionIds.flatMap((id) => [id, String(id)])`) — reconciling this predicate with `validateSecurityColumnValues` (`mutations/mutationBuilder.ts`), which already string-normalizes region comparisons to tolerate a TEXT-typed region column. Before this, a numeric-claims deployment with a TEXT-typed region column would have its scoped reads/writes error or coerce inconsistently at this WHERE clause even though the mutation value-validator explicitly accommodated that column type. Emitting both forms keeps a NUMERIC region column matching exactly as before (the original numbers are still present in the list) while also matching a TEXT-typed one; `[].flatMap(...)` stays `[]`, so the empty-scope `1 = 0` behavior above is unaffected.
- **`applySecurityPredicatesToJoinOn(onBuilder, table, claims, securityColumns, mode)`** — the ON-clause analogue of `applySecurityPredicates`, used by `buildSecureQuery` to scope the _nullable_ side of an outer join (see "Outer-join security predicate placement" under "Query path in detail"). A joined table's security predicate placed in WHERE silently degrades a LEFT/RIGHT JOIN into an INNER JOIN — a NULL-extended row's `customers.tenant_id` is NULL, so `WHERE customers.tenant_id = :tenant` is false and the row the LEFT JOIN was meant to preserve is dropped. Emitting the identical predicate inside the JOIN's own `.on(...)` callback instead (via Knex's `andOnVal`/`andOnIn`, the ON-clause value-binding analogues of `.where`/`.whereIn`) scopes which rows _match_ the join — a matched joined row is still tenant-checked, so there is no cross-tenant fan-out — while leaving a genuinely-unmatched outer row NULL-extended and present. Both this function and `applySecurityPredicates` delegate to one shared, module-private `emitSecurityPredicates()` that decides which dimensions apply and to what values (identical region/department/tenant semantics as above); only the final `.where`/`.whereIn` vs. `.andOnVal`/`.andOnIn` calls differ, so WHERE and ON placement can never drift on scoping semantics.
- **`applyPredicates(query, predicates, mode)`** / **`applyPredicate`** — translate `FilterPredicate[]` into Knex `.where`/`.whereIn`/`.whereLike`/`.whereBetween` calls. `applyPredicate` itself emits whatever column string it is handed verbatim — table-qualification is the caller's responsibility, not this module's: on the read path, `buildSecureQuery` (`router/queryBuilder.ts`) qualifies an unqualified filter column with the primary table before calling `applyPredicates` (mirroring `execute.ts`'s `qualify()` for SELECT/GROUP BY/ORDER BY/aggregations, and closing the one column reference that used to reach Knex unqualified — finding 2.1); the write path never joins, so the mutation builders pass `where[].column` through unqualified. The `mode: 'read' | 'write'` parameter governs one deliberate divergence:
  - An empty `in` list means "match nothing." On `'read'` this is a no-op and the predicate is silently dropped (mirrors the client's empty-selection semantics — a widget with no selected values should show nothing extra removed).
  - On `'write'`, dropping an empty `in` would silently widen a scoped UPDATE/DELETE into an unscoped, full-tenant mutation, so it **throws** instead.
  - An unrecognized operator always throws, in both modes.
  - Every value-bearing operator runtime-guards its value's shape before touching it, since `FilterPredicate.value`'s TypeScript shape is not a runtime guarantee (it is client JSON): `in` requires `Array.isArray` (a bare string's truthy `.length` would otherwise slip past the empty-list check), `between` requires a two-element array (whose `const [lo, hi] = value` destructure would silently yield `undefined` bounds), `like` requires a string, and the scalar comparison operators (`eq`/`neq`/`lt`/`lte`/`gt`/`gte`) require a scalar — string/number/boolean/Date, with `null` deliberately allowed so the `eq`/`neq` cases can special-case it to `.whereNull`/`.whereNotNull` (`col IS NULL` / `col IS NOT NULL`); the 3-arg `.where(col, '=', null)` renders the never-true `col = NULL` (Knex's null→whereNull conversion applies only to the 2-arg / `'is'` forms), so `eq null` / `neq null` route through `.whereNull` / `.whereNotNull` explicitly rather than silently matching zero rows; a non-scalar object/array/`undefined` **throws** a clear per-widget error (fourteenth review, finding 3.1 extended the `in`/`between` precedent to `like`/scalar). Separately, `descriptor.limit` is validated to a non-negative integer in the unconditional `validateQueryPlan` stage (finding 3.1), so a malformed `limit` becomes a per-widget `{ error }` rather than being silently coerced by the DB driver into returning every tenant-scoped row. All of these remain fully parameterized — they are robustness/fail-closed-error-message guards, not new security boundaries.

Both `buildSecureQuery` (reads) and `buildUpdateMutation`/`buildDeleteMutation` (writes) call `applySecurityPredicates` (or, for the nullable side of an outer join on the read path, `applySecurityPredicatesToJoinOn`) first, then `applyPredicates` with the appropriate `mode`, guaranteeing the tenant/region/department scope is applied identically and cannot be bypassed from either path. Mutations never build joins, so they only ever use the WHERE-clause emitter.

## Security & claims model

### `JwtSecurityClaims` (`src/security/authTypes.ts`)

```ts
interface JwtSecurityClaims {
  tenantId: string; // primary isolation boundary
  userId: string;
  roleIds: string[];
  regionIds?: number[]; // optional row-level region restriction
  department?: string; // optional row-level department restriction
}
```

The package never authenticates; it only consumes pre-verified claims that the host constructs (typically via `extractSecurityClaims`).

### `SecurityColumns` / `SecurityColumnsConfig` / `TenancyConfig` (`src/security/authTypes.ts`)

```ts
interface SecurityColumns {
  tenant?: string;
  region?: string;
  department?: string;
}

interface SecurityColumnOverride {
  // A `string` renames the dimension's column for this table; `undefined`/absent
  // inherits the default; `null` DROPS just this one dimension (keeping the
  // others) — e.g. `{ region: null }` stays tenant-scoped but emits no region
  // predicate, for a joined table that carries `tenant_id` but has no region column.
  tenant?: string | null;
  region?: string | null;
  department?: string | null;
}

interface SecurityColumnsConfig {
  region?: string;
  department?: string;
  // An object (`SecurityColumnOverride`) overrides individual column names, or
  // drops an individual dimension via a per-dimension `null`. A whole-entry
  // `null` marks a shared/lookup table (no tenant column) that must join
  // UNSCOPED — distinct from a per-dimension `null`, which drops only that
  // dimension while keeping the table scoped on the others.
  perTable?: Record<string, SecurityColumnOverride | null>;
}

type TenancyConfig = { mode: 'multi-tenant'; tenantColumn: string } | { mode: 'single-tenant' };
```

The global tenant column is declared in exactly one place — the **required** `tenancy` posture (`HandleBatchQueryOptions.tenancy` / `HandleMutationOptions.tenancy`): `{ mode: 'multi-tenant', tenantColumn }` applies a tenant predicate everywhere; `{ mode: 'single-tenant' }` applies none. There is no silent-omission default — a deployment must declare its posture, so it cannot fall into an unscoped, cross-tenant-leaking state by leaving the tenant column unset. This is enforced at RUNTIME, not just in the `TenancyConfig`/`SecurityColumnOverride` types (seventh review, finding 2.1): `compileSecurityPolicy` throws when `tenancy.mode === 'multi-tenant'` and `tenantColumn` is empty/whitespace-only/non-string — the realistic misconfiguration is a column name wired to an unset environment variable — since the downstream resolvers and the `mutationBuilder.ts` force-stamp/rejection sites gate on truthiness and would otherwise silently treat an empty `tenantColumn` as "not scoped." The top-level `region`/`department` act as defaults for the primary table (defaulting further to `'region_id'` and `'department'`); `perTable[table].tenant` overrides the tenant column for one table, `perTable[table] = { region: null }` (or `department: null`) drops just that one dimension for a table while it stays scoped on the others, or `perTable[table] = null` opts a shared/lookup table out entirely — see `resolveJoinSecurityColumns` above. An empty/whitespace-only/non-string value for any of these per-table dimension overrides, or for the top-level `securityColumns.region`/`department`, is rejected the same fail-closed way — only `undefined` (inherit) and `null` (documented drop) are valid non-rename values. A `single-tenant` deployment that also sets a `perTable[table].tenant` is a contradiction and `compileSecurityPolicy` throws. `securityColumns` is passed as `HandleBatchQueryOptions.securityColumns` / `HandleMutationOptions.securityColumns` and consumed exclusively through `src/shared/predicates.ts`.

### `CompiledSecurityPolicy` (`src/security/compileSecurityPolicy.ts`)

`compileSecurityPolicy(opts: SecurityPolicyOptions)` is the single boundary object every enforcement site resolves security columns through, instead of each site running the `perTable[table]?.X ?? default` chain itself:

```ts
interface SecurityPolicyOptions {
  tenancy: TenancyConfig; // REQUIRED
  securityColumns?: SecurityColumnsConfig;
  columnAllowlist?: Record<string, string[]>; // folded into the digest only
}

interface CompiledSecurityPolicy {
  forPrimaryTable(table: string): SecurityColumns;
  forJoinedTable(table: string): SecurityColumns | undefined; // undefined only for perTable[table] = null
  readonly digest: string;
  readonly tenancy: TenancyConfig;
}
```

- `forPrimaryTable`/`forJoinedTable` delegate to `resolvePrimarySecurityColumns`/`resolveJoinSecurityColumns` (`shared/predicates.ts`) — compiling changes **where** the resolution chain runs (once, at the top of `handleBatchQuery`/`handleMutation`), never **what** it resolves to for a given table.
- `digest` is a stable SHA-256 (16 hex chars) via `computePolicyDigest()` over the `sortedStringify`'d `{ tenancy, securityColumns }` pair **plus `columnAllowlist` when supplied**. It is computed once at compile time and folded into `generateCacheKey`'s security hash (see below). Folding `securityColumns`/`tenancy` in means two nodes running a differently-resolved policy never serve one another's cached rows for the same claims. Folding `columnAllowlist` in means tightening which columns a client may see produces a different cache key, so results computed under a looser allowlist can never be served stale after the host locks column visibility down. The `columnAllowlist` key is only present in the hashed input when supplied (and each per-table column list is sorted first for order-independence), so an omitted allowlist yields a digest byte-identical to one computed without the field.
- The `single-tenant` + `perTable[table].tenant` contradiction check runs inside `compileSecurityPolicy` itself (a `single-tenant` deployment applies no tenant predicate, so a per-table tenant scope would either be silently ignored — reintroducing a cross-tenant leak — or silently contradict the declared mode; it throws rather than resolve the ambiguity either way). A region/department-only override or a `perTable[table] = null` opt-out does not trip it.
- `compileSecurityPolicy` also validates every column-name-shaped input at RUNTIME before returning (seventh review, finding 2.1): a `multi-tenant` `tenantColumn` that is empty/whitespace-only/non-string throws immediately, and so does an empty/whitespace-only/non-string per-table dimension override or top-level `region`/`department` value — via the module-private `isUsableColumnName()`/`assertOptionalColumnName()` helpers. `undefined` (inherit the default) and `null` (the documented drop/opt-out sentinel) are unaffected; only the undocumented empty-string value — which `resolveDimension('')` would otherwise return verbatim, and which every downstream truthiness gate (`if (securityColumns.tenant)`, the mutation force-stamp/rejection checks) silently treats as "not scoped" — is rejected. This closes the fail-open path where a deployment believes it declared `multi-tenant` (e.g. `tenantColumn: process.env.TENANT_COLUMN!` with the variable unset) but every read/write actually ran fully unscoped across tenants.
- `isCompiledSecurityPolicy()` / `toCompiledSecurityPolicy()` implement a dual-acceptance pattern used by `buildSecureQuery`, `runPreflight`, `executeForTier`, and every mutation builder: the request path always threads an already-compiled policy through (returned as-is, no recompile); a direct unit-test caller may instead pass the raw `SecurityPolicyOptions`, which is compiled on the spot. `SINGLE_TENANT_POLICY_DIGEST` is the digest of `{ mode: 'single-tenant' }` with no `securityColumns`/`columnAllowlist`, used as `generateCacheKey`'s default `policyDigest` for direct callers that don't pass one.
- `handleBatchQuery` compiles one policy for the whole batch; `handleMutation` compiles one policy for the whole batch of mutations. Neither recompiles per widget/mutation.

`ValidatedQueryPlan` (`src/security/validateQueryPlan.ts`) is the read-path analogue — see "Query path in detail" below.

### Canonical serialization (`src/security/canonicalize.ts`)

`sortedStringify(obj)` is the single deterministic serializer shared by the cache-key hashes (`cacheKey.ts`'s `computeSecurityHash` / `computeQueryHash`) and the policy digest (`compileSecurityPolicy.ts`'s `computePolicyDigest`). It recursively sorts object keys alphabetically at every depth, so property insertion order never affects the output, while **array element order is preserved and IS significant** (two inputs whose arrays differ only in order serialize differently). `undefined` serializes via plain `JSON.stringify` semantics (distinct from `null`). Both behaviors are load-bearing for existing hashes. Keeping one implementation guarantees the security hash and the policy digest can never canonicalize identical inputs differently — the function is deliberately not forked into per-file copies.

### `extractSecurityClaims` (`src/security/extractSecurityClaims.ts`)

A demonstration HMAC-SHA256 (HS256) JWT verifier — pure, no HTTP dependency — intended to be replaced in production with a real IdP verification library (`jose`, `jsonwebtoken`, etc.). It:

- Requires a non-empty `jwtSecret` (defaults to `process.env.JWT_SECRET`); throws if empty rather than verifying against an empty key (an empty key would accept forged tokens — no authentication).
- Parses `"Bearer <token>"`, splits the JWT into header/payload/signature, and recomputes the HS256 signature over `header.payload`.
- Compares expected vs. actual signature lengths **before** calling `timingSafeEqual` (which otherwise throws a `RangeError` on mismatched lengths instead of failing cleanly) — a truncated/garbage signature surfaces as a normal auth error.
- Checks `exp` against the current time, and requires `tenantId` and `sub` in the payload.
- Validates and coerces the payload's `regionIds` claim to `number[]` via `normalizeRegionIds()`: the JWT payload is client-controlled JSON, so the `regionIds?: number[]` field on `JwtPayload` is typed `unknown` at this boundary and only `normalizeRegionIds()` establishes the runtime guarantee. `undefined` passes through as `undefined` (not region-scoped); a non-array throws; each element is coerced to a number (accepting a numeric string) and a non-finite/non-numeric/object/`null` element throws. This closes a cache-key-fragmentation footgun: `computeSecurityHash` (`cacheKey.ts`) sorts `regionIds` with `(a, b) => a - b`, a no-op/`NaN`-producing comparator on strings, so an unvalidated string-typed claim (e.g. `["5","6"]`) could leave two callers with the same regions in a different order hashing to different cache keys. This was never a scope-bypass (the security predicate and mutation value-validator already string-normalize region comparisons) — validating here fails closed instead of letting a malformed claim silently degrade cache efficiency deeper in the pipeline.
- Returns `{ tenantId, userId: sub, roleIds, regionIds, department }`, with `regionIds` now guaranteed `number[] | undefined`.

### `generateCacheKey` (`src/security/cacheKey.ts`)

`generateCacheKey(claims, descriptor, hmacSecret?, policyDigest?)` produces a key of the form `studio:v1:<encodeURIComponent(tenantId)>:<securityHash>:<queryHash>`:

- **`securityHash`** — HMAC-SHA256 (16 hex chars) over a `sortedStringify`'d `{ tenantId, regionIds (sorted), department, policyDigest }` profile, keyed by `hmacSecret` (defaults to `process.env.CACHE_HMAC_SECRET ?? process.env.JWT_SECRET ?? ''`). `policyDigest` is the compiled security policy's `digest` (`CompiledSecurityPolicy.digest`); it defaults to `SINGLE_TENANT_POLICY_DIGEST` when the caller omits it, so direct callers (e.g. unit tests) that don't pass one stay deterministic and match a single-tenant deployment. Folding the policy digest in means two callers with identical claims but a differently-resolved security policy (tenancy, `securityColumns`, or `columnAllowlist`) get different hashes — and therefore never share a cache entry. Users with identical row-level permissions AND identical policy digests intentionally share a hash (and thus a cache entry) for cache efficiency. Memoized in a module-level `Map` bounded to `MAX_MEMO_SIZE = 1_000` entries (oldest evicted on overflow) so the HMAC cost is paid at most once per unique `(hmacSecret, permission set, policyDigest)` combination.
- **`queryHash`** — SHA-256 (16 hex chars) over the widget descriptor with `id` excluded (so two structurally identical widgets share a cache entry), serialized via `sortedStringify` (so property insertion order never affects the hash; array/filter order is preserved and _does_ affect it).
- The tenant segment is `encodeURIComponent(claims.tenantId)`, not the raw `tenantId`: `LRUCacheProvider.extractPrefix` recovers the tenant-scoped invalidation prefix by scanning to the 3rd colon, so a `tenantId` containing a `:` (e.g. `org:1234`) would otherwise shift every segment boundary and collapse distinct colon-prefixed tenants into one `invalidatePrefix` eviction bucket. Encoding keeps the tenant a single colon-free segment; a tenant id without a colon (the common case) is unchanged, so existing keys stay byte-identical. This affects only the plaintext tenant segment/prefix-invalidation granularity — the HMAC'd `securityHash` already covers `tenantId` verbatim, so it was never a cross-tenant read/collision risk.
- Throws if no HMAC secret is configured — an empty key would make the security hash guessable, breaking the "a client can't forge another tenant's cache key" guarantee.
- `handler.ts` always calls it as `generateCacheKey(claims, descriptor, undefined, policy.digest)`, letting `hmacSecret` fall back to the environment variable while explicitly threading the request's compiled policy digest.

## Query path in detail

### `buildSecureQuery` (`router/queryBuilder.ts`)

Signature: `buildSecureQuery(db, claims, descriptor, options: CompiledSecurityPolicy | SecurityPolicyOptions, plan?: ValidatedQueryPlan)`. `plan` is the pre-compiled `ValidatedQueryPlan` threaded from the handler on the request path; a direct (unit-test) caller that omits it gets one resolved on the spot via `toValidatedQueryPlan(descriptor)` (resolution only — the validators are **not** re-run, since these direct callers were never routed through `handleBatchQuery`'s validation). `options` is likewise resolved via `toCompiledSecurityPolicy(options)` — the already-compiled policy on the request path, or a freshly-compiled one for a direct caller passing raw `SecurityPolicyOptions`.

Given the resolved `queryPlan` and `policy`, builds (but does not execute) a Knex query in this order:

1. **Joins** — for each `queryPlan.joins[]` (already alias-resolved: every `on` pair carries physical `ColumnRef`s on both sides, the identical resolution `validateDescriptorColumns` checked against the allowlist), a single `join`/`leftJoin`/`rightJoin` call with one `.on()` per `[left, right]` pair inside a callback, so a composite-key join produces one join clause, not one per pair (avoiding "table name not unique" SQL errors). Each `on` pair is table-qualified before being handed to `.on()`: an unqualified left column is prefixed with the **primary** table and an unqualified right column with `join.table`, mirroring the left→primary/right→joined convention `validateDescriptorColumns` already uses to check the same pair against the allowlist, while a column already containing a `.` (a client-qualified reference) is left untouched — this closes the ambiguous-identifier error Postgres/MySQL raise when an unqualified `on` column shares a name across both joined tables, e.g. `region_id`/`id`/`tenant_id` in a multi-tenant schema (finding 2.1, sixth review). This function never calls `resolveAlias` itself — it only reads the plan's pre-resolved `ColumnRef`s. For an outer join, the ON callback also emits the nullable side's security predicate directly into the ON clause via `applySecurityPredicatesToJoinOn` (`shared/predicates.ts`) — see "Outer-join security predicate placement" below.
2. **Security predicates** — `applySecurityPredicates` (in `'read'` mode) for the primary table (via `policy.forPrimaryTable(queryPlan.table)`) unless the primary table is itself the nullable side of a RIGHT join (in which case its predicate already went into that join's ON clause in step 1), then for each joined table that is not the nullable side of a LEFT join (via `policy.forJoinedTable(join.table)`, which scopes the joined table by default with the inherited primary columns and only no-ops for a table explicitly opted out via `perTable[table] = null`).
3. **User filters** — every other column reference on the read path is table-qualified to avoid "ambiguous column" errors under joins (SELECT/GROUP BY/ORDER BY/aggregations via `execute.ts`'s `qualify()` — including a renamed (expression-field) projection column's physical source, see "Query path in detail" below — all three security-predicate dimensions, and the join `on` pair qualified in step 1 above), and user filter predicates follow the same convention: `buildSecureQuery` maps `queryPlan.filters` through a qualify-if-no-dot pass — an unqualified resolved filter column is prefixed with the **primary** table, while a column already containing a `.` (a client-qualified reference, e.g. `customers.region_id`) is left untouched — before calling `applyPredicates(query, qualifiedFilters, 'read')`, which builds the WHERE clause against these table-qualified, already-resolved physical columns (the identical resolution `validateDescriptorColumns` already applied when checking the column against `columnAllowlist`) — no re-resolution happens here. With the join `on`-pair qualification in step 1, every read-path column reference that reaches raw SQL is now table-qualified — the join `on` pair was the last remaining exception, closed by the sixth review's finding 2.1.
4. **HAVING** — `applyHaving()` for each `queryPlan.having[]` entry. The HAVING operator is mapped through a fixed `{ eq, gt, lt, gte, lte }` table, gated by an own-property check (`Object.prototype.hasOwnProperty.call(opMap, h.operator)`) before the lookup — since `opMap` is a plain object literal inheriting from `Object.prototype`, an unguarded bracket lookup would let a client-supplied operator naming an inherited member (`"toString"`, `"constructor"`, `"valueOf"`, …) resolve to a truthy inherited function and defeat a bare falsiness check. The own-property guard restricts the lookup to the five real operator keys, matching the same fail-closed allowlist posture as `SAFE_OPERATORS` on the filter path; anything else throws. The emitted SQL itself re-derives the **aggregate expression** — `query.havingRaw('FUNC(??) op ?', [physical, value])`, `FUNC` from a fixed five-entry map (`sum`/`avg`/`count`/`min`/`max`) keyed by the matching `PlanAggregation.func` — rather than referencing the SELECT output alias; see "HAVING re-emits the aggregate expression" below.

#### Outer-join security predicate placement

A joined table's row-level security predicate placed in the WHERE clause silently degrades a LEFT/RIGHT JOIN to an INNER JOIN: for `orders LEFT JOIN customers`, an `orders` row with no matching customer produces a NULL-extended row whose `customers.tenant_id` is NULL, so `WHERE customers.tenant_id = :tenant` is false and the row the caller explicitly asked to keep via the LEFT JOIN is dropped. The symmetric case holds for a RIGHT JOIN via the _primary_ table's WHERE predicate.

`buildSecureQuery` avoids this by routing the nullable side's predicate into the join's own ON clause instead of WHERE:

- `type: 'left'` — the joined (right) table is nullable, so `policy.forJoinedTable(join.table)`'s predicate is emitted inside that join's `.on(...)` callback via `applySecurityPredicatesToJoinOn`; the joined table is skipped in the WHERE-clause loop.
- `type: 'right'` — the primary (left) table is nullable, so `policy.forPrimaryTable(queryPlan.table)`'s predicate is emitted inside that join's ON clause instead; the primary table is skipped in its usual WHERE-clause application.
- `type: 'inner'` (the default) — both sides are non-nullable, so WHERE placement is equivalent and unchanged.

`applySecurityPredicatesToJoinOn` (`shared/predicates.ts`) uses Knex's `andOnVal`/`andOnIn` — the ON-clause analogues of `.where`/`.whereIn` that bind their value argument as a VALUE, not an identifier — so the tenant/region/department values stay parameterized exactly as on the WHERE path. Scoping the predicate in ON still tenant-checks every _matched_ joined row (no cross-tenant fan-out through a join); it only stops a security predicate from discarding a genuinely-unmatched outer row. Both `applySecurityPredicates` (WHERE) and `applySecurityPredicatesToJoinOn` (ON) delegate to one shared `emitSecurityPredicates()` implementation that decides _which_ dimensions apply and to what values — only the final `.where`/`.andOnVal` and `.whereIn`/`.andOnIn` calls differ between them — so the two placements can never drift on the region `undefined`-vs-`[]` distinction, the department empty-string distinction, or the numeric+string region matching.

#### HAVING re-emits the aggregate expression

`havingRaw('?? op ?', [alias, value])` — referencing the SELECT output alias — is invalid on PostgreSQL (`42703 column "..." does not exist`); PostgreSQL (and standard SQL) does not allow a HAVING clause to reference a SELECT-list alias, though MySQL/SQLite tolerate it (why the jsdom `mockDb` suite, which is not a real SQL engine, never caught this). `applyHaving()` instead looks up the matching `PlanAggregation` for `h.alias` (guaranteed to exist on the request path, since `validateHavingAliases` already rejected a mismatched alias) and re-emits `FUNC(??) op ?` with `FUNC` from a fixed `{ sum: 'SUM', avg: 'AVG', count: 'COUNT', min: 'MIN', max: 'MAX' }` map and the aggregation's physical column (table-qualified if not already, mirroring how `execute.ts` qualifies SELECT/GROUP BY/aggregate columns). The column identifier stays `??`-bound and the value `?`-bound; only fixed, own-property-gated tokens (`FUNC`, the mapped SQL operator) are ever interpolated as raw text. This is valid on MySQL/SQLite/PostgreSQL alike, closing the one dialect-portability gap in an otherwise driver-agnostic package.

### `validateQueryPlan` and the typed plan (`security/validateQueryPlan.ts`)

`ValidatedQueryPlan` is the read-path boundary object produced once per widget. Every field is already alias-resolved; it deliberately carries **no `columnAliases` map and no raw logical column names**, so the ambiguous client form is structurally unreachable past this boundary. `ColumnRef` is a branded `string` (`string & { __brand: 'ColumnRef' }`) whose only mint point is `asColumnRef()` inside this module — a downstream function that wants a `ColumnRef` cannot be handed an unresolved raw logical name, and TypeScript enforces that structurally rather than by convention. The plan's fields:

- `columns: PlanProjectionColumn[]` — each carries a `physical` `ColumnRef` and, only for an expression field whose logical id differs from its physical column, an `outputAlias` (executed as `physical AS outputAlias`).
- `filters: ResolvedFilterPredicate[]` — the `FilterPredicate` union with `column` narrowed to `ColumnRef`.
- `joins: ResolvedJoin[]` — every `on` pair carries a `ColumnRef` on both sides.
- `aggregations: PlanAggregation[]` — `physical`/`func`/`alias`, plus a precomputed `pureMeasure` (`agg.alias === agg.column` on the raw descriptor) flagging a measure like `SUM(total) AS total` that must appear only in the aggregate clause, never in GROUP BY.
- `orderBy: PlanOrderBy[]` — either an `aggAlias` (an ORDER BY targeting an aggregation alias — not a physical column, used as-is) or a `physical` `ColumnRef` (table-qualified at execution time).
- `having`, `table`, `limit` — carried through unchanged.

`validateQueryPlan(descriptor, columnAllowlist?)` runs five validators in order (`validateHavingAliases`, `validateAggregationAliases`, `validateOutputAliases`, `validateOrderByDirections` — all unconditional — then `validateDescriptorColumns` only when a `columnAllowlist` is supplied), builds the plan via pure `resolveAlias` resolution, and finally, when a `columnAllowlist` is configured for a widget with no columns and no aggregations, calls **`synthesizeProjectionFromAllowlist()`** to close the `SELECT *` allowlist-bypass: without it, Knex would emit `SELECT *` and return every column, including ones the host never allowlisted. That helper:

- throws fail-closed (mirroring `checkColumnAgainstAllowlist`'s "has no entry" error, so the extracted error code matches) when the table has no allowlist entry;
- for a `['*']` wildcard entry, synthesizes an explicit primary-table wildcard projection (`<table>.*`) rather than leaving the projection empty — `['*']` means "all columns of this table," not a bare `SELECT *`, so a bare-`*` projection would leak every column of any joined table regardless of its own (stricter) allowlist entry;
- otherwise synthesizes an explicit projection of exactly the allowlisted physical columns (no `outputAlias`), which `executeForTier`'s `qualify()` prefixes with the primary table.

Aggregation widgets are exempt from the synthesis — the db tier emits only aggregation/GROUP BY clauses, never `SELECT *`.

`isValidatedQueryPlan()` / `toValidatedQueryPlan()` mirror `compileSecurityPolicy`'s dual-acceptance: an already-compiled plan is returned as-is; a raw descriptor from a direct caller is resolved on the spot via `buildPlan` — **without** re-running the validators, deliberately, so `buildSecureQuery`/`executeForTier`'s direct (test) callers keep their no-throw resolution-only behavior.

### `runPreflight` (`router/preflight.ts`) / `executeForTier` (`router/execute.ts`)

`preflight.ts` holds only the COUNT(\*) logic; the tier-specific SELECT/GROUP BY/aggregate construction lives in the sibling `router/execute.ts`. Both take the same `(db, claims, descriptor, tier?, options: CompiledSecurityPolicy | SecurityPolicyOptions, plan?: ValidatedQueryPlan)`-shaped arguments as `buildSecureQuery` and forward `options`/`plan` to it unchanged.

- `runPreflight()` calls `buildSecureQuery(db, claims, descriptor, options, plan).count('* as row_count')` and returns just the numeric row count (coercing a string result, defaulting a missing result to zero). It does not decide the tier itself — that logic lives entirely in `tierDecision.ts`.
- `executeForTier()` resolves `queryPlan = plan ?? toValidatedQueryPlan(descriptor)` and reads pre-resolved `ColumnRef`s off it (`PlanProjectionColumn`, `PlanAggregation`, `PlanOrderBy`) — it never calls `resolveAlias` itself:
  - `'client'`/`'server'`: rebuilds via `buildSecureQuery`, adds a `.select()` projecting each `queryPlan.columns` entry via the shared `projectColumn()` helper — a direct (non-renamed) column is table-qualified via `qualify()` to avoid join ambiguity, and an entry with an `outputAlias` (a renamed expression-field column) SELECTs `qualify(physical) AS outputAlias` via `db.raw('?? as ??', [qualify(col.physical), col.outputAlias])`: the source column is qualified in both branches, since an unqualified renamed column is exactly as ambiguous under a join as an unqualified direct one (finding 2.2 — only the SELECT-list source is qualified; the output row key, `outputAlias`, is untouched, so client row shapes are unaffected) — then `.orderBy()`/`.limit()`. ORDER BY columns are table-qualified the same way SELECT columns are (a `PlanOrderBy` carrying `aggAlias` is left as-is, since it isn't a physical column) — this applies to both tiers, not just SELECT/GROUP BY. The `.limit()` call is gated on `queryPlan.limit !== undefined`, not truthiness, so `limit: 0` actually limits to zero rows rather than being silently treated as "no limit."
  - `'db'`: a query reaches this tier either because it declares `aggregations`, or because it's a plain (non-aggregation) descriptor whose preflight `COUNT(*)` exceeded `serverMemoryTier` (`tierFromRowCount()` routes purely on row count, independent of whether the descriptor aggregates). When `queryPlan.aggregations.length === 0`, the branch falls back to the same plain `select`/`orderBy`/`limit` shape the `client`/`server` tiers use (including the same `!== undefined` LIMIT gating) and returns plain raw rows — cached by `handler.ts` exactly like the `client`/`server` tiers (see the read-path step above), since a large-but-non-aggregated slice is just as reusable — rather than running the GROUP-BY/aggregate logic below — that logic assumes aggregation push-down, and running it with no aggregations would either GROUP BY every projected column (silently de-duplicating rows the other tiers return raw) or, with no columns either, emit an unbounded `SELECT *` over a tenant slice already known to exceed the server-memory threshold. When aggregations are present, it rebuilds via `buildSecureQuery`, splits `queryPlan.columns` into GROUP BY dimension columns vs. pure-measure columns (`PlanAggregation.pureMeasure` flags columns whose aggregation alias equals the column name, e.g. `SUM(total) AS total`, which must appear only in the aggregate clause, not GROUP BY), qualifies unqualified columns with the primary table to avoid ambiguous-column errors under joins, applies `.sum()/.avg()/.count()/.min()/.max()` per `PlanAggregation` (each called with Knex's object/alias-map form, `query.sum({ [agg.alias]: col })`, not a string-interpolated `` `col as alias` `` fragment; an `agg.func` outside this set is rejected with a clear per-widget error rather than silently omitted from the query), then `.orderBy()` (mapping a `PlanOrderBy` with `aggAlias` to itself, and otherwise table-qualifying its `physical` column) and `.limit()` (again gated on `queryPlan.limit !== undefined`).

## Mutation path in detail (`mutations/mutationBuilder.ts`)

Every function below takes `policy: CompiledSecurityPolicy | SecurityPolicyOptions` — the compiled policy threaded once from `handleMutation` on the request path, or raw `SecurityPolicyOptions` for a direct unit-test caller — and resolves the primary table's security columns via the local `resolvePrimaryCols(table, policy)` helper, which calls `toCompiledSecurityPolicy(policy).forPrimaryTable(table)`. There is no legacy string/loose-option arm: the only way to configure tenancy is the `tenancy` field inside `SecurityPolicyOptions`/`CompiledSecurityPolicy`.

- **`rejectQualifiedValueKeys(values, table)`** — a shared module-private guard: any `values` key containing a `.` is rejected. Mutation `values` always target exactly one table, so keys must be bare column names. A table-qualified key (`orders.region_id`) is malformed on two counts — Knex would render it as a qualified identifier in an INSERT column list / UPDATE SET clause (invalid SQL on mainstream databases), and, more importantly, it would slip past `validateSecurityColumnValues`'s bare-name scope matching, letting a caller stamp a value outside their scope. It is called both inside `validateMutation` and, as defense in depth, again at the top of `buildInsertMutation`/`buildUpdateMutation` so a direct caller that skips validation still cannot reach the Knex payload with a dotted key.
- **`validateMutation(descriptor, claims, { writableColumns, columnAllowlist, policy })`** — requires `where` for `update`/`delete`; resolves the table's security columns via `resolvePrimaryCols()`; validates `where[].column` against `columnAllowlist` (when supplied) and `values` keys against `writableColumns`, both via the shared `checkColumnAgainstAllowlist()` (fail-closed, `'*'`-aware — a referenced table with no allowlist entry is rejected). It calls `rejectQualifiedValueKeys()` then `validateSecurityColumnValues()`, which throws if the client-supplied `values` set the tenant column directly, or set a region/department value outside the caller's `claims.regionIds`/`claims.department` — independent of the writable-columns check. The department comparison gates on `claims.department !== undefined` (not truthiness), so an empty-string department claim is enforced the same as any other defined department rather than being treated as "unscoped" (finding 3.3 — the old truthiness check let a `department: ''` claim write any department value unchecked). Before comparing a supplied region value against the caller's permitted regions, it first rejects a non-scalar (array/object) region value fail-closed: `String([5])` is `"5"`, so an array value would otherwise coincidentally stringify-match a permitted `regionIds` entry and slip a non-scalar into the region column. For a scalar value, the comparison normalizes both sides to strings (`claims.regionIds.some((id) => String(id) === String(region))`) rather than relying on `Array.prototype.includes`'s strict SameValueZero equality — `claims.regionIds` is typed `number[]`, but a deployment whose region column is TEXT-typed sends a string value (`"5"`), and a strict comparison would never match it against `[5]`, rejecting a legitimately-scoped write with a confusing "outside the caller's permitted regions" error; normalizing keeps the check fail-closed (a value truly outside the permitted set still throws) while tolerating the numeric/string mismatch. A caller with `regionIds: []` (authorized for zero regions) is rejected for **any** region value (`[].some(...)` is always false), while `regionIds: undefined` leaves region unconstrained.
- **`resolveInsertScopeStamps(values, claims, cols)`** — INSERT-only, fail-closed region/department scope. Tenant is force-stamped on INSERT unconditionally (below), but before this helper existed region/department were validated only **when the client supplied them** (`validateSecurityColumnValues` gates on `hasOwnProperty`), so a region-restricted caller could simply omit `region_id` and mint a region-NULL row that escapes its own row-level read scope (bounded within the tenant, but visible to region-unrestricted users). This helper closes that gap: for each of region/department, if the caller carries a scope (`claims.regionIds !== undefined` / `claims.department !== undefined` — again gating department on definedness rather than truthiness, so an empty-string department claim is a real scope to stamp, not a no-op) and the column is configured but **absent** from `values`, it either derives an unambiguous in-scope value to stamp — a single authorized region (`claims.regionIds.length === 1`) or the caller's own (single-valued) department — or, when the server cannot unambiguously pick one (zero or multiple authorized regions), **throws** rather than silently letting the row land out of scope. A region/department value the client **did** supply is left untouched here and validated for in-scope-ness by `validateSecurityColumnValues` instead. Returns only the stamps to apply/throw-check; it never mutates `values`, so `validateMutation` can call it purely for the throw (discarding the stamps) while `buildInsertMutation` calls it again to actually apply them.
- **`buildInsertMutation(db, claims, descriptor, policy)`** — rejects qualified keys, then resolves the tenant column via `resolvePrimaryCols(table, policy)` and unconditionally sets `values[cols.tenant] = claims.tenantId` (overriding any client-supplied value), then merges in `resolveInsertScopeStamps(values, claims, cols)`'s region/department stamps, before `db(table).insert(values)`. Resolving through the compiled policy (the required `tenancy` posture, with an optional `securityColumns.perTable[table].tenant` override) is what makes INSERT tenant-stamping match how reads/updates/deletes resolve the same column. The tenant force-stamp, the region/department fail-closed omission stamp/throw (`resolveInsertScopeStamps`), AND the present-value scope check (`validateSecurityColumnValues`, which rejects a client-supplied region/department value outside the caller's claims) all run again here even for a direct caller that skips `validateMutation`, as defense in depth (fourteenth review, finding 3.2 — the builders now re-apply the present-value check too, not only tenant + insert-omission, so their defense-in-depth is symmetric with `validateMutation`).
- **`buildUpdateMutation(db, claims, descriptor, policy)`** / **`buildDeleteMutation(db, claims, descriptor, policy)`** — resolve security columns via `resolvePrimaryCols()`, call `applySecurityPredicates` first in `'write'` mode (unconditional, unbypassable scope; a `regionIds: []` scope throws rather than being dropped), then `applyPredicates(query, descriptor.where, 'write')` (empty `in` throws rather than widening the mutation). `buildUpdateMutation` additionally rejects qualified value keys, strips the tenant column from the client's `values` so a row can never be re-tenanted, and re-runs `validateSecurityColumnValues` (finding 3.2) so a present out-of-scope region/department value in `values` is rejected at the builder boundary too, not only inside `validateMutation`.

## Caching layer (`src/cache/`)

Two independent cache planes exist because tier boundaries shift far less often than the underlying data:

- **Data cache** (`CacheProvider`) — caches actual result rows, keyed by `generateCacheKey()`. Short TTL (LRU default 30s, Redis default 60s).
- **Tier cache** (`TierCacheProvider`) — caches only the routing decision (`tier`, `rowCount`) from a preflight, not row data. Longer-lived so repeated cold data-cache misses skip the COUNT(\*) preflight entirely. `handler.ts`'s own `DEFAULT_TIER_CACHE_TTL_MS = 30_000` is what's actually used in practice (always passed explicitly to `set()`); provider-level defaults (`MapTierCacheProvider` 300_000ms, `RedisTierCacheProvider` 300s) only apply to standalone usage outside `handler.ts`. Setting `HandleBatchQueryOptions.tierCacheTtlMs = 0` disables the tier cache entirely (`handler.ts` passes `null` as the provider in that case).

Both planes derive their key from the same `generateCacheKey()` output, so `handler.ts` prefixes the tier plane's key with `TIER_CACHE_KEY_PREFIX` (`'tier:'`, exported from `router/tierDecision.ts`) before using it. This namespacing is structural, not provider-specific: it holds even when a host points both `cacheProvider` and `tierCacheProvider` at the same underlying store (e.g. one shared Redis client, as in `RedisTierCacheProvider`'s "Combining with `RedisCacheProvider`" docblock example) — without it, an identical key string would let the two planes silently overwrite each other's entries.

### `CacheProvider` / `TierCacheProvider` interfaces (`cache/types.ts`)

- `CacheProvider.get/set/invalidatePrefix/deleteByTag` — `set()` takes `{ ttlMs?, tags? }`. `invalidatePrefix(prefix)` removes all keys sharing a prefix (used for tenant-scoped eviction — the Studio key format embeds `encodeURIComponent(tenantId)` as the 3rd segment; a caller constructing a tenant prefix to pass to `invalidatePrefix` must encode the tenant id the same way). `deleteByTag(tag)` removes all entries written with a matching tag (used for table-level invalidation after a mutation). Both are documented as O(matched entries), not full scans.
- `TierCacheProvider.get/set/invalidatePrefix` — no tagging; simpler shape since tier entries aren't invalidated per-table.
- `CacheEntry` carries `{ rows, cachedAt, tier?, rowCount? }` — `tier` and `rowCount` are both optional for backward compatibility with entries written before those fields existed; `handler.ts` falls back to `'server'` and `cached.rows.length` respectively when reading such entries.

### `ttlMs: 0` flooring (`cache/ttl.ts`)

All four shipped cache providers agree that an explicit `ttlMs: 0` means "expire almost immediately" (floored to a 1-second minimum), never "immortal." `lru-cache` (the engine behind `LRUCacheProvider` and `MapTierCacheProvider`) natively treats `{ ttl: 0 }` as "no TTL — never expires," which is the opposite convention, so both in-process providers pass every `ttlMs` through the shared `floorTtlMs()` helper (`cache/ttl.ts`, `MIN_TTL_MS = 1000`) before handing it to `lru-cache` — in their constructors (the provider-level default TTL) and in `set()` (a per-entry override). `floorTtlMs` only rewrites the literal value `0`; `undefined` (use the default) and any other TTL, including a legitimate sub-second one, pass through unchanged. This matches the Redis providers' own floor (`Math.max(1, ttlSeconds)`), so a host can swap an in-process cache for a Redis-backed one (or vice versa) without `ttlMs: 0` silently changing meaning.

### `LRUCacheProvider` (in-process data cache)

Backed by `lru-cache`'s `LRUCache` with **size-based bounding**: `maxSize` in bytes (default 128 MB) plus a fast `sizeCalculation` estimate (`rows.length * avgBytesPerRow(512) + 64`, avoiding an O(N) `JSON.stringify` on every write) rather than an unbounded entry count. Configured with `updateAgeOnGet: false` — `ttlMs` is a staleness bound, not an idle timeout, so a hot key read more often than `ttlMs` still expires on schedule and out-of-band writes (ETL jobs, other services, direct DB writes) are picked up within the advertised TTL; this mirrors `RedisCacheProvider`, which likewise never refreshes TTL on read. Both the constructor's default `ttlMs` and any per-`set()` override are passed through `floorTtlMs()` (see above) so a `ttlMs: 0` expires in 1s rather than living forever. Maintains two secondary indexes kept in sync via the LRU's `dispose` callback (fired on both explicit delete and LRU eviction):

- **Prefix index** (`Map<prefix, Set<key>>`) — the tenant-scoped prefix (`studio:v1:<encodeURIComponent(tenantId)>:`, derived by scanning to the 3rd colon) maps to its member keys, making `invalidatePrefix()` O(matched keys) with a full-scan fallback for prefixes that don't match the indexed shape. The 3rd-colon scan is exact only because `generateCacheKey` URL-encodes the tenant segment first — a raw `tenantId` containing a `:` would otherwise inject an extra colon and shift the boundary, collapsing distinct colon-prefixed tenants into one eviction bucket.
- **Tag index** (`Map<tag, Set<key>>`) plus a reverse **key→tags index** (`Map<key, Set<tag>>`) — populated at `set()` time from `opts.tags`. `deleteByTag()` looks up the tag's key set directly; the reverse index lets `dispose` clean up only the tags that belonged to the evicted key (O(tags on that key), not O(all tags)).

### `MapTierCacheProvider` (in-process tier cache)

Also backed by `lru-cache`, bounded by **both** entry count (`max: maxEntries`, default 10,000) and TTL — a plain `Map` would have no entry-count bound and could grow unboundedly under a stream of unique query shapes. Like `LRUCacheProvider`, both the constructor's default `ttlMs` and any per-`set()` override are floored via `floorTtlMs()` so `ttlMs: 0` expires in 1s instead of never. Exposes a `size` getter (calls `purgeStale()` first) for test/introspection use. `invalidatePrefix()` does a linear scan of `cache.keys()` (acceptable at this cache's much smaller scale than the data cache).

### `RedisCacheProvider` (multi-node data cache)

Implements `CacheProvider` against a minimal structural `RedisClient` interface compatible with both `ioredis` and node-redis v4+, auto-detecting which client family it was given (`detectClientStyle()`, exported for reuse by `RedisTierCacheProvider`) or honoring an explicit `clientStyle` option. It normalizes two API differences between the client families:

- **`SET key value EX seconds`** — ioredis takes positional args (`set(key, value, 'EX', seconds)`); node-redis v4 takes an options object (`set(key, value, { EX: seconds })`). The shared `setEx()` helper picks the right shape based on `clientStyle`.
- **Set commands for tag indexing** — ioredis exposes lowercase `sadd`/`smembers`/`srem`; node-redis v4 exposes camelCase `sAdd`/`sMembers`/`sRem`. The provider checks for either naming convention and calls `console.warn` **once** (`warnedTagsUnavailable` guard) if neither is present, rather than silently no-op'ing invalidation.

TTL default is 60 seconds (`defaultTtlSeconds`), floored to a minimum of 1 second (`Math.max(1, ttlSeconds)`) so a `ttlMs: 0` doesn't send `EX 0` to Redis — the same "floor to 1s" convention `floorTtlMs()` applies for the in-process providers (see "`ttlMs: 0` flooring" above), so all four shipped providers agree on what `ttlMs: 0` means. Tag-based invalidation maintains two Redis SET structures per tagged write: a forward index `<prefix>__tag__:<tag>` (tag → data keys) and a reverse index `<prefix>__ktag__:<key>` (data key → its tags) — both namespaced by the same `keyPrefix`, so two deployments sharing one Redis instance with different prefixes never collide on either index. The reverse index's expiry mirrors the data key's own TTL. The forward index's expiry is only ever **extended**, never shortened: `extendTagIndexExpiry()` reads the client's remaining `TTL` first (when the client implements it) and calls `EXPIRE` only if the new TTL would leave the index outliving its current expiry; when the client has no `TTL` command it falls back to an unconditional extend. This matters because one forward-index key is shared across every entry tagged with that tag — unconditionally resetting it to a later, shorter-TTL write's expiry would let the index expire while an earlier, longer-TTL entry sharing the tag is still live, silently breaking `deleteByTag` for that entry. `deleteByTag()` evicts all matching data keys, their reverse-index entries, and the forward index itself in one round trip. `invalidatePrefix()` uses `SCAN` (never the blocking `KEYS`) via the shared `scanKeys()` helper (`cache/redisCompat.ts`), cleaning up the reverse/forward indexes for every key it removes.

### `RedisTierCacheProvider` (multi-node tier cache)

Structurally parallel to `RedisCacheProvider` but simpler — no tagging, since tier decisions aren't invalidated per-table. Same `RedisClient` duck-typed interface, same `detectClientStyle()`/`clientStyle` override, same `SCAN`-based `invalidatePrefix()`. Default TTL is 300 seconds when `set()` is called without an explicit `ttlMs` (a case that essentially never occurs when driven through `handler.ts`, which always supplies its own 30s default explicitly).

### `cache/redisCompat.ts` — shared Redis wire-shape helpers

`RedisCacheProvider` and `RedisTierCacheProvider` both need to normalize the same two client-family disagreements: `SET key value EX seconds` (ioredis positional args vs. node-redis v4's `{ EX: seconds }` options object) and `SCAN` reply shape (ioredis's `[cursor, keys]` tuple vs. node-redis v4's `{ cursor, keys }` object). Rather than each provider carrying its own copy, `setEx(redis, style, key, value, seconds)` and `scanKeys(redis, style, pattern, count)` live once in `cache/redisCompat.ts` and are imported by both providers. `scanKeys()` falls back to a single `KEYS` call for clients without `scan`, and to `[]` when neither is available.

## Key design invariants

These must hold for any change to this package to be safe:

1. **Zero-Knowledge Rule** — nothing outside `schemaAllowlist` / `columnAllowlist` / `writableColumns` is ever reachable. Table names are checked _before_ any query is built via the shared `assertTablesAllowed()`; column references via `checkColumnAgainstAllowlist()`/`validateDescriptorColumns()` (`shared/columnValidation.ts`) — so the read and write paths can't independently drift on what "allowed" means. The two paths place the table check differently on purpose: the **write path** (`handleMutation`) checks the whole batch up front and rejects the entire request on any table violation (a mutation batch is not a set of independent widgets), whereas the **read path** moved the check _inside_ each widget's `processWidget` `try` (thirteenth review, finding 2.1) so one bad descriptor yields that widget's `{ error }` while well-formed siblings still resolve. When a `columnAllowlist` is configured, a no-columns/no-aggregations widget cannot silently fall back to `SELECT *`: `synthesizeProjectionFromAllowlist` projects exactly the allowlisted columns, or — for a `['*']` entry — an explicit primary-table-qualified `<table>.*` wildcard (never a bare `SELECT *`, which would otherwise also leak any joined table's columns past its own, stricter allowlist entry), or rejects fail-closed when the table has no allowlist entry at all.
2. **Security predicates are unconditional and applied first, from one shared implementation, compiled once per request** — `applySecurityPredicates` (tenant/region/department) runs before any user-supplied filter or WHERE in both `buildSecureQuery` and the mutation builders. The column names are resolved by the single shared `resolvePrimarySecurityColumns()`/`resolveJoinSecurityColumns()` (the tenant column derived from the required `tenancy` posture, with an optional `securityColumns.perTable[table].tenant` override), but no enforcement site calls them directly — `compileSecurityPolicy()` runs the resolution chain exactly once per request/batch and hands back a `CompiledSecurityPolicy` that `buildSecureQuery`, `buildInsertMutation`, `buildUpdateMutation`, and `buildDeleteMutation` all read from, so INSERT tenant-stamping can't silently diverge from how reads/updates/deletes resolve the same column. update/delete always overwrite/strip `values[cols.tenant]`; insert unconditionally sets it and additionally rejects an out-of-scope client-supplied region/department value via `validateSecurityColumnValues()`, and — for a region/department **omitted** from `values` — `resolveInsertScopeStamps()` either auto-stamps the caller's unambiguous in-scope value (a single authorized region, or the caller's own department) or throws when the server cannot pick one, so a region/department-restricted caller can no longer mint an out-of-scope row simply by leaving the column unset. A client can never override, remove, or "AND-away" these predicates, nor move a row to (or write a new row into) another tenant/region/department, nor slip a value past scope validation with a table-qualified key (`rejectQualifiedValueKeys`). A joined table is scoped by default (inheriting the primary table's resolved columns) unless explicitly opted out — per-dimension via `perTable[table] = { region: null }` (drops only that dimension, keeping tenant scoping) or entirely via the whole-entry `perTable[table] = null` — and `regionIds: []` (authorized for zero regions) is treated distinctly from `regionIds: undefined` (no region scoping): the former matches zero rows on reads and is rejected on writes, never silently widening to the full tenant. "Applied first, from one shared implementation" holds for _placement_ too, not only ordering: for an outer join, the nullable side's predicate moves from WHERE into that join's own ON clause (`applySecurityPredicatesToJoinOn`) so a security predicate can no longer discard a NULL-extended row the join was meant to preserve, and both the WHERE and ON emitters share one underlying `emitSecurityPredicates()` so they can never resolve the same table's scope differently.
3. **Tenancy is explicit and fail-closed, enforced at RUNTIME, not just in the types** — `tenancy` is a required field with no default; the only way to reach an unscoped (no-tenant-predicate) query is to explicitly declare `{ mode: 'single-tenant' }`. `compileSecurityPolicy` throws on a `single-tenant` + `perTable[table].tenant` contradiction rather than silently resolving it either way, and — since `TenancyConfig.tenantColumn: string` and `SecurityColumnOverride`'s fields are compile-time-only guarantees against client JSON — also throws when a `multi-tenant` deployment's `tenantColumn` is empty/whitespace-only/non-string, and when any per-table dimension override or the top-level `securityColumns.region`/`department` is (seventh review, finding 2.1): the realistic misconfiguration is a column name wired to an unset environment variable, which the downstream truthiness gates would otherwise silently treat as "not scoped." `policy.tenancy.mode === 'multi-tenant'` is the one tenancy check, and it comes from the same required input the resolvers use, so it can never drift from enforcement.
4. **Operator allowlisting and read/write predicate semantics are shared** — `SAFE_OPERATORS` and `applyPredicates`/`applyPredicate` in `src/shared/predicates.ts` are the only place operators are translated to SQL, for both reads and writes; adding an operator here automatically covers both paths, and the `mode: 'read' | 'write'` parameter is the only intentional divergence (empty `in`: dropped on read, throws on write).
5. **All SQL goes through Knex's binding/quoting, never raw string-concatenated SQL** — every _value_ reaches Knex via a `?` binding, and every _identifier_ reaches Knex either via a `??` binding (`db.raw('?? as ??', ...)`, `havingRaw('FUNC(??) op ?', ...)` — `FUNC` is a fixed token from `applyHaving()`'s own-property-gated func map, never client text; see invariant 2's HAVING note and "Query path in detail"), Knex's object/alias-map form (`query.sum({ [agg.alias]: col })` and the `avg`/`count`/`min`/`max` equivalents in `execute.ts`, which route both the aggregate column and its alias through Knex's own identifier-wrapping — the same escaping `??` bindings get elsewhere — rather than a string-interpolated `` `col as alias` `` fragment), Knex's ON-clause value binding (`andOnVal`/`andOnIn`, used by `applySecurityPredicatesToJoinOn` for an outer join's nullable-side predicate), or via Knex's own identifier-quoting builder methods (`.select`/`.groupBy`/`.orderBy`/`.on`), which escape the interpolated identifier they are handed. The one identifier string still assembled by interpolation before being passed to a builder method is a `` `${table}.${col}` `` qualification string — `execute.ts`'s `qualify()` fed to `.select`/`.groupBy`/`.orderBy`, `buildSecureQuery`'s equivalent qualify-if-no-dot pass over `queryPlan.filters` fed to `.where`/`.whereIn`/`.whereLike`/`.whereBetween` (finding 2.1, fourth review), or the identical qualify-if-no-dot pass applied to each join's `on` pair fed to `.on()` (finding 2.1, sixth review) — it is still escaped as an identifier by Knex, not spliced into raw SQL. As defense in depth the free-form, client-supplied tokens in these paths are additionally constrained to fail-closed allowlists before use: `agg.alias` to a safe identifier charset (`validateAggregationAliases()`), a renamed projection column's `outputAlias` to the same charset (`validateOutputAliases()` — the one other client-controlled token reaching an interpolated `?? as ??`), `orderBy[].direction` to `asc`/`desc` (`validateOrderByDirections()` — the direction is interpolated into the ORDER BY clause rather than bound), `join.type` to `inner`/`left`/`right` (`validateJoinTypes()` — the type selects a Knex join method AND decides whether a joined table's security predicate lands in ON vs WHERE, so an unrecognized/wrong-case value would silently degrade the join to INNER and misplace the predicate, finding 2.3; it also case-normalizes the value so `buildSecureQuery`'s exact-match checks stay correct), and the HAVING `operator` to the five keys of `applyHaving()`'s `opMap`, gated by an own-property check rather than a bare truthiness test (so an operator naming an inherited `Object.prototype` member can't resolve to a truthy inherited function and slip past the guard). All of these validators run unconditionally, independent of any `columnAllowlist`. The same own-property-gating posture extends to every other client-keyed plain-object lookup in the package: `resolveAlias`'s `descriptor.columnAliases?.[column]` and `checkColumnAgainstAllowlist`'/`synthesizeProjectionFromAllowlist`'s `allowlist[table]` are both gated by `Object.prototype.hasOwnProperty.call` before reading, so a client-supplied key naming an inherited `Object.prototype` member (`"constructor"`, `"toString"`, `"__proto__"`, …) resolves to the literal string / a fail-closed "no entry" rather than a truthy inherited value.
6. **Cache keys are opaque and policy-scoped** — `generateCacheKey` HMACs the security-claims portion (tenant/region/department) so a client cannot guess or enumerate another tenant's cache key, and additionally folds in the compiled security policy's `digest`, which covers `tenancy`, `securityColumns`, **and `columnAllowlist`** — so two deployments/nodes whose row-level-security policy or column visibility resolves differently for the same claims never share a cache entry, and tightening a `columnAllowlist` invalidates results computed under a looser one. The digest and both cache hashes canonicalize through the single shared `sortedStringify` (`security/canonicalize.ts`), so they can never disagree about how identical inputs serialize.
7. **No hard Knex/Redis dependency in source** — `db` is typed `any` and only called through Knex's chainable builder API (duck typing); `RedisClient` is a minimal structural interface compatible with both `ioredis` and node-redis v4+. Don't add a literal `import ... from 'knex'` or a specific Redis client import to core logic. `knex` appears in `package.json` only as a `peerDependencies` entry (plus `devDependencies` for local type-checking) — never as a direct `dependencies` entry and never imported by `src/` — so a consumer's own Knex install is what's used at runtime.
8. **Two independent cache planes** — the data cache (rows, short TTL) and the tier cache (routing decisions only, longer TTL) are separate because tier boundaries shift far less often than the underlying data. `tierCacheTtlMs: 0` disables the tier cache.
9. **Batch-level isolation, request-level rejection** — allowlist/tenancy-config violations reject the whole batch (fail fast, nothing partially executes against disallowed tables); per-item _execution_ errors (a bad filter value, a DB error) are isolated to that one widget/mutation result. On the write path this isolation is layered on top of **sequential** (not concurrent) execution — mutations run one at a time, in order, so a later item in the same batch can depend on an earlier one's effect.
10. **Column-reference resolution and validation are compiled once per widget, into a typed boundary** — `resolveAlias()` (`shared/columnValidation.ts`) is the one function that maps a logical column/field ID to its physical SQL column via `descriptor.columnAliases`, but `buildSecureQuery`/`executeForTier` never call it: `validateQueryPlan()` runs it (and the HAVING/aggregation-alias/ORDER-BY-direction/column-allowlist validators) exactly once per widget and returns a `ValidatedQueryPlan` of branded `ColumnRef`s that carries no raw logical names and no `columnAliases` map. Because every downstream site reads the same pre-resolved `ColumnRef`s off the plan instead of re-deriving `columnAliases?.[x] ?? x` itself, a filter predicate and a join predicate referencing the same logical column are structurally guaranteed to resolve to the same physical column.

## Extension points

- **New cache backend**: implement `CacheProvider` and/or `TierCacheProvider` (`cache/types.ts`) and pass it via `options.cacheProvider`/`options.tierCacheProvider` — `LRUCacheProvider`/`MapTierCacheProvider`/`RedisCacheProvider`/`RedisTierCacheProvider` are just the provided implementations. A new Redis-compatible provider can reuse `detectClientStyle()` (`RedisCacheProvider.ts`) and `setEx()`/`scanKeys()` (`cache/redisCompat.ts`) instead of re-deriving the ioredis/node-redis wire-shape differences.
- **New filter operator**: add it to `SAFE_OPERATORS` and the `switch` in `applyPredicate` in `src/shared/predicates.ts` — this single change covers both the read and write paths since both builders call through this module.
- **New join type**: extend `JoinDescriptor.type` in `security/queryTypes.ts`, the `SAFE_JOIN_TYPE` allowlist + `ResolvedJoin.type` union in `validateJoinTypes`/`buildPlan` (`security/validateQueryPlan.ts`, which runtime-validates and case-normalizes `join.type` — finding 2.3), and the join-method branch in `buildSecureQuery` (`router/queryBuilder.ts`) — and decide whether the new type has a nullable side; if so, route that side's security predicate through `applySecurityPredicatesToJoinOn` (ON clause) rather than `applySecurityPredicates` (WHERE), the same way `left`/`right` do today, to avoid re-introducing the outer-join row-drop bug (finding 2.3).
- **New security dimension** (beyond tenant/region/department): extend `SecurityColumns`/`SecurityColumnsConfig` in `security/authTypes.ts` and the corresponding branch in the shared `emitSecurityPredicates()` (`shared/predicates.ts`) — since both `applySecurityPredicates` (WHERE) and `applySecurityPredicatesToJoinOn` (ON) delegate to it, a new dimension applies uniformly to reads, writes, and both join placements in one change. For a value carried in mutation `values` (like region/department today), also extend `validateSecurityColumnValues()` in `mutations/mutationBuilder.ts` so out-of-scope writes are rejected.

## Review track record

This package has now been through more than a dozen consecutive from-scratch architecture reviews (covering every file under `src/`, cross-referenced against this document) with **zero Tier 1 (security) findings** in any of them — the detailed narrative below walks the third through seventh rounds, and later rounds (through the fourteenth review's findings cited above, and this iteration's cache-`Date`-collision, `eq/neq null`, join-type-validation and information-disclosure fixes) have stayed the same Tier 2/3 shape: the SQL-injection surface, tenant/row-scope enforcement, and cache-key tenant/policy isolation have held up each time under independent, no-carry-over scrutiny. The third review's six Tier 2 findings — all operational/correctness seams (cache-plane key collision, default-cache invalidation asymmetry, outer-join predicate placement, prototype-chain lookup gaps, a dialect-specific HAVING incompatibility, and cache-failure poisoning a successful write) rather than anything in the security core — were fixed and reflected throughout this document. The fourth review's single Tier 2 finding was the same shape again: user filter predicates were the one read-path column reference left unqualified, which a join with a shared column name (`region_id`, `id`, `status`, …) turns into a Postgres/MySQL "ambiguous column" error — a fail-closed correctness gap, not a leak, now closed by qualifying an unqualified filter column with the primary table (finding 2.1, mirroring the qualification already applied to SELECT/GROUP BY/ORDER BY/aggregations and all three security-predicate dimensions); its Tier 3 finding added a regression pinning the previously-untested `regionIds: []` + outer-join ON-clause combination (finding 3.1). The fifth review's two Tier 2 findings were, again, availability/correctness seams rather than anything in the security core: (2.1) `decideTierWithCache`'s tier-cache `get`/`set` were the one cache I/O path not yet failure-isolated — a throwing tier-cache backend failed every non-aggregation widget outright instead of degrading to the preflight `COUNT(*)`, the exact availability posture the data cache's own `get`/`set` guards (finding 2.6, third review) already established — now closed by wrapping both calls in `try`/`catch`, mirroring those guards; (2.2) a renamed (expression-field) projection column was the last unqualified read-path column reference, surviving four prior rounds only because the in-memory `mockDb` test fake never merges joined columns and so can't produce the ambiguity a real Postgres/MySQL would reject — now closed by qualifying the column's physical source (not its output alias) with the primary table in `execute.ts`'s shared `projectColumn()` helper, the same fix shape as the fourth review's filter-qualification finding. The sixth review's single Tier 2 finding was, again, the same shape a third time: the join `on`-pair columns (`ResolvedJoin.on`, alias-resolved but never table-qualified) were the last read-path column reference to reach raw SQL unqualified, surviving five prior rounds for the same reason as the filter-column (fourth review) and renamed-projection-column (fifth review) findings — the in-memory `mockDb` fake is not a SQL engine and every join test fixture used fully-qualified `on` pairs, so the unqualified-shared-name case was untested. `JoinDescriptor.on` deliberately accepts unqualified columns (`validateDescriptorColumns` checks the left side against the primary table and the right side against `join.table`), so a valid, allowlist-passing descriptor could carry an unqualified `on` column whose name exists on both joined tables, rendering an ambiguous identifier Postgres/MySQL reject outright — a fail-closed correctness gap, not a leak. Closed by qualifying an unqualified `on` column the same way — left with the primary table, right with `join.table` — in `buildSecureQuery`'s join loop (finding 2.1, sixth review). With that fix, every read-path column reference that reaches raw SQL — SELECT/GROUP BY/ORDER BY/aggregations, all three security-predicate dimensions, user filter columns, and the join `on` pair — was table-qualified, closing the three-round column-qualification invariant. The seventh review's four Tier 2 findings shifted focus away from column qualification (fully closed) onto config-input and cache-consistency robustness: (2.1) `compileSecurityPolicy` performed no runtime validation of `tenancy.tenantColumn` or the per-table/top-level dimension overrides, so an empty-string or `undefined` value (e.g. `tenantColumn: process.env.TENANT_COLUMN!` with the variable unset) passed the downstream truthiness gates and silently disabled tenant scoping on every read and write for a deployment that believed it was `multi-tenant` — the one security-posture-critical finding of the round, now closed by fail-closed runtime validation in `compileSecurityPolicy` itself, the single choke point where this config enters; (2.2) the two `config.perTable[table]` lookups in `resolvePrimarySecurityColumns`/`resolveJoinSecurityColumns` were the last client-keyed table lookups in the package not gated by `Object.prototype.hasOwnProperty.call`, closed via the shared `lookupPerTableOverride()` helper; (2.3) `generateCacheKey` ran outside `processWidget`'s `try` block, so a throw there (a missing HMAC secret) rejected the whole batch's `Promise.all` instead of producing a per-widget `{ error }` result, closed by moving the call inside the `try`; (2.4) a tier-cache hit trusted the cached `tier` field verbatim even though `thresholds` is folded into neither the tier-cache key nor the policy digest, so a decision cached under different thresholds (mid-rollout, or a different cluster node) could be served stale for up to the cache TTL — closed, at no extra I/O cost, by re-deriving the tier from the cached `rowCount` via `tierFromRowCount()` against the reader's current thresholds. None of the findings across any of these rounds ever crossed a tenant boundary in a way that reached a client — 2.1 of the seventh review was the first finding whose failure mode was a real cross-tenant data leak, but only under a host misconfiguration (an unset/empty `tenantColumn`) that is now unreachable rather than a flaw in the enforcement logic itself. A repeated zero-Tier-1 result across independently-run reviews is not a guarantee against a future finding, but it is a meaningful signal that the invariants in "Key design invariants" above continue to hold as the code evolves, and that new work should keep landing as Tier 2/3-shaped refinements to those invariants rather than exceptions to them.
